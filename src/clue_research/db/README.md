# `clue_research/db/` — Postgres + pgvector + migrations

**Status:** created by M0.1 (ENG-101); **implemented** by M0.3 (ENG-114).

**Spec:** [`docs/specs/M00-foundations-and-shared-contracts.md`](../../../docs/specs/M00-foundations-and-shared-contracts.md) §M0.3

Postgres + pgvector connection layer and the reviewed-migration workflow — the **only** path that
mutates schema. Postgres is the sole source of truth; nothing external sits in the write path
(substrate §12, §13; conventions §6 — "No Airtable or any external tool in the write path").

## What this package provides

- **`engine.py`** — the one async engine per process and its lifecycle:
  - `db_lifespan()` — an `@asynccontextmanager` (the FastAPI-`lifespan` shape, built on stdlib
    `contextlib` so `db` carries no web-framework dependency) that creates the engine on enter and
    disposes it — closing every pooled connection — on exit.
  - `get_engine()` / `get_pool()` — accessors that return the live engine (the connection pool
    owner); `get_pool()` is the alias the spec names.
  - `connection()` — a pooled connection; `transaction()` — a connection inside a transaction
    (commit on success, roll back on error). M1+ run claim reads/writes through these. **No
    business queries live here.**
  - `database_url()` — the DSN, read from `CLUE_DATABASE_URL` (see below).
- **`alembic/`** (repo root) + **`alembic.ini`** — the migration workflow. The initial migration
  enables the `vector` extension and creates **no domain tables**.

JSONB `value_json` serialization is **not** re-implemented here: callers serialize with
`clue_core.serialize_value_json` / `parse_value_json` (M0.2) so there is one round-trip
path for the typed payload.

## The DSN seam — `CLUE_DATABASE_URL`

The database DSN is read from the **`CLUE_DATABASE_URL`** environment variable (the shared seam).
`db` reads it directly from the environment via `database_url()`; it does **not** import
`clue_research.config` (that package is built in parallel — the env var is the contract between
them). The documentation of the variable in `.env.example` is owned by M0.4.

Local-dev default (used when `CLUE_DATABASE_URL` is unset), matching `docker-compose.yml`:

```
postgresql+asyncpg://clue:clue@localhost:5432/clue
```

The `+asyncpg` dialect suffix names the async driver explicitly. Postgres itself sees
`user=clue` / `password=clue` / `db=clue` on `localhost:5432`.

## Workflow

```bash
make db-up        # start local Postgres+pgvector (waits for healthcheck)
make migrate      # alembic upgrade head   — apply all migrations
make migrate-down # alembic downgrade -1   — roll back one migration
make db-smoke     # up to head -> down to base -> up to head (reversibility check)
make db-down      # stop the container and remove its volume
```

Migrations are **hand-reviewed, not autogenerated** (§M0.3): autogenerate-from-models is off by
default (no ORM models are registered; `target_metadata is None`). To add a migration, create
`alembic/versions/NNNN_<slug>.py` with the next zero-padded number, set `down_revision` to the
current head, and write both `upgrade()` and `downgrade()`.

### Numbering / naming convention

`NNNN_<slug>.py`, zero-padded sequential — e.g. `0001_enable_pgvector.py`. The `revision` /
`down_revision` chain defines order; the filename prefix makes that order obvious on disk and in
review (`file_template` in `alembic.ini`).

## Migration conventions checklist (what M1's `claim` migration MUST satisfy)

These are the conventions §M0.3 bakes in for every later table (the `claim` table is M1's first
migration). They are guidance + this checklist — M0.3 ships **no** domain tables. M1's `claim`
migration must satisfy all of:

- [ ] **Append-only via `superseded_by` — never `UPDATE`-in-place.** A new observation inserts a
  new `claim` row and sets `superseded_by` on the row it supersedes; a value column is never
  mutated in place (substrate §1). This is what gives the full audit trail / time-travel and makes
  erasure (DSAR) tractable. Writes go through `db.transaction()` so a supersession is atomic.
- [ ] **UTC `timestamptz` for time columns** — `observed_at`, `collected_at` (and any later time
  column) are `TIMESTAMP WITH TIME ZONE`, stored and compared in UTC (substrate §1).
- [ ] **JSONB `value_json`** — the typed payload is a `JSONB` column (shape declared by the field
  registry), serialized with `clue_core.serialize_value_json` / `parse_value_json`. JSONB
  carries the per-vertical variation without a schema change (substrate §12).
- [ ] **Real, indexed columns on hot query paths** — the keys the pipeline filters/joins on are
  promoted to real columns with indexes, not left only inside the JSONB blob. At minimum an index
  on `entity_id` (and the non-superseded predicate the merge view reads); `field_key`, `run_id`,
  and `source_tier` are likely hot too (substrate §12 — "real columns + indexes on hot query
  paths").
- [ ] **`entity_id`-keyed — never a free-text name.** Every row keys on a resolved `entity_id`
  (conventions §2); identity resolution (M2) is the only thing that turns a name into an id.
- [ ] **Forward + reversible** — `downgrade()` cleanly reverses `upgrade()` (CI runs `up → down →
  up`).
- [ ] **`source_tier ∈ 1..4`, `confidence ∈ 0..1`** carried as constrained columns; the promotion
  rule (a tier-4 claim with no `evidence_span` cannot be promoted past `unverified`) is enforced in
  the verification layer (M9) over these columns, mirroring `core.can_be_promoted`.

## Modular boundary (M0.1 / ENG-101)

May import only `core/`, `config/`, and `obs/` from within `clue_research` — though M0.3 in fact
imports **only** `core/` (for `value_json` serialization) and **does not** import `config/`, reading
the DSN from `CLUE_DATABASE_URL` directly because `config/` is built in parallel. Components
communicate by reading/writing typed **claims** in `claimstore/`, not by importing each other;
workers return claim-id references, not blobs.

The full machine-enforced rule set lives in
[`docs/specs/M00-foundations-and-shared-contracts.md` §M0.1](../../../docs/specs/M00-foundations-and-shared-contracts.md)
and [`docs/specs/_conventions.md` §2](../../../docs/specs/_conventions.md); the executable form is the
`[tool.importlinter]` contracts in `pyproject.toml` (run `make contracts`).
