# M0 — Foundations & Shared Contracts
**Layer label:** layer:foundations  ·  **Depends on:** —  ·  **Priority:** 1 (Urgent)
**Architecture sources:** substrate §11 (build order), §12 (stack mapping), §1 (claim store), §4 (Resolver), §6 (verification spans); overview §1 (output-first spine), §3 (output contract / `account_handoff`); staged-flow §7 (`source_manifest`), §9 (claim store dimensions); Doc C §4 (project-run state machine), §6 (observability); Doc D §1–§3 (jurisdiction switch, use-class, two gates); conventions §2 (modularity & DRY), §4 (canonical contracts), §6 (stack), §8 (template).

## Goal & scope of this milestone

M0 is the substrate-before-the-agents foundation. Per substrate §11 the unbreakable build order is *substrate first, LLM synthesis last*; everything in M1–M13 reads and writes through types, a database, config, tracing, and a test/eval harness that **must exist before any claim is written**. M0 builds exactly those, and nothing else: it is pure plumbing and shared contracts with **no business logic** — no resolvers, no merge policy, no scoring, no agents.

What M0 delivers:
- **A modular monorepo** with enforced dependency rules (conventions §2) so every later component is replaceable behind a seam, and the one shared package every component imports from.
- **The canonical domain types & shared contracts in code** — `Entity`, `Claim`, `FieldDef`/`field_definition`, the `Resolver` protocol, `SourceManifest`/`source_manifest`, plus the names of the larger contracts (`account_entity`, `current_value`, `ICP spec`, `account_handoff`) — as the single DRY source (conventions §4). These are illustrative-starting-point contracts (substrate §1 "not final DDL"); later milestones extend them, never redefine them.
- **Postgres + pgvector + a migrations tool** — the system of record (substrate §12, "Postgres is the only source of truth; no Airtable in the write path"), with the extension and the migration workflow stood up but **no domain tables** (those land in M1).
- **Config, secrets, and the per-client jurisdiction/policy config skeleton** — "policy is data, not code" (conventions §2), and "design for the strict (GDPR) case and switch down" (Doc D §1) needs the jurisdiction switch and use-class/posture config to exist from the start, even though the gate that reads it is M10.
- **The shared LLM gateway client (`LLMGateway`, OpenRouter)** — the single egress for every *direct* LLM call the subsystem makes (chat/completion + embedding), so the faithfulness judge, the query-planner, the synthesizers and the positioning step all import one client whose provider/model is config (conventions §2 LLM-gateway rule, §4 contract). It exists from the foundation because every later milestone that calls a model ("the LLM client from M0") binds to this one seam; Exa Deep / Parallel Task (M11) are research-product resolvers, not gateway calls.
- **Observability & tracing skeleton** — named spans per pipeline step, with the verification spans (faithfulness judge, appropriateness/use gate) and per-source-yield emission points reserved as distinct spans (substrate §6, Doc C §6, Doc D §5), so quality and cost are *measured, not assumed*.
- **Test + eval-harness scaffold + CI** — the eval-set harness (substrate §6 "Evals") and the unit/contract test framework, wired into CI, so accuracy and modularity are enforced from commit one.

What is explicitly **NOT** here: the `claim`/`account_entity` tables and merge policy (M1); identity resolution (M2); the ICP compiler (M3); any resolver implementation or the source registry rows/adapters (M4); the LangGraph per-account graphs and the project-run state machine *implementation* (M7 / Doc C §4 — M0 only reserves their seam and config shape); the faithfulness judge and use-gate *logic* (M9/M10 — M0 only reserves their trace spans and policy schema). M0 makes those buildable; it does not build them.

## Issues

### M0.1 — Repo & package structure + dependency rules (modular boundaries)
- **Purpose:** The product's explicit non-negotiable is that any one component must be replaceable without breaking its neighbours (conventions §2; substrate §13 anti-patterns). That property is impossible to retrofit; it has to be a structural fact of the repo from the first commit. This issue lays out the package topology and the *enforced* dependency rules that make every later seam real — most importantly that the shared-contracts package (M0.2) is the only thing everyone imports, that resolvers/adapters/judges/scorers never import each other, and that nothing downstream imports a concrete provider (Clay, Apollo, Exa, Parallel) directly. It also fixes where the spec docs live so issue bodies can link back by repo-relative path.
- **Architecture sources:** conventions §1 (specs live under `docs/specs/`, issue-body backlinks), §2 (modularity & DRY rules — stable seams, "DRY: shared types live in one shared package"), §6 (stack), §7 (milestone map); substrate §11 (build order — substrate packages before agent packages), §13 (anti-patterns: no mega-agent, no provider leakage).
- **Scope / deliverables:**
  - A documented package layout grouped by milestone-layer seam, e.g. `core/` (shared contracts — M0.2), `db/` (M0.3 migrations + connection), `config/` (M0.4), `obs/` (M0.5), and reserved empty packages with READMEs for the future layers (`claimstore/` M1, `identity/` M2, `icp/` M3, `sources/` + `resolvers/` + `adapters/` M4, `stage0/` M5, `discovery_scoring/` M6, `durable/` M7, `profiling/` M8, `verification/` M9, `compliance/` M10, `synthesis/` M11, `narrative/` M12, `review/` M13), plus an `api/` placeholder for the FastAPI app layer (front-edge surface M5; review surface M13). Layout reflects conventions §7 milestone map exactly (one reserved package per future milestone).
  - **Dependency-direction rules, machine-enforced** (import-linter / equivalent in CI): (1) every package may import the shared base `core/`, `config/`, `obs/` — and `db/` (M0.3), the shared persistence layer consumed by persistence-touching milestones (importable, but not part of the layered `obs→config→core` base); (2) `core/` imports nothing internal; (3) resolver/adapter/judge/scorer packages MUST NOT import one another (workers don't talk to each other — substrate §5b); (4) no package outside `resolvers/<provider>/` or `adapters/<source>/` may import a provider SDK (Clay/Apollo/ZoomInfo/BuiltWith/Exa/Parallel/Firecrawl) — the provider name never appears downstream (conventions §2, "swapping Clay → direct APIs is a registry/config change"); (5) nothing imports the FastAPI app layer (`api/`).
  - Project tooling baseline: package manager + lockfile, formatter, linter, type-checker config, `pyproject`/workspace manifest, repo `README` orienting to `docs/architecture/` and `docs/specs/`.
  - The `docs/specs/` location and the issue-body backlink convention recorded.
- **Interface / seam:** This issue *defines* the seam discipline rather than exposing a runtime contract. The enforced boundary: **the only cross-package surface is `core/` (M0.2) plus `config/`, `obs/`, and the `db/` access contract (M0.3).** Swaps stay behind seams because (a) a provider swap is confined to its `resolvers/<provider>/` package and a registry/config row; (b) the durable-execution swap (Postgres state machine → Temporal) is confined to `durable/`; (c) a judge-model swap is confined to `verification/`. The import-linter contract is the executable expression of conventions §2.
- **Data model / schema:** None (no tables). Touches only repo/package manifests and CI lint config.
- **Dependencies:** Blocks all other M0 issues (they populate the packages this defines) and the entire roadmap. Depends on nothing.
- **Acceptance criteria:**
  - `core/` has zero internal imports (verified by the import-linter contract in CI).
  - A test/lint rule fails the build if any non-`resolvers/*`/`adapters/*` module imports a provider SDK, and if two resolver/adapter/judge/scorer packages import each other, and if anything imports the `api/` app layer.
  - Every milestone M1–M13 has exactly one reserved layer package (M4 = `sources/`+`resolvers/`+`adapters/`), each with a one-line README naming the milestone that fills it; the `api/` app placeholder exists.
  - `docs/specs/` exists and the spec-backlink convention is documented; this milestone's spec resolves at `docs/specs/M00-foundations-and-shared-contracts.md`.
  - Format/lint/type-check run clean on an empty repo via a single `make`/script target.
- **Out of scope:** Any package's actual implementation (each owning milestone). The FastAPI app wiring beyond a placeholder (M5 front edge / M13 review surface). Temporal packaging (M7).
- **Open decisions:** None directly. The package boundaries are *built to absorb* D1/D2 (output boundary / design ingest) by isolating `narrative/` (M12) and any future content-schema adapter behind a seam, and D3 (personal-data posture) by isolating `compliance/` (M10) — no boundary hardcodes a decision.

### M0.2 — Core domain types & shared contracts (Entity, Claim, FieldDef, Resolver protocol, SourceManifest)
- **Purpose:** This is the DRY backbone in code (conventions §2 "shared domain types, the `Resolver` protocol, provenance/claim helpers … live in one shared package (M0.2)"). The architecture's one bet — *verifiability is a property of the data model* (substrate §0) — only holds if the typed-claim-with-provenance is a single shared type that resolvers, adapters, judges, scorers, the merge view, and the handoff all use without re-implementing. This issue ports the canonical contracts of conventions §4 into `core/` as typed objects with validation, so e.g. "a tier-4 claim with no `evidence_span` cannot be promoted" is expressible at the type/validation layer, not re-coded per component. It defines the contracts and their invariants; it does **not** implement merge, resolution, or any tier behavior.
- **Architecture sources:** conventions §4 (all canonical contracts), §3 (namespaces, source tiers, modes, personas, use-classes, identity-binding); substrate §1 (`claim`, `field_definition`, `current_value`), §2 (`account_entity`), §4 (`Resolver` protocol); staged-flow §7a (`source_manifest`), §9 (two provenance flavors, `research_mode`); overview §3 (`account_handoff`); Doc C §2 (`account.resonance.*`, `contact.facet.*` field-classes); Doc D §2 (use-class), staged-flow §6 (identity-binding).
- **Scope / deliverables:**
  - `Entity` and the `entity_type` enum `{account, contact}`; the `entity_id` value type — the architecture-wide rule "everything keys on a resolved `entity_id`, never a free-text name" (conventions §2) is encoded so a free-text name is *not* an `Entity`.
  - `Claim` mirroring the conventions §4 `claim` contract field-for-field: `id, entity_id, entity_type, field_key, value_json, source_url, source_tier(1..4), extraction_method{api|scrape|llm_synthesis|human|crm_import}, evidence_span, confidence(0..1), corroborations, observed_at, collected_at, cost_cents, run_id, research_mode, superseded_by`. Append-only by construction (no in-place mutation API). Plus the two provenance flavors (staged-flow §9): a *discovery-provenance* shape (where/why an entity matched) and *field-claim provenance* with `identity_binding{strong|weak}` + `use_class{professional-public|personal-public-non-sensitive|sensitive}` for contact claims.
  - The **claim-promotion invariant** as a validated rule object (not a write path): a tier-4 claim with no `evidence_span` is not promotable past `unverified` (substrate §1/§6). A verification-status enum `{unverified, verified, rejected}` and the predicate, callable by M9. (This status enum is an additive starting-point type — it is not a conventions §4 canonical contract and does not redefine one.)
  - `FieldDef` / `field_definition`: `field_key, type, validation, tier_plan (ordered resolver refs), freshness_ttl, pass{scoring|deep}, gate`. Field-key namespace constants (`core.*`, `account.*`, `account.resonance.*`, `contact.*`, `contact.facet.*`, `<pack>.*`) as a validated namespace helper — registered, never an enum (conventions §3).
  - The `Resolver` Protocol exactly per conventions §4 / substrate §4 (`tier: int`; `resolve(entity, field) -> list[Claim]`), plus `SourceManifest` / `source_manifest` per staged-flow §7a (`source_key, modality{text|video|audio|pdf|structured}, entity_scope{account|contact|both}, yields, tier, cost, latency, geo_coverage, freshness_profile, identity_binding_strength`).
  - Type stubs / dataclasses naming (not implementing) the larger composite contracts so later milestones extend a shared definition: `AccountEntity` (`account_entity`: `id, canonical_name, primary_domain, aliases[], hq_geo, registry_ids, status{candidate|active|merged}, merged_into`), the `current_value` result shape (value + winning provenance + conflict flag), `ICPSpec` (field set + discovery strategy + source profile + scoring rubric), and `AccountHandoff` (`account_handoff` per overview §3: `account_entity_id, fit_score, intent_score, account_profile_claims[], committee[]{contact_entity_id, persona, role_on_committee, profile_claims[]{value, evidence_span, source_tier, identity_binding, use_class}}, value_narrative[]{claim_id, persona, argument, supporting{account_evidence_ids[], client_knowledge_ids[]}}, provenance_index`).
  - Shared **provenance/claim helpers**: constructors that enforce required provenance, the source-tier ordering helper (1→2→3→4, stop at first confident hit), and serialization to/from `value_json`.
- **Interface / seam:** **This package IS the seam.** Exposes: the domain types, the `Resolver` protocol, `SourceManifest`, the field-key namespace helper, the claim/provenance helpers, and the promotion predicate. Consumes: nothing internal (enforced by M0.1). Because every resolver/adapter/judge/scorer/merge/handoff component imports these and only these for shared shape, a Clay→direct-API resolver swap, a judge-model swap, and a Postgres-state-machine→Temporal swap all leave these types untouched — that is what makes the swaps "behind the seam." Later milestones MAY add columns/fields (conventions §4 "may add columns; must not contradict") but MUST extend here, never fork.
- **Data model / schema:** No DDL (tables are M0.3-enabled, M1-defined). Defines the in-code mirror of conventions §4 `claim`, `field_definition`, `source_manifest`, `account_entity`, `current_value`, `ICP spec`, `account_handoff`. Validation rules: `source_tier ∈ 1..4`; `confidence ∈ 0..1`; `extraction_method` / `entity_type` / `modality` / `entity_scope` / `use_class` / `identity_binding` enums; tier-4 + null `evidence_span` ⇒ not promotable.
- **Dependencies:** Depends on M0.1 (package exists). Blocks M0.3 (migrations encode these shapes), M0.5 (spans annotate operations over these types), M0.6 (contract tests target these), and every M1–M13 component.
- **Acceptance criteria:**
  - Constructing a `Claim` without the provenance required for its tier raises a validation error; constructing one with `source_tier` outside 1..4 or `confidence` outside 0..1 raises.
  - The promotion predicate returns false for a tier-4 claim with empty `evidence_span` *and* for a weakly identity-bound contact claim (staged-flow §6), and true for an otherwise-valid corroborated claim (unit-tested in each direction).
  - A no-op/example resolver that satisfies the `Resolver` Protocol type-checks; a class missing `tier` or `resolve` fails the type-checker (contract test).
  - `SourceManifest` round-trips all five modalities and both `entity_scope` extremes; `account.resonance.*` and `contact.facet.*` field-keys validate against the namespace helper, and `SourceManifest.yields` entries are validated as field-keys or field-classes.
  - Contact `Claim`s expose `identity_binding` and `use_class`; account `Claim`s do not require them — verified by tests.
  - `AccountHandoff` type includes `account_entity_id`, `fit_score`, `intent_score`, `account_profile_claims`, `committee[]` (with per-contact `persona`, `role_on_committee`, `identity_binding`, `use_class`), `value_narrative[]`, and `provenance_index` fields matching overview §3.
- **Out of scope:** The `current_value` merge *algorithm* (M1); identity *resolution* logic (M2); the ICP *compiler* (M3); resolver *implementations* and the source registry *rows/adapters* (M4); narrative *generation* and handoff *assembly* (M12); the use-gate and faithfulness-judge *logic* (M9/M10). The `lawful_basis` claim-provenance field (Doc D §4) is added with M10, not here. M0.2 ships the shapes and invariants only.
- **Open decisions:** **D1** (output boundary — claims vs. + value narrative): the `AccountHandoff`/`value_narrative` type is defined per the recommended default (+ value narrative, overview §3) but the value-narrative field is structured so the boundary can move without breaking the type. **D2** (design ingest): no content-schema type is defined here (it lives downstream, not this repo); the handoff stops at value narrative per the recommended boundary. **D3** (personal-data posture): `use_class` and `identity_binding` are first-class on contact claims so all three postures are expressible as config (Doc D §6), without hardcoding one. **D4** (resolved: mixed/global) informs that contact claims carry jurisdiction-bearing fields downstream (M0.4 owns the switch).

### M0.3 — Postgres + pgvector + migrations tooling
- **Purpose:** Postgres is the only source of truth (substrate §12, §13; conventions §6 "No Airtable or any external tool in the write path"), and pgvector is the substrate for both identity-resolution candidate sets and client-knowledge retrieval (substrate §2, §8, §12). This issue stands up the database, the `vector` extension, and the **migrations workflow** — the disciplined, versioned, reversible mechanism through which every later milestone adds its tables (`claim`, `account_entity`, `field_definition`, `source_manifest`, project-run/state tables, etc.). It deliberately creates **no domain tables**; it makes the act of creating them safe, repeatable, and CI-tested.
- **Architecture sources:** substrate §1 (claim store is the spine — append-only), §2 (pgvector candidate sets), §8 (pgvector client-knowledge retrieval), §12 (Postgres system of record, JSONB for per-vertical payloads, "real columns + indexes on hot query paths"), §13 (no Airtable in write path); conventions §4 (contracts the migrations will later encode), §6 (stack).
- **Scope / deliverables:**
  - A pinned Postgres version with the `vector` (pgvector) extension enabled via an initial migration; a local/dev bring-up (containerized) and a CI database service.
  - A migrations tool (Alembic or equivalent) configured: forward + reversible migrations, an autogenerate-from-models option *off by default* (migrations are reviewed, not magic), a naming/numbering convention, and a "migrate up to head / down one" workflow documented.
  - The **connection layer** in `db/`: an async connection pool created/torn down under the FastAPI `lifespan`/`asynccontextmanager` pattern (substrate §12, conventions §6), JSONB-friendly serialization aligned to `core/`'s `value_json` (M0.2), and a session/transaction helper. **No business queries.**
  - Conventions baked in for later tables (documented, plus a lint/check where feasible): append-only via `superseded_by` (never UPDATE-in-place — substrate §1); UTC `timestamptz` for `observed_at`/`collected_at`; JSONB for per-vertical/`value_json` payloads with real indexed columns on hot keys; an `entity_id`-keyed convention. These are *guidance + a checklist the M1 migrations must satisfy*, not domain tables.
  - A migrations smoke test in CI: `up → down → up` against an ephemeral database leaves a consistent schema.
- **Interface / seam:** Exposes a single DB access contract (`get_pool()`/session dependency) consumed by every persistence-touching milestone; the concrete engine sits behind it. The migrations tool is the **only** path that mutates schema — no component issues DDL at runtime. This isolates the database so that the durable-execution swap (Postgres state machine → Temporal, conventions §2/§6) changes *where workflow state lives* without changing this DB seam, and so a future read-only projection to a client tool can be added without touching the write path (substrate §5c "never write-through it").
- **Data model / schema:** Only the pgvector extension + the migrations bookkeeping table. **No `claim`/`account_entity`/etc.** — those are defined by M1+ migrations and must conform to conventions §4 and to the append-only/JSONB/`timestamptz`/index conventions established here.
- **Dependencies:** Depends on M0.1 (the `db/` package + CI) and M0.2 (the serialization shapes the connection layer aligns to). Blocks M1 (claim store + merge, the first domain migration), M2 (pgvector candidate sets), M7 (durable-execution state tables), and every persisting milestone.
- **Acceptance criteria:**
  - `CREATE EXTENSION vector` succeeds in dev and CI; a trivial vector column can be created and queried in a throwaway migration test.
  - A reversible no-op (or pgvector-enabling) migration applies and rolls back cleanly; CI runs `up → down → up` green.
  - The async pool opens on app startup and closes on shutdown via `lifespan` with no leaked connections (verified by a startup/shutdown test).
  - The repo contains zero domain tables after M0 (a check enumerating tables finds only the extension + alembic version table).
  - Documented checklist that M1's `claim` migration must satisfy (append-only `superseded_by`, `timestamptz`, JSONB `value_json`, `entity_id` index) exists and is referenced from the M1 spec.
- **Out of scope:** The `claim`, `field_definition`, `account_entity`, `source_manifest`, project-run, and per-account-graph tables (M1, M3, M4, M7). LangGraph `AsyncPostgresSaver` checkpoint tables (M7 — M0 only ensures the database can host them). Redis (locks/rate-limit coordination — substrate §12) is M2/M7's concern, not M0. Any read-only projection/sync to external tools (out of scope entirely for the write path; substrate §5c).
- **Open decisions:** **D7** (economics) only indirectly — the schema must later carry `cost_cents` and per-run/per-account budget bookkeeping (substrate §5c, Doc C §5); M0.3 ensures JSONB + indexed numeric columns are first-class so budget tables (M7) need no engine change. No decision hardcoded.

### M0.4 — Config, secrets & per-client jurisdiction/policy config skeleton
- **Purpose:** "Policy is data, not code" (conventions §2): merge policy, scoring rubric, source profiles, tier/budget caps, freshness TTLs, and especially jurisdiction/use-class policy are versioned config the engine reads — swappable per client/ICP without code changes. Doc D §1 demands the system "design for the strict (GDPR) case and switch down," with jurisdiction as a *first-class per-client switch* and the three personal-data postures (Doc D §6) shipped as per-client config on one `use_class × jurisdiction` machinery. That switch and that policy schema must **exist from the foundation**, even though the gate that enforces them is M10 — retrofitting lawful-basis/jurisdiction tracking later is exactly the base-layer rework Doc D §1 warns against. This issue also stands up secrets handling so provider keys never enter code or `_memory/` (conventions §2; CLAUDE.md session-memory protocol).
- **Architecture sources:** conventions §2 ("policy is data, not code"), §6 (stack); Doc D §1 (jurisdiction first-class switch, design-strict-switch-down), §2 (use-class taxonomy `professional-public | personal-public-non-sensitive | sensitive`), §3 (the `(use_class × jurisdiction × client_policy)` gate inputs), §4 (lawful basis recorded as provenance, retention TTLs), §6 (three postures as per-client config, Option 1 default — Option 3 scopes at the *source level*); Doc C §5 (per-campaign hard cap, budget bands); substrate §3/§6 (freshness TTLs, scoring rubric as config).
- **Scope / deliverables:**
  - A typed, layered **config loader** in `config/`: defaults → per-client overrides → per-ICP/per-campaign overrides, each layer versioned (so a config change is auditable, mirroring versioned ICP specs — staged-flow §2). Loaded once and injected, not read ad hoc.
  - A **secrets** mechanism: provider API keys (Clay/Apollo/ZoomInfo/BuiltWith/Exa/Parallel/Firecrawl/CRM) plus the **`OPENROUTER_API_KEY`** for the LLM gateway, and the DB DSN, read from environment/secret store, never committed, never logged, never written to `_memory/`. A redaction helper for the obs layer (M0.5) so spans/logs cannot leak secrets.
  - **The shared LLM gateway client** (`LLMGateway`, conventions §4) — the single egress for all *direct* LLM calls (chat/completion + embedding), wrapping **OpenRouter** (OpenAI-compatible). Keyed by `OPENROUTER_API_KEY`; base URL, the per-call-site default model ids (judge / planner / synthesis), timeout, retry, and a fallback model are versioned config (policy-as-data) — so a model swap, or an OpenRouter→another OpenAI-compatible gateway swap, is a config change, not code. Every call is wrapped in the M0.5 trace span emitting token usage + `cost_cents`. Ships a **deterministic stub mode** so CI and the M0.6 eval harness make **no live LLM calls**. The gateway is to models what the `Resolver` is to data sources: no component constructs a model-vendor SDK directly. **Carve-out:** Exa Deep / Parallel Task (M11) are tier-4 research-product resolvers with their own keys — not gateway calls.
  - The **per-client jurisdiction/policy config skeleton** (data shapes + defaults, no enforcement logic): a per-client `policy` document carrying `jurisdiction` (resolved per contact downstream, default GDPR-grade per Doc D §1), `posture ∈ {conservative_default(Option 1), gather_broadly_gate_at_use(Option 2), professional_public_only(Option 3)}` defaulting to Option 1, the **use-class allow-map** `(use_class × jurisdiction) → {usable | stored_unusable | not_stored}` with the conservative default (`sensitive` locked, `professional-public` + `personal-public-non-sensitive` usable), and a **source-scope setting** the posture drives (Option 3 scopes research to professional-public surfaces at the source level — Doc D §6 — i.e. the deep personal-life classes are never collected; the allow-map governs Options 1/2). Plus placeholders for lawful-basis defaults and personal-claim retention TTLs (Doc D §4); the `lawful_basis` claim-provenance field itself lands with M10.
  - Config schema placeholders (typed, defaulted, **read by no engine yet**) for the other "policy is data" surfaces so later milestones bind to a shared shape: merge policy params (M1), scoring rubric weights (M3/M6), source profiles per pack (M4), tier/budget caps and the per-campaign hard cap (M7/Doc C §5), and field-level freshness TTLs (M1/M9).
  - Config validation on load (fail fast on an unknown posture, an out-of-range cap, an unknown jurisdiction key).
- **Interface / seam:** Exposes a `get_config(client_id, icp_id?)` accessor returning a typed, merged, validated config object, and a `get_policy(client_id)` accessor returning the jurisdiction/use-class/posture policy — both consumed by M9/M10 (gates), M1 (merge), M3/M6 (scoring), M4 (source profiles + source-scope from posture), M7 (budgets). The seam guarantees policy is swappable per client without code change, and that the strict→relaxed jurisdiction model is one machinery (Doc D §1) — switching a client from Option 1 to Option 3 is a config write (it flips the source-scope and the allow-map), not a code path. Secrets sit behind the loader so a Clay→direct-API swap changes which key is read, not any caller. Also exposes the injected **`LLMGateway`** client (conventions §4) that every direct-LLM call site receives, so a model swap (or OpenRouter→another OpenAI-compatible gateway) changes config, not callers — exactly as a resolver swap does.
- **Data model / schema:** No DB tables in M0 (config may persist as versioned rows later; M0 can ship file/typed-object defaults). Defines the typed config/policy shapes only. References the `use_class`/`identity_binding` provenance fields on `claim` (M0.2) and the future `lawful_basis` provenance field (M10/Doc D §4), plus the budget fields (`cost_cents`, caps) the schema (M0.3) will carry.
- **Dependencies:** Depends on M0.1 (`config/` package), M0.2 (uses the `use_class`/`identity_binding` enums and field-key namespaces). Blocks M0.5 (obs uses the redaction helper), M3/M6 (scoring rubric config), M4 (source profiles + posture-driven source-scope), M7 (budget caps), M9 (freshness/merge params), and especially M10 (the use-gate reads `get_policy`).
- **Acceptance criteria:**
  - `get_policy(client_id)` for a client with no overrides returns posture = Option 1 (conservative default), jurisdiction = GDPR-grade default, source-scope = full sweep, and `sensitive` ⇒ not usable for outreach (unit-tested against Doc D §6 Option 1).
  - Setting a client's posture to Option 3 via config (no code change) sets the source-scope to professional-public-only so the deep personal-life classes are never collected (per Doc D §6 Option 3) — verified by a config-only test.
  - The loader applies defaults → client → ICP overrides in that precedence (tested), and rejects an unknown posture/jurisdiction/out-of-range cap on load.
  - No secret value appears in any committed file, log line, or trace; the redaction helper masks a known key pattern (test).
  - A direct LLM call issued through the `LLMGateway` reads `OPENROUTER_API_KEY` and the configured per-call-site model id, emits the `llm.gateway_call` span (M0.5) with token usage + `cost_cents`, and uses the deterministic stub in CI (no live call); changing the configured model id changes which model is called with no code change.
  - Config schema placeholders for merge policy, scoring rubric, source profiles, budget caps, and freshness TTLs exist with typed defaults and validate.
- **Out of scope:** The use-gate enforcement and lawful-basis balancing (LIA) logic and the `lawful_basis` claim field (M10); the faithfulness judge (M9); jurisdiction *resolution* from contact location claims (M2/M8 — M0 only defines the field and default); the actual merge/scoring/source-profile/budget *engines* that read these configs (M1/M3/M4/M6/M7). 2026 legal specifics (D8) are not encoded — only the machinery to carry them.
- **Open decisions:** **D3** (personal-data posture): all three postures shipped as config with Option 1 default per Doc D §6 — decision deferred to the data/compliance owner, not hardcoded. **D4** (resolved: mixed/global): jurisdiction is the first-class switch this issue creates. **D7** (economics): the per-campaign hard-cap and budget-band config shapes are stubbed per Doc C §5 recommended (client-facing) default, confirmable later. **D8** (2026 legal verification): the policy schema is built to *carry* updated jurisdiction rules without code change; the specific 2026 values are left for the compliance owner's research pass.

### M0.5 — Observability & tracing skeleton (named spans per pipeline step)
- **Purpose:** The architecture treats verification and cost as things that must be *measured, not assumed*: the faithfulness judge runs "as a distinct graph step with its own observability span" (substrate §6), the appropriateness/use gate runs "as separate steps with separate observability" (Doc D §5), and per-source yield / verification health / cost burn-down are first-class live surfaces that *also feed the source-intelligence learning loop* (Doc C §6, staged-flow §7e). None of that is possible unless tracing exists before the pipeline does. This issue stands up the tracing skeleton — a consistent way to wrap each pipeline step in a named span carrying the cross-cutting attributes (`entity_id`, `field_key`, `source_tier`, `research_mode`, `run_id`, `cost_cents`) — with the verification and use-gate spans reserved as *distinct, separately-measurable* spans so "we fabricated something" and "we used something we shouldn't have" are different metrics from day one.
- **Architecture sources:** substrate §6 (faithfulness judge with its own trace span; evals measured), §12 (LLM-as-judge with its own trace span); Doc C §6 (phase progress, cost burn-down, per-source yield, verification health) + §6 note that observability and the learning loop read the same provenance; Doc D §5 (use-gate as a separate step with separate observability); staged-flow §7e (per-source yield feeds reweighting); conventions §2 (the tracing wrapper lives in the shared package).
- **Scope / deliverables:**
  - A tracing wrapper in `obs/` (OpenTelemetry-shaped) exposing a `traced_step(name, **attrs)` context manager / decorator that opens a named span and attaches standard attributes. Standard attribute set drawn from `core/` (M0.2): `entity_id, entity_type, field_key, source_tier, research_mode, run_id, cost_cents`, plus `client_id`/`icp_id`/`project_run_id`.
  - **Reserved canonical span names** for the cross-cutting steps so later milestones emit consistent, queryable spans (the steps themselves are not implemented here): per-resolver `resolve` spans tagged by `source_tier` and `source_key` (M4); `merge.current_value` (M1); `verification.corroboration`, `verification.faithfulness_judge`, `verification.identity_binding` (M9), and the **distinct** `compliance.use_gate` span (M10, Doc D §5) — explicitly a different span from the faithfulness judge; the `llm.gateway_call` span (M0.4 — every direct LLM call through the OpenRouter gateway, carrying `model`, token usage, and `cost_cents`); campaign-phase spans for the Doc C §4 phases (`reverse_profiling … handoff`) (M7).
  - **Metric emission points** for the Doc C §6 surfaces, wired to read the same provenance data the learning loop consumes (staged-flow §7e): per-source yield (claims that survive verification, by `source_key`), verification health (share of tier-4 claims passing the judge; share of personal claims at `strong` binding), cost burn-down (sum `cost_cents` vs. cap), and phase progress. M0 ships the emission *hooks/counters*; the values populate as later milestones run.
  - Structured logging integrated with the M0.4 redaction helper so no secret/raw-source-excerpt leaks into a span or log (aligns with CLAUDE.md "no raw proprietary source excerpts").
  - A local trace exporter (console/OTLP to a dev collector) and a CI smoke test that a wrapped operation emits a span with the expected name + attributes.
- **Interface / seam:** Exposes `traced_step()` and a metrics emitter consumed by every pipeline component; the concrete tracing backend (OTel collector, vendor) sits behind the wrapper so it can be swapped without touching callers. The reserved span names + standard attributes are the **observability contract** — M9's judge swap and M0.1's provider swaps keep emitting the same span shape, so dashboards and the learning loop are stable across swaps. Because per-source-yield metrics derive from claim provenance (M0.2) rather than a separate pipeline, observability and the learning loop (M13/staged-flow §7e) share one source of truth.
- **Data model / schema:** No DB tables. Defines span names, the standard attribute schema (typed), and metric names. Reads attribute values from `core/` types (M0.2); reads cost/cap context from M0.4 config.
- **Dependencies:** Depends on M0.1 (`obs/` package), M0.2 (attribute types), M0.4 (redaction helper, cap context). Blocks M9 (judge/gate spans must pre-exist as a contract), M13 (review & observability surface reads these), M4/M6/M7 (resolver/scoring/phase spans), Doc C §6 surfaces.
- **Acceptance criteria:**
  - `traced_step("merge.current_value", entity_id=…, field_key=…)` emits a span with that exact name and attributes (CI smoke test).
  - The faithfulness-judge span name and the use-gate span name are reserved as **two distinct** canonical names (test asserts they differ), satisfying Doc D §5's separation requirement.
  - A wrapped operation handling a secret-bearing value produces a span/log with the secret redacted (test using a known key pattern + M0.4 helper).
  - Metric emitters for per-source yield, verification health (judge pass-rate, strong-binding share), and cost burn-down exist and increment correctly against synthetic claim data (unit test); per-source-yield reads from claim provenance fields, not a separate input.
  - The canonical campaign-phase span names match the Doc C §4 phase list exactly.
- **Out of scope:** The faithfulness judge, corroboration, identity-binding, and use-gate *implementations* (M9/M10 — M0 reserves only their span names). The project-run state machine and per-account graphs that *emit* the phase/step spans (M7). The client-facing dashboard UI and the disposition feedback loop *logic* (M13). Eval scoring (M0.6).
- **Open decisions:** None hardcoded. The reserved-but-distinct verification vs. use-gate spans directly serve **D3** (any posture must keep accuracy-failure and appropriateness-failure separately measurable — Doc D §5). Per-source-yield emission is the data feed the **D7** cost-governance surface and the learning loop both consume.

### M0.6 — Test + eval-harness scaffold + CI
- **Purpose:** The accuracy claim is only defensible if it is enforced by tooling, not asserted (substrate §6 "Evals … this is how you defend an accuracy claim to an enterprise buyer and how you catch regressions when you swap a model or resolver"). And modularity (conventions §2) is only real if the dependency rules (M0.1) and contracts (M0.2) are checked on every commit. This issue stands up the three-layer test scaffold — unit/contract tests, the **eval-harness skeleton** over a hand-verified account set (substrate §6), and CI — so that from the first commit: contracts are enforced, swaps are regression-tested, and the eval battery (factual accuracy / citation validity / source quality, LLM-as-judge + human spot-check hooks) has a place to live. M0 ships the harness *frame and fixtures*, not the eval *content* (the gold set and judge live with M9/M11).
- **Architecture sources:** substrate §6 (eval set of hand-verified accounts; rubrics for factual accuracy / citation validity / source quality; human spot-checks; regression-on-swap), §11 (build order — substrate, incl. its tests, before agents), §13 (anti-pattern: untyped dossiers + after-the-fact QA — the harness exists to replace vibe-checks with claim-level evals); Doc C §6 (verification health as a measured surface); conventions §2 (replaceability must be testable), §6 (LLM-as-judge with its own span — the harness invokes it behind a seam).
- **Scope / deliverables:**
  - A unit-test framework (pytest or equivalent) wired into the repo with fixtures for the `core/` types (M0.2) and an ephemeral test database (M0.3) per the CI service.
  - **Contract tests** that enforce M0's seams: the import-linter dependency rules (M0.1) run as a test; a `Resolver`-protocol conformance test fixture any future resolver can subclass; a `SourceManifest` validity fixture; the claim-promotion-invariant tests; the config precedence + policy-default tests (M0.4); the span-emission tests (M0.5).
  - The **eval-harness skeleton** (substrate §6): a runner that loads a gold set of hand-verified accounts/claims (fixture format defined; **content stubbed** — the real gold set is M9/M11), runs the standard rubric battery (factual accuracy, citation validity, source quality) as pluggable scorers behind a seam, and reports per-rubric metrics. The LLM-as-judge scorer is invoked behind the shared `LLMGateway` (M0.4) so the judge model is swappable as config (conventions §2 "judge model swap stays behind the seam") and so the harness runs in CI with the gateway's deterministic stub by default (no live LLM calls in CI). A human-spot-check hook (export the sample, ingest dispositions) is stubbed.
  - **CI pipeline**: on every PR run format → lint → type-check → dependency-rule contract test → unit/contract tests → migrations `up/down/up` smoke (M0.3) → span-emission smoke (M0.5) → the eval harness against the stub gold set. CI must require a database service and must not require live provider keys (uses stubs/recorded fixtures).
  - A documented "regression-on-swap" workflow: the harness can be pointed at a new resolver/judge/model to compare metrics before merge (substrate §6).
- **Interface / seam:** Exposes the eval-harness runner + the pluggable scorer interface (rubric scorers and the judge are swappable behind it) and the resolver-conformance test fixture. Consumes `core/` (M0.2), `db/` (M0.3), `config/` (M0.4), `obs/` (M0.5). The seam: CI enforces the *contracts*, not implementations, so any component swap that keeps the contract passes, and any swap that regresses eval metrics is visible before merge — making "replaceable without breaking neighbours" a CI-checked property rather than a hope.
- **Data model / schema:** No domain tables. Defines the gold-set fixture format (entity + expected claims + expected provenance) aligned to `core/` `Claim`/`Entity` (M0.2), and the eval-result/metric shape (aligned to the M0.5 verification-health metrics).
- **Dependencies:** Depends on M0.1 (dependency rules to test), M0.2 (types under test), M0.3 (test DB + migration smoke), M0.4 (config tests), M0.5 (span tests, metric shapes). Blocks nothing structurally, but is the gate every later milestone's PRs run through; M9/M11 fill the harness with the real gold set and judge.
- **Acceptance criteria:**
  - CI is green on the M0 repo: format, lint, type-check, dependency-rule contract test, unit/contract tests, migration `up/down/up`, span smoke, and eval-harness (stub gold set) all pass.
  - The dependency-rule test fails the build when a deliberately-introduced provider-SDK import is added outside `resolvers/*` (negative test).
  - The `Resolver`-conformance fixture passes for a valid stub resolver and fails for one missing `tier`/`resolve` (both asserted).
  - The eval harness runs end-to-end against the stub gold set with the deterministic stub judge (no live LLM/provider call) and emits per-rubric metrics matching the M0.5 verification-health metric shape.
  - The harness can be re-pointed at an alternate stub judge and reports a metrics delta (demonstrates the regression-on-swap workflow).
  - CI requires a Postgres+pgvector service and requires no live provider API key.
- **Out of scope:** The real hand-verified gold account set and rubric thresholds (M9 verification, M11 synthesis). The production faithfulness-judge implementation (M9). Load/perf testing and cost-burn budget tests against real providers (later, with D7 economics data). The human-review *product surface* (M13 — M0 only stubs the spot-check ingest hook).
- **Open decisions:** **D8** (2026 legal verification) — the eval harness is where any future compliance/appropriateness eval set will plug in; M0 reserves the seam without encoding legal specifics. No decision hardcoded; the swappable judge interface keeps **D-level** model choices out of the harness frame.
