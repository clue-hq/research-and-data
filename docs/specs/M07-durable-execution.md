# M7 — Durable Execution — Per-Account Graphs + Campaign State Machine

**Layer label:** layer:durable-exec  ·  **Depends on:** M1, M4  ·  **Priority:** 2 (High)
**Architecture sources:** substrate §5 (execution model), §5a (two-pass + tier-checkpoint shape), §5b (per-account orchestrator-worker, references-not-blobs), §5c (durable state machine, idempotency, budget caps, Temporal-shaped), §10 (`interrupt()` secure-input pause/resume), §12 (stack mapping); Doc C §3 (bounded recursion knob, two-level fan-out, per-tier caps), §4 (campaign-run state machine, pause/resume/adjust, idempotency at both levels), §5 (cost dial & governance), §6 (cost burn-down / verification health surface); overview §2 (end-to-end phase map)

## Goal & scope of this milestone

This milestone is the **execution substrate** that runs the rest of the pipeline durably, at 5k-account scale, under hard cost control. It delivers the two-level durable execution the architecture insists on (substrate §5c, Doc C §4):

1. an **outer campaign-run state machine** (Postgres-backed, Temporal-shaped) that owns the long-lived job spanning Stage 0 → discovery → Pass A → tier checkpoint → Pass B → verification → handoff, with checkpointing and client-driven pause/resume/adjust; and
2. an **inner per-account orchestrator-worker graph** (LangGraph + `AsyncPostgresSaver`) that plans gap-fields, fans out parallel aspect/facet workers that **write claims to the store and return only references**, and is capped per tier by a **bounded recursion knob**.

Both levels are made safe by **idempotency keys** (`(account, field, tier)` inner, `(campaign_run, phase)` outer) so retries and re-entry never double-spend, and by a **budget/cost-governance engine** that enforces per-account, per-tier, and per-run hard caps and feeds the client-facing cost surface.

Where this sits in the end-to-end map (overview §2): M7 is the scheduler and runtime *underneath* every other phase — Stage 0 (M5), discovery + Pass A (M6), deep profiling (M8), verification (M9). It does not implement those phases; it implements the durable container that runs them, hands each phase its budget envelope and idempotency contract, and persists state so the whole run survives crashes, rate limits, and multi-day latencies.

**What is explicitly NOT here.** The *content* of any phase — discovery logic and Pass A scoring (M6), the mode M2/M3/M4 deep-profiling node bodies and the actual aspect/facet worker prompts and resolver calls (M8), verification gates and the faithfulness judge (M9), tier-4 synthesis (M11) — is owned by those milestones; M7 provides only the graph/state-machine skeleton, the recursion-cap enforcement, the idempotency layer, and the budget engine they plug into. The claim store and `current_value` (M1) and the `Resolver` protocol + waterfall (M4) are consumed, never redefined. The human review *surface* (the UI/disposition loop) is M13; M7 only provides the durable `interrupt()`/pause primitive the checkpoint suspends on. The pre-run cost *estimate UI* and burn-down dashboard are M13 (M13.4 — the client-facing cost & progress surface); M7 owns the underlying cost-accounting engine and the estimate function they call. Migration to Temporal is out of scope — the V1 design is Temporal-shaped so the migration stays mechanical and behind the seam.

## Issues

### M7.1 — Per-account orchestrator-worker graph (LangGraph + AsyncPostgresSaver; workers return references)

- **Purpose:** Every Pass B account is researched by one constrained orchestrator-worker graph, not a mega-agent. A lead node reads the active research schema + current claims, plans which gap-fields need filling, and spawns parallel aspect workers that do not talk to each other; each worker writes typed claims to the store and hands the orchestrator only lightweight references (claim ids), so the lead's context never re-ingests detail and token/cost stay bounded (substrate §5b, the artifact pattern). The graph must be crash-resumable: its plan and state are persisted to Postgres before context grows, so a run survives truncation, rate limits, and restarts. This issue delivers the graph skeleton and the worker→store→reference contract; the actual worker bodies (mode M2/M3/M4 logic, resolver calls) are M8's.
- **Architecture sources:** substrate §5b (orchestrator-worker topology, workers return references, externalize the plan early, tools-over-skills, effort-scaling), §5a (two-pass execution model), §12 (LangGraph + `AsyncPostgresSaver` for per-account graphs); Doc C §3 (the per-account orchestrator the recursion knob extends).
- **Scope / deliverables:**
  - A LangGraph graph definition for a single account-research run: `plan` (orchestrator/lead) → `fan_out` (spawn aspect workers) → `collect_references` → `score_handoff` node boundaries, with `AsyncPostgresSaver` checkpointing wired to the M0/M1 Postgres pool.
  - An **orchestrator/lead** node that loads the compiled research schema (M3, via M4) + `current_value` for the account (M1), computes the gap-field set (fields not yet `verified`/fresh), and emits a typed **research plan** (ordered aspect clusters + per-aspect budget envelope + worker count) which is persisted before any worker spawns.
  - An **aspect-worker** node contract: a worker is given (entity_id, aspect field-cluster, allowed resolver tools via M4, budget envelope, idempotency context). It MUST write results as claims to the store (M1) and return a `WorkerResult` containing only references (claim ids + a compact status), never blobs. No worker→worker communication.
  - The **reference-collection** step: the orchestrator merges `WorkerResult` reference sets, updates the persisted plan/state, and never re-reads claim bodies into its own context (it reads `current_value` only when it must re-plan).
  - A `tools-over-skills` worker harness: workers are configured with well-described resolver tools (the M4 waterfall as the tool surface) rather than long prompts; aspect→resolver mapping comes from the field registry's `tier_plan`.
  - Effort-scaling hook: the plan's worker-count and aspect depth are parameters supplied by the tier (the actual numbers are enforced by M7.2's caps and M7.5's budget).
  - Standard named trace spans (M0.5) per node (`plan`, per-aspect `fan_out`, `collect`), so per-account execution is observable.
- **Interface / seam:**
  - **Exposes** `AccountResearchGraph` with a stable entrypoint `run(entity_id, tier, campaign_run_id, idempotency_ctx) -> AccountRunResult` and a typed `WorkerResult{claim_refs: list[ClaimId], status, cost_cents, spans}` contract. Consumers (M8 worker bodies) implement an `AspectWorker` interface `research(ctx: AspectContext) -> WorkerResult`; M7 owns spawning, checkpointing, reference collection, and budget/cap enforcement around them. The graph framework itself (LangGraph + `AsyncPostgresSaver`) sits behind this seam — swapping the checkpoint backend or the graph engine, or later folding the inner graph into a Temporal activity, is a runtime change that does not alter `AccountResearchGraph.run` or `AspectWorker`.
  - **Consumes** the claim store write path and `current_value` read (M1, §4 `claim` / `current_value`); the `Resolver` protocol + waterfall as the worker tool surface (M4, §4 `Resolver`); the compiled research schema / `field_definition.tier_plan`/`pass` (M3/M4, §4 `field_definition`); `entity_id` (never a free-text name) from M2 via the campaign run.
  - **Replaceability call-out:** because workers communicate only through the claim store and return references, the claim store *is* the shared filesystem (substrate §5b); any worker implementation is swappable without touching the orchestrator, and the orchestrator is swappable without touching workers.
- **Data model / schema:** No new claim columns. Adds an `account_run` table — `id, campaign_run_id, entity_id, tier, status{pending|planning|running|paused|done|failed|budget_exceeded}, plan_json, references_index jsonb (aspect → claim_ids), cost_cents, started_at, updated_at`. LangGraph checkpoints land in the `AsyncPostgresSaver` tables. All claims written carry `run_id` = `account_run.id` and `research_mode` (§4 `claim`) so provenance ties back to the producing run. Reads §4 `current_value`, `field_definition`.
- **Dependencies:** M1 (claim store + `current_value` + field registry write/read), M4 (`Resolver` + waterfall as worker tools). Blocks M7.2 (recursion knob extends this graph), and M8 (deep-profiling worker bodies plug into this skeleton). Indirectly needs M0.2/M0.3/M0.5 (shared types, Postgres, tracing) per the milestone map.
- **Acceptance criteria:**
  - Running `AccountResearchGraph.run` on a seeded account produces claims in the store and an `AccountRunResult` whose payload contains only claim references — assert the orchestrator node never holds full claim bodies (the lead's context size is independent of claim count).
  - Killing the process mid-fan-out and re-invoking `run` with the same `idempotency_ctx` resumes from the last `AsyncPostgresSaver` checkpoint without re-spawning completed workers (verified via M7.4's idempotency check and trace spans).
  - The plan is persisted to `account_run.plan_json` before any worker spawns (kill-after-plan / kill-before-plan tests both leave consistent state).
  - Aspect workers run in parallel and share no state except the claim store; a deliberately failing worker does not crash sibling workers (its aspect is marked failed; the run continues).
  - Worker tooling is the M4 resolver surface (no resolver is called outside the `Resolver` protocol); swapping a resolver behind M4 requires zero changes here.
  - Per-node trace spans are emitted and queryable.
- **Out of scope:** Aspect/facet worker *bodies* and mode M2/M3/M4 logic (M8); the recursion *caps* themselves (M7.2); budget *enforcement* logic (M7.5); idempotency *key derivation* (M7.4 — consumed here); verification (M9); tier-4 synthesis resolvers (M11).
- **Open decisions:** D7 (economics) — the effort-scaling worker-count/depth defaults per tier are configured, not hardcoded; this issue exposes the parameters and proceeds on Doc C §5 proposed bands pending confirmation.

### M7.2 — Bounded recursion knob (aspect/facet sub-workers; per-tier depth & worker caps)

- **Purpose:** The GTM-engineer insight is that a **two-level** fan-out (orchestrator → aspect workers → facet sub-workers) yields the best, most surprising research; ungoverned, that exact depth becomes the prototype's "spawn excessive subagents" cost blowout (Doc C §3). This issue adds a **bounded recursion knob** to the per-account graph (M7.1): the richest aspects (e.g. a single contact's interests under `contact.facet.*`, or `account.resonance.*`) may spawn parallel facet sub-workers, but **depth and worker-count are capped per tier** — top tier gets the full two-level dive, lower tiers get one level or none. The cap is enforced in two places, as the architecture requires: in the orchestrator's instructions *and* as a hard runtime limit, so "be thorough" can never translate into unbounded spawn. Sub-workers obey the same references-not-blobs rule.
- **Architecture sources:** Doc C §3 (the bounded two-level fan-out, depth/worker-count capped per tier, cap in prompt *and* hard runtime limit, per-entity hard budget cap, sub-workers return references); substrate §5b (effort-scaling explicit, the excessive-subagent failure mode); Doc C §8 (concrete per-tier depth numbers deferred until real cost data exists).
- **Scope / deliverables:**
  - A `RecursionPolicy` config object resolved per tier: `max_depth (0|1|2)`, `max_aspect_workers`, `max_facet_workers_per_aspect`, and the set of aspect field-classes eligible to recurse (e.g. `account.resonance.*`, `contact.facet.*`). Policy is **data, not code** (versioned config, per-ICP/pack-overridable), per the DRY rule (conventions §2 policy-as-data).
  - Extension of the M7.1 graph so an aspect worker may request facet sub-workers; the orchestrator/runtime grants or denies based on `RecursionPolicy` and remaining budget.
  - **Dual enforcement:** (a) the cap is injected into the orchestrator/worker prompt/instructions (soft, model-visible); (b) a hard runtime guard in the spawn path rejects any spawn that would exceed depth or worker-count, regardless of what the model asked for. A spawn over cap is a no-op + a logged `cap_hit` event, not an error that fails the run.
  - Facet sub-worker contract identical to aspect workers: write claims, return references, no cross-talk.
  - A `cap_hit` / fan-out telemetry span (worker counts, depth reached, caps applied) feeding M7.5's cost accounting and M13's observability.
- **Interface / seam:**
  - **Exposes** `RecursionPolicy` (loaded by tier) and a `SpawnGuard` the runtime calls before any sub-worker spawn (`may_spawn(depth, current_count, policy, remaining_budget) -> bool`). The dial values live entirely in versioned config — tuning per-tier depth/worker numbers (Doc C §8) is a config change, never code. The recursion mechanism is behind the same `AccountResearchGraph` seam as M7.1, so it is invisible to worker bodies (M8) beyond the depth/budget they are handed.
  - **Consumes** the M7.1 graph and `AspectWorker`/facet contracts; the per-account budget envelope from M7.5 (a spawn may be denied for budget even when depth/count allow); the tier value from the campaign run.
  - **Replaceability call-out:** the policy-as-data seam means a different fan-out strategy (e.g. single-level only, or three-level for a special pack) is a config swap; the runtime guard is the single chokepoint, so no caller can bypass it.
- **Data model / schema:** No new tables. `RecursionPolicy` stored as versioned config (alongside merge/scoring policy config from M1/M3). `account_run.plan_json` records the depth/worker counts actually used; fan-out telemetry recorded on trace spans (M0.5) and rolled into `account_run.cost_cents` accounting (M7.5). Facet-produced claims carry `run_id` = the account run and the recursing aspect's `research_mode` (§4 `claim`).
- **Dependencies:** M7.1 (the graph it extends). Coupled with M7.5 (budget can deny a spawn the depth policy allows). Blocks M8 (deep aspect/facet workers rely on the cap contract). Reads tier from M7.3's campaign-run/account-run state.
- **Acceptance criteria:**
  - With `max_depth=0` (low tier), no facet sub-workers ever spawn; with `max_depth=2` (top tier), eligible aspects spawn facet workers up to `max_facet_workers_per_aspect` and no further.
  - A worker that *requests* more sub-workers than the cap (simulated) is hard-limited: actual spawns never exceed the runtime cap and a `cap_hit` event is logged — proving the hard limit holds even when the model misbehaves.
  - Only field-classes listed as recursion-eligible can spawn facet workers; a non-eligible aspect requesting recursion is denied.
  - Changing per-tier depth/worker numbers requires only a config/version bump (no code change) — verified by overriding `RecursionPolicy` in a test fixture.
  - Sub-workers return references only (same assertion as M7.1) and never communicate with each other.
  - A spawn denied for budget (delegated to M7.5) is denied gracefully (run continues, aspect marked partial).
- **Out of scope:** The concrete production depth/worker numbers per tier (Doc C §8 — deferred until real cost data; this issue ships the dial and safe defaults); worker *bodies* (M8); budget *math* (M7.5).
- **Open decisions:** D7 (economics) — per-tier fan-out depth caps are exactly the Doc C §8 deferred item; ship configurable, proceed on conservative defaults (top tier depth 2, others depth ≤1) pending real cost data.

### M7.3 — Campaign-run state machine (phases, checkpointing, pause/resume/adjust)

- **Purpose:** The substrate nails *per-account* durable execution but does not model the **campaign run** — the long-lived job spanning Stage 0 → discovery (thousands of accounts) → Pass A → tier checkpoint → Pass B → verification → handoff, potentially days of work (Doc C §4). This issue delivers the **outer state machine** that owns that lifecycle: an explicit phase sequence, per-phase checkpointing so the run survives crashes and resumes from its last checkpoint, the durable human gate at the tier checkpoint, and client-driven **pause / resume / adjust** mid-flight (pause a long discovery, edit the ICP, raise/lower the budget) with safe re-entry. It is the outer scheduler that owns concurrency limits and phase ordering; the per-account graphs (M7.1) are spawned and bounded by it.
- **Architecture sources:** Doc C §4 (campaign-run state machine, the phase list, pause/resume/adjust mid-run, idempotency at both levels, Temporal-shaped Postgres-backed, outer scheduler over LangGraph graphs); substrate §5c (durable execution, Postgres-backed state machine, scheduling/concurrency/budget ownership, Temporal-shaped migration), §5a (the two-pass + tier-checkpoint shape), §10 + §12 (`interrupt()` secure-input pause/resume for the checkpoint; Postgres state machine in the stack); overview §2 (the end-to-end phase map).
- **Scope / deliverables:**
  - A `campaign_run` workflow with the canonical phase enum (conventions §3 / Doc C §4 sequence): `reverse_profiling → icp_confirmed → discovery → scoring → tier_checkpoint → deep → verification → handoff`, plus terminal `paused`/`failed`/`completed` and per-phase status. (`tier_checkpoint` is the human gate; conventions §3 annotates it `tier_checkpoint(human)`.)
  - Per-phase **checkpointing**: each phase transition is committed durably; on restart the run resumes at the last committed phase. Phase bodies are supplied by other milestones (M5/M6/M8/M9/M12) via a registered phase-handler interface — M7.3 owns transitions, persistence, and re-entry, not phase content.
  - The **durable tier checkpoint** (`tier_checkpoint`): a Postgres-backed `interrupt()`-style suspension (the secure-input/pause-resume pattern, substrate §10/§12) that holds the run until the human action arrives, then resumes `deep`. M7.3 owns the durable suspend/resume primitive; the review UI is M13.
  - **Pause / resume / adjust** controls: `pause(run)` brings the run to a safe boundary and records `paused`; `resume(run)` continues from the last checkpoint; `adjust(run, {icp_version | budget_cap | tier_cutoffs})` applies a versioned change that the next phase picks up (ICP edits re-version the spec via M3; budget changes flow to M7.5). Adjustments are journaled.
  - **Concurrency control:** the outer machine limits how many per-account graphs (M7.1) run in parallel within `deep`, and coordinates with Redis in-flight locks (M2.4) so two campaign runs never deep-research the same account simultaneously.
  - A `pre_run_estimate(run)` call that produces the projected-spend figure (delegates math to M7.5) shown before discovery/deep spend (Doc C §5) — the engine, not the UI.
- **Interface / seam:**
  - **Exposes** a `CampaignRun` API — `start`, `advance`, `pause`, `resume`, `adjust`, `await_checkpoint`/`submit_checkpoint`, `status` — and a `PhaseHandler` protocol (`run_phase(run_ctx) -> PhaseResult`) that M5/M6/M8/M9/M12 implement and register. The state machine is **Temporal-shaped**: phases map to activities, checkpoints to timers/signals, so the V1 Postgres machine → Temporal migration is mechanical and stays behind `CampaignRun` (substrate §5c/§12, conventions §2 swap call-out). The phase-handler seam means M7.3 never imports phase logic.
  - **Consumes** per-account graphs via `AccountResearchGraph.run` (M7.1) during `deep`; Redis locks (M2.4) for concurrency; the ICP spec version (M3, §4 `ICP spec`) for `adjust`; the budget engine (M7.5) for caps/estimates; `account_handoff` (§4) is the artifact the `handoff` phase emits (built by M12, persisted by the run).
  - **Replaceability call-out:** swapping the durable backend (Postgres state machine → Temporal) changes only the `CampaignRun` implementation; phase handlers, the per-account graph, and the budget engine are untouched.
- **Data model / schema:** Adds `campaign_run` — `id, client_id, icp_spec_version, phase (enum above), status, budget_cap_cents, spent_cents, tier_cutoffs_json, paused_at, resumed_at, adjustments_json[], created_at, updated_at` — and `campaign_phase_checkpoint` — `id, campaign_run_id, phase, idempotency_key, status, payload_json, committed_at` (the per-phase durable record M7.4 keys on). Per-account graphs (`account_run`, M7.1) FK to `campaign_run`. Reads/re-versions §4 `ICP spec`; the run's `handoff` phase writes/links §4 `account_handoff`.
- **Dependencies:** M1 (Postgres substrate, claim store the phases read/write). M4 (the source layer phases use). Consumes M7.1 (per-account graphs), M7.4 (phase idempotency keys), M7.5 (budget caps + estimate). Coordinates with M2.4 (Redis locks). Blocks M8 (deep phase runs under it) and is the scheduler M5/M6/M9/M12 phases register into. The milestone-map dependency for M7 is M1, M4; the M7.1/M7.4/M7.5 couplings are intra-milestone.
- **Acceptance criteria:**
  - A run advances through all phases in order; killing the process mid-`deep` and restarting resumes at `deep` from the last committed checkpoint (no phase re-runs from scratch, verified via `campaign_phase_checkpoint` and M7.4).
  - `pause` brings a running discovery to a safe boundary and records `paused`; `resume` continues without re-spending the already-completed work.
  - `adjust(budget_cap=…)` mid-run is honored by the next phase and by M7.5 (a lowered cap can trigger a graceful stop at the next checkpoint); `adjust(icp_version=…)` re-versions the ICP and the next phase compiles against the new version.
  - At `tier_checkpoint` the run suspends durably and survives a restart while suspended; submitting the human decision resumes `deep`.
  - Two concurrent runs cannot deep-research the same `entity_id` at once (Redis-lock-mediated); the parallel-account concurrency limit is enforced.
  - `pre_run_estimate` returns a projected spend before any deep spend occurs.
  - The phase set and ordering exactly match the conventions §3 / Doc C §4 sequence.
- **Out of scope:** Phase *bodies* — reverse-profiling/ICP (M5), discovery + Pass A (M6), deep modes (M8), verification (M9), narrative/handoff (M12); the review *UI* and disposition loop (M13); the actual Temporal migration (future; design is only Temporal-shaped).
- **Open decisions:** D7 (economics) — typical campaign size (hundreds vs thousands) and budget bands shape concurrency limits and checkpoint cadence; proceed on Doc C §5 defaults, configurable. D5 (ICP multiplicity) — `adjust(icp_version)` and the run's `icp_spec_version` are designed to support multiple ICPs (each its own run/compile) per the recommended default, without hardcoding one-ICP-per-client.

### M7.4 — Idempotency keys ((account,field,tier) + (campaign_run,phase))

- **Purpose:** At 5k-account scale research *is defined by* partial failure, rate limits, and long steps; retries and crash-resumes are constant. Without idempotency, a retry double-charges a paid resolver and double-writes claims, and a re-entered phase double-spends. This issue delivers the **two-level idempotency layer** the architecture requires: per-account steps are idempotent on `(account_id, field_key, source_tier)` (substrate §5c) and campaign phases are idempotent on `(campaign_run, phase)` (Doc C §4), so retries never double-charge or double-write and phase re-entry never double-spends. This is the safety property that makes M7.1's resumable graph and M7.3's resumable state machine actually safe, not just restartable.
- **Architecture sources:** substrate §5c (each step idempotent on `(account_id, field_key, source_tier)` so retries never double-charge/double-write; per-step retry with backoff); Doc C §4 (idempotency at both levels — per-account `(account, field, tier)` and campaign `(campaign_run, phase)` — so re-entry never double-spends); substrate §1 (append-only claims, supersede-not-overwrite — idempotency must respect this).
- **Scope / deliverables:**
  - A canonical **idempotency key derivation**: `account_step_key = hash(account_run_id, entity_id, field_key, source_tier)` and `phase_key = hash(campaign_run_id, phase)`; deterministic and stable across retries.
  - An `idempotency_ledger` table recording, per key: `key, scope{account_step|campaign_phase}, status{in_progress|succeeded|failed}, result_ref (claim_ids / phase payload ref), cost_cents_charged, first_seen_at, completed_at`. A step/phase checks the ledger before executing: if `succeeded`, it returns the recorded result without re-spending; if `in_progress` (and not stale), it is a duplicate and is skipped/joined; if absent/`failed`, it executes and records.
  - Per-step **retry policy with backoff** (substrate §5c) wired to the ledger so a retry reuses the same key and never charges twice.
  - Integration with M1's append-only/supersede rule: an idempotent re-run that produces an equivalent observation does not create a duplicate competing claim (the ledger short-circuits the write); a genuinely new observation supersedes per M1 policy — idempotency must not mask real refreshes, only suppress duplicate work for the *same* `(account, field, tier)` step within a run.
  - Helpers in the shared package (M0.2) so workers (M7.1/M8) and phase handlers (M7.3) wrap their effectful sections in `with idempotent(key): …` rather than re-implementing the check.
  - Cost-charge coupling: the ledger is the single record of what a step *actually* charged, so M7.5's burn-down counts each spend exactly once.
- **Interface / seam:**
  - **Exposes** `idempotency_key(...)` derivation helpers and an `idempotent(key, scope)` context manager / decorator used by both the per-account graph (M7.1) and the campaign state machine (M7.3). The key shapes `(account, field, tier)` and `(campaign_run, phase)` are the stable contract; the ledger backend (Postgres now) is behind it, so a Temporal migration (where activity idempotency/dedup is built-in) can map onto the same key shapes without changing callers.
  - **Consumes** §4 `claim` (the append-only/supersede write path it guards), `field_definition` (`field_key`, `source_tier` from `tier_plan`), the `account_run`/`campaign_run`/`campaign_phase_checkpoint` ids (M7.1/M7.3), and the resolver-cost figures (M4) the ledger records.
  - **Replaceability call-out:** because idempotency is expressed purely as key-shapes + a context manager, the dedup mechanism is swappable (Postgres ledger → Temporal-native idempotency) without any worker or phase-handler change.
- **Data model / schema:** Adds `idempotency_ledger` (above), unique-constrained on `(key)`. References §4 `claim` (via `result_ref` claim ids), `field_definition` (key composition). Couples to `account_run`, `campaign_run`, `campaign_phase_checkpoint`. No change to the `claim` schema itself — idempotency sits in front of the write path.
- **Dependencies:** M1 (claim store + field registry — the keyed write path). Consumed by M7.1 (per-account step idempotency), M7.3 (phase idempotency), M7.5 (single-count cost charging). Provides helpers via M0.2. The milestone-level dependency stays M1, M4.
- **Acceptance criteria:**
  - Executing the same `(account, field, tier)` step twice (simulated retry) results in exactly one claim write and exactly one cost charge; the second call returns the recorded `result_ref`.
  - Re-entering a phase with the same `(campaign_run, phase)` key does not re-run completed phase work or double-spend (ledger short-circuits).
  - A crash *during* a step (status left `in_progress`) is handled: stale-`in_progress` recovery re-executes safely under the same key without orphaning or double-charging.
  - Idempotency suppresses duplicate work but does **not** suppress a legitimate refresh: a later run with a genuinely new observation for the same field still supersedes per M1 merge policy (the key is run-scoped for steps, not a global freshness lock).
  - Resolver cost recorded in the ledger matches M7.5's burn-down exactly (no double-counting).
  - Key derivation is deterministic and stable (same inputs → same key) across processes.
- **Out of scope:** The freshness/TTL re-research cadence (M9.5 — when to refresh, vs M7.4's "don't duplicate this run's step"); the budget *enforcement* that reads the ledger's charges (M7.5); the merge policy itself (M1.2).
- **Open decisions:** none directly; supports D7 by guaranteeing spend is counted once for accurate economics.

### M7.5 — Budget caps & cost-governance engine (per-account, per-run hard stops)

- **Purpose:** The founders' entire cost concern reduces to one dial — **fan-out cost per account × accounts per pass** — and the architecture demands it be explicit, client-controllable, and *enforced* (Doc C §5, substrate §5c). This issue delivers the cost-governance engine: hard budget caps at three scopes (per-account/per-entity by tier, per-pass, per-campaign-run), a **hard stop** when `sum(cost_cents)` would exceed the allowance (graceful, at a checkpoint), a **pre-run cost estimate** before any spend, a client-set **per-campaign hard cap** that stops the run and asks the client to raise it or tighten cutoffs, and the live **burn-down** accounting (spent vs estimate vs cap) that the client-facing surface consumes. This is what keeps "go to any lengths" affordable: the lengths are bounded by tier and budget, not by the agent's enthusiasm.
- **Architecture sources:** Doc C §5 (the cost dial, proposed budget bands, pre-run estimate, client-set per-campaign hard cap, graceful stop at a checkpoint, cost pass-through → client-facing surface), §3 (per-entity hard budget cap, the spawn-denial-on-budget path), §6 (cost burn-down + verification health as the observability/learning signal); substrate §5c (per-account and per-run budget caps, hard stop when `sum(cost_cents)` exceeds the tier's allowance), §12 (Postgres-backed; cost accounting on the state machine).
- **Scope / deliverables:**
  - A **budget policy** (data, not code; per-ICP/pack/client-overridable, versioned; conventions §2 policy-as-data): per-tier per-account caps, per-pass caps (Pass A cents/account; Pass B dollars/account; committee/contact highest per-entity), and the campaign-run cap (Doc C §5 bands as defaults, confirm D7).
  - A **cost-accounting engine** that aggregates `cost_cents` from claims/ledger (M1/M7.4) at all three scopes in real time (`spent_cents` on `account_run` and `campaign_run`).
  - **Hard-stop enforcement** at each scope: before a resolver call / worker spawn, check projected spend; if it would exceed the per-account or per-entity cap, deny (this is the spawn-denial M7.2 calls); if it would exceed the per-run cap, bring the campaign run to a **graceful stop at the next checkpoint** (via M7.3) rather than a hard kill. Enforcement reads exactly-once charges from M7.4's ledger.
  - A **pre-run estimate** function: given discovered/imported account count × tier cutoffs × per-tier budget bands, project `~$X` ("~N discovered → ~M go deep → est $X") — the engine behind Doc C §5's estimate and M13.4's UI.
  - **Client-set cap & raise loop:** expose `set_campaign_cap`, and on projected breach emit a `budget_breach_pending` event that M7.3 surfaces to the client (raise cap or tighten cutoffs) — the run waits at a checkpoint rather than overspending.
  - **Burn-down + governance telemetry**: spent/estimate/cap per scope, per-source yield-vs-cost, exposed for M13.4's cost surface and the source-intelligence learning loop (Doc C §6, staged-flow §7e) — same provenance/cost data, two consumers.
- **Interface / seam:**
  - **Exposes** a `BudgetEngine` — `estimate(run) -> Estimate`, `check(scope, projected_cost) -> Allow|Deny`, `record(charge)` (or reads M7.4's ledger), `set_campaign_cap`, `burn_down(run) -> BurnDown` — and `BudgetPolicy` as versioned config. The dial (fan-out × accounts) and all caps live in config, swappable per client/ICP with no code change (conventions §2 policy-as-data). The engine is the single chokepoint for spend authorization, so no worker/phase can overspend around it; behind the seam, the accounting store (Postgres) can move to Temporal/another backend without changing callers.
  - **Consumes** `cost_cents` on §4 `claim` and the M7.4 ledger (exactly-once charges); `source_manifest.cost` (M4, §4) and `field_definition.tier_plan` for estimation; tier from M7.3; the spawn path of M7.2 (budget can deny a within-cap-depth spawn); checkpoints from M7.3 for graceful stops.
  - **Replaceability call-out:** swapping cost-source data (Clay-billed vs direct-API cost) or the estimation model is a config/manifest change behind `BudgetEngine`; the spawn-denial and graceful-stop contracts to M7.2/M7.3 are stable.
- **Data model / schema:** `spent_cents` (live) and `budget_cap_cents` on both `account_run` (M7.1) and `campaign_run` (M7.3); a `budget_event` table — `id, campaign_run_id, scope{account|pass|run}, kind{check_deny|graceful_stop|breach_pending|cap_raised}, projected_cents, cap_cents, created_at` — for audit and the burn-down feed. Reads §4 `claim.cost_cents`, `source_manifest.cost`, the M7.4 ledger. `BudgetPolicy` stored as versioned config beside merge/scoring/recursion policy.
- **Dependencies:** M1 (claim `cost_cents`), M4 (`source_manifest.cost` for estimates; the resolver calls being budgeted). Tightly coupled to M7.2 (spawn denial), M7.3 (graceful stop, client raise loop), M7.4 (exactly-once charge accounting). Feeds M13.4 (cost surface) and the staged-flow §7e learning loop (via M13.3). Milestone-level dependency: M1, M4.
- **Acceptance criteria:**
  - A per-account run that reaches its tier's cap stops spending (further resolver calls/spawns denied) and is marked `budget_exceeded`/partial — never silently overspends.
  - A campaign run projected to breach its per-run cap performs a **graceful stop at the next checkpoint** (via M7.3) and emits `breach_pending`, rather than a hard kill mid-step.
  - `set_campaign_cap` lower than current spend triggers `breach_pending`/graceful stop; raising the cap (or tightening cutoffs) lets `resume` continue.
  - `estimate` produces a projected spend before any deep spend, decomposed as discovered → go-deep → $; re-estimating after a cutoff `adjust` reflects the new projection.
  - Burn-down (spent vs estimate vs cap) is queryable live at account, pass, and run scope and ties exactly to the M7.4 ledger charges (no double-count, no missed charge).
  - A within-depth spawn is denied when it would exceed budget (the M7.2 coupling), and the run continues gracefully (aspect marked partial).
  - All caps are config-driven: changing a band is a versioned config change, no code change.
- **Out of scope:** The cost-estimate/burn-down **UI** and per-source-yield dashboard (M13.4); the source-yield *reweighting* learning loop itself (M13.3 / staged-flow §7e — M7.5 only emits the cost/yield signal); deciding cost pass-through billing (D7, founders); the resolver pricing data itself (lives in M4 `source_manifest`).
- **Open decisions:** D7 (economics) — the budget bands (Doc C §5), typical campaign size, and **cost pass-through (client-facing vs internal)** are exactly this issue's deferred decisions. Ship the engine config-driven and surface-ready; proceed on Doc C §5 recommended defaults (client-facing transparency, the proposed bands) without hardcoding the decision.
