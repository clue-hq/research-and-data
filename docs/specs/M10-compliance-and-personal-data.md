## Goal & scope of this milestone

This milestone adds the cross-cutting governance layer the original substrate/staged-flow docs were **silent** on (Doc D opening): the machinery that makes the subsystem lawful and tasteful about real, named, mostly-non-US people, not just accurate about them. The substrate's accuracy/identity-binding gate (M9.4) protects against *wrongness*; M10 adds the **second, orthogonal gate** that protects against *inappropriateness/unlawfulness* — a true, well-sourced, correctly-attributed personal fact can still be illegal or reputation-destroying to use, and that is a different failure measured separately (Doc D §3, §5; conventions §5).

Concretely, this layer delivers, all as **policy-as-data behind stable seams** (conventions §2):
1. **Jurisdiction resolution per contact entity** (M10.1) — every contact carries a resolved jurisdiction derived from its location claims; every personal claim inherits it. D4 is resolved (mixed/global), so jurisdiction is first-class, never an afterthought.
2. **Use-class tagging at extraction** (M10.2) — every personal claim is stamped `professional-public | personal-public-non-sensitive | sensitive` the moment it is extracted, independent of accuracy. The taxonomy is the hinge the postures turn on.
3. **The appropriateness/use gate** (M10.3) — a new member of the verification layer (substrate §6) that decides `(use_class × jurisdiction × client_policy)` whether a `contact.facet.*` claim may drive outreach, running after identity-binding and the faithfulness judge with its own trace span.
4. **The three postures as per-client config** (M10.4) — Options 1/2/3 are not forks but settings on the same `use_class × jurisdiction` machinery, with Option 1 shipped as the default (D3).
5. **Lawful-basis recording, retention TTLs, and DSAR/erasure** (M10.5) — lawful basis stored as provenance, shorter retention TTLs on personal claims, and a deterministic, append-only-friendly tombstone erasure path keyed on `contact_entity_id`.

**Where it sits in the end-to-end map (overview §2):** M10 governs the deep pass (Pass B / modes M2–M4) — specifically the personal-data surface produced by M8 Contact Profiling — and supplies the `use_class` field that crosses the handoff (overview §3). It runs *inside* the verification step of the campaign-run flow (`… → deep → verification → handoff`), as a peer to M9's gates.

**What is explicitly NOT here.** M10 does not produce personal claims (M8 owns `contact.facet.*` / `account.resonance.*` collection); does not perform identity-binding scoring (M9.4 owns strong/weak); does not run the faithfulness judge (M9.3); does not author the claim table, `current_value` merge, or field registry (M1); does not implement the value narrative or the handoff object (M12), only stamps the `use_class`/lawful-basis fields it carries; does not implement the review surface (M13). It also does not *decide* the legal facts of 2026 (D8) — it builds the machinery that a verified legal config drives.

## Issues

### M10.1 — Jurisdiction resolution per contact entity (D4 resolved: mixed/global)
- **Purpose:** Because target contacts are mixed/global (D4 resolved), jurisdiction cannot be an afterthought — the use-gate (M10.3), lawful-basis selection (M10.5), and posture relaxation (M10.4) are all *parameterized by jurisdiction* (Doc D §1). This issue resolves a single, queryable jurisdiction for every contact entity from its location claims so that every personal claim inherits it. Designing for the strict (GDPR-grade) case and switching down (conventions §3; Doc D §1) requires that "which regime applies to this person" be a first-class, evidence-backed property, not inferred ad hoc at gate time.
- **Architecture sources:** Doc D §1 (jurisdiction as a first-class per-client switch; every contact carries a resolved jurisdiction; every personal claim inherits it; design-strict-switch-down); overview §5 D4 (resolved: mixed/global); substrate §1 (append-only claim with provenance; `current_value` merge; `superseded_by`), substrate §2 (`account_entity.hq_geo`, contacts resolve under accounts); conventions §3 (jurisdiction is a per-client switch), §4 (`claim`, `current_value`, `account_entity` contracts).
- **Scope / deliverables:**
  - A `JurisdictionResolver` that takes a resolved `contact_entity_id` and returns a `resolved_jurisdiction` (an ISO-3166 region rolled up to a *regime* code, e.g. `EU_GDPR | UK_GDPR | US_GENERIC | US_<state> | OTHER`) plus a confidence and the provenance (which location claim(s) it derived from).
  - Resolution policy: prefer the contact's own location claims (`core.*` / `contact.*` location fields from M8/M1) read via `current_value`; fall back to the parent `account_entity.hq_geo` (substrate §2) with a lowered confidence and an explicit `derived_from = account_hq` flag; if neither is available, emit `OTHER` with a `jurisdiction_unknown` flag.
  - A **strict-by-default rule**: when jurisdiction is unknown or low-confidence, the resolver returns the strictest regime (`EU_GDPR`-grade) for gate purposes, so absence of evidence never relaxes governance (Doc D §1 "design for the strict case").
  - A regime-mapping table (region → regime) authored as versioned config (policy-as-data, conventions §2), so adding/adjusting a regime is a config change, not code. The *legal content* of each regime is left to M10.4's policy config; M10.1 only resolves *which* regime applies.
  - Re-resolution on new location evidence: jurisdiction is itself stored as a claim, so a later, higher-tier location claim supersedes via the normal merge (substrate §1), and the contact's `resolved_jurisdiction` recomputes deterministically.
- **Interface / seam:** **Exposes** `JurisdictionResolver.resolve(contact_entity_id) -> JurisdictionResolution{regime, region, confidence, derived_from, provenance_claim_ids}` and writes the result as a `contact.jurisdiction` claim (so it carries provenance and supersession like any other claim — conventions §4 `claim`). **Consumes** the M1 claim store / `current_value` (location claims), the M2 `account_entity` (`hq_geo` fallback), and the regime-mapping config. The seam is the `regime` code: M10.3/M10.4/M10.5 key only on the regime, never on raw geography, so the region→regime mapping (or a future geo-IP/registry resolver) can be swapped behind `JurisdictionResolver` without touching the gate.
- **Data model / schema:** Adds a registered field `contact.jurisdiction` to the field registry (M1.3) — a `contact.*` field-class entry (conventions §3) whose `value_json` is `{regime, region, confidence, derived_from}`; stored as a normal `claim` (conventions §4) so it is append-only, superseded, and provenance-backed. No new table; the `resolved_jurisdiction` for a contact is `current_value(contact, "contact.jurisdiction")`. Regime-mapping lives in the per-client/jurisdiction policy config skeleton (M0.4).
- **Dependencies:** **Blocked by** M1 (claim store, `current_value`, field registry), M2 (`account_entity.hq_geo`, contacts under accounts — via M1/M8 chain), M8 (contact location claims). **Unblocks** M10.3 (gate input), M10.4 (posture relaxation per regime), M10.5 (lawful-basis selection per regime).
- **Acceptance criteria:**
  - Given a contact with a tier≤2 EU location claim, `resolve` returns `regime = EU_GDPR` with `derived_from = contact_location` and provenance pointing at that claim.
  - Given a contact with no location claim but an EU `account_entity.hq_geo`, `resolve` returns `EU_GDPR` with `derived_from = account_hq` and a confidence strictly below the contact-location path.
  - Given a contact with neither, `resolve` returns the strict-default regime and sets `jurisdiction_unknown = true`.
  - A later higher-tier location claim that supersedes the earlier one changes `resolved_jurisdiction` deterministically via `current_value`, with the prior jurisdiction claim marked `superseded_by` (no UPDATE-in-place).
  - The region→regime mapping is loaded from config; adding a new region row changes resolution with zero code change (verified by a config-only test).
  - A **claim-derived** resolution (`derived_from` ∈ {`contact_location`, `account_hq`} read from a location *claim*) carries the upstream location claim id(s) in `provenance_claim_ids`. *(Implementation note: a resolution read from a resolved **entity column** — `ContactEntity.geo` / `AccountEntity.hq_geo`, which carries no claim id — and the strict-default fall-through carry empty `provenance_claim_ids` by construction; the resolution is itself always persisted as a provenance-bearing `contact.jurisdiction` claim, so the regime is never *stored* without provenance. This supersedes the original "none is emitted without provenance" wording, which conflicted with the column-fallback and strict-default ACs above.)*
- **Out of scope:** Authoring the legal *content* of each regime (M10.4 policy config; legal facts gated by D8). Geo-IP or third-party jurisdiction enrichment (a future resolver behind the seam). Account-level jurisdiction for firmographic data (firmographic claims are not personal data and are out of the use-gate's scope).
- **Open decisions:** D4 (**resolved: mixed/global**) — this issue exists precisely because of that resolution; build accordingly. D8 — the *list* of regimes and their boundaries (US state laws, EU/UK) must be confirmed before go-live; the mapping is config so the list is replaceable without code.

### M10.2 — Use-class taxonomy tagging at extraction
- **Purpose:** Every personal claim must be stamped with a **use-class** the moment it is extracted — *independent of whether it is accurate* (Doc D §2) — because the use-class is "the hinge the three postures turn on" and the primary input to the appropriateness gate (M10.3). Tagging at extraction (not at gate time) is deliberate: it makes the gather/store decision (postures, M10.4) and the use decision both readable from the claim itself, and it ensures `sensitive` content is recognizable for default exclusion (Doc D §4) before it can leak into outreach. This is the contact-axis analogue of stamping `identity_binding` at extraction (staged-flow §6, §9).
- **Architecture sources:** Doc D §2 (the three-value taxonomy: `professional-public`, `personal-public-non-sensitive`, `sensitive`; tag at extraction; the "interests that quietly fall into sensitive" caveat); Doc C §2 (`contact.facet.*` is the governed field-class; `account.resonance.*` is personal-adjacent); staged-flow §9 (field-claim provenance for contacts carries `identity_binding`); conventions §3 (the canonical use-class values), §4 (field-claim provenance additionally carries `use_class` for contact claims; `claim` provenance flavors).
- **Scope / deliverables:**
  - A `UseClassTagger` invoked during M8 contact-claim extraction (and resonance extraction where personal-adjacent) that assigns exactly one use-class to every personal claim from the canonical set: `professional-public | personal-public-non-sensitive | sensitive`.
  - Classification rules combining (a) the source's nature (e.g. a LinkedIn role-history claim → `professional-public`; a marathon-finish → `personal-public-non-sensitive`) and (b) the claim's *content*, with an explicit **special-category detector** for GDPR Art. 9 categories (health, religious/philosophical belief, political opinion, sexual orientation, racial/ethnic origin, trade-union membership, biometric/genetic) **and** the "reasonable-person-private" extension (family/children, financial status, religion-adjacent hobbies) — Doc D §2.
  - A **conservative tie-break**: when a claim is ambiguous or "special-category-adjacent" (e.g. a hobby tied to a religious or political cause), classify it as the more-restrictive class (`sensitive`), so the gate can never under-protect (Doc D §2 caveat; universal rule "empty is correct").
  - Tagging is mandatory for `contact.facet.*` and for any `account.resonance.*` claim that names or is attributable to an individual; firmographic / non-personal claims carry no use-class (or an explicit `not_personal`).
  - Emit the tag as part of field-claim provenance, with its own observability span so tag distribution (share `sensitive`, etc.) is measurable (Doc C §6).
- **Interface / seam:** **Exposes** `UseClassTagger.tag(claim_draft, source_manifest) -> use_class` and writes `use_class` into the claim's provenance at extraction time. **Consumes** the M4 `source_manifest` (to read the source's nature) and the M8 extraction pipeline (the call site). The seam is the `use_class` enum value on the claim: M10.3/M10.4 read only the value, so the *classifier implementation* (rules now, a fine-tuned model later, or a judge-model swap) is replaceable behind `UseClassTagger` without changing any downstream consumer. Mirror of the M9 judge-swap seam — the classifier model is hot-swappable behind the tagger.
- **Data model / schema:** Extends the `claim` field-claim provenance (conventions §4) with a `use_class` field (the canonical enum) on contact / personal-adjacent claims — already named in the conventions `claim` contract and the `account_handoff.committee[].profile_claims[]` shape (overview §3). No new table. The special-category detector's category list is versioned config (policy-as-data) so the Art. 9 set is editable without code.
- **Dependencies:** **Blocked by** M1 (claim provenance fields), M8 (the extraction pipeline that produces `contact.facet.*` / `account.resonance.*` and is the tagging call site), M4 (`source_manifest`). **Unblocks** M10.3 (gate reads `use_class`), M10.4 (postures act on `use_class`), M10.5 (`sensitive` drives default exclusion/retention).
- **Acceptance criteria:**
  - Every `contact.facet.*` claim written by M8 carries a non-null `use_class`; a claim missing it fails a store-time invariant (test: insert without tag → rejected).
  - A role-history / public-talk / publication claim is tagged `professional-public`; a public hobby/alma-mater claim is tagged `personal-public-non-sensitive`; a health/religion/political claim is tagged `sensitive`.
  - An ambiguous "religion-adjacent hobby" claim is tagged `sensitive` (conservative tie-break verified).
  - Tagging is independent of accuracy: a claim that later fails the faithfulness judge still carried a use-class at extraction (the two are decoupled — Doc D §5).
  - The Art. 9 category list is loaded from config; adding a category re-classifies matching claims with zero code change.
  - The tag-distribution span emits counts per use-class for observability (Doc C §6).
- **Out of scope:** Deciding whether a `sensitive` claim is *stored* vs. *stored-but-locked* vs. *not collected* (that is the posture decision, M10.4). Deciding whether a tagged claim may *drive outreach* (the gate, M10.3). Identity-binding strength (M9.4). Collecting the claims themselves (M8).
- **Open decisions:** D8 — the precise special-category boundaries depend on confirmed 2026 law; the category list is config so it tracks D8's resolution. D3 — tagging happens under all three postures (Doc D §6 all "use-class-tagged at extraction"), so this issue is posture-agnostic.

### M10.3 — Appropriateness/use gate (use_class × jurisdiction × client_policy)
- **Purpose:** This is the new gate Doc D was written to add: a deterministic check that decides *"may we lawfully and tastefully **use** this true claim on this person, in this jurisdiction, for this client?"* — distinct from accuracy (Doc D §3, §5; conventions §5). A `contact.facet.*` claim may drive outreach **only if it clears both** the accuracy/identity-binding gate (M9.4 strong-binding) **and** this appropriateness gate (allowed `use_class` for its `resolved_jurisdiction` under the client's policy). Disallowed-use-class claims never promote (the unlawful/creepy trap) just as weak-binding claims never promote (the same-name trap); either failure leaves the field empty, which is a correct output (Doc D §3; universal rule). It is a peer member of the verification layer (substrate §6), running *after* identity-binding and the faithfulness judge, with its own observability span so "we used something we shouldn't have" is a distinct, separately-measurable failure from "we fabricated something" (Doc D §5, §7).
- **Architecture sources:** Doc D §3 (the two-gate table; "clears both"; weak-binding vs. disallowed-use-class traps), §5 (the appropriateness gate is *not* the accuracy judge — separate steps, separate observability), §7 (use-gate is a new verification-layer member running after identity-binding and the faithfulness judge, own trace span; output contract carries `use_class`); substrate §6 (verification layer); conventions §5 (the two gates & universal rule), §4 (`account_handoff` carries `identity_binding` + `use_class`); Doc C §6 (verification-health observability — share of personal claims at strong binding; this gate adds the new "share usable" metric).
- **Scope / deliverables:**
  - A `UseGate` verification step: `evaluate(claim) -> UseDecision{usable: bool, reason, policy_version}` where input is a `contact.facet.*` (or personal-adjacent) claim that has *already* passed M9.4 (strong identity-binding) and M9.3 (faithfulness).
  - Decision is a pure function of `(use_class, resolved_jurisdiction, client_policy)`: look up the client's posture policy (M10.4) for the regime (M10.1), find the allow-rule for the claim's `use_class`, and return `usable = true/false` with a machine-readable `reason` (e.g. `sensitive_locked`, `use_class_disallowed_for_regime`, `allowed`).
  - **Hard floor independent of policy:** `sensitive` claims are *never* usable for outreach regardless of posture (Doc D §4 "excluded from outreach by default regardless of posture") — Option 2 may *store* them but the gate still blocks *use* unless an explicit, legally-reviewed override exists; the floor is enforced in the gate, not left to per-client config alone.
  - Runs strictly **after** identity-binding (M9.4) and the faithfulness judge (M9.3) in the verification sequence (Doc D §7), as a distinct graph step with its **own trace span** (Doc D §5; substrate §6); never collapsed into the accuracy judge.
  - Sets a `usable_for_outreach` decision (with reason + policy version) on the claim's provenance so the downstream content layer can *also* see why a hook is/ isn't usable (overview §3; Doc D §7).
  - A "clears-both" composite helper that content/handoff (M12) calls: a hook is promotable iff `identity_binding == strong AND usable_for_outreach == true`.
- **Interface / seam:** **Exposes** `UseGate.evaluate(claim) -> UseDecision` and the composite `is_promotable(claim) -> bool`; registers itself as a verification-layer member alongside M9's gates. **Consumes** M10.1 (`resolved_jurisdiction`), M10.2 (`use_class`), M10.4 (`client_policy` config), M9.4 (`identity_binding` result), the M1 claim store (to read claim + write the decision). The seam is `UseDecision` + the registered verification-step interface (shared with M9, conventions §2): the gate is replaceable (rules engine now, policy-as-code DSL later) without the orchestrator or content layer knowing, and it sits behind the same verification-step seam as the faithfulness judge so the Postgres-state-machine→Temporal swap (conventions §2) carries it for free.
- **Data model / schema:** Extends field-claim provenance (conventions §4) with `usable_for_outreach{decision, reason, policy_version, evaluated_at}` on personal claims — distinct from `identity_binding` and from the faithfulness verdict, so the two gates remain separately queryable (Doc D §5). Feeds `account_handoff.committee[].profile_claims[]{value, evidence_span, source_tier, identity_binding, use_class}` (overview §3) — this issue guarantees the `use_class` and usability are populated before handoff. No new table.
- **Dependencies:** **Blocked by** M10.1 (jurisdiction), M10.2 (use-class), M10.4 (policy config — co-dependent; M10.3 reads the policy M10.4 defines), M9.3/M9.4 (it runs after them and reads their results), M1 (claim store), M8 (the personal claims it gates). **Unblocks** M12 (handoff/value-narrative may only promote hooks that clear both gates), M13 (verification-health metric "share usable"). *(Priority note: this is the load-bearing core of M10 — the gate the whole milestone exists to add — and is raised to 2/High above the milestone's Medium default.)*
- **Acceptance criteria:**
  - A `professional-public`, strong-binding claim in an `EU_GDPR` jurisdiction under the default policy returns `usable = true, reason = allowed`.
  - A `sensitive` claim returns `usable = false` under **every** posture, including Option 2 (hard floor), with `reason = sensitive_locked`.
  - A `personal-public-non-sensitive` claim returns `usable` per the client's policy for that regime (true under default Option 1, configurable).
  - A claim that passes the faithfulness judge but is `sensitive` is recorded as **accurate-but-not-usable** — the two outcomes appear as separate fields/spans, never conflated (Doc D §5 test).
  - The gate runs *after* M9.4/M9.3 in the verification step ordering (assert sequence); a claim that failed identity-binding is not even evaluated (short-circuits to not-promotable).
  - `is_promotable` returns true only when `identity_binding == strong AND usable_for_outreach == true`; all other combinations return false (truth-table test).
  - Each evaluation emits its own trace span with `(use_class, regime, policy_version, decision)`; the span is distinct from the faithfulness-judge span (observability assertion).
  - Swapping the gate implementation behind `UseGate` leaves M12/M13 untouched (seam test).
- **Out of scope:** Authoring posture policies (M10.4). Resolving jurisdiction (M10.1) or use-class (M10.2). The accuracy/identity-binding judge itself (M9.3/M9.4). Generating the narrative or building the handoff object (M12). The human review surface that displays usability (M13.1).
- **Open decisions:** D3 — the gate is policy-driven; the default policy is Option 1 (M10.4) but the gate machinery is posture-agnostic. D8 — what `use_class × jurisdiction` combinations are *lawful* (vs. merely tasteful) depends on confirmed 2026 law; the gate reads that as policy config and does not hardcode legality.

### M10.4 — Three postures as per-client config (D3 default: Option 1)
- **Purpose:** The three deep-research postures (conservative-default, gather-broadly-gate-at-use, professional-public-only) are **not permanent forks** — they are settings on the *same* `use_class × jurisdiction` machinery, so a regulated client dials down to Option 3 and an aggressive US client dials up to Option 2 without a separate code path (Doc D §6; conventions §2 "policy is data, not code"). This issue makes posture a per-client policy object that parameterizes (a) what is *gathered* (source-level scoping), (b) what is *stored* for `sensitive` data, and (c) what is *usable* (the inputs to the M10.3 gate) — and ships **Option 1 as the platform default** (D3). Building it as config (not branches) avoids the base-layer rework the substrate doc warns against (Doc D §1).
- **Architecture sources:** Doc D §6 (the three options in full — gathered/usable/legal-posture/resonance/ops-load for each; "not permanent forks"; Option 1 = recommended default; dial up to 2 / down to 3 per client), §4 (`sensitive` excluded from outreach by default and, per posture, may not be stored at all), §1 (design-strict-switch-down — postures are relaxations of the strict machinery); overview §5 D3 (posture deferred to data/compliance owner; all three shipped as per-client config, Option 1 default); conventions §2 (policy-as-data), §3 (use-classes); Doc C §2 (source-level scoping interacts with the source-intelligence layer for Option 3).
- **Scope / deliverables:**
  - A versioned `ClientPolicy` config object with three named postures, each expressed entirely as parameters over `use_class × jurisdiction`:
    - **Option 1 (default):** full deep sweep gathered; all personal claims use-class-tagged at extraction; usable = `professional-public` + `personal-public-non-sensitive`; `sensitive` is *stored-but-locked* (or not stored, per a sub-flag) and never usable.
    - **Option 2 (gather broadly, gate at use):** same sweep **including `sensitive`, all stored**; nothing excluded at gather time; usability decided entirely at the M10.3 gate per claim × jurisdiction × policy. (The gate's `sensitive` hard floor from M10.3 still applies unless an explicit legally-reviewed override flag is set.)
    - **Option 3 (professional-public only):** research scoped at the **source level** to professional-public surfaces (LinkedIn, company pages, talks, publications, professional posts) — the deep personal-life dimension is *never collected*; usable = effectively everything gathered; the use-gate is light.
  - A **gather-time enforcement hook** for Option 3 (and Option 1's "do not store sensitive" sub-flag): the policy exposes which source-classes/use-classes M8 + the Source Planner (M4.6) may consult/collect, so source-level scoping is honored *before* spend (Doc D §6 Option 3 "scoped at the source level").
  - Platform default = Option 1 for any client with no explicit posture set (D3).
  - Per-jurisdiction relaxation: a posture's usability rules read down from the strict default per regime, so "design strict, switch down" is implemented as policy lookup, not branching (Doc D §1).
  - Policy is versioned (like the ICP spec and merge policy — conventions §2); a gate decision records the `policy_version` used (consumed by M10.3's `UseDecision`).
- **Interface / seam:** **Exposes** a `ClientPolicy` config contract: `posture`, `usable_use_classes(regime)`, `store_sensitive: bool`, `gather_scope` (source-class allow-list for Option 3), `policy_version`, plus an override register for legally-reviewed `sensitive` exceptions. **Consumes** the M0.4 per-client jurisdiction/policy config skeleton (where this lives), the M10.1 regime codes (relaxation keys on regime). The seam is the `ClientPolicy` object: M10.3 reads it for usability; M8 / M4.6 read `gather_scope` for source-level scoping; nothing reads posture as a branch. Swapping a client between postures, or editing the Art. 9 lock, is a config edit — no redeploy (policy-as-data seam, conventions §2). The gather-scope hook reuses the M4.6 Source-Planner seam (the planner already selects "within the pack's allowed set"), so Option 3 is an allow-list narrowing, not a new planner.
- **Data model / schema:** `client_policy` versioned config (JSON, in the M0.4 config store), referenced by `client_id` (and optionally per-ICP). Each gate decision (M10.3) stamps `policy_version`. No claim-table change; postures act through M10.2's `use_class` tags, M10.1's regimes, M10.3's gate, and M8/M4.6's gather scope. Aligns with the conventions principle that merge policy, scoring rubric, source profiles, jurisdiction/use-class policy and TTLs are all versioned config the engine reads (conventions §2).
- **Dependencies:** **Blocked by** M0.4 (config skeleton), M10.1 (regimes), M10.2 (use-classes). **Co-dependent with** M10.3 (the gate reads this policy). **Unblocks** M10.3 (usability rules), M10.5 (`store_sensitive` and retention interplay), and constrains M8 / M4.6 gather scope under Option 3. **Milestone-level dependency M8** is exercised here (gather-time scoping).
- **Acceptance criteria:**
  - A client with no posture set resolves to Option 1; its gate (M10.3) allows `professional-public` + `personal-public-non-sensitive` and locks `sensitive` (default verified).
  - Switching a client to Option 2 makes `sensitive` claims *stored* but still not *usable* (gate hard floor) unless the explicit override flag is set; the change is config-only (no code change/redeploy).
  - Switching a client to Option 3 causes M8 / M4.6 to *not collect* personal-life source-classes (assert the gather-scope allow-list is honored before spend); the use-gate then passes effectively everything gathered.
  - Option 1's `store_sensitive = false` sub-flag prevents `sensitive` claims from being persisted at all (assert no `sensitive` row written).
  - Per-jurisdiction relaxation: the same posture yields stricter usability for `EU_GDPR` than for `US_GENERIC` where configured, by reading down from the strict default (regime-keyed lookup, not branch).
  - Each posture is expressed only as parameters over `use_class × jurisdiction` — a grep/test confirms no posture-named `if/else` branch exists in gate or collection code (Doc D §6 "not permanent forks").
  - A posture change bumps `policy_version`; subsequent gate decisions record the new version.
- **Out of scope:** The gate evaluation itself (M10.3). Use-class assignment (M10.2). Jurisdiction resolution (M10.1). The *legal correctness* of which posture a client should pick (decision deferred to the data/compliance owner — D3). Retention TTL values (M10.5). The source registry / planner internals (M4) — M10.4 only supplies the allow-list it consumes.
- **Open decisions:** D3 (**posture**) — surfaced here directly: ship all three as config, Option 1 default, decision deferred to the data/compliance owner; do not hardcode a single posture. D8 — whether Option 2's broad *storage* of `sensitive` is lawful in a given regime depends on confirmed 2026 law; the override register and per-regime locks are config so the answer is encoded as policy.

### M10.5 — Lawful-basis recording + retention TTLs + DSAR/erasure (tombstone)
- **Purpose:** Make "why are we allowed to hold this" and "stop holding this" first-class, queryable operations rather than assumptions (Doc D §4). Lawful basis (typically legitimate interest, GDPR Art. 6(1)(f), for `professional-public` B2B) is recorded as provenance alongside each personal claim; personal claims carry **shorter retention TTLs** than firmographic facts (people change, and minimizing retained personal data shrinks risk); and data-subject rights — access, rectification, **erasure**, objection to direct-marketing (Art. 21, near-absolute) — are serviceable. The append-only claim store keyed on a resolved `contact_entity_id` is exactly what makes erasure tractable: a request resolves to a *deterministic set* of claims to tombstone — the same provenance model that makes research verifiable makes erasure tractable (Doc D §4; conventions §2).
- **Architecture sources:** Doc D §4 (lawful basis as provenance + LIA; special-category needs more than legitimate interest → `sensitive` excluded by default; Art. 14 transparency flag; retention TTLs on personal claims; DSAR/erasure resolves to a deterministic tombstone set keyed on `contact_entity_id`); substrate §1 (append-only, `superseded_by`, never UPDATE-in-place — the basis for tombstone; `extraction_method` enum); substrate §6 (freshness TTL as a first-class signal; merge treats stale as refresh-eligible); substrate §3 (`field_definition` freshness/TTL); conventions §4 (`claim` provenance, `extraction_method` enum, `account_handoff`), §2 (TTLs are versioned policy).
- **Scope / deliverables:**
  - **Lawful-basis recording:** every personal claim records a `lawful_basis` in provenance (e.g. `legitimate_interest`, `consent`, `none`), derived from `(use_class, regime, client_policy)`. For `professional-public` B2B under GDPR the default basis is `legitimate_interest` with a pointer to the client's documented balancing test (LIA reference). `sensitive` claims default to `none` for outreach (Art. 9 — explicit consent unavailable in cold outreach), reinforcing the M10.3 hard floor.
  - **Retention TTLs on personal claims:** register shorter `freshness_ttl` / retention for `contact.facet.*` and personal-adjacent fields than for firmographic fields (substrate §3, §6). Expired personal claims **age out**: an eligible-for-expiry view marks them stale, and (per policy) they are tombstoned/excluded from `current_value` and from any handoff.
  - **DSAR/erasure path (tombstone):** an `erase(contact_entity_id, scope)` operation that resolves the deterministic claim set for that contact (and optionally a use-class/field scope), writes **tombstone** records that supersede them so the values are no longer readable via `current_value` or handoff, while preserving an audited, value-redacted record of the erasure (append-only discipline, substrate §1 — never a destructive UPDATE). Supports the four rights: **access** (export the contact's claims + provenance), **rectification** (supersede with a corrected claim — reuses merge), **erasure** (tombstone), **objection** (mark the contact `outreach_objected` so all hooks are blocked at the gate, near-absolute under Art. 21).
  - **Transparency flag (Art. 14):** when personal data is collected from sources other than the person, set a `third_party_collected` flag on the claim and surface an aggregate "notice may be owed" report for the compliance owner (Doc D §4 — M10 flags, does not decide).
  - Erasure/objection propagate to the gate: an objected contact's claims return not-promotable at M10.3; an erased claim is invisible to M12 handoff.
- **Interface / seam:** **Exposes** a `DataSubjectRights` service — `access(contact_entity_id)`, `rectify(claim_id, corrected)`, `erase(contact_entity_id, scope)`, `object(contact_entity_id)` — and a retention/expiry view over personal claims. **Consumes** the M1 claim store (append-only supersede / tombstone mechanics, `current_value`), the field registry (M1.3, for personal-field TTLs), M10.1 (regime → which rights apply), M10.2 (`use_class` → lawful basis + retention class), M10.4 (`store_sensitive`, retention policy). The seam: erasure is implemented purely as supersession-by-tombstone over the existing claim store (no new deletion path), so the same machinery works whether durable execution is the Postgres state machine or Temporal (conventions §2), and tombstones flow through the normal merge so every consumer (`current_value`, handoff, gate) honors erasure with zero special-casing.
- **Data model / schema:** Extends `claim` provenance (conventions §4) with `lawful_basis`, `lia_ref` (LIA pointer), `third_party_collected` flag, and a `retention_until` derived from the field's personal-data TTL. A **tombstone** is a claim row written with `extraction_method = human` (the existing enum value — no new enum is invented; if a dedicated `erasure` method is wanted it must first be added to the `claim.extraction_method` enum in M1), `value_json` redacted, that sets the target claim's `superseded_by` and a `tombstoned_by_dsar` marker — append-only, consistent with substrate §1. A per-contact `outreach_objected` flag (stored as a `contact.*` claim) read by the M10.3 gate. Personal-field TTLs live in `field_definition` freshness/retention (substrate §3) plus a retention-policy config (versioned, M0.4). No destructive deletes anywhere.
- **Dependencies:** **Blocked by** M1 (append-only store, `current_value`, supersede, field registry/TTL — milestone dependency), M9 (freshness TTL engine M9.5 — co-located TTL mechanics; M10.5 adds the *personal-data retention* semantics on top), M10.1 (regime), M10.2 (use-class → basis/retention), M10.4 (`store_sensitive`/retention policy), M8 (the personal claims being governed). **Unblocks** M12 (handoff must exclude erased/objected/expired personal claims), M13 (verification-health / compliance reporting). Depends on milestone **M8** (it governs M8's output) and **M9** (TTL/freshness machinery).
- **Acceptance criteria:**
  - Every personal claim written carries a `lawful_basis`; a `professional-public` GDPR claim defaults to `legitimate_interest` with an LIA reference; a `sensitive` claim defaults to `none` for outreach.
  - Personal-field TTLs are strictly shorter than firmographic TTLs (config assertion); an expired personal claim is excluded from `current_value` and from `account_handoff` (aged-out test).
  - `erase(contact_entity_id)` resolves a deterministic, complete set of that contact's claims (keyed on `contact_entity_id`) and tombstones them via supersession; afterward `current_value` and `account_handoff` return none of those values, and no row was destructively deleted (append-only audit preserved).
  - `object(contact_entity_id)` causes M10.3 to return not-promotable for all of that contact's hooks (objection honored at the gate).
  - `access(contact_entity_id)` exports the contact's claims with full provenance; `rectify` supersedes a claim with a corrected value via the normal merge.
  - A claim collected from a third-party source carries `third_party_collected = true` and appears in the "notice may be owed" aggregate report.
  - The tombstone uses an existing `claim.extraction_method` enum value (no contract violation); erasure works identically under the Postgres state machine and would under Temporal (no execution-engine-specific code in the erasure path — seam test).
- **Out of scope:** The legitimate-interest balancing test (LIA) *content* and the legal *decision* of whether a basis holds (compliance-owner / legal task; M10.5 records and points at it). The exact 2026 TTL durations and which DSAR timelines apply per regime (D8 — values are config). The faithfulness/freshness *judge* internals (M9). The client-facing rights-request UI (M13). Cross-tenant erasure coordination for shared public-footprint claims (note: public firmographic claims are not personal data; personal claims are tenant-scoped — defer any cross-tenant nuance to M2.5's isolation rules).
- **Open decisions:** D8 — current US-state/EU/UK retention durations, DSAR response windows, and Art. 14 notice triggers must be confirmed before go-live; all are config so they track D8. D3 — `store_sensitive` (and therefore what erasure/retention must cover) depends on the chosen posture (M10.4); the retention machinery is posture-agnostic and reads the policy.
