# M13 — Review, Feedback Loops & Observability Surface
**Layer label:** layer:review-observability  ·  **Depends on:** M6, M9, M12  ·  **Priority:** 3
**Architecture sources:** substrate §9 (scoring — explainable, provenance-backed, learning; "the feedback loop is free in V1"), §10 (human-in-the-loop — designed surface; approve/correct/reject per claim; corrections = labeled training data for extraction *and* scoring), §6 (verification — the outputs review reads: provenance, corroboration, faithfulness judge, freshness), §5c (durable execution — `AsyncPostgresSaver` crash-resumability + idempotency + budget caps), §12 (stack — `interrupt()`-based pause/resume for Tier-1 review; Postgres-only write path); staged-flow §7e (source learning loop — per (ICP, field-class, source) precision/coverage/freshness/cost/downstream-signal → reweight source profiles), §9 (feedback loop now reweights *sources* in addition to scoring — same disposition signal, one more target), §10 (end-to-end sequence — review → disposition + source-yield feedback → reweight scoring & source profiles); Doc C §5 (cost dial & governance — pre-run estimate, client-set hard cap, graceful stop, cost pass-through D7), §6 (observability & progress surface — phase progress, cost burn-down, per-source yield, verification health), §7 (coverage confidence — estimate + unsearched channels, not exhaustiveness); Doc D §3, §5 (the use-gate / appropriateness gate the review surface must surface per personal claim), §4 (downstream dispositions about a person are data tied to a `contact_entity_id` — erasure/tombstone applies), §6, §7 (per-client posture; every handoff contact claim carries `identity_binding` + `use_class`); overview §2 (the feedback arc at the end of the map), §3 (the `account_handoff` that review gates).

## Goal & scope of this milestone

This layer closes the loop. Everything upstream produces the four required outputs (overview §1) and assembles them into the `account_handoff` (M12); M13 puts a **human review surface** in front of that handoff, **captures every disposition** as labeled training data, **feeds those dispositions back** into the scoring rubric (M3) and the source profiles (M4), and **exposes the live cost/progress/health of a campaign run** to the client. It is the realization of substrate §9's "the feedback loop is free in V1" and §10's "human-in-the-loop is a designed surface, not a caveat," plus Doc C §6's observability surface and staged-flow §7e's source-learning loop.

Where it sits in the end-to-end map (overview §2, staged-flow §10): M13 owns the final arc — `Verification → Human review (Tier-1) → disposition + source-yield feedback → reweight scoring & source profiles`, and the cross-cutting `Observability & progress surface` that runs alongside the whole campaign run. It reads from the claim store (M1), the verification layer (M9), the campaign-run state machine and budget engine (M7), the Pass A scorer and coverage estimator (M6), and the `account_handoff` (M12). It writes only: review dispositions, reweighting deltas to versioned config (scoring rubric, source profiles), and read-projected observability views.

**Note on dependencies.** The milestone-level `Depends on` is fixed by `_conventions.md §7` at **M6, M9, M12**. M13.1 and M13.4 additionally *read* M7 (the per-account graph's `interrupt()`/resume, the campaign-run state machine, idempotency keys, and the budget engine) at the issue level — M7 is a read/consume dependency surfaced per issue, not a milestone-level blocker, and this spec does not add it to the milestone header.

**Four issues:**
- **M13.1** — Tier-1 review surface: per-claim approve / correct / reject, with durable `interrupt()`-based pause and resume on the per-account graph, gating handoff.
- **M13.2** — Disposition capture: turn every review action *and* every downstream sales accept/reject into a normalized, labeled `disposition` record (the training-data substrate the learning loop consumes). Raised to **Priority 2 (High)** — it is the foundation M13.3 reads from, and dispositions lost at capture time can never be recovered.
- **M13.3** — Source-yield + scoring learning loop: reweight per-(ICP, field-class, source) source profiles and the fit/intent scoring rubric from measured outcomes (verification survival + dispositions), as versioned config bumps — never an autonomous in-place mutation.
- **M13.4** — Client-facing cost & progress surface: phase progress, cost burn-down vs. estimate vs. cap, per-source yield, verification health, pre-run estimate, and coverage confidence.

**Explicitly NOT here.** The claim store / `current_value` merge (M1); identity resolution and its mid-band review queue (M2 — a *different* queue from the Tier-1 claim review here); the verification mechanisms themselves — gates, corroboration, faithfulness judge, identity-binding, use-gate (M9, M10) — M13 *displays* their results and *consumes* their pass/fail signals but does not implement them; the campaign-run state machine, per-account graph, idempotency keys, and budget-cap engine (M7) — M13 reads phase/cost state and registers an `interrupt` checkpoint but does not own the state machine; the Pass A scorer and coverage estimator computation (M6) — M13 surfaces their outputs and reweights their rubric; the `account_handoff` object, positioning step, and the output API to the content layer (M12); model/extractor retraining itself — M13 produces labeled data and config deltas, it does not train extraction or fit *models* beyond rubric reweighting (model retraining is a downstream/V2 consumer of the M13.2 dataset). No external tool (CRM, Airtable, spreadsheet) sits in the write path — Postgres is the only source of truth (substrate §5c, §12); a CRM may be a *read* source of downstream dispositions and a *read-only* projection target, never write-through.

## Issues

### M13.1 — Tier-1 review surface (per-claim approve/correct/reject, interrupt/resume)

- **Purpose:** Substrate §10 makes Tier-1 review a *designed checkpoint*, not a disclaimer: "Tier-1 review before content generation" — before a high-tier account's research crosses to the content layer, a human sees each claim with its source, confidence, freshness, and corroboration and can approve / correct / reject it. In this subsystem the boundary "before content generation" is the M12 handoff, so this is the human gate immediately before the `account_handoff` is finalized. It is the surface that earns the sales line "every fact in this report links to its source" (substrate §10) — and, by Doc D, that lets a reviewer see *why* a personal hook is or isn't usable (its `identity_binding` and `use_class`). The review must suspend the per-account graph durably and resume on the human action, so a campaign that spans days survives crashes at the checkpoint.
- **Architecture sources:** substrate §10 (Tier-1 review before content generation; approve/correct/reject per claim; `interrupt()`-style pause/resume — the secure-input pattern; corrections become labeled training data for extraction *and* scoring); §6 (the verification outputs — provenance, corroboration count, faithfulness verdict, freshness — that each claim row displays); §5c (`AsyncPostgresSaver` crash-resumability + idempotency keys); §12 (stack — `interrupt()`-based pause/resume for Tier-1 review); §9 (scores read from claims, every score links to its evidence — the review shows the decomposed fit/intent sub-scores with claim links); Doc D §3, §5, §7 (each personal claim row shows `identity_binding` strength and `use_class`, and whether it cleared the appropriateness/use gate); overview §3 (the `account_handoff` this review gates).
- **Scope / deliverables:**
  - A **review session** model scoped to one `account_handoff` candidate (one high-tier `account_entity_id` within a `campaign_run`): the set of `account_profile_claims[]`, the `committee[]` with their `profile_claims[]`, the decomposed fit/intent sub-scores each linked to its claims, and the draft `value_narrative[]` lines — all as read projections over the claim store (M1) and verification results (M9).
  - **Per-claim review actions:** `approve`, `correct` (reviewer supplies a corrected `value_json` and/or evidence note), `reject` (with a reason code). Every action is recorded; corrections and rejections emit dispositions to M13.2. A correction is written as a **new human-extraction claim** (`extraction_method = human`, conventions §4 claim contract) that supersedes the corrected claim via `superseded_by` — never an in-place UPDATE (substrate §1, append-only).
  - **Per-claim display payload:** value, `source_url`, `source_tier`, `confidence`, freshness (`observed_at` + field TTL state from M9.5), `corroborations`, faithfulness-judge verdict (M9.3) for tier-4 claims, and for contact claims `identity_binding` + `use_class` + appropriateness/use-gate result (M10.3). Empty/flagged fields render as a *correct* output (universal rule, conventions §5), with the reason they are empty (no evidence span / weak binding / disallowed use-class).
  - **Durable interrupt/resume:** register an `interrupt()` checkpoint on the per-account LangGraph graph (M7.1) at the `ready_for_review` boundary; the graph suspends with state persisted via `AsyncPostgresSaver` (substrate §5c); resume is triggered by the review-session completion (all claims dispositioned or reviewer explicitly finalizes). Idempotent on `(account_entity_id, campaign_run, review_round)` so resume never double-advances (M7.4).
  - **Handoff gating:** the M12 `account_handoff` for this account is only finalized after review completes; rejected claims are excluded from the handoff; corrected claims flow through `current_value` (M1.2) so the merge view reflects the human-tier claim.
  - **Batch/queue ergonomics:** a reviewer works a queue of `ready_for_review` accounts for a campaign, ordered by tier then fit score; bulk-approve of unflagged claims is allowed; flagged/conflict claims (M1.2 conflict flag, M9 failures) are forced to explicit disposition.
- **Interface / seam:**
  - **Exposes** a `ReviewSurface` service contract: `open_session(account_entity_id, campaign_run) -> ReviewSession` (read projection), `apply_action(claim_id, action{approve|correct|reject}, payload) -> Disposition`, `finalize(session) -> resumes graph + unblocks handoff`. The UI (out of scope as a *built* frontend; the API is in scope) is a pure client of this contract — the surface is swappable (internal admin UI → client portal) behind it.
  - **Consumes:** the claim store read API and `current_value` (M1); verification results (M9.1–M9.5) and the appropriateness/use-gate result (M10.3) as read-only per-claim annotations; the per-account graph's `interrupt()`/resume primitive and idempotency keys (M7.1, M7.4); the campaign-run phase state (M7.3) to know which accounts are `ready_for_review`; the `account_handoff` assembler (M12.2) which it gates.
  - **Swap points behind the seam:** the durable-execution engine is Temporal-shaped (conventions §2, substrate §5c/§12) — replacing the Postgres state machine + LangGraph `interrupt()` with Temporal human-task timers is mechanical and stays behind the `ReviewSurface.finalize → resume` boundary. The review UI is a client of the contract, replaceable without touching the engine. A correction is always a `human`-method claim so the merge policy (M1.2), not the review surface, decides precedence.
- **Data model / schema:**
  - New `review_session(id, account_entity_id, campaign_run_id, review_round, opened_by, opened_at, status{open|finalized|abandoned}, finalized_at)`.
  - New `review_action(id, review_session_id, claim_id, action enum(approve|correct|reject), reason_code, corrected_value_json nullable, note, actor, acted_at)` — append-only; one row per action, the audit trail.
  - A **correction** writes a `claim` (conventions §4 contract) with `extraction_method = human`, `evidence_span` = reviewer note/source, and `superseded_by` set on the original — no new claim shape, reuses M1.
  - Emits a `disposition` (M13.2 contract) per correct/reject (and optionally per approve) — does not define it here.
  - No change to the `claim`, `account_entity`, or `account_handoff` contracts (conventions §4) beyond consuming them.
- **Dependencies:** M9 (verification results to display) and M12 (the handoff being gated) are the milestone-level blockers; within the milestone it is the primary producer for **M13.2**. Reads M1 (claims), M6 (Pass A score decomposition shown for context), M7 (interrupt/resume + idempotency — issue-level read), M10 (use-gate annotations on personal claims). Unblocks the disposition loop (M13.2 → M13.3).
- **Acceptance criteria:**
  - Opening a session for a `ready_for_review` account returns every account claim, every committee contact with its claims, the decomposed fit/intent sub-scores each with claim links, and draft narrative lines — each claim row carrying source_url, tier, confidence, freshness state, corroboration count, and (for tier-4) the faithfulness verdict; for contact claims, `identity_binding` + `use_class` + use-gate result.
  - `correct` produces a new `human`-method claim that supersedes the original; `current_value` for that field now returns the corrected value with human provenance; the original remains queryable (append-only verified).
  - `reject` excludes the claim from the finalized `account_handoff`; an integration test confirms a rejected claim does not appear in handoff output or the provenance index.
  - The per-account graph suspends at the review checkpoint with state persisted; killing and restarting the process resumes the same session with no double-advance and no duplicate handoff (idempotent on `(account, campaign_run, review_round)`).
  - Every `approve`/`correct`/`reject` produces exactly one `review_action` row and emits the corresponding M13.2 disposition; replaying the same action is idempotent.
  - An empty/flagged field renders with its reason (no span / weak binding / disallowed use-class) and is *not* treated as a defect by the surface.
  - Finalizing a session unblocks M12 handoff assembly for that account; an un-finalized session leaves the handoff in `pending`.
- **Out of scope:** the identity-resolution mid-band review queue (M2.3 — a different queue, different object); the verification mechanisms themselves (M9/M10 — only their results are shown); the production frontend styling (only the API contract is delivered here); model/extractor retraining from corrections (M13.2 captures the labels; consumers are downstream); the `account_handoff` object and positioning (M12).
- **Open decisions:** **D2** (design-subsystem ingest interface) — review gates the handoff but does not assume what the content layer ingests; proceed on the recommended boundary (handoff = claims + value narrative, overview §3, D1) without hardcoding the downstream consumer. **D3** (personal-data posture) — the surface *displays* `use_class`/`identity_binding`/use-gate result for every personal claim regardless of posture; the posture (Option 1 default, Doc D §6) decides what is even present to review, set as per-client config, not in this surface.

### M13.2 — Disposition capture → labeled training data

- **Purpose:** Substrate §9 calls the feedback loop "free in V1": when the client's sales team accepts or rejects accounts we scored, that disposition is *labeled training data for the fit model*; and (substrate §10) when a reviewer corrects or rejects a claim, those corrections are *labeled training data for extraction and scoring*. (Staged-flow §7e) the same disposition signal tells the source-learning loop which sources actually drove accepted accounts / replies. This issue is the normalized capture substrate for **all** disposition signals, from two origins: (1) internal Tier-1 review actions (M13.1), and (2) downstream sales outcomes (account accepted/rejected/replied/meeting-booked) ingested from the client. Dispositions not captured at the moment they occur are gone forever, which is why this is foundational (Priority 2). It is the single dataset M13.3 reads.
- **Architecture sources:** substrate §9 (disposition = labeled training data for the fit model; capture from day one — "static-scoring competitors can't claim a model that improves on the client's own outcomes"); §10 (corrections become labeled training data for extraction *and* scoring); staged-flow §7e (downstream signal — did claims from this source drive accepted accounts / replies — feeds source reweighting), §9 (the same disposition signal pointed at sources too); §10 (the disposition feedback arc at the end of the sequence); overview §2 (the same arc on the map); Doc D §4 (downstream dispositions about a person are themselves data tied to a `contact_entity_id` — must respect erasure/tombstone).
- **Scope / deliverables:**
  - A normalized **`disposition`** record: the atomic unit of feedback. Keyed on the resolved `account_entity_id` (and optional `contact_entity_id` and `claim_id`), tagged with a `disposition_type` taxonomy and the `campaign_run` / `icp_spec_version` context so reweighting can be scoped per (ICP, run).
  - **Two ingest paths, one schema:** (a) an internal emitter that M13.1 calls on every review action (claim approve/correct/reject); (b) a **downstream-outcome ingest API** that accepts sales dispositions (account accepted / rejected / contacted / replied / meeting / closed-won|lost) keyed by `account_entity_id` — sourced from the client (CRM read, webhook, or manual mark). The CRM is a *read* source here, never write-through (substrate §5c, §12).
  - **Provenance linkage for the source-learning loop:** each disposition resolves, via the provenance index (M12.2) and the claim store (M1), to the set of claims (and thus sources) that contributed to the scored/handed-off account — so "claims from source X drove N accepted accounts" is computable. The disposition stores the linkage snapshot (the `icp_spec_version`, the contributing `source_key`s and `field_key`s at handoff time) so later config changes don't rewrite history.
  - **A labeled-dataset read view** (the training-data export): a queryable projection joining dispositions to their accounts' feature vectors (the Pass A signals and their provenance, M6) and outcomes — the shape M13.3 and any future model-training consumer reads. Append-only and versioned; never mutated in place.
  - **Erasure compliance:** because dispositions can reference `contact_entity_id`, an erasure/tombstone request (M10.5, Doc D §4) over a contact tombstones its dispositions too; the dataset view excludes tombstoned rows.
- **Interface / seam:**
  - **Exposes** a `DispositionStore` contract: `record(disposition) -> id` (idempotent on a natural key), `ingest_downstream(payload) -> [Disposition]`, and a `labeled_dataset(icp_spec_version | campaign_run, since) -> rows` read view. M13.3 consumes only `labeled_dataset`; nothing downstream reads raw disposition tables directly.
  - **Consumes:** M13.1 review actions (internal emitter); the provenance index + handoff (M12.2) to resolve disposition → contributing sources/claims; identity resolution (M2) so every disposition keys on a resolved `entity_id`, never a free-text name (conventions §2); the erasure/tombstone surface (M10.5).
  - **Swap points behind the seam:** the downstream-outcome source is pluggable — CRM-read adapter, webhook, or manual UI all land as the same `disposition` via `ingest_downstream`, so swapping how outcomes arrive is an adapter change. The labeled-dataset view is the only contract M13.3 sees, so the storage layout can change without touching the learning loop.
- **Data model / schema:**
  - New `disposition(id, disposition_type enum(claim_approved|claim_corrected|claim_rejected|account_accepted|account_rejected|account_contacted|reply_received|meeting_booked|closed_won|closed_lost), entity_id, entity_type{account|contact}, claim_id nullable, campaign_run_id, icp_spec_version, actor enum(internal_reviewer|client_sales|system), origin enum(review_surface|crm_ingest|webhook|manual), occurred_at, recorded_at, tombstoned_at nullable, natural_key)` — append-only; `natural_key` enforces idempotent capture.
  - New `disposition_provenance(disposition_id, contributing_source_keys[], contributing_field_keys[], contributing_claim_ids[])` — the snapshot of which sources/claims fed the account at handoff time (read from the M12.2 provenance index).
  - **Labeled-dataset view** = a SQL view/materialization joining `disposition` × `disposition_provenance` × the account's Pass A signal claims (M6) × `icp_spec` (M3). No new claim shape; reuses `claim`, `account_entity`, ICP spec (conventions §4).
- **Dependencies:** **M13.1** (the internal disposition source) and **M12** (provenance index for source linkage) block this; M2 (entity keys) and M6 (signal features) are read. It is the **sole input** to **M13.3**. Blocks M13.3.
- **Acceptance criteria:**
  - Every M13.1 review action produces exactly one `disposition` row with the correct type, entity, claim link, and campaign/ICP context; replaying the action does not duplicate (idempotent on `natural_key`).
  - `ingest_downstream` accepts a batch of sales outcomes keyed by `account_entity_id`, resolves each through identity (rejecting unresolvable rows to an error queue rather than guessing), and records one disposition each; a stale/free-text company name is resolved or rejected, never silently best-guessed (conventions §2: everything keys on a resolved `entity_id`).
  - For an accepted account, `disposition_provenance` lists the exact `source_key`s and `claim_id`s that contributed to its handoff, snapshotted at disposition time and stable against later config changes.
  - `labeled_dataset(icp_spec_version)` returns one row per disposed account joining its outcome label to its signal features and contributing sources; the view is reproducible and append-only (re-running yields the same rows plus any new ones).
  - Tombstoning a contact (M10.5) removes its dispositions from the dataset view while leaving an audited tombstone marker.
  - No CRM or external tool appears in the write path; downstream outcomes enter only via `ingest_downstream` into Postgres.
- **Out of scope:** the reweighting logic itself (M13.3); training extraction or fit *models* beyond exposing the dataset (downstream/V2); the CRM connector implementation details (an adapter behind `ingest_downstream`); the Tier-1 UI (M13.1).
- **Open decisions:** **D7** (economics / cost pass-through) indirectly — whether downstream outcomes are even shared depends on the client relationship; the schema supports both internal-only and client-fed dispositions. **D3** (personal-data posture) — contact-level dispositions inherit the same erasure/retention machinery as contact claims (Doc D §4); proceed on Option 1 default.

### M13.3 — Source-yield + scoring learning loop (reweight source profiles & scores)

- **Purpose:** Staged-flow §7e specifies how source importance "honestly adjusts per industry": profiles start as curated priors and are reweighted by *measured outcomes* the provenance layer already records — per (ICP, field-class, source) track precision (claims that survived verification), coverage (fields filled), freshness, cost, and downstream signal (did the source's claims drive accepted accounts / replies). Substrate §9 makes the same disposition signal reweight the *fit/intent scoring rubric*; staged-flow §9 states the feedback loop "now reweights *sources* in addition to scoring — the same disposition signal, pointed at one more target." This issue implements both reweightings as a deterministic, auditable, **versioned-config** loop — "start with priors, learn from yield — not autonomous magic" (staged-flow §7e). It is the loop that makes the subsystem improve on the client's own outcomes, which static-scoring competitors cannot claim (substrate §9).
- **Architecture sources:** staged-flow §7e (the learning loop — per (ICP, field-class, source) precision/coverage/freshness/cost/downstream-signal → reweight source profiles; priors-then-yield, not magic), §9 (feedback now reweights sources in addition to scoring; same disposition signal, one more target); substrate §9 (disposition → labeled training data → reweight the fit model/rubric; provenance-backed and learning; "decompose, don't ship an opaque 87/100"), §6 (verification survival is the precision signal — claims that survived the gates/judge); Doc C §6 (per-source yield is the *same* signal the learning loop consumes — observability and the loop read the same provenance data); conventions §2 (policy-as-data: scoring rubric and source profiles are versioned config the engine reads, swappable per client/ICP without code).
- **Scope / deliverables:**
  - **Per-(ICP, field-class, source) yield metrics** computed from the provenance/verification data: precision = claims from this source that survived verification (M9) ÷ claims produced; coverage = fields/field-classes this source filled; freshness = age profile of its surviving claims; cost = `cost_cents` per surviving claim; downstream-signal = accepted-account / reply rate among accounts this source contributed to (from M13.2 dispositions). All read-only aggregations over existing provenance — no new collection (staged-flow §7e: "which your provenance layer already records for free").
  - **Source-profile reweighter:** turns those metrics into proposed per-source weight deltas for the ICP/pack's source profile (M4.6 / staged-flow §7c), as a **new versioned source-profile revision** — never an in-place mutation. The reweighting function is deterministic and documented (e.g., weight ∝ priors × measured precision × downstream-signal, cost-penalized), with bounded step size so one bad run can't zero a source.
  - **Scoring-rubric reweighter:** from the labeled dataset (M13.2), propose fit/intent weight adjustments for the scoring rubric (M3.4, itself part of the versioned ICP spec — conventions §4) — again as a **new versioned rubric revision**, decomposed and explainable (which signals' weights moved and why), preserving substrate §9's "decompose, don't ship an opaque 87/100."
  - **Promotion policy = config, with a human gate by default:** reweighting *proposes* a new config version; promotion to "active" for a client/ICP is gated (auto-promote within bounds, or human-approve for larger moves) — policy is data (conventions §2). New runs read the active version; existing runs keep the version they started with (reproducibility — the ICP spec is versioned, conventions §4 / staged-flow §2).
  - **Backtest / guardrail:** before promotion, evaluate a proposed rubric against the golden account set / eval harness (M9.6) so a reweight that regresses accuracy is blocked.
- **Interface / seam:**
  - **Exposes** a `LearningLoop` contract: `compute_yield(icp_spec_version | campaign_run) -> YieldMetrics`, `propose_source_profile_revision(icp, metrics) -> SourceProfileRevision`, `propose_scoring_rubric_revision(icp, dataset) -> ScoringRubricRevision`, `promote(revision, mode{auto|human}) -> active_version`. Outputs are *config revisions* — the engine (M4 waterfall/planner, M6 scorer) reads them via the existing config loader (M0.2); the loop never calls the scorer or planner directly.
  - **Consumes:** the labeled dataset (M13.2 `labeled_dataset`); verification survival data (M9); the provenance index (M12.2) / claim store (M1) for source attribution; the source-profile model (M4.6) and scoring-rubric model (M3.4) it revises; the eval harness (M9.6) for the backtest guardrail.
  - **Swap points behind the seam:** the reweighting *function* is policy/data — swapping a heuristic reweighter for a learned model is a strategy swap behind `propose_*`, with the contract (metrics in, versioned config revision out) unchanged. Because the loop only ever emits versioned config that the existing engines read, the scorer and source planner remain unaware the loop exists (DRY seam, conventions §2). The same loop machinery serves both targets (sources and scoring) — one disposition signal, two reweight outputs (staged-flow §9).
- **Data model / schema:**
  - Reuses and revisions, never mutates: **`source_profile`** (M4.6, staged-flow §7c) gains versioned revisions; the **scoring rubric** within the **ICP spec** (M3.4, conventions §4) gains versioned revisions. New `config_revision(id, target enum(source_profile|scoring_rubric), icp_spec_version, parent_revision, payload_json, derived_from{yield_metrics_ref|dataset_ref}, proposed_at, status enum(proposed|promoted|rejected), promoted_by, promoted_at)`.
  - New `source_yield(icp_spec_version, source_key, field_class, precision, coverage, freshness_score, cost_per_surviving_claim, downstream_signal, window_start, window_end)` — the materialized metric table, shared with M13.4's per-source-yield surface (Doc C §6: same provenance data).
  - No change to `claim`, `disposition`, or `account_handoff` contracts.
- **Dependencies:** **M13.2** (labeled dataset) blocks this; reads M9 (verification survival + eval harness), M4.6 (source profiles), M3.4 (scoring rubric), M12.2 (provenance). Shares the `source_yield` table with **M13.4**. Unblocks improved future runs (config-only).
- **Acceptance criteria:**
  - `compute_yield` returns per-(ICP, field-class, source) precision/coverage/freshness/cost/downstream-signal computed purely from existing provenance + dispositions, with no new data collection; numbers reconcile against hand-checked claim counts on a fixture campaign.
  - A reweight run emits a **new** versioned `source_profile` revision (parent linked); the prior active version is unchanged and still readable; a run started before promotion continues to read its original version (reproducibility test).
  - A scoring-rubric reweight emits a new decomposed rubric revision; an explainability check shows, per moved weight, which signals and disposition outcomes drove the change.
  - Promotion is gated: an out-of-bounds weight move requires human approval; an in-bounds move can auto-promote; reweighting never mutates active config in place.
  - The backtest guardrail blocks promotion of a rubric revision that regresses the golden-set accuracy below threshold (M9.6).
  - Bounded step size: a single run's per-source weight change is capped; a fixture where one source emitted only rejected claims down-weights it but does not zero it.
- **Out of scope:** the Tier-1 review surface (M13.1); disposition capture (M13.2); the cost/progress UI (M13.4, though it shares `source_yield`); training extraction/fit *models* end-to-end (the loop reweights rubric/profile config; full model training is downstream); the source registry/manifest and planner implementation (M4 — only their config is revised).
- **Open decisions:** **D7** (economics) — the downstream-signal term depends on whether sales outcomes are shared (D7/M13.2); when absent, the loop falls back to verification-survival + coverage + cost and notes reduced confidence. **D5** (ICP multiplicity) — reweighting is scoped per `icp_spec_version`, so multiple ICPs per client each learn independently (Doc B / overview §5 recommended default: support multiple ICPs); proceed on the multi-ICP default.

### M13.4 — Client-facing cost & progress surface (phase progress, burn-down, per-source yield, verification health, pre-run estimate)

- **Purpose:** Doc C §6 requires that a long campaign run never leave the client staring at a spinner: expose phase progress, live cost burn-down vs. estimate vs. cap, per-source yield, and verification health. Doc C §5 requires a **pre-run cost estimate** ("~N discovered → at these cutoffs, ~M go deep → ~$X") and a client-set hard cap with graceful stop at a checkpoint. Doc C §7 requires **coverage confidence** (estimated % of the addressable set found via the searched channels, plus the channels *not yet* searched) rather than a false completeness claim. This surface makes the two-pass discipline and the cost dial (fan-out cost per account × accounts per pass, Doc C §5) legible as a client benefit and a trust feature, and it is an early-warning system: a drop in verification health flags a model/resolver regression (Doc C §6).
- **Architecture sources:** Doc C §5 (cost dial & governance — pre-run estimate, client-set hard cap, graceful stop at checkpoint, cost pass-through D7), §6 (observability & progress surface — phase progress, cost burn-down, per-source yield, verification health), §7 (coverage confidence — estimate + unsearched channels, not exhaustiveness); substrate §5c (per-account/run budget caps the burn-down reads); §6 (verification mechanisms — faithfulness judge, corroboration, freshness — whose health this panel reports); §9 (provenance-backed, the same data the dashboard reads); Doc C §6 note (verification health = share of tier-4 claims passing the faithfulness judge + share of personal claims at strong binding; per-source yield is the *same* signal M13.3 consumes); Doc D (strong identity-binding share is the personal-claim health metric); overview §2 (observability runs alongside the whole map).
- **Scope / deliverables:**
  - **Phase progress** read view over the campaign-run state machine (M7.3): current phase in `reverse_profiling → icp_confirmed → discovery → scoring → tier_checkpoint(human) → deep → verification → handoff` (conventions §3 / Doc C §4), with per-phase completion (e.g., "discovery 60% — 1,240 found; Pass A 12%"), read from M7 state and M6 discovery/scoring counters.
  - **Cost burn-down:** spent (Σ `claim.cost_cents` + run overhead) vs. pre-run estimate vs. the client-set cap, live, from M7.5's budget engine — the dial made visible. Includes graceful-stop status when projected spend approaches the cap (the run pauses at a checkpoint and asks the client to raise the cap or tighten cutoffs — M7.3 pause/adjust, Doc C §5).
  - **Pre-run cost estimate** computed before any spend: from the discovered/imported count (M6 / M5.3), the proposed tier cutoffs, and the per-stage budget bands (Doc C §5, D7) — "~N → ~M deep → ~$X," recomputed live as cutoffs change at the tier checkpoint (M6.4).
  - **Per-source yield** panel = the `source_yield` materialization shared with M13.3 (Doc C §6: observability and the learning loop read the same provenance data) — which sources are producing surviving claims, surfaced read-only.
  - **Verification health** panel: the two metrics Doc C §6 enumerates — share of tier-4 claims passing the faithfulness judge (M9.3) and share of personal claims at `strong` identity-binding (M9.4 / Doc D) — plus, as an added M9.2 signal, the corroboration pass rate; a configurable alert threshold that flags a drop as a possible model/resolver regression (Doc C §6 early-warning).
  - **Coverage confidence** panel: the M6.5 coverage estimate (estimated % of addressable set found via searched channels) **plus the named channels not yet searched**, framed as confidence not completeness (Doc C §7) — never an "we found them all" claim.
  - **Client-facing vs. internal toggle:** all panels are read projections; whether they are exposed to the client (with cost pass-through) or kept as an internal control is a per-client config flag (D7), not two code paths.
- **Interface / seam:**
  - **Exposes** an `ObservabilitySurface` read API: `campaign_progress(campaign_run)`, `cost_burndown(campaign_run)`, `pre_run_estimate(icp_spec, cutoffs)`, `source_yield(icp_spec_version)`, `verification_health(campaign_run)`, `coverage_confidence(campaign_run)` — all **read-only projections**; the surface writes nothing to the domain (it may write/refresh materialized views only). A client portal or internal dashboard are interchangeable clients of this contract.
  - **Consumes:** the campaign-run state machine + budget engine (M7.3, M7.5) for phase + burn-down; the discovery/scoring counters and coverage estimator (M6.1, M6.3, M6.5); the `source_yield` materialization (shared with M13.3); verification results (M9.2–M9.4); the per-client cost pass-through / exposure config (M0.4, D7).
  - **Swap points behind the seam:** because every panel is a read projection over Postgres provenance (substrate §9, §12 — "no Airtable in the write path; the review surface reads from it"), the durable-execution engine can migrate Postgres state machine → Temporal (conventions §2) and the surface still reads phase state through the same `campaign_progress` contract. The optional read-only projection to a client's tool of choice (substrate §5c) is a sync downstream of this contract, never write-through. Per-source yield is a single shared materialization, so M13.3 and M13.4 never diverge on the number.
- **Data model / schema:**
  - Read-only materialized views over existing tables: `campaign_run` phase state (M7.3), `claim.cost_cents` aggregates (M1), budget caps (M7.5), the `source_yield` table (defined in M13.3, shared), verification results (M9), coverage estimate (M6.5).
  - New `cost_estimate(campaign_run_id, icp_spec_version, discovered_count, projected_deep_count, cutoffs_json, estimated_cents, computed_at)` — recomputed snapshots as cutoffs change.
  - Per-client exposure flag lives in the existing per-client config (M0.4 / conventions §2 policy-as-data); no new contract. No change to `claim`, `account_handoff`, or campaign-run contracts.
- **Dependencies:** **M6** (counts + coverage) and **M9** (verification health) are the milestone-level blockers; the implementation also reads **M7** (state machine + budget engine — issue-level read) and **M0.4** (exposure config). Shares `source_yield` with **M13.3**. Does not block other M13 issues (it is a read surface).
- **Acceptance criteria:**
  - `campaign_progress` returns the current phase and per-phase completion for a running campaign matching the state-machine ground truth; advancing a phase updates the surface with no manual refresh of the underlying state.
  - `cost_burndown` shows spent vs. estimate vs. cap reconciling to within rounding against Σ `claim.cost_cents` + overhead for a fixture run; when projected spend crosses the cap the run shows a graceful-stop/checkpoint status (M7.3) rather than a hard crash or silent overspend.
  - `pre_run_estimate` produces "~N → ~M deep → ~$X" before any spend, and recomputes when tier cutoffs are adjusted at the checkpoint (M6.4).
  - `verification_health` reports tier-4 faithfulness-pass share, strong-identity-binding share, and corroboration-pass rate; a fixture where faithfulness pass-rate drops below threshold raises the configured alert.
  - `coverage_confidence` reports an estimated coverage % **and** a non-empty list of unsearched channels; the surface never returns a 100%/"complete" claim (Doc C §7 honesty guarantee).
  - `source_yield` returns the same numbers M13.3 consumes (single shared materialization; a test asserts equality).
  - Flipping the per-client exposure flag toggles client visibility without code change; the surface writes nothing into the domain write path (Postgres-only, read projection — verified by asserting no domain mutation occurs on any read call).
- **Out of scope:** the budget-cap *enforcement* engine and the campaign-run state machine (M7 — this surface reads them); the discovery/coverage *computation* (M6 — surfaced, not computed); the reweighting loop (M13.3 — shares the yield table only); the production frontend (only the read API is delivered); billing/invoicing of pass-through cost (out of subsystem).
- **Open decisions:** **D7** (economics / cost pass-through) — directly: whether this is a *client-facing* surface (estimates, caps, burn-down the client sees) or an *internal control* is the D7 decision; built as a per-client exposure flag over one read API, defaulting to the recommended client-facing posture (Doc C §5) without hardcoding. **D8** (2026 legal verification) indirectly — the coverage and verification-health panels are also the honesty surface (Doc C §7) that supports the "we don't claim completeness / every fact is sourced" posture; proceed on the recommended honest-coverage default.
