# M4 — Source Layer & Source Intelligence
**Layer label:** layer:source-layer  ·  **Depends on:** M1 (Claim Store & Merge Policy), M2 (Identity Resolution), M3 (ICP & Research-Schema Compiler)  ·  **Priority:** 2 (High)
**Architecture sources:** substrate §4 (the trust-tiered source waterfall — resolve in tier order, stop at the first result clearing the field's confidence threshold; the uniform `Resolver` protocol; the CRM resolver as tier-1; Firecrawl as tier-2; Exa Deep / Parallel Task as pluggable tier-4), §1 (`field_definition.tier_plan`, `claim` write contract), §3 (research-schema compilation — the field plan names the `tier_plan` this layer executes), §11 build-order step 3 ("deterministic resolvers + the trust-tiered waterfall — tiers 1–3, real verifiable data with zero LLM"), §13 (anti-patterns: LLM research as the base layer is refused; empty-flagged beats fabricated), §12 (stack: Apollo/ZoomInfo/BuiltWith/Places/registries/client CRM behind the uniform interface, Firecrawl for tier-2, Exa/Parallel pluggable tier-4); staged-flow §7 (the Source Intelligence Layer — (a) Source Registry + capability manifests, (b) modality adapters fetch→adapt→extract, (c) Source Profiles per ICP/pack, (d) config-bounded Source Planner, (e) learning loop), §5/§6 (the waterfall + Source Planner feed modes M2/M4), §9 (one substrate, richer typing); the Clay note (Clay is one swappable resolver among many — permanent-until-proven-otherwise; per-field economics decide insourcing; nothing downstream knows Clay specifically exists). Shared contracts: `_conventions.md` §2 (modularity/DRY; resolvers are hot-swappable behind one protocol; resolvers must not import each other; open by registration), §3 (source tiers 1–4; field-key namespaces; modes M1–M4; identity-binding strength), §4 (`claim`, `current_value`, `account_entity`, `Resolver` protocol, `field_definition`, `source_manifest`, `ICP spec`), §6 (stack).

## Goal & scope of this milestone

M4 builds **the source substrate** — the layer that actually *fills* the fields M3 named, by turning every external provider into a uniform, hot-swappable `Resolver` and orchestrating them as the **trust-tiered waterfall** of substrate §4. This is build-order step 3 (substrate §11): *deterministic resolvers + the trust-tiered waterfall — tiers 1–3, real verifiable data with zero LLM* — the step that produces "a genuinely useful, trustworthy account list before a single synthesis LLM call exists." Everything here exists so that one fact about one entity has a path from an external source into a typed claim in the M1 store, chosen by trust rather than by convenience, and so that *which* provider answered is recorded as provenance and never leaked downstream.

The milestone realizes the two complementary structures the architecture insists on:

1. **The trust-tiered waterfall** (substrate §4) — per field, resolve in trust-tier order (`1` deterministic API → `2` official-source scrape → `3` reputable third party → `4` LLM synthesis) and **stop at the first result that clears the field's confidence threshold.** This is the Clay pattern, but ordered by *trustworthiness* (which correlates with but isn't identical to cost), writing typed claims instead of cells. The single non-negotiable: LLM research is the least-trusted source, so it runs last and only fills fields no deterministic/official source can answer (substrate §4, §13).
2. **The Source Intelligence Layer** (staged-flow §7) — the subsystem that sits *parallel to the field registry* and makes the platform *intelligent about where to look*: a Source Registry of capability manifests (§7a), a modality-adapter framework so "anything on the internet" is open by registration (§7b), Source Profiles of per-ICP/per-pack priors (§7c), and a config-bounded Source Planner (§7d) that selects and orders the source set within a pack's allowed, weighted set.

Concretely, M4 owns six things, one per issue:

1. **The Resolver protocol + waterfall engine** (M4.1) — the `Resolver` protocol made executable and the stop-at-first-confident waterfall that drives a field's `tier_plan`, writing claims through the M1 seam.
2. **The Source Registry + capability manifests** (M4.2) — the `source_manifest` table and registry API; the swappability spine. A provider is a row; swapping one is a registry edit.
3. **The modality-adapter framework** (M4.3) — `fetch → adapt → extract` so video/audio/PDF/structured surfaces become claims by registering an adapter, not forking the pipeline.
4. **Deterministic resolvers** (M4.4) — Clay (the swappable aggregator), Apollo/ZoomInfo (people/firmographics), BuiltWith (technographics), and registries (NPI/DUNS/CIK/LEI) as concrete tier-1 implementations behind the protocol.
5. **The CRM import resolver (tier-1) + Firecrawl official-site scrape (tier-2)** (M4.5) — the client's own data as the highest-trust grounding source, and the tier-2 official-source scraper.
6. **Source Profiles + the config-bounded Source Planner** (M4.6) — the per-ICP/per-pack source priors (the storage/serving half) and the planner that, given (mode, entity, field, profile), picks and orders the sources to consult within the allowed weighted set.

**Where it sits in the end-to-end map** (overview §2; staged-flow §10): M4 is the execution layer beneath discovery and both passes. M3 compiles the field plan and the source-profile *priors*; M4 *executes* the `tier_plan`s and *serves/plans* the sources. M6's Pass A scoring fills `scoring` fields through the tier-1–3 waterfall behind the `Resolver` seam; M6's discovery (mode M1) calls entity-producing channels that are *just resolvers*; M8's deep profiling (modes M2/M3/M4) fills `deep` fields and consumes the Source Planner's ordered set; M11 plugs tier-4 synthesis providers (Exa Deep / Parallel Task) in behind the very same `Resolver` seam. M4 produces claims; it does not score them (M6), judge them (M9), gate their use (M10), or assemble the handoff (M12).

**What is explicitly NOT here (the seams M4 must not cross):**
- **The claim table, merge view, and field registry** — M1. M4 *writes* claims via M1.1's `insert_claim`/`supersede_claim` and *reads* `field_definition.tier_plan`/`gate`/confidence-threshold; it never re-implements the store, the merge policy, or the registry. Workers return claim-id references, not blobs (`_conventions.md` §2).
- **Identity resolution** — M2. Every resolver receives an already-resolved `entity_id`/`Entity` and never turns a name into an id; the CRM resolver (M4.5) *feeds* observations to M2 for resolution but does not mint ids. Identity-binding *strength on a claim* is declared by the source's `source_manifest.identity_binding_strength` and stored by M1.4; M4 supplies the strength, it does not compute the binding gate (M9.4) or the use-gate (M10).
- **The ICP→field-plan compiler, the field-set/source-profile *authoring*, and the pack catalog** — M3. M3.3 *authors* source-profile priors (the per-pack/per-ICP weights); M4.6 *stores, serves, and plans against* them, and references `source_manifest.source_key`s M4.2 owns. M3 names `tier_plan`s; M4 implements the resolvers they name.
- **The faithfulness judge, corroboration rules engine, and any verification verdict** — M9. M4 produces claims with `evidence_span`, `confidence`, and `cost`; M9 decides `verified`/`rejected`. The waterfall's confidence-threshold stop is a *cheap pre-spend* heuristic, not the verification verdict.
- **Tier-4 LLM synthesis resolver internals** (Exa Deep / Parallel Task) — M11. M4.1 reserves tier-4 in the waterfall and the `Resolver` seam these plug into; M4 ships tiers 1–3 (substrate §11 step 3, before the judge exists).
- **The orchestrator-worker graph, bounded-recursion knob, budget *enforcement*, idempotency keys, and the project-run state machine** — M7. M4 resolvers report `cost_cents` per call and are *called by* M7-driven workers; M4 does not own the budget engine, the durable scheduler, or `(account, field, tier)` idempotency (it is *keyed on* it by callers).
- **The source-profile *learning/reweighting* loop** (staged-flow §7e / Doc C §6) — M13. M4.6 ships the *writable* source-profile config the loop reweights and emits the per-source yield telemetry it consumes; the loop itself is M13.

**Cross-cutting modularity rule (`_conventions.md` §2):** the `Resolver` protocol + the Source Registry are *the* swappability seam of the whole subsystem. Every external provider — Clay, Apollo, ZoomInfo, BuiltWith, registries, the client CRM, Firecrawl, Exa, Parallel — is *just a resolver*, declared by a `source_manifest` row, reached only through `resolve(entity, field) -> list[Claim]`. **Nothing downstream knows a specific provider exists**: callers see claims with provenance, not provider SDKs. Swapping Clay → direct APIs (or any provider) is a registry/config change — a manifest edit and a `tier_plan` edit — never a code fork in a caller. **Resolvers must not import each other** (the waterfall composes them; they do not compose themselves), and they import the shared `Resolver` protocol, `Claim`/provenance helpers, config loader, and tracing wrapper from M0.2 — never re-implementing them.

## Issues

### M4.1 — Resolver protocol + trust-tiered waterfall engine (stop-at-first-confident)
- **Purpose:** Make the architecture's central source mechanism executable: a field is filled by walking its `tier_plan` in **trust-tier order** and **stopping at the first result that clears the field's confidence threshold** (substrate §4). This is the engine that turns "research" into "produce claims by trust" and structurally encodes the one bet that the LLM is the *least-trusted* source — it can never be the base a later trustworthy source fails to overwrite (substrate §4, §13). The waterfall is the only thing that *composes* resolvers; individual resolvers stay dumb, uniform, and independently testable behind the `Resolver` protocol (substrate §4). Without this engine, every caller (Pass A scoring, deep-pass workers, discovery channels) would re-implement tier ordering, stop conditions, and claim-writing — exactly the duplication the seam exists to kill.
- **Architecture sources:** substrate §4 (the waterfall diagram and ordering tiers 1→4; "resolve in trust-tier order and stop at the first result that clears the field's confidence threshold"; the `Resolver` protocol verbatim; "research agents are your least trustworthy source, so they go last, not first"), §1 (`field_definition.tier_plan`, the `claim` write contract, `confidence`, `cost_cents`), §3 (the `tier_plan` is named by the compiler, executed here), §11 step 3 (tiers 1–3 first, zero LLM), §13 (LLM-as-base-layer refused; empty-flagged beats fabricated); staged-flow §5 (the waterfall fills mode-M2 fields; "which open-web sources within the synthesis tier is chosen by the Source Planner — not a fixed list"); `_conventions.md` §3 (source tiers, stop-at-first-confident), §4 (`Resolver`, `field_definition`, `claim`), §2 (resolvers hot-swappable, must not import each other; workers return references).
- **Scope / deliverables:**
  - The executable **`Resolver` protocol** wiring (the type itself lives in M0.2 per `_conventions.md` §4): `tier: int` and `resolve(self, entity: Entity, field: FieldDef) -> list[Claim]`, where returned claims carry `value`, `source_url`, `evidence_span`, `confidence`, and `cost` (substrate §4). A `ResolverRegistry`-aware dispatch maps a `source_key`/tier in a field's `tier_plan` to a concrete registered resolver (M4.2/M4.4/M4.5/M11).
  - A pure-ish **waterfall engine** `resolve_field(entity, field_def, *, mode, run_id, budget_envelope) -> WaterfallResult` that:
    - reads the field's ordered `tier_plan` from `field_definition` (M1.3) — an ordered list of `source_key`s ascending by trust tier (`_conventions.md` §3);
    - for each step, resolves the bound resolver and calls `resolve(entity, field)`; collects returned claims;
    - applies the **stop rule**: stop at the first step whose best returned claim has `confidence ≥ field.confidence_threshold` (a field-level threshold read from `field_definition`; default per field-class), recording the **stop reason** `{confident_hit | tier_exhausted | budget_stop | no_resolver}`;
    - **never** advances to tier 4 unless tiers 1–3 produced no confident hit (substrate §4) — and in this milestone tier 4 resolves to a registered-but-absent capability (M11 fills it), so a tier-4-only field correctly yields empty+flagged, which is a *correct* output (`_conventions.md` §5);
    - writes every returned claim through M1.1's `insert_claim`/`supersede_claim` with the correct `source_tier`, `extraction_method`, `evidence_span`, `confidence`, `cost_cents`, `run_id`, `research_mode` (from `mode`), and (for contacts) the source's `identity_binding_strength` from the manifest (stored by M1.4) — returning only `claim_id` **references** (`_conventions.md` §2), never blobs.
  - **Confidence-threshold-stop is a pre-spend heuristic, not a verdict.** Document explicitly that clearing the threshold short-circuits *spend* (don't call tier 3 if tier 1 was confident) but does **not** set `verification_status='verified'` — that remains M9's job; M4 emits `unverified` claims (M1.1 default).
  - **Budget awareness (caller-driven):** the engine accepts an optional `budget_envelope` and a `cost_so_far`; before each resolver call it checks the envelope and stops with `budget_stop` if the next call would exceed it. The *enforcement policy/engine* and per-account caps are M7.5; M4.1 only honors the envelope it is handed and reports per-call `cost_cents`.
  - **Per-step idempotency hook:** the engine derives/accepts the `(entity_id, field_key, source_tier)` idempotency key (substrate §5c) so a retried step does not double-charge or double-write; the key *derivation/storage* is M7.4 — M4.1 consumes it and is safe to re-run.
  - **Observability:** each tier step is a trace span (M0.5 wrapper) recording `source_key`, `tier`, `confidence`, `cost_cents`, latency, and stop reason — the per-source yield substrate the learning loop (M13) and cost surface (M7.5/M13) read.
  - **Conflict handling deferred to merge:** the waterfall does not resolve disagreements between tiers; it writes all returned claims and lets `current_value` (M1.2) apply the tier/freshness/corroboration merge and raise the conflict flag.
- **Interface / seam:**
  - **Exposes:** `resolve_field(entity, field_def, mode, run_id, budget_envelope) -> WaterfallResult` (`{claim_refs: list[ClaimId], stop_reason, per_tier_summary, total_cost_cents}`) and a `resolve_fields(entity, field_defs[], ...)` batch convenience. This is the single seam M6 (Pass A tier-1–3 fill), M8 (deep-pass fill), and M6 discovery channels call to populate a field — they never iterate tiers or call resolvers directly. The waterfall *algorithm* (ordering, stop rule, batching) is fully hidden behind it.
  - **Consumes:** `field_definition.tier_plan`/`confidence_threshold`/`gate` (M1.3); the `ResolverRegistry` binding `source_key → Resolver` (M4.2); the M1.1 write helpers; M0.2 `Resolver` protocol, `Claim`/provenance helpers, config loader, tracing. It consumes the *manifest* (`source_manifest`, M4.2) to know each step's tier/cost/identity-binding without importing the resolver's internals.
  - **Swap note (the heart of the milestone):** because the waterfall reads `tier_plan` (an ordered list of `source_key`s) and dispatches through the registry, **swapping Clay → a direct API for a field is editing one `tier_plan` row + ensuring the direct-API resolver is registered** — zero engine change, zero caller change (the Clay note's "nothing downstream knows Clay specifically exists"). Adding tier 4 later (M11) is registering a tier-4 resolver under its `source_key`; the engine already walks to it. Resolvers never import each other; the engine is the only composer.
- **Data model / schema:** No new tables. Reads `field_definition` (`tier_plan`, `confidence_threshold`, `freshness_ttl`, `gate`; `_conventions.md` §4, M1.3) and `source_manifest` (tier/cost/identity-binding; §4, M4.2). Writes `claim` rows (§4 + M1.4 provenance flavors) via M1.1 helpers — `source_tier`, `extraction_method`, `evidence_span`, `confidence`, `cost_cents`, `run_id`, `research_mode`, and contact `identity_binding`. Per-step idempotency keys on `(entity_id, field_key, source_tier)` (substrate §5c; owned by M7.4).
- **Dependencies:** Depends on **M1** (M1.1 write helpers + `claim`; M1.3 `tier_plan`/`confidence_threshold`/`gate`; M1.4 provenance-flavor columns the engine stamps), **M2** (resolvers receive a resolved `Entity`/`entity_id`), and **M4.2** (the registry that binds `source_key → Resolver`). Soft-coupled to **M4.6** (deep-pass callers pass a planner-ordered subset of `tier_plan`) and **M7.4/M7.5** (idempotency key + budget envelope). **Unblocks** every caller that fills a field: **M6** (Pass A + discovery channels), **M8** (deep pass), and **M11** (tier-4 plugs in here).
- **Acceptance criteria:**
  - For a field with `tier_plan = [apollo(t1), firecrawl(t2), news(t3)]` where the tier-1 resolver returns a claim with `confidence ≥ threshold`, `resolve_field` calls **only** the tier-1 resolver, writes its claim, and returns `stop_reason='confident_hit'` (asserted via resolver call counters).
  - When tier-1 returns below threshold (or empty), the engine advances to tier-2, then tier-3, stopping at the first confident hit; if none is confident, it returns `stop_reason='tier_exhausted'` and the field is left to merge (which may emit empty+flagged) — **never fabricated**.
  - A tier-4-only field (`tier_plan=[llm_synthesis]`) with no tier-4 resolver registered (M11 absent) yields zero claims and a clearly-flagged empty result — a correct output (`_conventions.md` §5), not an error that fails the run.
  - Every written claim carries the correct `source_tier`, `extraction_method`, non-null `evidence_span` where the resolver supplied one, `confidence`, `cost_cents`, and `research_mode`; tier-4 claims with null `evidence_span` are written `unverified` and cannot be promoted (M1.1 CHECK, re-asserted).
  - Swapping a field's tier-1 provider (e.g. `clay → apollo` in `tier_plan`, both registered) changes which resolver is called with **no code change** in the engine or any caller — verified by call counters against two registered resolver doubles.
  - The confidence-stop short-circuits *spend* but never sets `verification_status='verified'`: a "confident" tier-1 claim is still written `unverified` (M9 owns the verdict).
  - A `budget_envelope` smaller than the next resolver's cost halts with `stop_reason='budget_stop'` before that call; per-call `cost_cents` are summed into `total_cost_cents`.
  - Re-running `resolve_field` with the same `(entity, field, tier)` idempotency context does not double-write a claim (idempotent retry).
  - Resolvers never import one another (static check / lint rule); only the engine references the registry.
- **Out of scope:** Concrete resolver implementations (M4.4/M4.5/M11); the registry/manifest schema (M4.2); selecting *which* sources within a tier for synthesis-tier fields (M4.6 Source Planner); the merge/`current_value` (M1.2); the faithfulness judge / corroboration verdict (M9); budget *enforcement* policy + idempotency key derivation (M7.4/M7.5); the campaign/per-account scheduler (M7).
- **Open decisions:** **D7 (economics/budgets)** — the per-field `confidence_threshold` and the budget envelope are the levers of source spend; both are versioned config the engine reads (not constants), so confirming D7's per-pass budget bands needs no engine change. The Clay note's **per-field insourcing** decision rides on this engine: it logs per-source `cost_cents` + yield per field so the build-vs-buy math (drop Clay for a field where a direct resolver matches coverage and beats cost) is *measured*, not guessed — proceed on Clay-as-permanent-swappable-resolver, decided per field by data. Surface, do not hardcode.

### M4.2 — Source Registry + capability manifests
- **Purpose:** Stand up the registry that makes a *source* a first-class, self-describing, registered thing — the spine of the Source Intelligence Layer (staged-flow §7a) and the structural answer to "we can never enumerate every place data lives" (staged-flow §7b: the system is *open by construction*, like the field registry). Every source — structured API, web search, scraper, social platform, video host, podcast index, journal/preprint index, the client CRM — declares a **capability manifest** (`source_manifest`, `_conventions.md` §4) saying *what it can populate, at what tier, modality, cost, latency, geo coverage, freshness, and identity-binding strength*. This is **the** swappability seam together with the `Resolver` protocol: a provider is a row; adding Clay, dropping ZoomInfo, or wiring a new directory is a registry edit, and **nothing downstream learns a provider's name** — the waterfall (M4.1), the field plan's `tier_plan` (M3/M1.3), and the Source Planner (M4.6) all reference sources by `source_key` only (the Clay note's discipline made structural).
- **Architecture sources:** staged-flow §7a (the `source_manifest` schema verbatim: `source_key`, `modality`, `entity_scope`, `yields`, `tier`, `cost`, `latency`, `geo_coverage`, `freshness_profile`, `identity_binding_strength`), §7b (open by registration), §9 ("packs carry two prior sets … the source profile"); substrate §4 (resolvers are hot-swappable and individually testable; the providers list: Apollo/ZoomInfo/BuiltWith/Places/registries/CRM/Firecrawl/Exa/Parallel), §12 (the same provider list in the stack table); the Clay note (Clay self-declares its capabilities, sits at a tier, writes claims like everything else; nothing downstream knows Clay exists); `_conventions.md` §2 (open by registration; resolvers hot-swappable; nothing downstream knows a provider exists), §3 (source tiers, identity-binding strength), §4 (`source_manifest`).
- **Scope / deliverables:**
  - DDL for **`source_manifest`** matching `_conventions.md` §4 / staged-flow §7a exactly: `source_key text pk, modality enum(text|video|audio|pdf|structured), entity_scope enum(account|contact|both), yields jsonb (field_keys / field-classes it can populate), tier int(1..4), cost jsonb (per-call/per-record cost model in cents), latency jsonb (typical/p95), geo_coverage jsonb, freshness_profile jsonb, identity_binding_strength enum(strong|weak)`. Extend (not redefine, per `_conventions.md` §4) with registry-standard `active boolean`, `provider text` (the human/vendor name — used for ops/billing, **never** read by callers as control flow), `auth_ref text` (a reference to the credential store, never the secret itself; `_conventions.md` forbids secrets in repo/`_memory`), `rate_limit jsonb`, `requires_adapter text` nullable (the modality adapter key, M4.3), `version`, `created_at`.
  - **Registry API** in the shared package (M0.2): `register_source(SourceManifest)`, `get_source(source_key)`, `list_sources(tier=?, modality=?, entity_scope=?, yields_field_class=?, active=true)`, and the binding `get_resolver(source_key) -> Resolver` (the `source_key → concrete Resolver` map the waterfall M4.1 and the Source Planner M4.6 dispatch through). The registry is the **single source of valid `source_key`s** for the whole system, exactly as the field registry (M1.3) is for `field_key`s.
  - **`yields` validation against the field registry:** a manifest's `yields` reference `field_key`s/field-classes from M1.3 (`_conventions.md` §3 namespaces); `register_source` validates they exist (a source claiming to yield an unregistered field is rejected) so the `tier_plan ↔ manifest` join is sound.
  - **Capability-coverage query:** `sources_for(field_key|field_class, tier?, entity_scope?) -> [source_key]` — "who can populate this field, at which tier" — the lookup M4.6's planner and any tooling use to assemble a candidate source set without hardcoding provider lists.
  - **Seed manifests** for every source this milestone ships (so the waterfall/planner have a real registry): Clay, Apollo, ZoomInfo (structured, tier-1), BuiltWith (structured, tier-1, technographics), the registries (NPI/DUNS/CIK/LEI, structured, tier-1), the **CRM** (structured, tier-1, `identity_binding_strength=strong` for contacts), **Firecrawl** (text/pdf via scrape, tier-2), and *placeholder* tier-4 manifests for Exa Deep / Parallel Task (registered, resolver-absent until M11) — proving a tier-4 source can be *named* in a `tier_plan` before its resolver exists.
  - Migration + rollback; fixtures.
- **Interface / seam:**
  - **Exposes:** the `source_manifest` registry API (`register_source`, `get_source`, `list_sources`, `sources_for`) and the `get_resolver(source_key)` binding. This is the seam that makes **sources data, not code**: M4.1 dispatches the waterfall through it, M1.3's `tier_plan` references its `source_key`s by name, M4.6's planner reads `tier`/`cost`/`identity_binding_strength`/`yields` from it, and M3.3's source profiles reference its `source_key`s. Adding/removing a provider = `register_source` / `active=false`; no caller changes (the Clay note's optionality, made structural).
  - **Consumes:** the M1.3 field registry (validates `yields` against real `field_definition`s — DRY: the field registry stays the system of record for `field_key`s; the source registry is its sibling, not a parallel store, per `_conventions.md` §4 "the §4 `source_manifest` is a sibling registry; M1.3 must not redefine it"); M0.2 `SourceManifest`/`Resolver` types, config loader, credential-reference resolver, tracing. It does **not** consume any resolver's internals — a resolver registers *itself* (its manifest + its `resolve` impl) without the registry knowing its provider SDK.
  - **Swap note:** the registry is the single inventory of providers. The `provider` column carries the vendor's real name for billing/ops only and is **never** branched on by callers — enforce that nothing outside billing/observability reads `provider`, so "nothing downstream knows Clay specifically exists" is checkable. Insourcing a field's commodity enrichment (the Clay note) is: register the direct-API resolver, flip the field's `tier_plan` (M1.3) to it, optionally `active=false` on Clay for that field-class — all registry/config.
- **Data model / schema:** new `source_manifest` table (this milestone owns it; `_conventions.md` §4 contract + the extensions above). References `field_definition.field_key`/field-classes (M1.3) via `yields`. Referenced by `field_definition.tier_plan` (M1.3, by `source_key`), by `source_profile` (M3.3/M4.6, by `source_key`), and by the M4.1 waterfall dispatch. Credentials live in the credential store referenced by `auth_ref` — never in this table, the repo, or `_memory/`.
- **Dependencies:** Depends on **M1** (M1.3 field registry — `yields` validation) and **M0** (shared types, config loader, credential-reference resolver, tracing). Naturally precedes/unblocks **M4.1** (the registry binds `source_key → Resolver` for waterfall dispatch), **M4.4/M4.5** (resolvers register their manifests here), **M4.6** (the planner reads manifests; source profiles reference `source_key`s), and is referenced by **M3.3** (source profiles) and **M3/M1.3** (`tier_plan`). **M11** registers tier-4 resolvers here later.
- **Acceptance criteria:**
  - Migration creates `source_manifest` with every staged-flow §7a / `_conventions.md` §4 column plus the extensions; rollback drops it cleanly.
  - `register_source` rejects a manifest whose `yields` names a `field_key`/field-class absent from the M1.3 registry, naming the offender; accepts one whose yields all resolve.
  - `get_resolver(source_key)` returns the bound `Resolver` for a registered source and raises a clear "no resolver bound" for a registered-but-resolver-absent source (e.g. the tier-4 Exa placeholder pre-M11) — the waterfall (M4.1) treats this as `no_resolver`, not a crash.
  - `sources_for('core.primary_tech_stack', tier=1)` returns `builtwith` (and any other tier-1 technographic source) but not Firecrawl (tier-2); `sources_for(field_class='contact.*', entity_scope='contact')` returns the people sources.
  - The seed manifests load idempotently (registering twice is a no-op or a versioned update per the documented rule); the CRM manifest carries `identity_binding_strength='strong'` and `tier=1`; Firecrawl carries `tier=2`, `modality∈{text,pdf}`; Clay/Apollo/ZoomInfo/BuiltWith/registries carry `tier=1`, `modality='structured'`.
  - No secret value is stored in `source_manifest`; `auth_ref` is a reference resolved against the credential store (asserted: the table contains no credential material).
  - A static check confirms no caller outside billing/observability branches on `source_manifest.provider` (the "nothing downstream knows the provider" invariant).
  - Setting `active=false` on a source removes it from `list_sources`/`sources_for` results without deleting the row (auditability) and without touching any `tier_plan` (the field plan still references it by key; the waterfall treats an inactive source as skipped).
- **Out of scope:** The waterfall execution engine (M4.1); concrete resolver implementations (M4.4/M4.5/M11); modality adapters (M4.3 — the manifest only *references* an adapter via `requires_adapter`); source profiles / the planner (M4.6 — they *consume* manifests); the field registry table (M1.3); credential storage/rotation (M0/infra — the manifest only holds an `auth_ref`).
- **Open decisions:** **D7 (economics)** — the `cost` model per source is the input to the per-field build-vs-buy math (the Clay note); kept as structured config so cost re-negotiation is a manifest edit. The Clay note's **per-field insourcing**: the registry is exactly where Clay is "one swappable resolver among many" — keeping `provider` un-branchable and `source_key` the only reference is what preserves the freedom to swap the commodity layer whenever per-field math says so. **D8 (2026 legal)** — `geo_coverage` and a (future) per-jurisdiction exclusion flag on the manifest are the hook for jurisdiction-scoped source disablement; the override mechanism (M3.3 / M4.6) layers over it, so resolving D8 needs no schema fork. Surface, do not hardcode.

### M4.3 — Modality-adapter framework (fetch → adapt → extract)
- **Purpose:** A source isn't always "fetch a URL and read text" — many require **fetch → adapt → extract** before claim extraction: video and podcasts go through transcription, PDFs/journals through text extraction, structured payloads through parsing (staged-flow §7b). This framework makes that heterogeneity **open by registration, not enumeration**: adding "anything on the internet" (YouTube, Vimeo, X/Substack/Medium, journals, preprints, podcasts — the mode-M4 long tail of staged-flow §6) is registering a manifest (M4.2) plus, if the modality is non-trivial, an adapter here. It is the architectural answer to the non-exhaustive source list (staged-flow §7b: "open by construction, like the field registry") and the precondition for the resonance (`account.resonance.*`) and personal-facet (`contact.facet.*`) field-classes (Doc C §2) that live on non-text surfaces. Without it, each new modality would be a bespoke fetch in a worker — the fork the architecture forbids.
- **Architecture sources:** staged-flow §7b ("Modality adapters — heterogeneity by registration, not enumeration; a source isn't just fetch URL; many require fetch → adapt → extract; video/podcasts through transcription, PDFs/journals through text extraction, before claim extraction; adding anything = registering a manifest + (if needed) an adapter; open by construction like the field registry"), §6 (mode M4 consumes YouTube/Vimeo/X/Substack/Medium/journals/podcasts — the long tail), §7a (`source_manifest.modality`); Doc C §2 (`account.resonance.*` and `contact.facet.*` come from non-text/semi-structured surfaces); substrate §4 (resolvers write claims with `evidence_span`); `_conventions.md` §2 (open by registration; adapters/judges import shared helpers, never re-implement), §4 (`source_manifest.modality`, `claim`).
- **Scope / deliverables:**
  - A **`ModalityAdapter` protocol** (registered in M0.2 alongside `Resolver`): a small uniform contract `fetch(ref, ctx) -> RawArtifact`, `adapt(RawArtifact, ctx) -> NormalizedText` (e.g. transcribe audio/video, OCR/extract PDF, parse structured), `extract(NormalizedText, entity, field) -> list[ClaimDraft]` — three composable stages so a source's *transport*, *normalization*, and *claim-extraction* are independently swappable. Each `ClaimDraft` carries the **`evidence_span`** (the exact normalized text the value came from) so the claim it becomes satisfies the substrate §4 / M1.1 span requirement.
  - An **adapter registry + dispatch:** `register_adapter(modality | source_key, ModalityAdapter)` and a `run_pipeline(source_key, ref, entity, field) -> list[Claim]` that, given a source's manifest (`modality`, `requires_adapter`), selects and runs the right `fetch→adapt→extract` chain, then hands `ClaimDraft`s to the M1.1 write helpers. A **text passthrough** adapter is the default for `modality=text`/`structured` where no adaptation is needed (so simple sources stay simple).
  - **Concrete adapters this milestone ships** (enough to prove the framework end-to-end and to unblock M8's long tail): a **PDF text-extraction** adapter (journals/filings → text), a **Firecrawl-backed HTML→markdown** adapter (the tier-2 scrape normalization M4.5 uses), and a **transcription adapter** for audio/video that calls a pluggable transcription provider behind a `Transcriber` seam (so the provider is swappable and the expensive call is *gated* — see below). Adapters that call an external service register their own `source_manifest`/`auth_ref` discipline via M4.2.
  - **Expensive-modality gating hook:** the framework exposes a `cost_estimate(source_key, ref) -> cents` and accepts a `gate_decision` from the caller (the Source Planner, M4.6 / the deep-pass worker, M8) so that "transcribe a 90-minute podcast" only runs when the planner decided it is worth it (high tier + source-class weighted high — staged-flow §7d). M4.3 *exposes* the estimate and honors the decision; it does not *make* the gating decision (that is M4.6/M8/M7 budget).
  - **`extraction_method` + tier fidelity:** a claim produced via `fetch→adapt→extract` records the correct `extraction_method` (`scrape` for adapted HTML/PDF, `api` for structured, `llm_synthesis` only when extraction itself is tier-4 synthesis) and the source's `source_tier` from the manifest — so adaptation never silently upgrades trust (a transcribed podcast claim is still tier-3/4 per its manifest, not tier-1).
  - **Idempotency & caching:** raw artifacts and normalized text are content-addressed (hash of `ref` + fetch params) so a re-fetch/re-adapt is idempotent and a costly transcription is not repeated within a run (keyed under the M7.4 `(entity, field, tier)` discipline); cache lifetime honors the manifest `freshness_profile`.
  - **Observability:** each of `fetch`/`adapt`/`extract` is its own trace span with cost + latency (M0.5) so the per-stage cost (esp. transcription) is measured for the cost surface (M7.5/M13) and the learning loop (M13).
- **Interface / seam:**
  - **Exposes:** the `ModalityAdapter` protocol, `register_adapter(...)`, and `run_pipeline(source_key, ref, entity, field) -> list[Claim]`. A resolver whose source needs adaptation (M4.5 Firecrawl, M8 long-tail sources) calls `run_pipeline` rather than hand-rolling fetch/transcribe/parse. Adding a new modality or a new extractor for an existing modality is a `register_adapter` call — **no pipeline fork** (staged-flow §7b), invisible to the waterfall (M4.1) and to callers (M8) beyond the claims returned.
  - **Consumes:** `source_manifest.modality`/`requires_adapter`/`source_tier`/`freshness_profile` (M4.2); the M1.1 claim write helpers; M0.2 `ModalityAdapter`/`Claim`/provenance helpers, config loader, credential-reference resolver, tracing; pluggable provider seams (`Transcriber`, PDF extractor) whose providers are registry/config choices.
  - **Swap note:** transport, normalization, and extraction are three independent seams — swapping the transcription provider, the PDF extractor, or the HTML→markdown backend is a config/registration change behind `run_pipeline`. Because `extract` produces `ClaimDraft`s with `evidence_span` and the manifest's tier, the claim contract is identical regardless of modality — so a new modality is genuinely "just another source." Adapters never import resolvers or each other; they import only M0.2 shared helpers (`_conventions.md` §2).
- **Data model / schema:** No new claim columns. May add an `artifact_cache` (content-hash → stored normalized text + fetch metadata, TTL per `freshness_profile`) kept strictly behind the `run_pipeline` seam (swappable to object storage). Writes `claim` rows (§4) via M1.1 with the correct `extraction_method`/`source_tier`/`evidence_span`. Reads `source_manifest` (M4.2).
- **Dependencies:** Depends on **M4.2** (manifests declare `modality`/`requires_adapter`), **M1** (claim write helpers; `evidence_span` requirement), and **M0** (shared protocols, config, tracing, credential-reference resolver). Soft-coupled to **M4.6** (the planner supplies the expensive-modality `gate_decision`) and **M7** (budget/idempotency). **Unblocks** **M4.5** (Firecrawl scrape uses the HTML→markdown adapter) and **M8** (mode-M2 resonance + mode-M4 long-tail consume video/audio/PDF via this framework; M8 *requests* sources, does not implement adapters).
- **Acceptance criteria:**
  - A PDF source runs `fetch→adapt(extract text)→extract(claims)` and writes a claim with a non-null `evidence_span` drawn from the extracted text, `extraction_method='scrape'`, and the manifest's `source_tier` (no silent trust upgrade).
  - A `modality=text`/`structured` source uses the passthrough adapter (no transcription/OCR) and still produces correctly-typed claims.
  - A video/audio source routes through the transcription adapter; swapping the `Transcriber` provider (config change) produces the same claim contract — verified against a transcriber double.
  - An expensive-modality call is **not** made when the caller's `gate_decision` is "skip" (e.g. a low-tier entity, or a source-class weighted low); `cost_estimate` is exposed and reflected in the trace span.
  - Re-running `run_pipeline` on the same `ref` within a run hits the content-addressed cache and does not re-incur the costly fetch/transcription (idempotent + de-duplicated cost), respecting the manifest `freshness_profile` on cache expiry.
  - Registering a brand-new modality adapter (e.g. a podcast-index source) makes that source consumable end-to-end with **no change** to the waterfall (M4.1) or any worker (M8) — only a `register_source` (M4.2) + `register_adapter` call (open-by-registration proven).
  - Each of `fetch`/`adapt`/`extract` emits its own trace span with cost + latency; transcription cost appears as a distinct span.
  - Adapters do not import resolvers or each other (static check).
- **Out of scope:** The waterfall ordering/stop rule (M4.1); the source registry schema (M4.2); deciding *whether* an expensive modality is worth triggering — the Source Planner gate (M4.6) and the deep-pass worker (M8) make that call; M4.3 only exposes the estimate and honors the decision. Claim-level groundedness judging of extracted claims (M9 faithfulness judge); tier-4 synthesis extraction internals (M11); credential storage (M0/infra).
- **Open decisions:** **D7 (economics)** — transcription/OCR are the most expensive non-LLM source operations; the `cost_estimate` + caller `gate_decision` keep the spend governed and measured, so D7's budget bands are honored without baking gating thresholds into the framework. **D8 (2026 legal)** — some modalities (scraping certain platforms, transcribing gated content) carry per-jurisdiction/per-platform constraints; the manifest `geo_coverage`/exclusion hook (M4.2) governs *whether* the source is consulted, upstream of the adapter — M4.3 proceeds adapter-agnostic. Surface, do not hardcode.

### M4.4 — Deterministic resolvers: Clay (swappable) + Apollo/ZoomInfo + BuiltWith + registries
- **Purpose:** Ship the concrete **tier-1 deterministic resolvers** that produce the *trustworthy base* of the whole subsystem (substrate §11 step 3: "real, verifiable data with zero LLM" — the step that yields a useful, trustworthy account list before any synthesis call). These are the providers substrate §4/§12 name: structured-DB enrichment (Clay/Apollo/ZoomInfo), technographics (BuiltWith), and authoritative registries (NPI/DUNS/CIK/LEI). The headline is **Clay as one swappable resolver**: per the Clay note, Clay collapses dozens of provider integrations into one and is the pragmatic V1 move, but it is **permanent-until-proven-otherwise** and **one resolver among many** — it self-declares its capabilities, sits at a tier, writes claims with provenance like everything else, and **nothing downstream knows Clay specifically exists.** This issue proves the swappability seam by implementing both Clay *and* a direct alternative (Apollo) for the same field-class, so a Clay→direct swap is demonstrably a registry/`tier_plan` edit, not a code change in any caller.

- **Out of scope:** The waterfall engine + stop rule (M4.1); the registry schema (M4.2); modality adapters (M4.3 — these are structured-API resolvers needing no adaptation); the CRM resolver + Firecrawl scrape (M4.5); tier-4 synthesis (M11); identity *resolution* (M2 — resolvers enrich already-resolved entities); the Source Planner (M4.6); scoring/verification (M6/M9); the actual per-field insource *decision* (a data/ops call informed by M13's measured yield — M4.4 only makes it measurable and swappable).

Because the CRM is *just a tier-1 resolver*, "already a customer" detection is a normal claim in the store, not a special pipeline. Tenant isolation is enforced at the claim level so swapping the CRM vendor never weakens the privacy boundary.
- **Data model / schema:** No new tables. CRM resolver writes tenant-private `claim` rows (§4) `source_tier=1`, `extraction_method='crm_import'`, contact `identity_binding='strong'` (M1.4), plus the `account.crm_relationship_status` claim; feeds observations to M2 (which owns `account_entity`/contact records). Firecrawl resolver writes `claim` rows `source_tier=2`, `extraction_method='scrape'`, mandatory `evidence_span`, official `source_url`. Both register `source_manifest` (M4.2). Credentials via `auth_ref`. **No CRM/customer data in `_memory/` or repo.**
- **Dependencies:** Depends on **M4.1** (waterfall), **M4.2** (manifest registration + binding), **M4.3** (Firecrawl uses the HTML→markdown / PDF adapter), **M2** (CRM observation resolution; scrape entity-binding; tenant-isolated reuse logic), **M1** (claim write helpers; `extraction_method` enum incl. `crm_import`/`scrape`; M1.4 `identity_binding`), and **M0** (protocol, config, credential-reference resolver, tracing). **Unblocks** **M6** (CRM grounding + "already a customer" at Pass A; CRM/customers as lookalike seeds for discovery; tier-2 official-site facts for scoring), **M8** (tier-2 official surfaces for deep profiling), and the hybrid discovery seed surface (M6, Doc B §4).
- **Acceptance criteria:**

  - CRM-sourced claims are tagged **tenant-private** and are **excluded from cross-tenant reuse**; a second tenant touching the same public entity does *not* see the first tenant's CRM claims (isolation asserted); public-footprint claims remain reusable.

### M4.6 — Source Profiles + config-bounded Source Planner
- **Purpose:** Make the platform **intelligent about *which* sources to consult for *what*** — the part of the Source Intelligence Layer that turns "we have a registry of sources" into "we look in the right places, in the right order, for this industry, this entity, this field" (staged-flow §7c/§7d). The waterfall (M4.1) walks a field's `tier_plan`, but *within* a tier — especially the open-web synthesis tier for modes M2/M4 — *which* sources to consult is not a fixed list; it is chosen by the **Source Planner** using the ICP's **source profile** (staged-flow §5: "which open-web sources are consulted within the synthesis tier is chosen by the Source Planner — not a fixed list"). The planner is the architecture's resolution of the rigidity-vs-fabrication tension: **config-bounded LLM planning** — the planner may expand specific queries and pick among sources, but **only within the pack's allowed, weighted set** (staged-flow §7d). This issue owns the *storage/serving* half of source profiles (the priors M3.3 authors live in M4's `source_key` namespace) and the planner engine itself. It also emits the per-source yield telemetry the learning loop (M13) reweights.
- **Architecture sources:** staged-flow §7c (Source Profiles per ICP/pack — priors that weight/prioritize sources per field-class for an industry; the `frontier_ai`/`healthcare_practice`/`data_infra` weightings; authored into packs, overridable per client), §7d (the Source Planner — "given (mode, entity, objective/field, ICP source profile), it selects and orders the source set to consult"; config-bounded LLM planning within the pack's allowed weighted set; decides when an expensive modality is worth triggering — gated to high-tier entities and high-weighted source classes), §7e (the learning loop reweights profiles from measured yield — M4.6 emits the telemetry, M13 reweights), §5/§6 (the planner feeds modes M2/M4); substrate §4 (the planner orders sources *within* the trust-tiered waterfall, never overriding tier trust order); Doc C §3/§5 (expensive work gated to high tier; cost governance); the Clay note (always log which source produced each fact — the per-source yield this enables); `_conventions.md` §2 (policy is data; open by registration; planner bounded by config), §3 (field-classes, tiers, modes), §4 (`source_manifest`, `field_definition`, `ICP spec`).
- **Scope / deliverables:**
  - **Source-profile storage/serving (the M4 half of the M3.3 seam):** the `source_profile` config — per (ICP / pack, field-class): an ordered/weighted set of `source_key`s (referencing M4.2 manifests), e.g. `frontier_ai`→{arXiv high, GitHub high, research-X high, press medium, Glassdoor low}; `healthcare_practice`→{NPI/CMS high, Places-reviews high, job-boards high, journals low}; `data_infra`→{job-posting-tech high, BuiltWith high, eng-blogs medium} (staged-flow §7c). **M3.3 *authors* these priors; M4.6 stores, serves, and resolves them** (pack default ⊕ per-client override, override > default — the same precedence M3.3 documents) and exposes `get_source_profile(icp_version, field_class) -> WeightedSourceSet`. (DRY: M4.6 does not re-author packs; it is the runtime home of the priors keyed to M4.2 `source_key`s.)
  - **The Source Planner engine** `plan_sources(mode, entity, field|field_class, icp_version, tier_scope, budget_envelope) -> OrderedSourcePlan`:
    - resolves the field-class's `WeightedSourceSet` from the source profile and intersects it with the sources the registry says *can* yield that field (`sources_for`, M4.2) at the relevant tier — the **allowed set**;
    - **config-bounded LLM planning:** an LLM may (a) expand/specialize the *queries* handed to chosen sources and (b) **rank/pick among the allowed sources** — but it can **never introduce a source outside the allowed weighted set** and **never invent an entity or a fact** (staged-flow §7d; the anti-fabrication spine). Enforce as a hard runtime guard: any planner output naming a `source_key` not in the allowed set is dropped; the planner returns *sources + queries*, not claims.
    - **respects trust-tier order:** the plan orders *within* the waterfall's tier discipline (M4.1) — the planner picks/orders sources, but a tier-3 source never jumps ahead of an available tier-1; the planner refines *which* sources at each tier, not the tier order itself (substrate §4).
    - **expensive-modality gating:** for modes M2/M4 the planner decides when an expensive modality (transcribe a 90-min podcast) is worth triggering — **gated to high-tier entities and to profiles weighting that source class high** (staged-flow §7d) — and emits the `gate_decision` the M4.3 adapter honors; the decision also respects the `budget_envelope` (M7.5).
  - **Per-source yield telemetry (the learning-loop substrate, §7e / Doc C §6):** for every planned/executed source, record per (ICP, field-class, source) — precision (claims that survived M9 verification), coverage (fields filled), freshness, cost, and a hook for downstream disposition signal — into versioned, **writable** source-profile telemetry. M4.6 *emits and stores* this; **M13 reweights** the priors through the same config seam (so the loop is a config writer, not an engine change). This is "always log which source found each fact" (the Clay note) made into the adaptive loop's input.
  - **Read/serve API:** `get_source_profile(...)`, `plan_sources(...)`, `record_source_yield(...)`, and a `resolve_allowed_set(field_class, icp_version, tier)` helper used by both the planner and audits.
- **Interface / seam:**
  - **Exposes:** `plan_sources(mode, entity, field|field_class, icp_version, tier_scope, budget_envelope) -> OrderedSourcePlan` (`{ordered_sources: [(source_key, tier, queries[], gate_decision)], rationale}`) and the source-profile serving/telemetry API. M8's deep-pass workers and M6's resonance/long-tail callers ask the planner for the ordered set and then drive the waterfall (M4.1) over it; they never hardcode a source list. The planner is replaceable as a whole behind `plan_sources` — its LLM-planning internals can change without touching the waterfall or callers.
  - **Consumes:** the `source_profile` priors (authored by **M3.3**, keyed to M4.2 `source_key`s, resolved with client overrides here); the `source_manifest` registry (M4.2) for `sources_for`/tier/cost/`identity_binding_strength`/`requires_adapter`; the `ICP spec` (M3.1, §4) for the active source-profile reference; `field_definition` (M1.3) for the field-class and its tier scope; the `budget_envelope` (M7.5) and tier (M7) for gating; an LLM behind a config-bounded prompt (the planning model is swappable, behind the seam); M0.2 config loader, tracing, types. It writes yield telemetry M13 consumes.
  - **Swap note:** the planner's LLM/model is a swap behind `plan_sources`; the source profile is **data, not code** (`_conventions.md` §2) — per-ICP, versioned, overridable, and **reweighted by M13 through the same writable config**, so the learning loop is config, not a planner rewrite. Because the planner emits `source_key`s only and the waterfall dispatches through the registry, a Clay→direct-API swap (the Clay note) is invisible to the planner too — it ranks `source_key`s, not providers. The hard "allowed-set only" guard means the LLM can never widen the source set or fabricate, preserving the anti-fabrication spine even as the planning model changes.
- **Data model / schema:** `source_profile` config tables (the runtime home of M3.3's priors; per (pack/ICP, field-class) weighted `source_key` sets + per-client overrides, versioned) and a `source_yield` telemetry table (per (ICP, field-class, source): precision/coverage/freshness/cost/disposition hook), both writable by M13's loop. References `source_manifest.source_key` (M4.2), `field_definition` field-classes (M1.3), and the `ICP spec` source-profile slot (M3.1, §4). No claim-store changes.
- **Dependencies:** Depends on **M4.2** (manifests — the allowed set + tier/cost/binding), **M3** (M3.1 ICP-spec source-profile slot; **M3.3 authors the priors** this serves), **M1** (field registry field-classes), and **M0** (config, tracing, LLM client wrapper). Soft-coupled to **M4.1** (callers drive the waterfall over the planner's ordered set), **M4.3** (`gate_decision` for expensive modalities), and **M7.5** (budget envelope / tier). **Unblocks** **M8** (modes M2/M4 consume the planner's ordered set; resonance + long-tail), **M6** (resonance/discovery channel ordering where relevant). Emits the telemetry **M13**'s learning loop reweights.
- **Acceptance criteria:**
  - `get_source_profile(icp_version, field_class)` returns the pack priors resolved with client overrides (override > default), versioned; the three starter packs reproduce their staged-flow §7c weight orderings (e.g. `frontier_ai` ranks arXiv/GitHub above Glassdoor; `healthcare_practice` ranks NPI/CMS + reviews above journals).
  - `plan_sources` returns only `source_key`s that are **both** in the field-class's weighted allowed set **and** registry-capable of yielding the field at the relevant tier; a planner (LLM) output naming a source outside the allowed set is **dropped** by the hard guard (asserted with a planner that tries to add an off-profile source).
  - The plan **never reorders trust tiers**: an available tier-1 source is never placed after a tier-3 source for the same field (tier discipline asserted against the M4.1 waterfall).
  - The planner **never emits a candidate entity or a claim** — only sources + queries (anti-fabrication invariant; asserted that planner output contains no `value`/entity).
  - For a high-tier entity with a profile weighting podcasts high, the planner's `gate_decision` triggers the expensive transcription modality; for a low-tier entity or a low-weighted source class, it does **not** (gating asserted; M4.3 honors the decision).
  - A budget envelope too small for the next planned source halts the plan/gate before that source (budget honored; delegated cap from M7.5).
  - `record_source_yield(...)` writes per (ICP, field-class, source) precision/coverage/freshness/cost telemetry; a simulated M13 reweight (writing new profile weights) changes the planner's subsequent ordering **with no engine change** (config-driven learning proven).
  - Swapping the planning LLM/model (config) leaves the `OrderedSourcePlan` contract and the allowed-set guarantee unchanged.
- **Out of scope:** **Authoring** pack source-profile priors and the pack catalog (M3.3 — M4.6 stores/serves/plans against them); the waterfall execution + stop rule (M4.1); modality adapter internals (M4.3 — the planner only emits the `gate_decision`); the source-profile **learning/reweighting loop** itself (M13 — M4.6 ships the writable config + the yield telemetry it targets); the verification verdict that defines "precision" (M9 — M4.6 reads the verdict to compute yield); budget *enforcement* (M7.5); discovery channel selection for mode M1 (M6 — though discovery may consult the same registry/profile seam).
- **Open decisions:** **D7 (economics/budgets)** — the planner is *the* place expensive-source spend is decided (gating transcription, picking among paid sources); it reads budget bands as config, so confirming D7 needs no planner change. **D8 (2026 legal)** — per-jurisdiction source exclusions layer onto the source profile/manifest (M4.2 hook); the planner intersects the allowed set with active+jurisdiction-permitted sources, so resolving D8 is a config/override change. The **learning loop direction** (the Clay note's "point the feedback loop the right way") is realized here: per-source yield is measured so insourcing/source-weighting decisions are data-driven, not all-or-nothing. Surface, do not hardcode.
