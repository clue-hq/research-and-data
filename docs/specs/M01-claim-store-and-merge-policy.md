# M1 — Claim Store & Merge Policy
**Layer label:** layer:claim-store  ·  **Depends on:** M0  ·  **Priority:** 1 (Urgent)
**Architecture sources:** substrate §0 (the one bet), §1 (claim store, field registry, merge view), §3 (research-schema compilation / field plan), §4 (source tiers, `Resolver` protocol), §6 (structural provenance + corroboration, freshness), §11 (build order), §12 (stack); staged-flow §1 (2×2 modes), §3 (discovery-provenance + existence gate), §5/§6 (field-claim provenance, identity-binding), §8 (mode-specific anti-hallucination), §9 (claim store gains `research_mode` + two provenance flavors); overview §1 (output-first spine), §3 (output contract). Shared contracts: `_conventions.md` §3 (namespaces, tiers, modes, use-classes, identity-binding), §4 (`claim`, `current_value`, `account_entity`, `Resolver`, `field_definition`, `source_manifest`), §5 (the two gates + universal rule).

## Goal & scope of this milestone

M1 builds **the spine** — the typed-claim-with-provenance substrate that every other component reads from and writes to. This is the realization of the subsystem's one architectural bet (substrate §0): *verifiability is a property of the data model, not a QA pass bolted on at the end.* The atomic unit of the entire subsystem is a **typed claim with provenance** (value + source + evidence span + tier + confidence + freshness), never a free-text dossier. "Research" is the act of producing, corroborating, and scoring these claims. The prototype inverted this — built research agents first, data discipline last — and shipped fabricated facts; M1 exists so that ordering is impossible here (substrate §11, build order step 1).

This milestone delivers four things:

1. **The append-only `claim` table** (M1.1) — the immutable, supersede-only event log of every observation about every entity, with the full provenance envelope and the structural anti-fabrication constraint (no `evidence_span` ⇒ a tier-4 claim cannot be promoted past `unverified`).
2. **The `current_value` merge view** (M1.2) — the *pure deterministic* "current truth" function the rest of the platform reads, implementing the tier → freshness → corroboration → confidence merge policy with a conflict flag. Merge is a policy, never an agent (substrate §1).
3. **The field registry** (`field_definition`, M1.3) — the contract that types every `field_key`, declares its tier plan, freshness TTL, scoring/deep pass tag and gate, and registers the namespaced field-classes (`core.*`, `account.*`, `account.resonance.*`, `contact.*`, `contact.facet.*`, `<pack>.*`). Open by registration, not enumeration (`_conventions.md` §2).
4. **The `research_mode` dimension + the two provenance flavors** (M1.4) — the staged-flow §9 extension that lets one substrate carry both *discovery-provenance* (modes M1/M3: where/why an entity matched) and *field-claim provenance* (modes M2/M4: value + span + tier, plus `identity_binding` + `use_class` for contact claims) with richer typing rather than two tables.

**Where this sits in the end-to-end map (overview §2):** M1 is the substrate underneath everything. Stage 0 (M5) writes ICP/client-knowledge claims into it; identity resolution (M2) supplies the `entity_id` every claim keys on; the schema compiler (M3) populates `field_definition`; resolvers (M4) write claims through it; discovery + Pass A scoring (M6) read the merge view; deep profiling (M8), verification (M9), compliance (M10), tier-4 synthesis (M11) and the value-narrative handoff (M12) all read and write claims. Every score and every fact in the `account_handoff` (overview §3) traces back to a row here.

**What is explicitly NOT here (the seams M1 must not cross):**
- **Identity resolution** — M1 stores `entity_id` as the key and (for M1.1) a soft FK to `account_entity`, but the dedup → linkage → canonicalization machinery that *mints* an `entity_id` is M2. M1 never turns a name into an id.
- **Resolvers / source adapters** — M1 defines the write contract (a `Claim` shaped to the `claim` table) and the read contract (`current_value`); the actual `Resolver` implementations (Clay, Apollo, ZoomInfo, BuiltWith, Firecrawl, Exa, Parallel, CRM) are M4. The `Resolver` protocol and `source_manifest` themselves live in the shared package (M0.2).
- **The verification layer** — M1 provides the *structural* verification primitives that fall out of the data model (evidence-span requirement, corroboration counters, conflict flag, freshness TTL, a `verification_status` lifecycle column). The corroboration *rules engine*, the faithfulness **judge**, the appropriateness/use **gate**, and the eval harness are M9/M10. M1 stores the inputs and the verdict; it does not compute the verdict.
- **The schema *compiler*** — M1 owns the `field_definition` *table and registry API*; the ICP → field-plan *compiler* that emits rows is M3. M1 ships the schema and a seed pack so M3 has a target.
- **Scoring, durable execution, narrative** — M6/M7/M12.

**Cross-cutting modularity rule (`_conventions.md` §2):** the claim store is the *only* shared substrate; components communicate by reading/writing typed claims, not by calling each other, and workers return claim-id *references*, not blobs. Every M1 issue states the exact read/write contract it exposes so the implementation behind the seam (e.g. Postgres → a different store, a materialized view → an incremental merge service, a Postgres state machine → Temporal) is replaceable without touching callers.

## Issues

### M1.1 — Claim table — append-only, supersede, provenance fields
- **Purpose:** Stand up `claim`, the append-only event log that is the atomic unit of the whole subsystem. Every fact about an account or contact is a *row*, not a field on a document (substrate §1). Append-only + supersede (never UPDATE-in-place) buys a full audit trail and time-travel for free, which is exactly what is needed when a client disputes a claim that drove outreach, and it is the precondition for safe merge — you cannot merge safely over untyped, mutated blobs (substrate §0/§1). This issue also encodes the single structural constraint that kills the prototype's "made-up facts" error class at the schema level: a tier-4 (LLM-synthesis) claim with no `evidence_span` cannot be promoted past `unverified` (substrate §1/§6, staged-flow §8) — a fabricated fact has no span to point at.
- **Architecture sources:** substrate §0 (the bet), §1 (claim schema, append-only, evidence-span rule), §4 (source tiers 1–4, `extraction_method`), §6 ((2) provenance + corroboration; freshness as first-class), §12 (Postgres + JSONB); overview §3 (`provenance_index` — every fact → its source); `_conventions.md` §4 (`claim` contract — extend, don't redefine), §5 (universal rule: empty/flagged is correct, fabricated is the only failure).
- **Scope / deliverables:**
  - DDL for the `claim` table matching the `_conventions.md` §4 `claim` contract exactly: `id uuid pk, entity_id uuid, entity_type enum(account|contact), field_key text, value_json jsonb, source_url text, source_tier int(1..4), extraction_method enum(api|scrape|llm_synthesis|human|crm_import), evidence_span text, confidence numeric(0..1), corroborations int, observed_at timestamptz, collected_at timestamptz, cost_cents numeric, run_id uuid, research_mode <enum, owned by M1.4>, superseded_by uuid nullable`.
  - Add the **`verification_status`** lifecycle column `enum(unverified|verified|rejected|flagged)` defaulting to `unverified` (extends §4; the column M9/M10 transition, the column M1.2 reads). This is the structural home of the evidence-span rule's verdict.
  - **Append-only enforcement:** a DB trigger (or rule) that rejects any `UPDATE`/`DELETE` of immutable provenance columns; supersede is modelled by inserting a new claim and setting the prior row's `superseded_by` (the only permitted mutation, plus `verification_status`/`corroborations` transitions by the verification owner). Document the exact allow-list of mutable columns (`superseded_by`, `verification_status`, `corroborations`).
  - **CHECK constraints** encoding the substrate invariants: `source_tier between 1 and 4`; `confidence between 0 and 1`; **the evidence-span rule** — `verification_status` may not be `verified` when `source_tier = 4 AND evidence_span IS NULL` (enforced as a CHECK and re-asserted by the M1.2 view, which never *reads* such a claim as a winner).
  - Indexes for the hot read paths the merge view and scoring need: `(entity_id, field_key) WHERE superseded_by IS NULL` (the "live claims" partial index), `(field_key)`, `(run_id)`, `(collected_at)`, and a GIN index on `value_json` for JSONB filtering.
  - A typed `Claim` domain object + an `insert_claim()` / `supersede_claim(old_id, new_claim)` write helper in the shared package (M0.2) so resolvers/workers never hand-write SQL; helpers stamp `collected_at`, default `verification_status`, and enforce the evidence-span precondition before insert.
  - Soft FK to `account_entity(id)` (M2) on `entity_id` for accounts; documented as deferrable so M1 can land before M2's table is populated (verified in tests with a fixture entity).
  - Migration + rollback; seed/fixture claims for tests.
- **Interface / seam:**
  - **Exposes (write contract):** `insert_claim(Claim) -> claim_id` and `supersede_claim(old_id, Claim) -> claim_id`. The `Claim` type is the shared domain type (M0.2). This is the *only* sanctioned write path into the substrate — every resolver (M4), worker (M8), Stage-0 ingest (M5), tier-4 synthesis (M11) writes here and returns the `claim_id` *reference*, never a blob (`_conventions.md` §2). Swapping the underlying store (Postgres → anything) stays behind these two functions.
  - **Exposes (read contract for raw history):** a `claims_for(entity_id, field_key?, include_superseded=false)` reader used by audit, time-travel, and the `provenance_index`. The *merge* read is M1.2, not here.
  - **Consumes:** `entity_id` from M2's identity service (shared `Resolver`/identity seam); `field_key` validity from M1.3's `field_definition` (`validate_value`); `research_mode` + provenance-flavor columns from M1.4; shared `Claim`/provenance helpers and the tracing wrapper from M0.2.
- **Data model / schema:** `claim` (§4 contract + `verification_status`). Soft-references `account_entity` (§4, M2). Indexed for `current_value` (M1.2). `research_mode` and the discovery-vs-field-claim provenance columns are added by M1.4 as ALTERs on this table (one substrate, richer typing — staged-flow §9).
- **Dependencies:** Depends on **M0** (shared package, domain types, migration tooling, tracing). Blocks **M1.2** (merge view reads this table), **M1.4** (extends this table), and everything that writes claims (M4, M5, M6, M8, M9, M10, M11, M12). Soft dependency on **M2** for `entity_id` population (deferrable FK).
- **Acceptance criteria:**
  - Migrating up creates `claim` with every §4 column plus `verification_status`; migrating down cleanly drops it.
  - Inserting a claim via `insert_claim()` persists all provenance fields; `collected_at` and `verification_status='unverified'` are auto-stamped.
  - Attempting to `UPDATE` an immutable provenance column (e.g. `value_json`, `source_url`, `source_tier`, `evidence_span`) is rejected by the trigger; the test asserts the error.
  - `supersede_claim()` inserts a new row and sets the old row's `superseded_by`; the old row is otherwise unchanged; both rows are retrievable via `claims_for(..., include_superseded=True)` and only the new one via the default reader.
  - A tier-4 claim with `evidence_span IS NULL` cannot reach `verification_status='verified'` (CHECK rejects the transition); the same claim with a non-null span can.
  - CHECK constraints reject `source_tier=0`, `source_tier=5`, `confidence=-0.1`, `confidence=1.1`.
  - The `(entity_id, field_key) WHERE superseded_by IS NULL` partial index is present and used by a representative live-claims query (EXPLAIN asserts index scan).
  - No raw-SQL write exists in any caller path in the test suite — all writes go through the helpers.
- **Out of scope:** Computing `verification_status` transitions beyond the structural span check (the corroboration rules engine + faithfulness judge are **M9**; the appropriateness/use gate is **M10**). Minting `entity_id` (**M2**). The merge/read-of-truth (**M1.2**). `research_mode` enum values and provenance-flavor columns (added by **M1.4**). Resolver implementations that produce claims (**M4**).
- **Open decisions:** **D8** (2026 legal verification) — the retention/erasure (DSAR) story leans on append-only + provenance making erasure tractable (overview "traceability is what makes erasure tractable"; Doc D §4 — erasure resolves to a deterministic set of claims to tombstone); M1.1 keeps the audit trail but does not implement the erasure/tombstone workflow (M10.5). Note as open; proceed on append-only-with-supersede as the default.

### M1.2 — current_value merge view (tier/freshness/corroboration policy + conflict flag)
- **Purpose:** Provide the **"current truth"** the rest of the platform reads — a *pure deterministic function*, not an agent (substrate §1). This is the direct fix for the prototype's worst data bug: "bad base facts never overwritten," where an early LLM guess became a base that later trustworthy sources silently failed to correct. Here, merge is a policy over source tiers: a tier-4 synthesized value can *never* outrank a tier-1–3 fact, conflicts between authoritative sources surface as a *flag* for human review instead of being silently resolved, and staleness is queryable (substrate §1/§6). Everything that consumes "the value of field X for entity Y" — Pass A scoring (M6), deep-profiling gap detection (M8), the handoff's `provenance_index` (overview §3) — reads through this seam and nothing else, so the merge algorithm can evolve without touching callers.
- **Architecture sources:** substrate §1 (the `current_value` algorithm verbatim: among non-superseded claims, highest tier satisfying the field's freshness TTL → tie-break corroborations desc, confidence desc, collected_at desc → emit value + winning provenance + conflict flag if two tier≤2 disagree), §6 ((2) corroboration structural rule; freshness as first-class signal with field-level TTL — stale claims are *eligible for refresh and discountable*, not silently dropped); overview §3 (`provenance_index` — winning provenance per fact); `_conventions.md` §4 (`current_value` contract — "pure deterministic merge policy, not an agent"), §5 (universal rule: an empty/flagged field is correct).
- **Scope / deliverables:**
  - Implement `current_value(entity_id, field_key)` exactly per substrate §1 / §4: among non-superseded claims, pick (1) the highest `source_tier` whose `collected_at`/`observed_at` satisfies the field's `freshness_ttl` (from `field_definition`, M1.3); tie-break by `corroborations` desc, then `confidence` desc, then `collected_at` desc; emit `{value, winning_claim_id, source_tier, source_url, evidence_span, confidence, freshness_state, conflict_flag}`.
  - **Conflict flag:** set when two **non-superseded tier≤2** claims for the same `(entity, field)` carry disagreeing `value_json`. Emit the flag *with both contender claim ids* so the review surface (M13.1) can show the disagreement; do **not** auto-resolve.
  - **Freshness handling (reconcile §1 and §6, then document the chosen rule explicitly):** read `freshness_ttl` per field from `field_definition`. The substrate is deliberately under-specified here and the two sources pull in different directions — §1's selection clause picks "the highest tier *that satisfies* the field's freshness TTL" (i.e. TTL gates which claims are eligible to win), while §6 says stale claims are *not dropped* but kept as "eligible for refresh" and "discountable by the scoring layer." Resolve this in the spec, not in scattered code: surface `freshness_state ∈ {fresh|stale}` on every result and **never drop a stale claim from the readable set** (§6). The exact behaviour when the *only* in-TTL candidates are lower-tier than an out-of-TTL higher-tier claim is a **documented merge-policy decision** (see Open decisions / D7), implemented as versioned policy data, not hardcoded — so it can be set/changed without a code fork. Do not assert a doc-derived default that neither §1 nor §6 states outright.
  - **Exclude un-promotable claims:** a tier-4 claim that has not cleared the evidence-span/`verification_status` bar (M1.1) is **not eligible to win** (it may be returned as a clearly-flagged low-confidence fallback only when no eligible claim exists). Default: never emit an unverified tier-4 value as `current_value` truth; emit empty + flag instead (`_conventions.md` §5 — empty is correct).
  - Implement as a Postgres **view or table-valued function** for ad-hoc reads *and* a batch `current_values(entity_ids[], field_keys[])` reader for Pass A scale (1k–10k accounts; substrate §5a); document the materialization choice (view vs. materialized view + refresh) and keep it behind the function seam so it can be swapped to an incremental merge service later.
  - A `current_value` domain type + reader helper in the shared package (M0.2); the `provenance_index` builder (overview §3) is a thin wrapper that collects winning provenance across an entity's fields.
  - Property/unit tests covering tier ordering, every tie-break level, freshness gating + `freshness_state`, conflict detection, and tier-4 exclusion.
- **Interface / seam:**
  - **Exposes (read contract):** `current_value(entity_id, field_key) -> CurrentValue` and batch `current_values(...)`, plus `provenance_index(entity_id) -> {field_key: winning_provenance}`. This is the canonical "current truth" seam — scoring, deep-profiling gap detection, handoff, and the review surface read here and **never** scan `claim` directly for truth. The merge *algorithm* is fully hidden: swapping view → materialized view → incremental service, or changing tie-breaks/freshness rule, is invisible to callers.
  - **Consumes:** non-superseded rows + `verification_status` from `claim` (M1.1); `freshness_ttl` (and `pass`/`gate` where relevant) from `field_definition` (M1.3); shared `CurrentValue` type and tracing from M0.2. Merge-policy parameters (tier ordering, conflict scope, freshness/staleness rule, any corroboration thresholds) are read as **versioned config/policy data**, not hardcoded (`_conventions.md` §2 — policy is data) so per-client/per-ICP policy variation stays behind the seam.
  - **Swap note:** the merge policy is config-driven; a future change (e.g. require ≥N corroborations before a tier-3 claim can win a scoring field, or change the stale-higher-tier-vs-fresh-lower-tier rule) is a policy/config edit, not a code fork.
- **Data model / schema:** Reads `claim` (M1.1) and `field_definition` (M1.3). Emits the `current_value(entity, field)` contract (§4) — no new table unless materialized (then a refresh-tracked `current_value_cache` is documented, still behind the function seam).
- **Dependencies:** Depends on **M1.1** (claim table + `verification_status` + live-claims index) and **M1.3** (`freshness_ttl`, `pass`, `gate` per field). Soft dependency on **M1.4** (so the policy can optionally scope by `research_mode`/provenance flavor and must honour the weak-binding non-promotion rule). Blocks **M6** (Pass A scoring), **M8** (gap detection), **M9** (verification reads current truth), **M12** (handoff `provenance_index`), **M13** (review surface).
- **Acceptance criteria:**
  - For one `(entity, field)` with a tier-1, tier-3, and tier-4 claim all fresh, `current_value` returns the tier-1 value and its provenance.
  - When two in-TTL tier-1 claims exist, the more-corroborated/higher-confidence/later one wins per the tie-break chain; when a tier-1 claim is past its field TTL it is returned with `freshness_state='stale'` and is never dropped from the readable set.
  - The documented stale-higher-tier-vs-fresh-lower-tier rule (the D7 policy decision) is exercised exactly as documented, and is overridable via policy config without code changes (a test flips the policy and observes the winner change).
  - Tie-break order is exercised: equal tier → higher `corroborations` wins; equal corroborations → higher `confidence` wins; equal confidence → later `collected_at` wins. Each level has a dedicated test.
  - Two disagreeing non-superseded tier≤2 claims produce `conflict_flag=true` with both claim ids; a tier-2 vs tier-4 disagreement does **not** raise the conflict flag (only tier≤2 ↔ tier≤2).
  - A tier-4 claim with `verification_status='unverified'` is never returned as the winning truth when any eligible claim exists; when it is the only claim, the reader returns empty-with-flag by default (configurable).
  - Superseded claims are never considered.
  - `current_values()` batch over a 1k-entity fixture returns within the documented latency budget and produces results identical to per-entity calls.
  - `provenance_index(entity)` returns a winning-provenance entry for every field that has at least one eligible claim and is absent/empty for fields with none.
- **Out of scope:** Mutating `verification_status` (set by **M1.1** structurally / **M9/M10** by verdict). The corroboration *rules engine* and faithfulness judge (**M9**). The appropriateness/use gate filtering on `use_class` for outreach (**M10** consumes `current_value` but the use-gate is its own span). Scoring math over current values (**M6**). UI for conflict resolution (**M13**).
- **Open decisions:** **D3/D8** (personal-data posture / 2026 legal) — whether `current_value` for `contact.facet.*` fields must additionally pass the use-gate before being read for outreach is decided in M10; M1.2 returns the value + its `use_class`/`identity_binding` and leaves the gate to the consumer. **D7** (economics) — both the freshness-TTL defaults that drive re-research cadence (≈90-day default, signal-fields faster; substrate §6) *and* the stale-higher-tier-vs-fresh-lower-tier merge rule are config, surfaced not hardcoded; M1.2 honours them as versioned policy data.

### M1.3 — Field registry (field_definition) + namespaced field-classes
- **Purpose:** Make the field set **the contract** rather than hardcoded columns (substrate §1/§3). The prototype was welded to dental/NPI and could not generalize; the field registry is the generalization move — every `field_key` is a *row* declaring its type, validation, ordered tier plan, freshness TTL, scoring/deep pass tag and gate, so adding a per-vertical field (NPI, FDA clearance) or a whole vertical is a registration, never a pipeline fork (`_conventions.md` §2 — open by registration, not enumeration). It also registers the **namespaced field-classes** so resonance (`account.resonance.*`) and personal-hook (`contact.facet.*`) classes are *registered*, not enumerated, exactly as the architecture requires (overview/Doc C §2). This table is what the ICP→schema compiler (M3) writes into and what the merge view (M1.2), resolvers (M4), and the Source Planner (M4) all read to know "what to know, how to validate it, how fresh it must be, and which tiers may answer it."
- **Architecture sources:** substrate §1 ("the field registry is the contract"; `field_definition` declares type, validation, tiers that may populate, freshness TTL, scoring/deep), §3 (research-schema compilation: `field_key`, ordered `tier_plan`, `pass`, `gate`; vertical pluggability), §6 (freshness TTL per field); staged-flow §1 (modes the fields serve), §7 (Source Intelligence Layer sits parallel to the field registry — fields say *what to know*); Doc C §2 (the two new field-classes `account.resonance.*` / `contact.facet.*`, registered not enumerated; a single signal class spans `scoring`+`deep`); `_conventions.md` §3 (namespaces `core.*`, `account.*`, `account.resonance.*`, `contact.*`, `contact.facet.*`, `<pack>.*`; source tiers), §4 (`field_definition` contract).
- **Scope / deliverables:**
  - DDL for `field_definition` matching `_conventions.md` §4: `field_key text pk, type, validation, tier_plan (ordered resolver/source keys), freshness_ttl, pass enum(scoring|deep), gate`. Extend with: `field_class` (the namespace, derived/validated from the `field_key` prefix), `value_schema` (the JSONB shape that `claim.value_json` must validate against for this field), `corroboration_min` (default # independent tier≤3 sources required before `verified` — substrate §6(2); consumed by M9), `description`, `active`, `pack` (nullable; the owning vertical pack), and registry-standard `version`/`created_at`.
  - **Namespace validation:** enforce that every `field_key` belongs to a registered namespace prefix (`core.`, `account.`, `account.resonance.`, `contact.`, `contact.facet.`, or `<pack>.`); reject unknown namespaces. `contact.facet.*` and `account.resonance.*` rows must carry the metadata M10/Doc D need (e.g. `field_class` flagged as governed/deep/tier-4) but M1.3 only *stores* it.
  - **Registry API** in the shared package (M0.2): `register_field(FieldDef)`, `get_field(field_key)`, `list_fields(pass=?, field_class=?, pack=?, active=true)`, and `validate_value(field_key, value_json)` (used by `insert_claim` in M1.1 so a claim's payload must match the field's `value_schema`). The registry is the single source of valid `field_key`s for the whole system.
  - **A seed core pack** of `field_definition` rows for the commodity `core.*` and a few `account.*` fields cited in the docs (`core.employee_count`, `core.primary_domain`, `core.work_email`, `core.primary_tech_stack`, `account.recent_funding`, `account.hiring_velocity_eng`, `account.operational_pain`, `account.strategic_moves`) with illustrative tier plans, freshness TTLs (≈90-day default; signal fields faster — substrate §6), pass tags and gates per substrate §3's worked example — so M3's compiler and M4's resolvers have a real target and M1.2 has TTLs to read. Seed at least one `account.resonance.*` and one `contact.facet.*` row to prove the field-class machinery (deep-pass, tier-4, governed — Doc C §2).
  - **Pack loading:** a documented, idempotent loader that registers a pack's field set from versioned config (packs carry two prior sets — field set *and* source profile, staged-flow §9; M1.3 owns the field-set half, the source profile is M4). Loading is additive and namespaced so two packs never collide.
  - Migration + rollback; tests + fixtures.
- **Interface / seam:**
  - **Exposes:** the `field_definition` registry API (`register_field`, `get_field`, `list_fields`, `validate_value`). This is the seam that makes the field set *data, not code* (`_conventions.md` §2): the M3 compiler writes rows, M1.1 validates payloads, M1.2 reads `freshness_ttl`, M4 reads `tier_plan` to drive the waterfall and `gate` to know pre-spend conditions, M9 reads `corroboration_min`/`gate`. Adding a vertical = `register_field` calls + a pack file; no caller changes.
  - **Consumes:** versioned pack/ICP config (the *content* of fields comes from M3's compiler and from pack files); shared `FieldDef` type, config loader, and tracing from M0.2. `tier_plan` entries reference resolver/source keys whose *manifests* live in M4's source registry (`source_manifest`, §4) — M1.3 stores the ordered keys by name; it does not validate that a resolver exists (that join is M4, kept behind the seam).
  - **Swap note:** because `tier_plan` is an ordered list of source/resolver keys (not code), swapping Clay → a direct API for a field is editing one row's `tier_plan`; the field's identity, validation, TTL and gate are unchanged.
- **Data model / schema:** `field_definition` (§4 contract + `field_class`, `value_schema`, `corroboration_min`, `pack`, `active`, `version`, `created_at`). Referenced by `claim.field_key` (M1.1) and read by `current_value` (M1.2). The §4 `source_manifest` (M4) is a sibling registry; M1.3 must not redefine it — `tier_plan` references source keys by name only.
- **Dependencies:** Depends on **M0** (shared package, config loader, types). Naturally precedes/unblocks **M3** (the compiler emits `field_definition` rows — M3 is the *writer*, M1.3 is the *table + API + seed*), **M1.1** (`validate_value` is called by `insert_claim`), **M1.2** (reads `freshness_ttl`), **M4** (reads `tier_plan`, `gate`), **M9** (reads `corroboration_min`, `gate`). No hard dependency on M1.1/M1.2 (can land in parallel) but `validate_value` wiring into `insert_claim` requires M1.1 present.
- **Acceptance criteria:**
  - Migration creates `field_definition` with every §4 column plus the extensions; rollback drops it cleanly.
  - `register_field` rejects a `field_key` whose prefix is not a registered namespace; accepts one in each of `core.`, `account.`, `account.resonance.`, `contact.`, `contact.facet.`, and a `<pack>.` namespace.

### M1.4 — research_mode dimension + discovery vs field-claim provenance flavors
- **Purpose:** Let *one* substrate carry the two structurally different kinds of provenance the 2×2 of modes produces, with richer typing rather than a second table (staged-flow §9). Discovery (modes M1/M3) and profiling (modes M2/M4) fail in opposite ways and produce opposite provenance: discovery answers *"where was this entity found and why did it match"* (**discovery-provenance**), profiling answers *"what is the value, from what span, at what tier, and — for contacts — how tightly is it bound to this exact person and under what use-class"* (**field-claim provenance**). This issue adds the `research_mode` dimension to `claim` and the columns/typing for both flavors, so the existence-gate's discovery evidence and the target-locked field claims live in the same store, and so identity-binding (the contact-axis analogue of the evidence-span rule) and use-class are first-class on contact claims (staged-flow §5/§6/§8/§9, Doc D).
- **Architecture sources:** staged-flow §9 (claim store gains a `research_mode` dimension + two provenance flavors — *discovery-provenance* and *field-claim provenance*), §1 (the 2×2 of modes M1–M4), §3 (discovery-provenance: where found, matched signal, discovery confidence; existence gate), §5 (target-lock field claims), §6 (identity-binding `strong|weak`; weak never promotes/drives outreach), §8 (mode→failure→mechanism table); substrate §1 (`claim` already has `run_id`); Doc D §2 (use-class taxonomy, tagged at extraction), §3 (the appropriateness/use gate, distinct from accuracy); `_conventions.md` §3 (research modes M1–M4; identity-binding `strong|weak`; use-classes), §4 (`claim` provenance flavors: discovery-provenance + field-claim provenance incl. `identity_binding` + `use_class` for contact claims), §5 (the two gates).
- **Scope / deliverables:**
  - ALTER `claim` (M1.1) to add **`research_mode`** `enum(M1|M2|M3|M4)` (nullable for non-mode-tagged claims like CRM import / Stage-0 ingest, with a documented convention) — the dimension recording which of the four modes produced the claim.
  - Add the **field-claim provenance** columns for contact claims: `identity_binding enum(strong|weak)` (nullable; required when `entity_type='contact'` and the field is a personal claim) and `use_class enum(professional-public|personal-public-non-sensitive|sensitive)` (nullable; required for contact personal claims per Doc D §2 taxonomy). For account/value claims these stay null. (`source_url`, `evidence_span`, `source_tier`, `value_json` already exist from M1.1 and *are* the field-claim provenance core.)
  - Add the **discovery-provenance** flavor: a `discovery_provenance jsonb` envelope (`{discovered_via, matched_signal, discovery_confidence, channel/source_key}`) populated for mode-M1/M3 claims that record *why an entity was admitted* (staged-flow §3), plus a lightweight `claim_flavor enum(discovery|field_claim)` discriminator (or document deriving it from `research_mode` + populated columns). Keep it JSONB so discovery channels stay open-by-registration, not a fixed column set.
  - **CHECK / validation rules:** a `field_claim` contact personal claim must carry a non-null `identity_binding` and `use_class`; a `discovery` claim must carry a non-null `discovery_provenance` and a discovery-mode `research_mode`; helper `insert_claim` (M1.1) enforces these per flavor before insert.
  - **The weak-binding rule, structurally:** `identity_binding='weak'` claims are flagged so they are **never promoted** and **never drive outreach** (staged-flow §6/§8) — encode this so M1.2's `current_value` and M10's use-gate both honour it (default: a weak-binding contact personal claim is not eligible to win `current_value` for outreach-driving fields; it remains stored and queryable). This is the contact-axis analogue of the tier-4 evidence-span rule.
  - Extend the shared `Claim` domain type + provenance helpers (M0.2) with the two flavors and constructors (`discovery_claim(...)`, `field_claim(...)`, `contact_field_claim(..., identity_binding, use_class)`); update `insert_claim` flavor enforcement.
  - Indexes: `(research_mode)`, partial index on weak-binding contact claims, and a GIN index on `discovery_provenance`.
  - Migration + rollback; tests + fixtures for each mode/flavor.
- **Interface / seam:**
  - **Exposes:** the two provenance-flavor write constructors and the `research_mode`/`identity_binding`/`use_class`/`discovery_provenance` columns. Mode M1 (discovery) and mode M3 (committee discovery) write **discovery-provenance** claims through the existence gate; mode M2 (account profiling) and mode M4 (contact profiling) write **field-claim** provenance; mode M4 specifically writes `identity_binding` + `use_class` on contact personal claims. The flavor split is the seam that lets discovery and profiling evolve independently over one substrate (staged-flow §9).
  - **Consumes:** `claim` (M1.1) as the base table; `field_definition` (M1.3) to know whether a contact field is a *personal* claim requiring binding/use-class (e.g. `contact.facet.*` ⇒ requires both); shared types/helpers/tracing from M0.2; identity-binding strength is *determined* upstream by the resolver/source (`source_manifest.identity_binding_strength`, M4) and *stored* here.
  - **Swap note:** because identity-binding and use-class are stored as data on the claim (set by the source manifest / verification), tightening the policy (e.g. require strong binding for an additional field-class) is a policy/config change in M1.2/M10, not a schema fork; the substrate already carries the inputs.
- **Data model / schema:** ALTERs on `claim` (M1.1): `research_mode`, `identity_binding`, `use_class`, `discovery_provenance jsonb`, `claim_flavor`. Realizes the `_conventions.md` §4 "provenance flavors" note on `claim` (staged-flow §9). Read by `current_value` (M1.2, to honour the weak-binding rule) and by M10 (use-gate reads `use_class`).
- **Dependencies:** Depends on **M1.1** (the base `claim` table it ALTERs) and **M1.3** (to classify which contact fields are personal claims requiring binding/use-class). Soft-coordinated with **M1.2** (the merge view must honour the weak-binding non-promotion rule). Unblocks **M6** (discovery writes discovery-provenance), **M8** (profiling writes field-claim provenance, contact claims carry binding/use-class), **M9** (verification reads flavors), **M10** (use-gate reads `use_class`/`identity_binding`), and the `committee[].profile_claims[]` shape in the **M12** handoff (overview §3 / `_conventions.md` §4: each carries `identity_binding`, `use_class`).
- **Acceptance criteria:**
  - Migration adds `research_mode`, `identity_binding`, `use_class`, `discovery_provenance`, `claim_flavor` to `claim`; rollback removes them; existing M1.1 rows remain valid (new columns nullable as documented).
  - A discovery claim (mode M1) inserts with a populated `discovery_provenance` (discovered_via, matched_signal, discovery_confidence) and `claim_flavor='discovery'`; an attempt to insert a discovery claim with null `discovery_provenance` is rejected.
  - A contact personal field claim (e.g. a `contact.facet.*` field) requires non-null `identity_binding` and `use_class`; inserting one without either is rejected; an account field claim with both null is accepted.
  - An `identity_binding='weak'` contact personal claim is stored but is **not** returned as the winning `current_value` for an outreach-driving field (asserted against M1.2); a `strong` one is eligible.
  - `research_mode` accepts only `M1|M2|M3|M4` (and the documented null convention for CRM-import/Stage-0 claims); invalid values are rejected.
  - `use_class` accepts exactly `professional-public|personal-public-non-sensitive|sensitive`; `identity_binding` accepts exactly `strong|weak` (aligned to `_conventions.md` §3 / Doc D §2).
  - Fixtures exist for all four modes and both flavors; the `(research_mode)` and weak-binding partial indexes are present and used by representative queries.
- **Out of scope:** *Computing* identity-binding strength (the resolver/source determines it via `source_manifest.identity_binding_strength` in **M4**; the identity-binding gate/judge is **M9.4**). The appropriateness/**use-gate** evaluation `(use_class × jurisdiction × client_policy)` (**M10.3** — M1.4 stores `use_class`, M10 enforces it). The existence/identity gate that *admits* a discovered entity (**M2** identity service + **M6** discovery existence gate). Sensitive-data exclusion policy (**M10**; M1.4 stores the `sensitive` use-class so M10 can exclude it by default).
- **Open decisions:** **D3** (personal-data posture: conservative-default vs gather-broadly-gate-at-use vs professional-only) — M1.4 stores `use_class` + `identity_binding` on every contact personal claim so *all three* postures (Doc D §6) are a relaxation of the same machinery (`_conventions.md` §2 "design for the strict case and switch down"); the posture itself is M10 config. **D4** (contact geography — *resolved: mixed/global*) — jurisdiction is a per-client switch consumed by M10's use-gate; M1.4 carries the per-claim `use_class` that switch operates on. **D8** (2026 legal) — the `sensitive` use-class is excluded from outreach by default downstream; M1.4 records it faithfully and defers the exclusion to M10.
