# M8A — Campaign-Run Deep Orchestration — the per-account account→committee→contact sequence
**Layer label:** layer:deep-orchestration  ·  **Depends on:** M6, M7, M8 (M8.1/M8.3/M8.4 callables), composes-with M9 (M9.1 gate, M9.4 binding) · **Priority:** 2 (High — it is the integration milestone that makes Pass B actually run end-to-end)
**Architecture sources:** substrate §5 (durable execution at two levels), §5b (orchestrator-worker, references-not-blobs), §7 (contact graph + persona keys); Doc C §3 (bounded two-level fan-out), §4 (campaign phases), §5 (cost governance, the fan-out-per-account × accounts-per-pass dial); staged-flow §9 (composition), §10 (per-account execution); overview §2 (end-to-end map), §3 (the `account_handoff` shape M12 consumes); M07-durable-execution.md (CampaignRun state machine, AccountResearchGraph, AccountScheduler, M7.4 ledger, M7.5 BudgetEngine); M08-deep-profiling.md (the three worker families).

## Why this milestone exists (the seam no issue owns)

M8 built three correct-in-isolation deep-research worker families — **M8.1** account profiling (`profile_account`), **M8.3** committee discovery (`discover_committee`), **M8.4** contact profiling (`profile_contact`) — and M7 built the durable substrate beneath them (the `CampaignRun` state machine, the per-account `AccountResearchGraph`, the `AccountScheduler`, the M7.4 idempotency ledger, the M7.5 `BudgetEngine`). But **nothing sequences the three families per account.** The intended Pass-B loop —

```
for each human-approved high-tier account:
    1. profile_account     → the deep account picture            (M8.1/M8.2)
    2. discover_committee   → find + admit the buying committee   (M8.3)
    3. for each admitted member:
           profile_contact  → fill that person's facets           (M8.4)
    4. leave the claim store (account,persona)-keyed for M12       (handoff inputs)
```

— falls into a seam between three milestones, each of which *explicitly disclaims it*:
- **M8 spec** punts it upward: *"Per-account orchestrator-worker graph, campaign-run state machine, idempotency keys, budget caps — all M7"* and *"Value narrative / the `account_handoff` assembly — M12."*
- **M7** ships the substrate but `CampaignPhase.DEEP` has **no registered handler** — `CampaignRun.advance()` raises `NoPhaseHandlerRegistered(DEEP)` the moment a run enters it. The M7 `AccountResearchGraph` is **M2-only** (`plan → parallel aspect fan_out → collect → handoff`); its single parallel super-step cannot express the **committee→contact data dependency** (contacts are *discovered by* committee discovery), and its planner clusters only *account gap-fields* into aspects — it never emits `committee` (people-enumeration, not a field-fill) or `contact.facet.*` (a different entity).
- The **M8 kickoff** assumed *"DEEP phase = M8.1 trunk + api root"* — i.e. that integration was "register the aspect workers, load the packs, inject the gates." That assumption is the bug: committee/contact do not slot into the graph's field-clustering, so registering them as aspect workers makes them *dispatchable* but nothing *decides to dispatch them in the right order with the right fan-out*.

M8A is that decision, made once, as a milestone of its own: **the durable, resumable, budget-bounded `DEEP` phase.** It also folds in the two follow-ups the Track-B integration surfaced — graph campaign-coordinate threading (the "#2" change, needed only on the account axis) and the per-account/per-contact fan-out governance — and it **closes the exactly-once spend hole the M7.5 budget engine explicitly deferred to "the M8 claim-write path"** (`budget.py::record` docstring).

## The output contract M8A serves (and where it stops)
M8A produces no new *kind* of output: it is the orchestration that guarantees the M8 worker families run in the right order so the claim store ends up holding, per high-tier account, **Output 2** (verified account profile incl. resonance) and **Output 3** (the identity-resolved, persona-tagged, governed buying committee), each claim provenance-backed and `(account, persona)` / `(contact)`-keyed. The boundary is sharp: **M8A leaves verified-claim *references* in `account_run.references_index`, keyed for assembly; it does not build the `account_handoff` object** — that is M12.2's pure read (`HandoffAssembler` over the claim store). M8A emits a references-only per-account "deep-complete" manifest (account_run id, admitted committee member ids, coverage band, cost) as its `PhaseResult.payload`, never claim bodies.

## Chosen design (and the two rejected)
**Approach C — hybrid.** A thin `DeepPhaseHandler` (a `core.PhaseHandler` for `CampaignPhase.DEEP`, registered at the api composition root) delegates each high-tier account to an `AccountDeepOrchestrator` that sequences `profile_account → discover_committee → bounded profile_contact fan-out` via the workers' **direct callables**, running inside the existing `AccountScheduler`'s bounded-parallelism + per-entity single-flight slot. The whole milestone lives at the composition seam (a new `api/deep/` package — the only home the import-linter independence contract permits, since the work co-imports `durable` + `profiling` + `verification`, and only `api` is import-exempt).

Two alternatives were designed and scored by an adversarial judge panel and rejected:
- **Approach B — one parent LangGraph with a second, contact-fan-out super-step.** Rejected: it stakes its entire "free crash-resume" value on an **unproven LangGraph behavior** — a second dynamic `Send` super-step whose member list is computed from the *first* super-step's checkpointed state replaying correctly mid-fan-out — inside `durable/graph.py`, the most load-bearing durable file (it reshapes a 4-node single fan-out into ~8 nodes / two sequential dynamic fan-outs and overloads the one-entity-per-thread model to host many contact entities). Highest blast radius, riskiest semantics, discoverable only at integration; the ledger backstop only downgrades double-*spend*, not structural double-*dispatch*.
- **Approach A — pure composition, "reuse the scheduler for free, add nothing to M7."** Rejected as written because the premise is false: `AccountScheduler._invoke` hard-binds `self._graph.run` with no injectable callback (`scheduler.py:119-132`), so driving a three-stage pipeline per account requires either modifying `durable` *or* re-implementing semaphore+Redis-single-flight in the composition layer (a DRY violation), and A defers the exactly-once spend transaction. **C beats A by owning these honestly** (the additive durable seam M8A.0, the exactly-once transaction M8A.4) rather than waving them off, while keeping A's two genuinely-good ideas: **direct callables** (designing out the `ctx.params` KeyError hazard and shrinking graph param-threading to the account axis only) and **the four explicit fan-out bounds at one chokepoint**.

## Explicitly NOT in this milestone
- **Gate *logic* (M9.1) and binding *classification* (M9.4).** Both seams already exist on the callables — `discover_committee` gates people-enumeration (`committee/worker.py:259`) and role inference (`:311`); `profile_contact`→`fill_contact_field` calls `gate.check()` at its spend site (`contact/fill.py:155`); `profile_contact` accepts an injectable `binding_classifier`. M8A **injects** the concrete `PreSpendGate` and `verification.classify_binding` at the composition root and asserts they are routed (the deferred M9.1 AC-6 and M9.4 AC-4 tests); it never owns gate or classifier logic.
- **Claim *promotion* / verification.** `DEEP` produces `unverified` claims; the separate `VERIFICATION` phase (M9, the next phase in the state machine) promotes them. M8A does not run the faithfulness judge, corroboration, freshness, or the identity-binding *promotion* gate.
- **The `account_handoff` assembly and value narrative (M12).** M8A guarantees the inputs exist and are keyed; M12.2's `HandoffAssembler` reads them. M8A writes no `value_narrative`, no `provenance_index`, no fit/intent scores.
- **The worker bodies (M8) and the substrate engines (M7).** M8A composes `profile_account`/`discover_committee`/`profile_contact`, the `AccountResearchGraph`, `AccountScheduler`, the M7.4 ledger, and the M7.5 `BudgetEngine`; it does not re-implement them. The one exception is M8A.0's *additive* durable seams (a scheduler callback + an `account_run.sub_phase` marker), landed inside `durable` by its owner.
- **Resolver/source/pack authoring (M4/M3.3), Stage-0/discovery/scoring phases (M5/M6).** M8A reads the committed tier-checkpoint decision and the ICP spec; it does not produce them.

## Issues

### M8A.0 — Durable seams for deep orchestration (scheduler callback + `account_run.sub_phase`)
- **Owner package:** `durable` (M7-owned, additive). **Priority:** 2 (it is the substrate everything else depends on; lands first, in its own worktree).
- **Purpose:** Add the two small, additive, durable-OWNED changes the orchestration depends on, landed inside `durable` by its owner so the independence contract is never perturbed by an `api → durable` reach-in. The Track-B integration verified both are required and neither exists today.
- **Scope / deliverables:**
  - **A per-account callback on `AccountScheduler`.** `_invoke` today hardcodes `self._graph.run(...)` (`scheduler.py:119-132`) — there is no seam to run a *three-stage* pipeline per account under the same `Semaphore(max_parallel)` + per-entity single-flight lock. Add an optional `run_one: Callable[[AccountSpec, *, campaign_run_id, checkpointer], Awaitable[AccountRunResult]]` to `run_accounts` (or a sibling constructor) that, when supplied, is invoked inside the existing semaphore+lock slot instead of `self._graph.run`. **Default (omitted) preserves today's `graph.run` path exactly** — the account-axis behavior and all existing M7.3 scheduler tests are unchanged.
  - **An additive `account_run.sub_phase` marker.** `AccountRunStatus` (pending/planning/running/paused/done/failed/budget_exceeded) has no per-account *sub*-granularity, so a crashed account cannot resume at its last completed boundary (it would re-discover the committee). Add an `account_run.sub_phase` column (`AccountRunSubPhase ∈ {account_profiled, committee_discovered, contacts_complete}`, NULL = not started) + a `set_account_sub_phase(account_run_id, sub_phase)` helper on the `AccountRunStore` seam. New Alembic migration: **hash revision id chained off the current head, matching reversible `downgrade()`**, enum mirrored in `durable/enums.py` (and `core.enums` if cross-read), enum-parity test green (per the migration conventions).
- **Interface / seam:** exposes the scheduler callback parameter and the `set_account_sub_phase` store method. Both are additive — no existing signature changes meaning; the default scheduler path is byte-for-byte the same.
- **Data model:** one additive nullable column on `account_run`; one new enum; one migration. No other table touched.
- **Dependencies:** none (pure substrate). **Unblocks** M8A.1 (needs the callback + sub-phase setter).
- **Acceptance criteria:**
  - `AccountScheduler.run_accounts(..., run_one=<callable>)` drives an arbitrary per-account async callable under the same `Semaphore(max_parallel)` + per-entity lock, returning results in input order; with `run_one` omitted it invokes `AccountResearchGraph.run` unchanged and every pre-existing scheduler test stays green.
  - `account_run.sub_phase` round-trips through the store seam; a fresh row defaults to NULL and advances monotonically `account_profiled → committee_discovered → contacts_complete`.
  - `alembic upgrade→downgrade→upgrade` on a clean per-branch throwaway DB is green; `alembic heads` returns exactly one; enum-parity and "no domain tables at M0 head" tests pass.
- **Out of scope:** the orchestration that *uses* these (M8A.1); the exactly-once transaction (M8A.4, which co-touches `durable/budget.py`).
- **Open decisions:** none material. (Marker semantics: it is *advisory* — the M7.4 ledger remains authoritative for spend; see M8A.1's resume note.)

### M8A.1 — `AccountDeepOrchestrator` — the per-account M2→M3→M4 sequence (direct callables)
- **Owner package:** `api/deep/` (new composition package). **Priority:** 2 (the trunk; M8A.2/M8A.3/M8A.5 build against its interface).
- **Purpose:** The per-account composer. For ONE account, inside the scheduler's bounded+locked slot, it runs the three stages in order and advances the `sub_phase` marker. It is **pure composition with injected collaborators typed against `core` protocols + explicit callable types** — so it imports only `core` + the shared base, is unit-testable with fakes, and contains no gate, budget-transaction, narrative, or handoff logic.
- **Scope / deliverables:**
  - `src/clue_research/api/deep/orchestrator.py` — `AccountDeepOrchestrator` with injected callables (`profile_account`, `discover_committee`, `profile_contact`), the injected `set_account_sub_phase` writer, and `DeepPhaseConfig` (M8A.3). One account run_id (`= account_run.id = claim.run_id`) threads through all three stages so every claim shares provenance.
  - **Stage 1 — account axis (through the M7 graph):** invoke `profile_account` for the account, passing the campaign coordinates via `params_for_run(client_id, icp_key, icp_version, tenant_id)` (the **graph param-threading "#2"**, confined here so the account planner can load the ICP spec and write tenant-private resonance claims). Stamp `sub_phase=account_profiled`.
  - **Stage 2 — committee axis (direct callable):** `discover_committee(conn, account_entity_id=…, run_id=…, tenant_id=…, sources=…, gateway=…, role_model=…, spec=…, budget_cap_cents=…, pre_spend_gate=…)` — **no `AspectContext`, so the `ctx.params` KeyError hazard (`committee/worker.py:419-421`) never arises.** Stamp `sub_phase=committee_discovered`.
  - **Stage 3 — contact axis (bounded fan-out of direct callables):** for each admitted `CommitteeMemberRef.contact_entity_id`, `profile_contact(conn, contact_entity_id=…, account_entity_id=…, run_id=…, tenant_id=…, tier=…, spec=…, facet_subworker_budget=…, binding_classifier=…, use_class_tagger=…, pre_spend_gate=…)`. Bounded by `DeepPhaseConfig` (committee-size cap) + an intra-account `asyncio.Semaphore(max_contacts_in_flight)` + the budget admission gate (M8A.3). Stamp `sub_phase=contacts_complete`.
  - **Sub-phase resume:** on re-entry, read `account_run.sub_phase` and skip stages already marked complete; the claim-store gap-recompute (`compute_contact_gap_fields` / the account planner's gap detection skip FRESH fields, and the M4 waterfall is idempotent on `(entity, field, source, run)`) is the correctness backstop, so a double-entered stage converges to a no-op even if the marker is stale.
- **Interface / seam:** exposes `AccountDeepOrchestrator.run_one(spec: AccountSpec, *, campaign_run_id, checkpointer) -> DeepAccountResult` (a references-only result: account/committee/contact claim-id lists + coverage + cost), shaped to be the `run_one` callback M8A.0 added to `AccountScheduler`. Collaborators injected at construction; nothing concrete imported.
- **Data model:** writes nothing new; the three callables write claims; the orchestrator only advances `sub_phase` (via the injected writer) and returns references.
- **Dependencies:** **blocked by** M8A.0 (callback + sub_phase). Consumes the M8 callables (injected), `profiling.context.params_for_run` (account axis only). **Unblocks** M8A.2/M8A.3/M8A.4/M8A.5.
- **Acceptance criteria:**
  - Given fakes, the orchestrator runs `profile_account`, then `discover_committee`, then `profile_contact` per admitted member, **in that order**; a contact is never profiled before the committee admits it (committee is a hard gate before the contact fan-out).
  - Re-entry after a simulated crash at `committee_discovered` does **not** re-run `profile_account` or re-discover the committee — it resumes at the contact fan-out.
  - The committee-size cap and the intra-account semaphore are honored (≤ N contacts processed, ≤ K in flight); the account-axis call carries `client_id/icp_key/icp_version/tenant_id` in its params while committee/contact pass campaign coords as **explicit kwargs**, never via `ctx.params`.
  - `orchestrator.py` imports no `durable`/`profiling`/`verification` source — only `core` protocols + injected callables (import-linter green).
- **Out of scope:** the handler/high-tier resolution (M8A.2); the budget admission gate body + config (M8A.3); the exactly-once transaction (M8A.4); handoff assembly (M8A.5); injecting concretes (M8A.6).
- **Open decisions:** **per-account checkpoint mechanism** — the `sub_phase` marker + ledger (chosen) vs folding the whole sequence into one LangGraph thread. Recommended default: the marker + gap-recompute backstop (keeps committee/contact off the unproven second-dynamic-`Send` path); accept that two checkpoint mechanisms coexist in one `account_run` (LangGraph for the account axis *inside* `profile_account`; the marker for committee/contact), with **the ledger authoritative and the marker advisory**.

### M8A.2 — `DeepPhaseHandler` — the `CampaignPhase.DEEP` handler
- **Owner package:** `api/deep/`. **Priority:** 2.
- **Purpose:** The `core.PhaseHandler` (`phase=CampaignPhase.DEEP`) that resolves the human-approved high-tier account set and drives the scheduler with the M8A.1 orchestrator bound as the per-account callback. Registering it makes `CampaignRun.advance()` dispatch `DEEP` with zero new dispatch code — the run no longer raises `NoPhaseHandlerRegistered(DEEP)`.
- **Scope / deliverables:**
  - `src/clue_research/api/deep/handler.py` — `DeepPhaseHandler` implementing `core.PhaseHandler`; injected `AccountScheduler`, the orchestrator factory, and a `high_tier_resolver`.
  - **High-tier resolution.** Read the human-approved set from the **claim store**: `account.scoring.tier ≥ cutoff` filtered by the committed `cutoff_version` carried in the tier-checkpoint checkpoint payload (`PhaseContext.params` / the COMMITTED `tier_checkpoint` payload). This honors the human decision (the approved `cutoff_version`) while reading the per-account list from where `persist_tier` actually writes it (claims) — see Open decisions; the payload's `tier_distribution` is aggregate, not the per-account list.
  - Map the resolved accounts to `durable.AccountSpec(entity_id, tier, tenant_id, field_keys)`, call `AccountScheduler.run_accounts(specs, campaign_run_id, checkpointer, run_one=<orchestrator.run_one>)`.
  - **Per-account isolation:** the scheduler uses `asyncio.gather` and one account raising propagates, so wrap each account so a single FAILED account marks its `account_run` FAILED and the batch continues (the handler owns the isolation policy the scheduler delegates).
  - Aggregate cost + coverage; return `PhaseResult(COMPLETED, accounts_processed, cost_cents, payload=<references-only deep-complete manifest>)`. Return `PhaseResult(PAUSED)` on a RUN-scope `GRACEFUL_STOP` so the campaign suspends cleanly and re-enters `DEEP` fresh on resume.
- **Interface / seam:** the registered `PhaseHandler`; payload is references-only (per-account `account_run_id`, admitted committee member ids, coverage band, cost). No claim bodies.
- **Dependencies:** **blocked by** M8A.1. **Unblocks** M8A.6 (which registers it).
- **Acceptance criteria:**
  - `register_phase_handler(DeepPhaseHandler(...))` makes `CampaignRun.advance()` dispatch `DEEP`; entering `DEEP` no longer raises `NoPhaseHandlerRegistered`.
  - The approved high-tier set is read from `account.scoring.tier` at/above the committed `cutoff_version`; with a present committed decision the handler does not invent or re-derive cutoffs.
  - A single account raising is caught, recorded FAILED/partial, and the remaining accounts still process; `PhaseResult` reflects `accounts_processed` and partial coverage.
  - A RUN-scope `GRACEFUL_STOP` returns `PhaseResult(PAUSED)`; `PhaseResult.payload` contains no claim `value_json` (references-only).
- **Out of scope:** the per-account sequence (M8A.1); fan-out budget (M8A.3); concrete injection (M8A.6).
- **Open decisions:** **high-tier source of truth** (see Cross-cutting). Recommended: claimstore `account.scoring.tier ≥ cutoff` keyed by committed `cutoff_version` (primary); verify the exact `tier_checkpoint` COMPLETED payload keys against `discovery_scoring/phases.py` at build time and, only if a clean per-account list is present there, prefer it.

### M8A.3 — Fan-out bounding + budget admission at the contact chokepoint
- **Owner package:** `api/deep/` (orchestrator body) + `config` (schema extension, co-owned with M0.4). **Priority:** 2.
- **Purpose:** The four-way bound and the budget admission gate for the per-contact fan-out, at the single chokepoint where committee members become known — the concrete expression of the architecture's cost dial (*fan-out-per-account × accounts-per-pass*, Doc C §5) and bounded fan-out (Doc C §3).
- **Scope / deliverables:**
  - **Policy-as-data `DeepPhaseConfig`** in `config/schema.py` (versioned, per-ICP overridable, alongside `BudgetPolicy`/`RecursionPolicy`): `committee_size_cap`, `per_contact_estimate_cents`, `per_contact_cap_cents`, `max_parallel_accounts`, `max_contacts_in_flight`. Changing the cost dial is a config edit, no code change.
  - **The four bounds, all at the chokepoint, all legible/unit-testable:** (a) `committee_size_cap` truncates admitted members (mirroring the graph's `_dispatch` `max_aspect_workers` truncation); (b) `BudgetEngine.check(scope=ACCOUNT, projected_cents=per_contact_estimate, campaign_run_id, entity_id, account_run_id)` before each `profile_contact`; (c) the contact worker's own per-tier `facet_subworker_budget` (already wired, level-2 fan-out); (d) the intra-account `asyncio.Semaphore(max_contacts_in_flight)`.
  - **Budget verdict handling:** an ACCOUNT-scope `DENY` stops admitting further contacts for that account → a **partial committee with coverage metadata, not a failure** (coverage-confidence, not completeness). A RUN-scope `GRACEFUL_STOP` bubbles up to `PhaseResult(PAUSED)`. Carve the `per_contact_cap_cents` sub-envelope from the account envelope at admission.
- **Interface / seam:** `DeepPhaseConfig` (config); the admission gate is internal to the orchestrator's contact loop. The cost dial is the config; the engine is M7.5 (injected).
- **Dependencies:** **blocked by** M8A.1. Consumes `core.BudgetEngine` (injected). **Unblocks** M8A.4 (which wraps the admitted-spend steps).
- **Acceptance criteria:**
  - An ACCOUNT-scope budget `DENY` stops admitting further contacts and records a partial/coverage-capped outcome (not FAILED); a RUN-scope `GRACEFUL_STOP` returns `PhaseResult(PAUSED)`.
  - All caps (committee-size, `max_contacts_in_flight`, `per_contact_estimate`) are read from `DeepPhaseConfig`; no bound is hardcoded in the orchestrator body; all four bounds are exercised by tests.
- **Out of scope:** the exactly-once charge transaction (M8A.4); the budget *engine* implementation (M7.5).
- **Open decisions:** whether the per-account envelope is derived from the M7.5 `Estimate` or set as a flat `DeepPhaseConfig` value (recommended default: flat config value, reconciled against `estimate()` for the burn-down surface).

### M8A.4 — Exactly-once spend on the committee/contact path (single-transaction charge)
- **Owner package:** `api/deep/` (orchestrator spend steps) + `durable` (budget single-writer/reservation, M7.5-owned). **Priority:** 2 (it sits directly on the client-set cost-governance hard cap).
- **Purpose:** Close the durability hole the M7.5 budget engine **explicitly deferred to "the M8 claim-write path"** (`budget.py::record` docstring: *"the increment commits in its own transaction, separate from the ledger `succeed` … airtight exactly-once requires the caller to commit the charge and finish the ledger in one transaction"*). This is not a new concern invented here; it is the named, deferred V1 caveat, and the deep-phase committee/contact spend path is the caller that must close it.
- **Scope / deliverables:**
  - **Single transaction per spend step.** Wrap each committee admission and each contact field-fill so the claim write(s), the `BudgetEngine` charge, and the M7.4 idempotency-ledger `succeed()` commit in **one** DB transaction — closing the window where a crash leaves the ledger SUCCEEDED but `spent_cents` un-incremented (under-counting the client hard cap by up to one contact per crash).
  - **`cost_cents` single-writer reconciliation.** `BudgetEngine.record` already moves both `campaign_run.spent_cents` and `account_run.cost_cents` (when `account_run_id` is given); the M2 graph's `account_run.save_references` *SETs* `account_run.cost_cents` (`account_run.py:189`). Decide and implement: **`BudgetEngine.record` is the single live writer for committee/contact spend**, and the account-axis SET is reconciled to `SUM(ledger cost_cents_charged)` (or made report-only) at `contacts_complete` — so the two writers cannot clobber/double-count.
  - **Per-account spend reservation.** `check(ACCOUNT)` reads spend-so-far while concurrent peers have not yet `record()`-ed, so N concurrent admits can collectively exceed the per-account cap. Add a small decrement-at-admit / reconcile-on-record reservation that bounds the over-commit window (paired with M8A.3's `max_contacts_in_flight`).
- **Interface / seam:** the single-transaction spend helper lives in the orchestrator; the single-writer + reservation changes live in `durable/budget.py` (M7.5-owned — coordinate with M8A.0's branch owner since both touch `durable`).
- **Data model:** no new table; the reservation can be an in-transaction counter on the existing account budget state (M7.5's ledger/state).
- **Dependencies:** **blocked by** M8A.1, M8A.3. **Unblocks** M8A.6 (the end-to-end correctness it asserts).
- **Acceptance criteria:**
  - After a simulated crash inside a per-contact step, on resume the campaign hard-cap counter (`spent_cents`) equals `SUM(ledger cost_cents_charged)` for that account — no under-count, no double-charge (proven by a crash-injection test, not a convergence argument).
  - Exactly one component increments `account_run.cost_cents` for committee/contact spend; a reconciliation test asserts `cost_cents == SUM(ledger charges)` at `contacts_complete`.
  - Concurrent `profile_contact` admits cannot collectively exceed the per-account cap beyond the bounded reservation window.
- **Out of scope:** the broader campaign-cap/graceful-stop machinery (M7.5, already built); the account-axis graph's own cost path (unchanged, only reconciled).
- **Open decisions:** **single-writer resolution** — `record` as sole live writer + reconcile the account-axis SET (recommended, lowest-surprise, testable) vs reconcile-only at sub-phase close.

### M8A.5 — Per-account handoff skeleton (references-only, (account,persona)-keyed)
- **Owner package:** `api/deep/` (reuses `core.handoff` read-only). **Priority:** 3.
- **Purpose:** Guarantee M12.2's inputs exist and are correctly keyed — **not** to build the final `AccountHandoff` (that is M12.2's pure read over the claim store). The skeleton is the references-only join that proves "this account is M12-ready."
- **Scope / deliverables:**
  - `src/clue_research/api/deep/handoff_skeleton.py` — for each account: fold `AccountProfileResult` account+resonance `claim_refs`; project `CommitteeResult.committee()` (already `→ core.handoff.CommitteeMember(profile_claims=())`) to `(contact_entity_id, persona)` shells; **join** each admitted member's `ContactProfileResult.profile_claims` (`core.handoff.ProfileClaimView`: `claim_id + value_json + evidence_span + source_tier + identity_binding + use_class`) onto its shell by `contact_entity_id`; fold the union of claim ids into `account_run.references_index` under `{account, resonance, committee, contact:<id>}` keys (ids only, never blobs).
  - Carry `CommitteeCoverage` (point + band + named unsearched channels) through so a budget-capped or marginal-yield-stopped account reads as **partial, not failed**.
  - **No persisted intermediate** (see Open decisions): compute-on-read from `references_index` + the claim store; the materialized `account_handoff` row, if any, is M12.2's call.
- **Interface / seam:** reuses `core.handoff.{CommitteeMember, ProfileClaimView, AccountHandoff}` read-only; exposes a references-only skeleton the handler folds into its payload + `references_index`.

## Cross-cutting open decisions (recommended defaults)
- **D-A — package home.** `api/deep/` (under the import-exempt composition root; **no new import-linter contract entry needed**) vs a new top-level `orchestration` package (needs a new contract rule permitting it to import the milestone packages). **Recommended: `api/deep/`** — lowest friction, honors "the api root is the one coordination point," and `orchestrator.py`/`handler.py` stay import-light (core + injected callables) so they remain unit-testable and could be relocated later if a top-level package is ever wanted.
- **D-B — high-tier source of truth.** Committed `tier_checkpoint` decision payload vs claimstore `account.scoring.tier` query. **Recommended: claimstore `account.scoring.tier ≥ cutoff` keyed by the committed `cutoff_version`** — verified that `persist_tier` writes the per-account decision as claims while the COMPLETED payload carries only aggregate `tier_distribution` + `cutoff_version`. The payload supplies the *approved cutoff* (honoring the human gate) and the audit link; the per-account set comes from the claims. Confirm the exact payload keys against `discovery_scoring/phases.py` when building M8A.2.
- **D-C — checkpoint mechanism duality.** The account axis resumes from LangGraph/`AsyncPostgresSaver` (inside `profile_account`); committee/contact resume from the `account_run.sub_phase` marker + the M7.4 ledger. **Recommended: accept the duality** — ledger authoritative, marker advisory, gap-recompute the correctness backstop. (Folding everything into one LangGraph thread is Approach B, rejected.)
- **D-D — handoff intermediate persistence.** **Recommended: none** — `references_index` + compute-on-read; the materialized `account_handoff` row is M12.2's call.
- **D-E — Redis 7 floor (carried M2 caveat).** The scheduler's per-entity single-flight lock rides the M2 entity-lock that requires Redis 7+. **Recommended: accept the floor for M8A** (correct for the composed/tested stack); note it in the api composition README as a deployment prerequisite; do not block M8A on the M2 6-compat decision.
