# M3 — ICP & Research-Schema Compiler
**Layer label:** layer:icp-schema  ·  **Depends on:** M1 (Claim Store & Merge Policy; field registry)  ·  **Priority:** 2 (High)
**Architecture sources:** substrate §3 (research-schema compilation — ICP becomes a typed plan; its two payoffs: vertical pluggability and two-pass economics), §1 (`field_definition`, `current_value`), §11 build-order step 2 ("field registry + research-schema compiler"); staged-flow §2 (Stage 0 output: the versioned ICP spec compile target), §7c (source profiles per ICP/per pack), §9 (packs carry two prior sets); Doc B §3 (ICP synthesis, multi-ICP — D5), §5 (Stage 0 output); Doc C §1 (two-tier signal model: one signal class spans `scoring`+`deep`), §2 (`account.resonance.*`, `contact.facet.*` field-classes registered, not enumerated); overview §1 (Output 1: fit + intent), §3 (`account_handoff`).

## Goal & scope of this milestone

This milestone delivers the **compiler that turns a confirmed ICP into the executable contract the rest of the subsystem runs against** — the "research schema compilation" move of substrate §3 and the compile target named in staged-flow §2 / Doc B §3 / Doc B §5. It is the generalization the prototype could not make: the prototype was welded to one vertical (dental/NPI); here a client's ICP definition *compiles* into a typed field plan, a discovery strategy reference, a source-profile reference, and a scoring rubric, all as **versioned config rows the engine reads** (conventions §2: policy is data, not code).

Concretely, M3 owns four things:
1. **The `ICP spec` data model** (M3.1) — the versioned, multi-ICP-capable container named in conventions §4 (`Versioned ICP spec`) and staged-flow §2: active field set + discovery strategy + source profile + scoring rubric, addressable by `(client, icp_key, version)`.
2. **The research-schema compiler** (M3.2) — the function that resolves an ICP spec into a concrete, typed **field plan**: an ordered set of `field_definition` rows (conventions §4), each tagged `scoring` vs `deep` (substrate §3), with its `tier_plan`, `freshness_ttl`, and `gate`. This is where the two-pass economics are *declared and auditable* (substrate §3, payoff 2).
3. **The industry-packs framework** (M3.3) — the registration mechanism by which a vertical contributes a field set **and** a source profile (staged-flow §9: packs carry two prior sets), namespaced under `<pack>.*` (conventions §3), so adding a vertical is registration, never a pipeline fork.
4. **The scoring-rubric model** (M3.4) — the versioned, explainable fit + intent weight structure (substrate §9; overview §1 Output 1) that Pass A and the `account_handoff` decomposition read.

**Where it sits in the end-to-end map** (overview §2; staged-flow §10): M3 is the bridge between Stage 0's human ICP co-definition (M5) and *everything that executes against the plan* — M4 (source layer reads the field plan's `tier_plan` and the pack source profiles), M6 (discovery reads the discovery strategy; Pass A reads the `scoring`-tagged fields and the rubric), and M8 (deep profiling reads the `deep`-tagged fields). M3 produces a contract; it does not execute it.

**What is explicitly NOT here:**
- The field **registry** itself (the `field_definition` table, the `core.*`/`account.*`/`contact.*` namespaces, `current_value` merge) — that is M1.3 (conventions §7). M3 *reads and composes* `field_definition` rows into a per-ICP plan; it does not own the table.
- The **source registry** (`source_manifest`), modality adapters, and the **Source Planner** — those are M4 (conventions §7; staged-flow §7a/b/d). M3 produces and references a *source profile* (the per-ICP/per-pack priors that the Source Planner consumes); it does not select or call sources at runtime.
- **Resolvers** and the trust-tiered waterfall execution — M4. M3 names the ordered `tier_plan` per field; M4 implements the resolvers it names.
- **Stage 0 itself** — client reverse-profiling, the ICP-synthesis elicitation loop, and the human confirm UI are M5 (Doc B §2/§3). M3 is what M5 *compiles into*; the LLM-assisted *proposal* of an ICP belongs to M5, the *compilation* of a confirmed ICP belongs here.
- **Running** Pass A scoring or computing actual fit/intent scores — that is M6. M3 defines the rubric model and a pure scoring function spec; M6 wires it to live claims.

## Issues

### M3.1 — ICP spec data model (versioned)
- **Purpose:** Everything downstream of Stage 0 executes against *one contract*: the versioned ICP spec (conventions §4 `Versioned ICP spec`; staged-flow §2; Doc B §5). This issue defines that container as durable, versioned Postgres config so a campaign run is reproducible (it pins an exact ICP-spec version), a client can support several segments (D5: multiple ICPs per client, each compiling its own plan — Doc B §3), and edits never mutate a running campaign's plan (append-only versioning, the same discipline the claim store uses in M1). Without this, the discovery strategy, source profile, field set, and scoring rubric would be scattered, unversioned, and impossible to reproduce or attribute.
- **Architecture sources:** staged-flow §2 ("a structured, versioned ICP spec that plans the next three stages … reproducible because it is versioned"); Doc B §3 (ICP synthesis output; multi-ICP — D5), §5 (Stage 0 output: "one or more versioned ICP specs"); conventions §4 (`Versioned ICP spec`), §2 (policy-is-data, per-client/ICP swappable config); overview §2 (the end-to-end map's compile output).
- **Scope / deliverables:**
  - An `icp_spec` table (versioned config), keyed `(client_id, icp_key, version)` with `status{draft|active|archived}`, `created_from{synthesis|client_edit|import_rederive}`, `created_at`, `created_by`, `parent_version` (append-only lineage), and a human label/description.
  - The four sub-contract slots referenced by name, stored structurally (JSONB acceptable for V1, real columns on hot keys):
    - **active field set** — an ordered list of `field_key`s (conventions §3 namespaces: `core.*`, `account.*`, `account.resonance.*`, `contact.*`, `contact.facet.*`, `<pack>.*`) plus the set of enabled packs (M3.3) — the input the compiler (M3.2) resolves.
    - **discovery strategy** — channels, ICP filters (firmographic/technographic dimensions per Doc B §3), and seed/lookalike anchors for mode M1 (consumed by M6; M3 stores it, does not run it).
    - **source profile reference** — a pointer to the per-ICP source-profile config (the pack-derived priors + per-client overrides; the object itself is shaped in M3.3 and consumed by M4's Source Planner — source profile is for modes M2/M4 per staged-flow §2).
    - **scoring rubric reference** — a pointer to / embedded `scoring_rubric` (M3.4).
  - Versioning semantics: an `active` spec is immutable; an edit produces a new `version` with `parent_version` set; activating a new version supersedes (does not delete) the prior. A `campaign_run` (Doc C §4; M7) pins `(client_id, icp_key, version)` so re-entry is deterministic.
  - Multi-ICP support (D5 default = support multiple): `icp_key` distinguishes segments under one `client_id`; each compiles independently. Single-ICP is the degenerate case (one `icp_key`).
  - A read API: fetch active spec for `(client_id, icp_key)`, fetch a pinned version, list versions/lineage, diff two versions (which field-keys/packs/weights changed).
- **Interface / seam:**
  - **Exposes:** the `ICP spec` contract (conventions §4) as the single object M3.2/M3.4 read and M5 writes. Read accessors `get_active_icp(client_id, icp_key)`, `get_icp_version(client_id, icp_key, version)`, `diff_icp(v_a, v_b)`. The four slots are referenced *by name* so the discovery strategy (M6), source profile (M4), field set (M3.2), and rubric (M3.4) are independently replaceable — a change to the discovery-strategy shape does not touch the rubric.
  - **Consumes:** `field_definition` keys from the M1.3 field registry (validates that every `field_key` in the active field set exists in the registry); the pack catalog from M3.3 (validates enabled packs exist). Nothing else — the data model is storage + versioning only, with no resolver, source, or LLM dependency, so it sits cleanly below M4.
  - **Swap note:** versioning is implemented as append-only Postgres rows; migration to a richer config store stays behind the read accessors. The campaign-run pin (`version`) is the same mechanism whether the state machine is Postgres-backed (V1) or Temporal (later) — conventions §2/§6.
- **Data model / schema:** new `icp_spec` table (this milestone owns it). References (does not redefine): `field_definition` / field registry (M1.3, conventions §4) for field-key existence; the pack catalog (M3.3). Slots reference `scoring_rubric` (M3.4) and the source-profile config (M3.3/M4). The pinned `(client_id, icp_key, version)` is what `campaign_run` (Doc C §4; M7) and `account_handoff` provenance (conventions §4) attribute scores back to.
- **Dependencies:** depends on **M1** (M1.3 field registry must exist so the active field set validates against real `field_definition` rows). Blocks **M3.2** (the compiler reads this), **M3.4** (the rubric is a slot here), **M5** (Stage 0 writes specs here), **M6** (discovery/Pass A read the discovery strategy + active field set), **M4** (source profile is referenced here). The `campaign_run` state machine (M7) *references* a pinned `(client_id, icp_key, version)` at runtime — a contract-consumer relationship, not a build-order block (M7 depends only on M1, M4 per conventions §7).
- **Acceptance criteria:**
  - Creating an ICP spec with N field-keys, K enabled packs, a discovery strategy, a source-profile ref, and a rubric ref persists one immutable versioned row addressable by `(client_id, icp_key, version)`.
  - Editing an active spec produces a **new** version with `parent_version` set; the prior version remains byte-identical and re-readable (append-only verified by re-fetch).
  - Two ICP specs under the same `client_id` with different `icp_key` coexist and are fetched independently (D5).
  - `get_active_icp` returns exactly one `active` spec per `(client_id, icp_key)`; activating a new version flips the prior to `archived` atomically.
  - An ICP spec referencing a `field_key` absent from the M1.3 registry is **rejected at write** with a clear error naming the missing key.
  - `diff_icp(v_a, v_b)` reports added/removed field-keys, added/removed packs, and changed rubric/source-profile references.
  - A pinned version is reproducible: fetching `(client_id, icp_key, version)` after later edits returns the originally pinned content.
- **Out of scope:** the ICP *synthesis* / proposal loop and human confirm UI (M5, Doc B §3); compiling the field set into a field plan (M3.2); the rubric internals (M3.4); the source-profile object internals (M3.3/M4); running discovery against the discovery strategy (M6).
- **Open decisions:** **D5 (ICP multiplicity)** — built on the recommended default (support multiple ICPs per client via `icp_key`); single-ICP is the degenerate case, so resolving D5 either way needs no schema change. **D6 (import non-fit behavior)** touched only via `created_from{import_rederive}` as an explicit, optional provenance value — the default (flag-and-proceed, Doc B §4) does not create a new spec; re-derive does. Surface, do not hardcode.

### M3.2 — Research-schema compiler (ICP → typed field plan; scoring vs deep tags)
- **Purpose:** This is the milestone's core engine and the exact move of substrate §3: *a client's ICP definition compiles into a research schema — a typed list of `field_key`s, each mapped to (a) the ordered source tier list that may populate it and (b) the gates that apply.* It is the generalization the prototype could not make (it was welded to dental/NPI). Given an active ICP spec (M3.1), the compiler resolves the active field set (core + enabled packs) into a concrete, typed **field plan**: a deterministic, ordered collection of `field_definition` rows, each carrying its `tier_plan`, `freshness_ttl`, `gate`, and — critically — its `pass{scoring|deep}` tag, because **this is where the two-pass economics are declared and auditable** (substrate §3 payoff 2; Doc C §1). Without this compiler, "what do we spend on whom" is implicit and un-inspectable.
- **Architecture sources:** substrate §3 (the whole section — ICP → research schema; the worked `tier_plan`/`pass`/`gate` table; payoff 1 vertical pluggability; payoff 2 two-pass economics), §1 (`field_definition`: `field_key, type, validation, tier_plan, freshness_ttl, pass, gate`), §11 build-order step 2 ("field registry + research-schema compiler"); Doc C §1 ("a single signal class spans both tags — its proxy is `scoring`, its narrative is `deep`"); staged-flow §2 (the compile target); conventions §3 (namespaces, source tiers), §4 (`field_definition`).
- **Scope / deliverables:**
  - A pure **compile function** `compile(icp_spec) -> field_plan` that, given a versioned ICP spec, produces a versioned, content-addressable field plan:
    - resolves the active field set = `core.*` baseline ∪ each enabled pack's contributed field set (M3.3) ∪ any per-ICP overrides, deduplicated and ordered;
    - for each `field_key`, materializes its `field_definition` (conventions §4): `type`, `validation`, `tier_plan` (ordered resolver list, conventions §3 tier order 1→4), `freshness_ttl`, `gate`, and `pass{scoring|deep}`;
    - resolves the **two-tier signal model** (Doc C §1): where a signal class has both a cheap proxy and a deep narrative, the compiler emits *two* field entries — the proxy tagged `scoring`, the narrative tagged `deep` — and records the link between them (`signal_class`) so Pass A and Pass B are coherent.
  - **Pass partitioning output:** the field plan exposes `scoring_fields[]` (Pass A, run on all accounts) and `deep_fields[]` (Pass B, high-tier only) as first-class, queryable subsets — the auditable statement of two-pass spend (substrate §3 payoff 2; staged-flow §4; Doc C §5).
  - **Gate propagation:** each field's `gate` (e.g. `tier>=1`, `committee-gated` per the substrate §3 worked table; Doc D use-gate marker for `contact.facet.*`) is carried verbatim from the `field_definition` into the plan so M4/M8/M10 read gates from one place.
  - **Pack precedence & conflict rules:** deterministic resolution when two enabled packs contribute the same `field_key` or differing `tier_plan`s (e.g. precedence = explicit per-ICP override > pack-priority order > core default); conflicts that cannot be auto-resolved are surfaced as a compile diagnostic, not silently merged (mirrors the claim-store conflict-flag discipline, substrate §1/§6).
  - **Validation:** every `field_key` resolves to a registry `field_definition`; every `tier_plan` names resolvers/tiers known to the source layer's expected interface; `pass`/`gate` values are within the allowed taxonomy. Invalid → compile fails with a diagnostic; a partial/ambiguous plan is never emitted (empty-or-correct discipline applied to config).
  - **Determinism & versioning:** `compile` is pure and reproducible — same ICP-spec version → identical field plan; the plan is stored/versioned and pinned to the ICP-spec version so M6/M8 execute exactly what was compiled.
- **Interface / seam:**
  - **Exposes:** `compile(icp_spec) -> field_plan` and the `field_plan` object (`fields[]`, `scoring_fields[]`, `deep_fields[]`, per-field `field_definition` view, `signal_class` links, compile diagnostics). This `field_plan` is the **single contract** M4 (resolver/tier_plan execution), M6 (Pass A reads `scoring_fields`), and M8 (Pass B reads `deep_fields`) consume — they never re-derive "which fields, which tiers, which pass."
  - **Consumes:** the `ICP spec` (M3.1); `field_definition` rows from the M1.3 field registry; pack field sets from M3.3. It does **not** consume `source_manifest`, resolvers, or any LLM — compilation is a pure config transform, so the compiler is testable in isolation and swappable without touching the source layer.
  - **Swap note:** the compiler is the only component that knows how field sets + packs + overrides combine into a plan; its inputs (ICP spec, registry, packs) and output (`field_plan`) are stable, so the merge/precedence algorithm can be reimplemented behind `compile(...)`. Because `tier_plan` is *named* here and *implemented* in M4, swapping Clay→direct APIs (conventions §2) is a registry/config change that never re-compiles a plan.
- **Data model / schema:** reads `icp_spec` (M3.1) and `field_definition` (M1.3, conventions §4); reads pack field sets (M3.3). Emits a `field_plan` (new, owned here — may be a materialized/versioned view keyed to `(client_id, icp_key, icp_version)`). No new claim-store tables; the `field_definition` contract is referenced and, where a `signal_class` link or `pass` partition needs persisting, *extended* (not redefined) per conventions §4.
- **Dependencies:** depends on **M3.1** (the spec to compile), **M3.3** (pack field sets to compose), and **M1** (M1.3 field registry rows). Blocks **M4** (resolvers execute the `tier_plan`s named here), **M6** (Pass A consumes `scoring_fields`), **M8** (Pass B consumes `deep_fields`).
- **Acceptance criteria:**
  - `compile` on a fixed ICP spec is deterministic: identical output across runs; identical output after re-fetching the pinned ICP-spec version.
  - The emitted plan partitions every field into exactly one of `scoring_fields`/`deep_fields`, matching each field's registry `pass` tag (verified against the substrate §3 worked example: `employee_count`/`primary_tech_stack`/`recent_funding` → scoring; `hiring_velocity_eng`/`operational_pain`/`strategic_moves` → deep).
  - A signal class with both a proxy and a narrative (Doc C §1, e.g. intent: job-count delta proxy + "why in-market" narrative) compiles to two linked field entries with the proxy `scoring` and the narrative `deep`.
  - Each field in the plan carries its `tier_plan` in trust-tier order (conventions §3) and its `gate` verbatim from the registry.
  - Enabling a healthcare pack injects `<pack>.*` fields (e.g. `healthcare.npi`) with deterministic (tier-1) `tier_plan`s; disabling it removes them — proving vertical pluggability with no pipeline change (substrate §3 payoff 1).
  - A field-key absent from the registry, or two packs contributing an irreconcilable `tier_plan` with no override, causes `compile` to **fail with a diagnostic**; no partial plan is emitted.
  - Per-ICP override of a field's `tier_plan` wins over the pack default in the compiled plan (precedence rule verified).
- **Out of scope:** implementing the resolvers / running the waterfall (M4); selecting which sources within a tier to call at runtime — the Source Planner (M4, staged-flow §7d); computing scores (M6, M3.4); the field registry table itself (M1.3); proposing the ICP (M5).
- **Open decisions:** **D7 (economics)** — the `scoring`/`deep` partition this compiler emits *is* the cost dial's "what runs on whom" (Doc C §5); proceed on the recommended two-pass default and keep the partition data-driven so confirming D7 (budget bands, % that goes deep) needs no compiler change. **D3 (personal-data posture)** — `contact.facet.*` fields carry their Doc D use-gate marker through the plan's `gate` field; the compiler propagates it, M10 enforces it. Surface, do not hardcode.

### M3.3 — Industry packs framework (field set + source profile, namespaced)
- **Purpose:** The platform must "handle different deterministic fields per client industry without per-client schema changes" (CLAUDE.md; substrate §3 payoff 1). Industry packs are how a vertical is added by **registration, not enumeration** (conventions §2/§3). Crucially, staged-flow §9 establishes that **packs carry two prior sets**: the **field set** (what to know — `<pack>.*` field-keys + their `field_definition`s) *and* the **source profile** (where to look — per-field-class source priors/weights for the Source Planner, staged-flow §7c). This issue delivers the framework that registers, validates, and serves both halves of a pack, so M3.2 can compose pack field sets into a plan and M4's Source Planner can read pack source profiles — without forking the pipeline for a new vertical.
- **Architecture sources:** substrate §3 payoff 1 (vertical pluggability: "NPI registry becomes a resolver that only activates for healthcare ICPs; adding a vertical = registering resolvers + field definitions, not forking the pipeline"), §1 (per-vertical fields are just `field_definition` rows); staged-flow §7c (source profiles per ICP/per pack — the `frontier_ai`/`healthcare_practice`/`data_infra` examples), §9 ("packs now carry two prior sets: the field set and the source profile"); Doc C §2 (`account.resonance.*`, `contact.facet.*` are registered, not enumerated); conventions §3 (`<pack>.*` namespace), §2 (open-by-registration).
- **Scope / deliverables:**
  - A **pack catalog** + registration mechanism: each pack registers under a namespace prefix (conventions §3, e.g. field-key namespace `healthcare` for pack `healthcare_practice`, `frontier_ai`, `data_infra`) and declares two prior sets:
    - **field set** — the `<pack>.*` `field_key`s the pack contributes, each with its `field_definition` (type, validation, `tier_plan`, `freshness_ttl`, `pass`, `gate`) registered into the M1.3 field registry (the pack is the *author* of these registry rows). Resonance/facet field-classes (Doc C §2) are registered here for packs that need them, never enumerated in code.
    - **source profile** — per-field-class source priors: an ordered/weighted set of source keys (the `source_manifest.source_key` space from M4, staged-flow §7a) per field-class, with weights ("arXiv high, Glassdoor low" — staged-flow §7c). This is config the Source Planner (M4) reads; M3.3 stores and serves it, M4 consumes it.
  - **Worked starter packs** (at least the three in staged-flow §7c) as data, not code: `frontier_ai`, `healthcare_practice`, `data_infra` — each with a field set and a source profile — to prove the framework end-to-end and to seed M3.2 tests.
  - **Per-client overrides:** a client/ICP may override a pack's source-profile weights or field selections (staged-flow §7c "overridable per client"); overrides are versioned config layered over the pack default, resolved deterministically (override > pack default), and referenced from the ICP spec (M3.1).
  - **Pack composition rules:** enabling multiple packs on one ICP composes their field sets (dedup) and source profiles; precedence/conflict rules align with M3.2's compile-time precedence so the two stay coherent.
  - **Catalog read API:** list packs, fetch a pack's field set, fetch a pack's source profile (resolved with client overrides), validate that a pack's registered fields exist in the registry.
- **Interface / seam:**
  - **Exposes:** the pack catalog contract — `list_packs()`, `get_pack_field_set(pack_key)`, `get_pack_source_profile(pack_key, client_id?)`, `validate_pack(pack_key)`. The **field set** half is consumed by M3.2 (composed into the field plan); the **source profile** half is consumed by M4's Source Planner (staged-flow §7d). Two distinct seams so a pack's "what to know" and "where to look" evolve independently.
  - **Consumes:** the M1.3 field registry (packs register `field_definition` rows into it; the registry remains the system of record for field definitions — packs are *authors*, not a parallel store, preserving DRY per conventions §2). The `source_manifest.source_key` namespace from M4 (a source profile references source keys M4 owns); M3.3 stores references, M4 owns the manifests — so a source being added/removed in M4 does not require a pack code change.
  - **Swap note:** packs are pure data/config; the registration framework is the only code. Source profiles are *priors that the learning loop (staged-flow §7e, Doc C §6) reweights from measured yield* — that reweighting writes back through the same source-profile config behind this seam, so the learning loop (M13) is a config writer, not a framework change. New vertical = new pack rows, never a pipeline fork.
  - **Boundary note (DRY):** M3.3 does not define `source_manifest`, modality adapters, or the Source Planner (all M4). It stores *source-profile priors* that reference M4's source keys. It does not own the field registry table (M1.3); it registers rows into it.
- **Data model / schema:** new `pack` catalog + `source_profile` config tables (owned here). Packs author rows into `field_definition` (M1.3, conventions §4) under the `<pack>.*` namespace (conventions §3). Source profiles reference `source_manifest.source_key` (conventions §4, owned by M4). Per-client overrides are versioned config rows referenced from `icp_spec` (M3.1).
- **Dependencies:** depends on **M1** (M1.3 field registry — packs register field definitions into it). Has a *namespace* dependency on **M4** (`source_manifest.source_key` space) but is not blocked by M4 for the field-set half; the source-profile half is authored against M4's key namespace and **unblocks M4** (the Source Planner reads pack source profiles). Blocks **M3.2** (compiler composes pack field sets) and **M3.1** (ICP spec validates enabled packs against the catalog). Source-profile reweighting is later wired by **M13** (learning loop).
- **Acceptance criteria:**
  - Registering a new pack (e.g. `healthcare_practice`) adds its `<pack>.*` field definitions to the M1.3 registry and its source profile to the catalog, with **no pipeline/code change** beyond the pack registration (vertical pluggability proven, substrate §3 payoff 1).
  - `get_pack_field_set("healthcare_practice")` returns `<pack>.*` fields (e.g. `healthcare.npi`) with tier-1 `tier_plan`s; `get_pack_source_profile("healthcare_practice")` returns the staged-flow §7c priors (NPI/CMS high, reviews high, journals low).
  - The three starter packs (`frontier_ai`, `healthcare_practice`, `data_infra`) load as data and reproduce their staged-flow §7c source-profile weight orderings.
  - A per-client override of a pack source-profile weight resolves as override > pack default and is versioned (the base pack profile is unchanged and re-readable).
  - Enabling two packs on one ICP composes their field sets with dedup and exposes both source profiles; a `field_key` defined by two packs resolves by the documented precedence (consistent with M3.2).
  - `validate_pack` fails if a pack references a `field_key` not registered or a `source_key` not in M4's manifest namespace, naming the offender.
  - A resonance/facet field-class (`account.resonance.*` / `contact.facet.*`) can be contributed by a pack via registration without code enumeration (Doc C §2).
- **Out of scope:** the `source_manifest` schema, modality adapters, and the Source Planner (M4, staged-flow §7a/b/d); executing resolvers (M4); the source-profile *learning/reweighting loop* (M13, staged-flow §7e / Doc C §6 — M3.3 provides the writable config it targets); the field registry table itself (M1.3); the use-gate enforcement for governed packs (M10, Doc D).
- **Open decisions:** **D3 (personal-data posture)** — packs that contribute `contact.facet.*` fields register them with their Doc D use-gate marker on the `field_definition.gate`; the posture (conservative / gather-broadly-gate-at-use / professional-only, Doc D §6) is per-client config enforced in M10, not baked into the pack. **D8 (2026 legal specifics)** — source profiles may need per-jurisdiction source exclusions later; the override mechanism is the hook, so resolving D8 needs no framework change. Surface, do not hardcode.

### M3.4 — Scoring rubric model (fit + intent weights)
- **Purpose:** The market's own critique is that a single opaque "87/100" tells a rep nothing; multi-dimensional, **explainable** scoring is the standard and the differentiator (substrate §9; conventions anti-patterns). This issue defines the **versioned scoring-rubric data model** — the structured fit + intent weights over the active fields (staged-flow §2; Doc B §3; overview §1 Output 1) — and the pure, provenance-aware **score function spec** that consumes it, so that every score decomposes into inspectable Fit and Intent sub-scores each traceable to the claims behind it (substrate §9; the `account_handoff.fit_score/intent_score` "decomposed, each linked to claims" of conventions §4). It is the model and contract only; M6 wires it to live claims at Pass A.
- **Architecture sources:** substrate §9 (decompose Fit / Intent; provenance-backed; explainable; the feedback loop is labeled training data), §3 payoff 2 (two-pass: scoring fields feed the rubric); staged-flow §2 (scoring rubric = fit + intent weights over active fields), §4 (Pass A computes provisional fit + intent → tiering); Doc B §3 (rubric proposed at ICP synthesis), §4 (import back-scoring uses the same rubric); Doc C §1 (cheap proxies are the deterministic inputs to Pass A scoring), §5 (tiering = where economics live); overview §1 (Output 1), §3 (`account_handoff` decomposition); conventions §4 (`account_handoff`).
- **Scope / deliverables:**
  - A versioned `scoring_rubric` model referenced as a slot in the ICP spec (M3.1):
    - **Fit** sub-rubric — weighted contributions over `core.*`/`account.*`/`<pack>.*` firmographic/technographic/vertical fields (substrate §9; Doc B §3 firmographic + technographic dimensions); each entry = `(field_key, weight, scoring_transform, match_predicate)`.
    - **Intent** sub-rubric — weighted contributions over the `scoring`-tagged signal **proxies** (Doc C §1: job-count delta, recent-funding event, headcount growth — tier-1 deterministic); same `(field_key, weight, transform)` shape.
    - Aggregation rules: how field contributions combine into a Fit sub-score and an Intent sub-score, kept **separate and inspectable** (substrate §9 — never collapse into one number), plus optional normalization and the default **tier-cutoff** thresholds Pass A proposes (staged-flow §4; the human adjusts cutoffs, not the rubric, at the checkpoint).
    - **Explainability contract:** the score output must enumerate, per sub-score, each contributing `(field_key, claim_id, value, weight, contribution)` so the score is "trending because eng hiring +40% and two committee members are new" (substrate §9) — i.e. every score links to its evidence, satisfying the `account_handoff` "decomposed, each linked to claims" requirement (conventions §4).
  - A **pure score-function spec** `score(rubric, current_values) -> {fit_score, intent_score, contributions[]}` defined over `current_value(entity, field)` (conventions §4; M1) — deterministic, no LLM, evidence-linked. (M3.4 specifies and unit-tests this against fixtures; M6 executes it on the live claim store at Pass A.)
  - **Handling of missing/stale/low-confidence inputs:** an absent or stale `current_value` (per the field's `freshness_ttl`, M1) contributes per an explicit, configured rule (e.g. zero contribution + a `missing`/`stale` flag in `contributions[]`), never a fabricated default — consistent with empty-is-correct (conventions §5).
  - **Disposition-feedback hook (model only):** the rubric model reserves the structure for reweighting from labeled accept/reject dispositions (substrate §9; staged-flow §7e), captured as a new rubric *version* — M3.4 defines the versioned target; M13 implements the loop.
- **Interface / seam:**
  - **Exposes:** the `scoring_rubric` contract (slot of the ICP spec) and the `score(rubric, current_values)` function signature + its decomposed, claim-linked output. This is the single contract M6 (Pass A) and the `account_handoff` builder (M12) read for fit/intent and their decomposition. Default tier cutoffs are exposed but adjustable at the human checkpoint (M6/M7) without editing the rubric.
  - **Consumes:** `current_value(entity, field)` (conventions §4; M1) as its only data input — so the rubric is decoupled from how claims are produced (any resolver/source in M4 feeding the same `field_key` works unchanged). It consumes the `field_plan`'s `scoring_fields` set (M3.2) to know which proxies are available as inputs.
  - **Swap note:** the rubric is **data, not code** (conventions §2): per-ICP, versioned, swappable. The score function is pure and side-effect-free, so swapping the aggregation algorithm (e.g. linear weights → a learned model from the disposition loop, M13) stays behind `score(...)`; the explainability output contract (per-field `claim_id` contributions) is preserved across any such swap so traceability is never lost. Because it reads `current_value`, a Postgres→Temporal state-machine change (conventions §2/§6) is invisible to scoring.
  - **Boundary note:** M3.4 owns the rubric *model and the scoring contract*; it does **not** run Pass A, assign tiers on live data, or own the human cutoff UI (M6/M7).
- **Data model / schema:** new `scoring_rubric` versioned config (referenced as a slot by `icp_spec`, M3.1). Reads `current_value` / `claim` (conventions §4; M1) at score time. Produces decomposed fit/intent + `contributions[]` (each linking a `claim_id`) that feed `account_handoff.fit_score`/`intent_score` (conventions §4; assembled in M12). No claim-store schema changes.
- **Dependencies:** depends on **M3.1** (rubric is a slot of the ICP spec), **M3.2** (knows which `scoring_fields` are inputs), and **M1** (`current_value`, `claim`). Blocks **M6** (Pass A executes `score`), and is consumed downstream by **M12** (handoff embeds decomposed scores) and **M13** (disposition reweighting writes new rubric versions). It is a model/spec, so it does not block M4.
- **Acceptance criteria:**
  - A rubric defines Fit and Intent as separate weighted sub-rubrics over named `field_key`s; the score output returns `fit_score` and `intent_score` as distinct values (never a single collapsed number — substrate §9).
  - `score(rubric, current_values)` is pure and deterministic on fixtures and returns a `contributions[]` enumerating, per sub-score, `(field_key, claim_id, value, weight, contribution)`; every nonzero contribution links to a real `claim_id` (provenance-backed, conventions §4 / substrate §9).
  - A missing or stale `current_value` contributes per the configured rule (e.g. zero + flagged `missing`/`stale`), never a fabricated default; the flag appears in `contributions[]`.
  - Intent inputs are the `scoring`-tagged deterministic proxies from M3.2/Doc C §1 (e.g. job-count delta, recent funding); a `deep`-tagged narrative field is **not** an Intent input at Pass A.
  - Editing weights produces a new rubric **version** (append-only, like M3.1); a campaign pinned to a prior version re-scores identically.
  - Default tier cutoffs are emitted with the score distribution and are adjustable at the checkpoint (M6) without mutating the rubric version.
  - Re-scoring the same entity with the same rubric version and the same `current_values` yields identical scores and identical contribution provenance (reproducibility).
- **Out of scope:** running Pass A on the live list and assigning tiers (M6, staged-flow §4); the human tier-cutoff checkpoint UI and pause/resume (M6/M7, substrate §10); implementing the disposition-feedback **reweighting** loop (M13, substrate §9 / staged-flow §7e — M3.4 only defines the versioned target and the explainability contract it must preserve); computing intent *narratives* (Pass B / M8); the source-profile learning loop (M13).
- **Open decisions:** **D7 (economics)** — tier cutoffs gate how many accounts go to expensive Pass B, so the rubric's cutoff defaults interact with budget bands; proceed on the recommended client-adjustable-cutoffs default (Doc C §5) and keep cutoffs data-driven so confirming D7 needs no model change. **D6 (import non-fit behavior)** — the same rubric back-scores imported accounts (Doc B §4); the recommended flag-and-proceed surfaces low-fit imports with their `contributions[]` evidence, requiring no rubric variant. Surface, do not hardcode.
