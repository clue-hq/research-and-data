## Goal & scope of this milestone

This milestone builds the **output edge** of the research subsystem — the last layer before the boundary the architecture pins in overview §3. It turns the verified substrate (account claims, the resonance layer, the identity-resolved & governed buying committee, decomposed fit/intent scores) plus the **Client Knowledge Base** (Doc B §2/§5) into the subsystem's actual product: **Output 4 — a persona-keyed, evidence-backed claim bundle + grounded value narrative** (overview §1), assembled into the canonical `account_handoff` contract object (overview §3, conventions §4) and exposed across a stable seam to the downstream **content layer**.

It delivers three things, in dependency order:

1. **M12.1 — the positioning step** (substrate §8): a bounded graph node that joins *verified account claims × client capabilities* into a per-`(account, persona)` **value narrative**, where each narrative line is *itself a claim-with-provenance* pointing at both the account evidence and the client-knowledge evidence. This is the synthesis the whole subsystem exists to produce — the "ammunition," not raw facts.
2. **M12.2 — the `account_handoff` contract object + provenance index**: a deterministic assembler/serializer that gathers Outputs 1–4 for a single high-tier account into the exact shape conventions §4 / overview §3 fix, with a `provenance_index` that makes "every line is sourced" literally true and traversable.
3. **M12.3 — the output/handoff API**: the boundary seam to the content layer — a read API (and an emit/notify path) over `account_handoff` objects, the precise place where this subsystem *ends* (overview §3, the recommended D1 boundary: research stops at the value narrative).

**Where it sits in the end-to-end map (overview §2 / staged-flow §10):** strictly *after* Pass B deep profiling (M8) and the verification layer (M9), and it consumes the Client Knowledge Base produced by Stage 0 (M5). It is the box labelled `OUTPUT persona-keyed claims + grounded value narrative → [ Content layer → Design subsystem ]`.

**Explicitly NOT in this milestone:**
- The **content schema / content** (mailer headline/body/CTA slots, landing-page sections, ad copy) — owned by the **downstream content layer, not this repo** (overview §3, D1 recommended boundary). M12 stops at *verified meaning*.
- The **design subsystem** and its actual ingest interface (overview §3 open dependency, D2) — lives in its own repo; this repo does not touch it.
- The **human review surface** over the handoff and the **disposition feedback loop** — owned by **M13** (Review, Feedback & Observability). M12 produces the object M13 reviews; it does not build the review UI.
- The **resonance and facet collectors / synthesis** themselves (`account.resonance.*`, `contact.facet.*`) — produced upstream by **M8** and gated by **M9/M10**. M12 only *reads* the verified, gated current values.
- **Tier-4 synthesis plumbing** (Exa Deep / Parallel Task resolvers) — owned by **M11**. The positioning step is a synthesis step but it runs *over already-verified claims*, behind the same faithfulness judge seam (M9.3), not a new resolver.

## Issues

### M12.1 — Positioning step (account claims × client knowledge → per-persona value narrative as a provenance-backed claim)

- **Purpose:** Every downstream artifact must answer "how does *our client's* product benefit *this* account, for *this* persona" — and the architecture's core bet forbids us from producing that as an untyped, after-the-fact dossier (substrate §0, §6). The positioning step (substrate §8) is the dedicated graph node that synthesizes the **value narrative** (Output 4, overview §1/§3): it joins the verified account picture (operational pain, strategic moves, and the `account.resonance.*` emotional register — Doc C §2) with the client's capabilities, differentiators and proof points from the **Client Knowledge Base** (Doc B §2/§5), and emits, *per `(account, persona)`*, the grounded argument for why the client matters and which angle to take. The non-negotiable discipline: each narrative line is **itself a claim-with-provenance** (substrate §8 — "its outputs are themselves claims with provenance pointing at both the account evidence and the client-knowledge source"), so the narrative is verifiable by the same machinery as every other claim, never a free-text blob.
- **Architecture sources:** substrate §8 (positioning step as its own graph node; outputs are provenance-backed claims pointing at both sides), overview §1 (Output 4 — facts *plus the argument*, per persona, sourced on both sides), overview §3 (`value_narrative[]` row shape: `claim_id, persona, argument, supporting{account_evidence_ids[], client_knowledge_ids[]}`), substrate §7 (persona keys — content keys on `(account, persona)`; economic buyer argues ROI, technical evaluator argues architecture), substrate §6 (faithfulness judge — synthesized claims are entailment-checked), substrate §5b (artifact pattern — return claim references, not blobs), Doc C §2 (`account.resonance.*` feeds the narrative's emotional register, not just ROI math), Doc B §2/§5 (Client Knowledge Base is the client side of every narrative; versioned), Doc D §3 / M10 (the use-class governing personal hooks that may flavor a persona angle).
- **Scope / deliverables:**
  - A **positioning graph node** (LangGraph node, runs inside the per-account graph from M7.1 *after* M8/M9 complete for the account, OR as a standalone post-verification step keyed on `(account_entity_id, icp_spec_version)`), invoked once per high-tier account.
  - **Inputs assembled deterministically (no free-text):** (a) the account's verified `current_value` set for narrative-relevant fields — `account.operational_pain`, `account.strategic_moves`, `account.resonance.*` (read via M1.2 merge view; verified-only per M9); (b) the committee with personas (M8.3); (c) the **Client Knowledge Base** retrieval (M5.1) over pgvector for capabilities/differentiators/proof points relevant to the account's pains.
  - **Per-`(account, persona)` synthesis:** for each committee persona present (champion / economic_buyer / technical_evaluator / blocker), produce one or more `value_narrative` claims — the grounded argument shaped to that persona's lens. The synthesis LLM call is issued through the shared OpenRouter `LLMGateway` (M0.4), with the model id and positioning prompt as versioned config.
  - **Each narrative claim is written to the claim store** as a tier-4 claim with `field_key = account.value_narrative` (a new registered field-class in M1.3, namespaced under `account.*`; persona carried in `value_json`), `entity_type = account`, `extraction_method = llm_synthesis`, mandatory `evidence_span`, and `supporting` pointers to **both** `account_evidence_ids[]` (the source claim ids it argues from) and `client_knowledge_ids[]` (the Client Knowledge Base claim/chunk ids it draws on).
  - **Faithfulness gate reuse:** every narrative claim passes the **M9.3 faithfulness judge** behind its existing seam — the judge scores whether `argument` is entailed by its cited account-evidence and client-knowledge spans; unsupported → reject (leave the persona angle empty, which is correct output) and optionally re-synthesize. No new judge is built here.
  - **Use-class respect:** any personal hook (a `contact.facet.*` claim) that the narrative leans on must already have cleared **both** M10 gates (strong identity-binding + allowed use-class for jurisdiction × client policy). The positioning step **reads only promoted/cleared facets**; it never re-derives or re-gates, and it never strengthens a weak-binding or disallowed claim into an argument.
  - **Prompt/config as data:** the positioning prompt, per-persona argument templates, and the field-relevance map (which fields feed which persona) are versioned config the node reads (conventions §2 "policy is data"), not hardcoded.
  - **Coverage handling:** if the Client Knowledge Base is too thin to ground an argument for a persona, emit an explicit empty/low-coverage flag on that `(account, persona)` (substrate §8 quality-ceiling note; Doc B §2 quality-ceiling note; conventions §5 universal rule — empty-flagged is correct, fabricated is the failure).
- **Interface / seam:**
  - **Exposes:** a `Positioner` (or `PositioningStep`) callable — `position(account_entity_id, icp_spec_version) -> list[ValueNarrativeClaim]` — that writes `account.value_narrative` claims to the store and returns references (claim ids), not blobs (substrate §5b artifact pattern). Consumed by M12.2 (the assembler reads these claims) and, after assembly, by M13's review surface.
  - **Consumes:** the **claim store + `current_value` merge view** (M1.1/M1.2) for verified account claims; the **Client Knowledge Base retrieval** seam (M5.1, over pgvector); the committee + personas (M8.3); the **faithfulness-judge seam** (M9.3); the **use-gate result** (M10.3) as a precondition on facet inputs.
  - **Replaceability:** the synthesis engine behind `Positioner` is swappable (a different LLM model id behind the M0.4 OpenRouter gateway, an Exa-Deep-style grounded synthesizer from M11, or a future template-only renderer) without changing the output contract, because the output is always `account.value_narrative` claims with the fixed `supporting` shape. The judge model swaps behind M9.3. The Client Knowledge Base store swaps behind the M5.1 retrieval seam. Nothing downstream knows which model wrote the argument.
- **Data model / schema:**
  - New registered field-class (M1.3 row, not a hardcoded enum): `account.value_narrative` — `value_json` carries `{persona, argument, angle_label}`; tier-4; `pass = deep`; `gate = faithfulness + evidence_span required`.
  - Extends the conventions §4 **`claim`** contract: a value-narrative claim is a normal claim row (append-only, supersede on re-synthesis) with `extraction_method = llm_synthesis`, mandatory `evidence_span`, and `supporting` provenance captured as `account_evidence_ids[]` + `client_knowledge_ids[]` (stored in `value_json` or a sidecar `claim_support` link table keyed on the narrative `claim_id`). Maps 1:1 onto the overview §3 `value_narrative[]` row (`claim_id, persona, argument, supporting{...}`).
  - Reads (does not redefine): conventions §4 `current_value`, `account_entity`, the committee/persona claims (`contact.persona`, `contact.role_on_committee`), the versioned **ICP spec** (a narrative is scoped to the ICP that produced the account's scoring rubric), and the **Client Knowledge Base** (Doc B §5).
- **Dependencies:** **M5** (Client Knowledge Base must exist — the client side of every narrative), **M8** (account profile + resonance + committee/persona claims to argue from), **M9** (only verified claims feed the narrative; faithfulness judge gates the synthesis). Soft: **M7.1** (runs as a graph node) and **M10** (use-gated facets). **Unblocks:** M12.2 (assembler reads value-narrative claims), and via M12.2/M12.3 the entire downstream content layer.
- **Acceptance criteria:**
  - For a high-tier account with ≥1 committee persona, the step produces ≥1 `account.value_narrative` claim per persona present, each with a non-empty `argument`, a non-empty `evidence_span`, **and** at least one id in *both* `account_evidence_ids[]` and `client_knowledge_ids[]` (a narrative line with zero account evidence OR zero client evidence is rejected, not stored as `verified`).
  - Every produced narrative claim is `extraction_method = llm_synthesis`, tier-4, and is run through the M9.3 faithfulness judge; a synthesized argument whose `evidence_span` does not entail it is **not promoted past `unverified`** (test with a deliberately ungrounded argument).
  - Personas are correct: the economic_buyer narrative and the technical_evaluator narrative for the same account differ in angle (testable via the `angle_label` and that they cite different supporting evidence), confirming `(account, persona)` keying (substrate §7).
  - The step **never invents** account facts or client capabilities: every `account_evidence_id` resolves to a real verified account claim and every `client_knowledge_id` resolves to a real Client Knowledge Base entry (referential-integrity test; dangling ids fail the build).
  - A facet-derived hook only appears in an argument if its source claim has `identity_binding = strong` AND a use-class allowed by the account's jurisdiction × client policy (test with a weak-binding and a `sensitive` facet — both must be absent from any argument).
  - When the Client Knowledge Base lacks grounding for a persona, the step emits a low-coverage flag for that `(account, persona)` rather than a fabricated argument.
  - Re-running the step on the same `(account_entity_id, icp_spec_version)` supersedes prior narrative claims rather than duplicating them (append-only + supersede).
  - The positioning prompt/templates and field-relevance map load from versioned config; swapping them changes output without code changes.
- **Out of scope:**
  - Producing content-schema slots / artifact copy — **content layer (not this repo)**.
  - Building the resonance or facet claims themselves — **M8**; gating them — **M9/M10**.
  - Building the faithfulness judge or the tier-4 synthesis resolvers — **M9.3 / M11** (this step *reuses* them).
  - The human review of narratives — **M13.1**.
- **Open decisions:**
  - **D1 (output boundary):** this issue *is* the implementation of the recommended boundary — research stops at the value narrative (overview §3). Built so that if D1 later narrows to "claims only," the positioning step can be disabled at config without affecting M12.2's ability to emit a claims-only handoff; if D1 widens to "through content schema," that work lands in the content layer, not here.
  - **D3 (personal-data posture):** the facets a narrative may lean on depend on the per-client posture (Doc D); the step reads M10's gate result and does not hardcode the posture.
  - **D5 (ICP multiplicity):** a narrative is scoped to `icp_spec_version`; an account targeted under multiple ICPs gets a narrative per ICP. Proceed on the recommended multi-ICP default (Doc B §3) without hardcoding single-ICP.

### M12.2 — `account_handoff` contract object + provenance index

- **Purpose:** The four required outputs (overview §1) are scattered across the substrate as claims (scores in M6/M9, account profile + resonance in M8, committee + governed contact claims in M8/M10, value narrative in M12.1). The boundary the subsystem ends at (overview §3) requires them **assembled into one canonical, deterministic object per high-tier account** — the `account_handoff` (conventions §4) — with a `provenance_index` that makes the marketing-grade promise literally true: *"every fact in this report links to its source."* This issue builds the **deterministic assembler/serializer** (not an agent) that gathers the current verified truth into the exact shape conventions §4 / overview §3 fix, and the provenance index that lets any consumer walk from any value back to its source claim, span, and tier. Like `current_value` (substrate §1), assembly is a **pure function over the claim store**, so the handoff is reproducible and auditable, never re-synthesized.
- **Architecture sources:** overview §3 (the `account_handoff` contract object, field-by-field, incl. `provenance_index`), conventions §4 (`account_handoff` canonical contract — reference, do not redefine), overview §1 (the four outputs that populate it), substrate §1 (`current_value` as a pure merge policy — the assembler reads from it), substrate §9 (decomposed, provenance-backed fit/intent — each sub-score links to its claims), substrate §6 (only verified claims are eligible for the handoff), Doc D §1/§3/§7 (each committee `profile_claim` carries `identity_binding` + `use_class`; every contact claim crossing the handoff carries both so the content layer can see why a hook is usable), Doc B §4 (import non-fit flag-and-proceed — D6; the misfit flag travels with the fit score), Doc C §7 (coverage confidence, not completeness).
- **Scope / deliverables:**
  - An **`account_handoff` assembler** — `assemble(account_entity_id, icp_spec_version) -> AccountHandoff` — a pure, deterministic read over the claim store and merge view that builds the exact conventions §4 object:
    - `account_entity_id`;
    - `fit_score`, `intent_score` — **decomposed** into their sub-scores, each linked to the claim ids that produced it (substrate §9 — "trending because eng hiring +40% and two committee members are new"); carry any import non-fit flag alongside the fit score (Doc B §4 / D6);
    - `account_profile_claims[]` — verified, sourced account claims incl. `account.resonance.*` (Output 2), each as `{value, evidence_span, source_tier, source_url, confidence, freshness}`;
    - `committee[]` — per contact `{contact_entity_id, persona, role_on_committee, profile_claims[]{value, evidence_span, source_tier, identity_binding, use_class}}` (Output 3; each contact claim carries `identity_binding` + `use_class` per Doc D §7 so the consumer can see why a hook is or isn't usable; only `strong`-binding + use-allowed claims are flagged outreach-eligible, with disallowed/weak claims either excluded or explicitly marked non-usable per M10);
    - `value_narrative[]` — the M12.1 claims as `{claim_id, persona, argument, supporting{account_evidence_ids[], client_knowledge_ids[]}}` (Output 4);
    - `provenance_index` — see below.
  - The **`provenance_index`**: a complete map from every value appearing anywhere in the object (each score sub-component, each profile claim, each committee profile claim, each narrative line) → its backing `claim_id` → `{source_url, source_tier, evidence_span, extraction_method, observed_at, collected_at, corroborations, confidence}`. Guarantees every line is traceable to a real claim row; an entry that cannot resolve is a build failure, not a silent omission.
  - **Verified-only filter:** the assembler includes only non-superseded claims that clear the verification bar appropriate to their field (M9): tier-4 claims without an `evidence_span` and weak-binding/disallowed personal claims are excluded from the outreach-eligible surface (conventions §5, Doc D). Excluded-but-present-as-flagged is preferred over silent drop where the consumer benefits from knowing a field was attempted (conventions §5 universal rule).
  - **Conflict & coverage surfacing:** where `current_value` raised a conflict flag (two tier≤2 sources disagree, substrate §1) the handoff carries that flag through; where coverage is low (M6.5 coverage-confidence / M12.1 thin-narrative flag) the handoff carries the estimate/flag — the subsystem reports coverage confidence, not a completeness guarantee (Doc C §7).
  - **Versioned & reproducible:** the object is stamped with `icp_spec_version`, `project_run_id`, and an `assembled_at`; re-assembly over the same claim state yields a byte-stable object (deterministic).
  - **Serialization:** a typed, versioned schema (JSON Schema / Pydantic in the shared package, M0.2) for `AccountHandoff` so producers and consumers share one definition (DRY).
- **Interface / seam:**
  - **Exposes:** the typed `AccountHandoff` object + a `HandoffAssembler.assemble(account_entity_id, icp_spec_version)` pure function. This is the **single canonical representation** of the subsystem's output; M12.3 serves it and M13 reviews it.
  - **Consumes:** the claim store + `current_value` (M1.1/M1.2); the decomposed scores (M6.3 Pass A / scoring provenance); the committee + governed contact claims (M8.3/M8.4 + M10); the value-narrative claims (M12.1); the verification status of each claim (M9).
  - **Replaceability:** because assembly is a pure function over the claim store, the *internals* (how scores were computed, which model wrote the narrative, which resolver filled a field) are invisible across this seam — the handoff shape is the contract. Swapping any upstream producer (Clay→direct API, a judge model, Postgres state machine→Temporal) leaves `account_handoff` unchanged. The serialization schema is versioned so the contract can evolve additively without breaking consumers.
- **Data model / schema:**
  - Implements the conventions §4 **`account_handoff`** contract verbatim (extends, never contradicts). May add `icp_spec_version`, `project_run_id`, `assembled_at`, `coverage_confidence`, and per-field `conflict_flag` columns/keys.
  - Reads conventions §4 `claim`, `current_value`, `account_entity`, committee/persona/contact-facet claims (with `identity_binding`, `use_class`), the decomposed scoring claims, and the M12.1 `account.value_narrative` claims.
  - Persistence: either materialized as a row in an `account_handoff` table (JSONB payload + key columns) for fast serve and audit, or computed on read — recommended **materialize on assembly, recompute on supersede** so the served object is stable and the provenance index is precomputed; Postgres remains the only source of truth (conventions §6, substrate §12).
- **Dependencies:** **M12.1** (value-narrative claims to embed), **M8** (account profile, committee, contact claims), **M9** (verification status that gates inclusion), **M5** (the Client Knowledge Base ids the narrative `supporting` points at must resolve). Soft: M6 (scores), M10 (use_class/identity_binding on committee claims). **Unblocks:** **M12.3** (the API serves this object), **M13** (the review surface and disposition loop operate over it).
- **Acceptance criteria:**
  - `assemble()` over a fully-profiled, verified high-tier account returns an object that **validates against the `AccountHandoff` schema** and populates all five conventions §4 sections (scores, account profile claims, committee, value narrative, provenance index).
  - **Every** value in the object — each fit/intent sub-component, each account profile claim, each committee profile claim, each value-narrative line — has a resolvable `provenance_index` entry pointing at a real, non-superseded `claim` row with a `source_url`/`source_tier` (and, for tier-4, an `evidence_span`). A value with no provenance entry fails the build (this is the literal "every line is sourced" test).
  - Scores are **decomposed**: `fit_score` and `intent_score` expose their sub-scores and each sub-score lists the claim ids behind it (substrate §9); an opaque single number fails the test.
  - Each committee `profile_claim` carries `identity_binding` and `use_class` (Doc D §7); a weak-binding or use-disallowed personal claim is **not** present in the outreach-eligible set (Doc D, conventions §5). Test with a weak-binding claim and a `sensitive` claim — both absent from outreach-eligible.
  - Assembly is **pure & deterministic**: two `assemble()` calls over an unchanged claim state produce equal objects; no LLM call occurs inside the assembler (it reads, it does not synthesize).
  - `current_value` conflict flags and low-coverage flags propagate into the handoff rather than being silently resolved (test with a planted tier≤2 conflict).
  - An imported account flagged non-fit during back-scoring carries that flag with its fit score in the handoff (Doc B §4 / D6); it is surfaced, not silently dropped.
  - Re-assembly after a claim is superseded reflects the new current truth and stamps a new `assembled_at`.
  - The object is scoped to `(account_entity_id, icp_spec_version)`; an account under two ICPs yields two distinct handoffs.
- **Out of scope:**
  - Serving the object over a network / auth — **M12.3**.
  - Computing scores, profiling, verification, or narrative synthesis — **M6/M8/M9/M12.1** (the assembler only reads results).
  - The review/correct/reject workflow over the object — **M13.1**.
  - Mapping the handoff into any content-schema or design-template shape — **content layer / design subsystem (not this repo)**.
- **Open decisions:**
  - **D1 (output boundary):** the object implements the recommended boundary (claims + value narrative). It is structured so a "claims-only" configuration simply omits `value_narrative[]` while the rest stays valid — the boundary is a config of *which sections populate*, not a fork.
  - **D2 (design-subsystem ingest):** the handoff is the subsystem-side contract; what the design system *actually* ingests (and whether a content layer sits between) is unresolved (overview §3). Keep `account_handoff` design-agnostic (verified meaning, not artifact slots) so any content layer can adapt it.
  - **D6 (import non-fit behavior):** the non-fit flag travels with the fit score in the handoff (flag-and-proceed, Doc B §4); the handoff surfaces it rather than excluding the account.
  - **D7 (economics):** `coverage_confidence` and the conflict flags surface the cost/quality trade so the client-facing cost surface (M13.4) and the recommended client-facing transparency posture (Doc C §5) can read them; the budget bands themselves are not decided here.

### M12.3 — Output / handoff API (boundary to the content layer)

- **Purpose:** This is the **exact place the research subsystem ends** (overview §3). Everything upstream exists to produce `account_handoff` objects; this issue exposes them across the **one stable seam** to the downstream content layer (and, through it, the already-built design subsystem). It must be a *narrow, replaceable* contract — the content layer must know nothing about how research was done, only how to read a verified, persona-keyed, fully-sourced handoff. Because the architecture's strongest sales line is "every fact links to its source," the API must serve the `provenance_index` alongside the values, and because Postgres is the only source of truth (conventions §6, substrate §5c/§12), the API is a *read/emit* projection over the claim store — never a write-back path from content/design into research.
- **Architecture sources:** overview §3 (the output contract & boundary; the recommended D1 boundary "research stops at the value narrative"; the §3 open dependency on D2 — what the design subsystem ingests), overview §2 (the `→ [ Content layer → Design subsystem ]` edge), substrate §12 (FastAPI lifespan pattern; Postgres-only source of truth), substrate §5c (never write-through the read-only projection), substrate §2 (cross-tenant reuse with tenant isolation), Doc C §4 (project-run state machine + `handoff` phase = the readiness gate), Doc C §6 (handoff is observable; verification health travels with the output), staged-flow §10 (handoff is the terminal phase before the content/design module).
- **Scope / deliverables:**
  - A **read API** over assembled handoffs (FastAPI, lifespan/`asynccontextmanager` per substrate §12):
    - `GET /project_runs/{project_run_id}/handoffs` — list ready handoffs for a run (filterable by tier, persona presence, verification health);
    - `GET /accounts/{account_entity_id}/handoff?icp_spec_version=…` — fetch one `account_handoff` (the M12.2 object), including the `provenance_index`;
    - `GET /accounts/{account_entity_id}/handoff/provenance/{claim_id}` (or the index inline) — resolve any value to its full provenance.
  - **Readiness/state contract:** a handoff is only servable once the account has passed verification (M9) and assembly (M12.2); the API exposes the handoff phase status (`handoff` phase of the project-run state machine, Doc C §4) so the content layer can poll/subscribe rather than guess.
  - **An emit/notify path** for push consumers: when the project-run reaches the `handoff` phase for an account (or batch), emit an event/webhook (or a durable outbox row) carrying `(project_run_id, account_entity_id, icp_spec_version, handoff_ref)` so the content layer can pull. **No content/design write ever flows back through this API into the research write path** (conventions §6, substrate §5c — "never write-through it").
  - **Versioned media type / schema negotiation:** responses carry the `AccountHandoff` schema version (M12.2) so the content layer pins a contract version; additive evolution does not break pinned consumers.
  - **AuthN/Z & tenancy:** tenant-scoped access (cross-tenant public claims are reusable in the store but a client's *assembled handoff* is tenant-private — substrate §2 cross-tenant rule); content-layer service auth (M0.4).

- **Interface / seam:**
  - **Exposes:** the HTTP read API + emit/notify path serving the M12.2 `account_handoff` object — the **terminal seam of the subsystem**. This is the boundary in overview §3; downstream owns everything past it.
  - **Consumes:** the M12.2 `HandoffAssembler` / materialized handoffs; the project-run state machine phase (Doc C §4 / M7.3) for readiness; the verification-health metrics (M9 / Doc C §6); auth/tenancy from M0.4; tracing from M0.5.
  - **Replaceability:** the content layer is coupled only to the versioned `account_handoff` schema and these endpoints — not to any resolver, model, judge, or store. The `HandoffPublisher` adapter lets the transport swap (pull/push/bespoke design-system adapter for D2) behind the seam. The Postgres state machine → Temporal migration (substrate §12) is invisible here because the API reads assembled objects, not workflow internals.
- **Data model / schema:** No new domain tables — serves the conventions §4 `account_handoff` (materialized by M12.2). May add an **outbox/event table** (`handoff_event`: `id, project_run_id, account_entity_id, icp_spec_version, handoff_ref, status, emitted_at`) for the durable emit/notify path (Postgres-backed, conventions §6). Reads the project-run phase (M7.3) and verification-health metrics (M9).
- **Dependencies:** **M12.2** (the object to serve — hard), **M9** (verification health + readiness gate), **M7.3** (project-run `handoff` phase for readiness/emit), **M0.4** (config/secrets/tenancy), **M0.5** (tracing/observability spans). **Unblocks:** the downstream **content layer** (not this repo) and, through M13.4, the client-facing handoff/progress surface.
- **Acceptance criteria:**
  - A content-layer consumer can `GET` a single account's handoff and receive a schema-valid `account_handoff` including a fully-resolvable `provenance_index` (every value → claim → source).
  - The list endpoint returns **only** handoffs whose account has reached the `handoff` phase (passed M9 verification + M12.2 assembly); an account still in `deep`/`verification` is **not** servable (test mid-run).
  - The emit/notify path produces a durable event per account reaching `handoff` (outbox row or webhook), carrying enough to fetch the object, and is **idempotent** on `(project_run, account, icp_spec_version)` so re-entry never double-emits (mirrors the campaign-phase idempotency on `(project_run, phase)`, Doc C §4 / M7.4).
  - **No write path** exists from content/design back into the claim store through this API (verified by absence of any write endpoint and by the outbox being one-directional) — Postgres-only-source-of-truth invariant (conventions §6) holds.
  - Responses carry the `AccountHandoff` schema version; a pinned old-version consumer keeps working after an additive schema change (contract-version test).
  - Access is tenant-scoped: a client cannot fetch another client's assembled handoff (cross-tenant test), even where underlying public claims are shared in the store (substrate §2).
  - Each served object exposes verification-health metrics (tier-4 judge pass rate, strong-binding share) for that account (Doc C §6).
  - Swapping the `HandoffPublisher` transport (pull → push) requires no change to the `account_handoff` schema or to upstream producers (seam test).
- **Out of scope:**
  - The **content schema / content / artifact generation** and any template mapping — **content layer (not this repo)**; this API hands over *verified meaning*, full stop (overview §3, D1).
  - The **design subsystem's** ingest specifics — **D2, unresolved**; the API stays design-agnostic and provides the `HandoffPublisher` adapter point for whatever D2 resolves to.
  - The **client-facing** cost/progress/verification dashboards — **M13.4** (this issue exposes the metrics; M13.4 renders them to the client).
  - Building the project-run state machine or verification layer — **M7.3 / M9** (consumed, not built).
- **Open decisions:**
  - **D1 (output boundary):** this API *is* the seam at the recommended boundary — research ends at claims + value narrative. If D1 narrows or widens later, only *which sections the served object carries* changes (M12.2), not the API's existence or shape.
  - **D2 (design-subsystem ingest interface):** **the central open dependency for this issue** (overview §3). The recommended assumption is a content layer between research and design; the `HandoffPublisher` adapter and a design-agnostic `account_handoff` are built so D2 can be resolved by adding/configuring an adapter, not by reshaping the contract. Proceed on the recommended default without hardcoding a specific design ingest format.
  - **D7 (economics / cost pass-through):** whether the served verification-health and coverage metrics become a *client-facing* surface (recommended, Doc C §5) vs. internal is a config of M13.4; the API exposes the data either way.
