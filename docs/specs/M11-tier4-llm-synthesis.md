# M11 — Tier-4 LLM Synthesis Resolvers
**Layer label:** layer:llm-synthesis  ·  **Depends on:** M4, M8, M9  ·  **Priority:** 3 (Medium)
**Architecture sources:** substrate §4 (trust-tiered waterfall; tier-4 last resort), §1/§6 (evidence-span rule, faithfulness judge), §11 step 6 (LLM agents added last, behind the judge), §12 (Exa Deep / Parallel Task as pluggable resolvers), §13 (anti-patterns); staged-flow §5 (synthesis within the mode-M2 waterfall), §7d (Source Planner gating expensive modalities), §8 (mode-specific anti-hallucination); Doc C §1–§3 (deep narratives, `account.resonance.*`, bounded fan-out); Doc D §2/§3/§5 (use-class, two gates, appropriateness ≠ accuracy); overview §1 (Output 2), §3 (output contract). Conventions §2 (modularity/DRY), §3 (tiers, field namespaces, research modes), §4 (claim, current_value, Resolver, field_definition, source_manifest), §5 (the two gates + universal rule), §6 (stack), §9 (open decisions).

## Goal & scope of this milestone

M11 adds the **last** capability in the build order (substrate §11 step 6): the tier-4 LLM-synthesis resolvers that fill the small set of fields no deterministic (tier-1), official-source (tier-2), or reputable-third-party (tier-3) resolver can answer — fields that genuinely require *synthesis* across many weak sources: `account.operational_pain`, `account.strategic_moves`, and the `account.resonance.*` narratives (substrate §3, §4; Doc C §1–§2). It does this by implementing two concrete `Resolver` instances — **Exa Deep** (M11.1, field-level grounded synthesis) and **Parallel Task** (M11.2, citations + reasoning + confidence) — plus the field wiring and runtime discipline (M11.3) that places those resolvers **behind** the verification layer so every synthesized claim is judged for faithfulness before it can be promoted past `unverified`.

Where it sits in the end-to-end map: tier-4 resolvers are invoked **only inside Pass B deep profiling** (mode M2 account profiling — staged-flow §5; the converge pattern from M8.1), as the final rung of the per-field waterfall (M4.1) after tiers 1–3 miss. They are the substrate doc's most dangerous source (§4, §13) and therefore the most heavily constrained: grounded-only (no parametric listing), evidence-span-mandatory, judge-gated, target-locked to a resolved `entity_id`, source-bounded by the Source Planner (M4.6), and budget-capped by the per-account/per-run cost engine (M7.5, Doc C §3/§5).

This milestone is the architecture's core bet made concrete one last time: *LLM research is the least-trusted source; it runs last, only fills fields no trustworthy source can answer, and a tier-4 claim with no evidence span cannot be promoted* (substrate §0, §1, §13; conventions §4 rule).

**Explicitly NOT in this milestone:**
- The waterfall engine, `Resolver` protocol, source registry, modality adapters and Source Planner themselves — owned by **M4** (M4.1/M4.2/M4.3/M4.6). M11 *implements* resolvers against that seam and *registers* their manifests; it does not build the engine.
- The faithfulness judge, corroboration rules, identity-binding gate, freshness engine and eval harness — owned by **M9** (M9.2/M9.3/M9.4/M9.5/M9.6). M11 *invokes* the judge via M9's seam; it does not implement judging.
- The orchestrator/worker graph, bounded recursion knob, campaign-run state machine and budget caps — owned by **M7** (M7.1/M7.2/M7.3/M7.5) and exercised by **M8**. M11 resolvers run *as tools inside* those workers.
- The use-class taxonomy, jurisdiction switch and appropriateness/use gate for personal hooks — owned by **M10** (M10.2/M10.3). M11 synthesizes **account-level** fields (`account.*`, `account.resonance.*`); `contact.facet.*` synthesis stays governed by Doc D / M10. M11 must *respect* the gate (never bypass it) but does not implement it.
- The positioning step and value narrative (Output 4) — owned by **M12** (M12.1). M11 produces the *raw synthesized claims* (Output 2) that M12 consumes; the value narrative is itself tier-4 synthesis but is specified in M12, not here.
- **The OpenRouter LLM gateway** (M0.4) and the *direct* chat/completion calls that route through it (faithfulness judge M9.3, query-planning M6.1, ICP synthesis M5.2, role inference M8.3, value-narrative positioning M12.1). M11's Exa Deep and Parallel Task are **tier-4 research-product resolvers** reached through their own provider APIs/keys (`CLUE_EXA_API_KEY`, `CLUE_PARALLEL_API_KEY`) — they are **not** OpenAI-compatible chat/completion endpoints and are therefore **not** routed through the OpenRouter gateway; they stay behind the `Resolver` protocol like every other provider (conventions §2 carve-out). Only if a future tier-4 resolver were implemented as a *direct* model call rather than a research-product API would it use the gateway.

## Issues

### M11.1 — Exa Deep resolver (field-level grounded synthesis)

- **Purpose:** Some fields — operational pain, strategic narrative, cultural resonance — cannot be read off a single API row or page; they must be *synthesized* from many weak, scattered web sources (substrate §3 `operational_pain [LLM_synthesis]`, §4 "ONLY for fields that genuinely require synthesis"; Doc C §1 deep narratives). Exa Deep performs **field-level grounded synthesis**: given a resolved entity and a target field, it retrieves real web evidence and returns a synthesized value *bound to an evidence span and citation*, with a confidence (substrate §12 "Exa Deep (field-level grounding)"). This issue implements Exa Deep as a tier-4 `Resolver` so it slots into the trust-tiered waterfall (M4.1) as the last rung, writes typed tier-4 claims, and is hot-swappable behind the protocol — nothing downstream knows "Exa" exists (conventions §2, §4).
- **Architecture sources:** substrate §4 (tier-4 last resort + the `Resolver` protocol), §1 (claim fields, evidence-span rule), §12 (Exa Deep as pluggable tier-4 resolver), §13 (LLM-as-base anti-pattern, "filling a field with a plausible guess" anti-pattern); staged-flow §5 (synthesis within the mode-M2 waterfall, target-lock), §7d (Source Planner picks/orders sources, gates expensive modalities); Doc C §1–§2 (deep narratives, resonance). Conventions §3 (tier 4, research modes), §4 (Resolver, claim, source_manifest), §5 (universal rule).
- **Scope / deliverables:**
  - An `ExaDeepResolver` class implementing the shared `Resolver` protocol (conventions §4; defined in M0.2) with `tier = 4` and `resolve(entity, field) -> list[Claim]`. It imports the shared `Resolver` protocol, `Claim`/`Entity`/`FieldDef` domain types, provenance helpers and the tracing wrapper from the shared package (M0.2) — it never re-implements them (conventions §2 DRY).
  - **Grounded-only synthesis:** the resolver issues entity-scoped, field-targeted retrieval and synthesizes *only over returned records/URLs*. It MUST NOT emit a value that has no retrieved evidence span — the parametric-listing prohibition (staged-flow §3, §8) applied to profiling: the LLM may plan/expand queries but may not *be* the source.
  - **Target-lock (anti-drift):** every query and the synthesis prompt are bound to the resolved entity — canonical domain (`site:`), canonical name + `hq_geo` disambiguators, `aliases[]` from `account_entity` (substrate §2; staged-flow §5). Synthesized claims must cite entity-bound evidence; off-entity evidence is rejected, not blended.
  - Each returned `Claim` is populated with: `value_json` (typed per the field registry), `source_url`, `source_tier = 4`, `extraction_method = llm_synthesis`, `evidence_span` (the exact retrieved text supporting the value — **mandatory**), `confidence` (Exa's score, normalized 0..1), `cost_cents`, `observed_at`/`collected_at`, `run_id`, `research_mode` (mode M2). Multiple supporting passages → one claim per distinct field value with its own span (corroboration/dedup is the verification path's job, M9.2).
  - **Source-bounded:** the resolver accepts the Source Planner's (M4.6) selected/ordered source set and query expansions for the field, and stays within the ICP source profile's allowed, weighted set (staged-flow §7c/§7d) — it does not free-range the open web.
  - **Cost/latency manifest + budget awareness:** register a `source_manifest` row (`source_key = "exa_deep"`, `modality = text`, `entity_scope = account`, `yields = [account.operational_pain, account.strategic_moves, account.resonance.*]`, `tier = 4`, plus cost/latency/geo_coverage/freshness_profile/identity_binding_strength) in the source registry (M4.2). The resolver reports actual `cost_cents` per call so the per-account/per-run budget engine (M7.5) can hard-stop tier-4 spend.
  - **No promotion inside the resolver.** The resolver returns claims at `unverified`; promotion is the merge/verification path's job (M1.2 + M9). The resolver never marks its own output verified (substrate §1, §6).
  - Config-driven model/endpoint selection (API key, model id, retrieval depth, timeout, retry/backoff) read from versioned config (conventions §2 policy-as-data; M0.4) — using Exa's own `CLUE_EXA_API_KEY`, **not** the OpenRouter gateway (Exa Deep is a research-product API, conventions §2 carve-out). Swapping Exa Deep for another grounded-synthesis provider is a config/registry change.
  - Failure handling: a miss / low-confidence / empty-retrieval returns `[]` (the field stays empty — a *correct* output, conventions §5), never a fabricated value.
- **Interface / seam:**
  - **Exposes:** the shared `Resolver` protocol (`tier: int`, `resolve(entity, field) -> list[Claim]`, conventions §4) plus a `source_manifest` row in the source registry (M4.2). This is the only surface the waterfall engine (M4.1) and per-account workers (M7.1) touch — they call `resolve(...)` and consume returned `Claim`s; they have no knowledge of Exa specifically. **Swap point:** Exa Deep → any other tier-4 grounded-synthesis provider is a registry/config change, identical to the Clay→direct-API swap pattern (conventions §2).
  - **Consumes:** the `FieldDef`/`field_definition` (tier_plan, type, validation) from the field registry (M1.3); the resolved `account_entity` (M2.1) for target-lock; the Source Planner's selected source set + query expansions (M4.6); the shared claim/provenance helpers and tracing wrapper (M0.2); the Exa API behind a config-injected client. It writes `Claim`s to the claim store via the M1 write path — it does not call other resolvers or the judge directly (the orchestrator/verification pass does, M7/M9).
- **Data model / schema:** Writes `claim` rows (conventions §4, substrate §1) — no new tables. Touched fields per row: `source_tier = 4`, `extraction_method = llm_synthesis`, mandatory `evidence_span`, `confidence`, `cost_cents`, `research_mode` (mode M2). Reads `field_definition` (tier_plan/type/validation/freshness_ttl — conventions §4) and `account_entity` (canonical_name/primary_domain/aliases/hq_geo — conventions §4). Registers one `source_manifest` row (conventions §4) in the M4.2 registry. No DDL changes; extends the existing contracts only.
- **Dependencies:** **M4** (M4.1 waterfall engine + `Resolver` protocol surface; M4.2 source registry to register the manifest; M4.6 Source Planner for the bounded source set) · **M8** (M8.1 mode-M2 converge orchestrator that invokes tier-4 last; provides the gap-field list and entity binding) · **M0.2** (shared domain types/protocol/helpers) · **M1.3** (field registry) · **M2.1** (resolved entity). **Unblocks:** M11.3 (field wiring that activates this resolver) and, transitively, M12 (raw synthesized claims feed the positioning step, M12.1).
- **Acceptance criteria:**
  - `ExaDeepResolver` satisfies the `Resolver` protocol (static type check passes; `tier == 4`) and is importable/registerable through the M4.2 source registry with a valid `source_manifest`.
  - For a resolved test entity, `resolve(entity, field=account.operational_pain)` returns `Claim`s each with `source_tier == 4`, `extraction_method == "llm_synthesis"`, a non-empty `evidence_span`, a `source_url`, a `confidence` in [0,1], and a positive `cost_cents`.
  - **Evidence-span invariant test:** no returned claim has an empty/null `evidence_span`; a contrived run where retrieval returns nothing yields `[]` (not a fabricated value).
  - **Target-lock test:** given an entity with a near-duplicate same-name competitor in the corpus, evidence drawn from the wrong domain/name is excluded; returned spans trace to the canonical domain/name/aliases.
  - **Grounded-only test:** every value in every returned claim is supported by a span that appears in a retrieved source (asserted programmatically), i.e. no value is produced without a backing passage.
  - **Swap test:** replacing the resolver with a stub tier-4 resolver via config/registry requires no change to the waterfall engine or workers (the call site is unchanged).
  - **Budget test:** the resolver reports `cost_cents` such that the M7.5 budget engine can stop further tier-4 calls when the per-account cap is reached; a per-call timeout/retry policy is honored.
  - **No-self-promotion test:** all returned claims carry `unverified` status; the resolver never sets `verified`/`corroborated`.
  - Tracing: each `resolve` call emits a named span (M0.5) with field_key, entity_id, cost, latency, retrieval count, and outcome (hit/miss/empty).
- **Out of scope:** the waterfall ordering/stop-at-first-confident logic (M4.1); the faithfulness judging of these claims (M9.3, invoked downstream); merge/promotion (M1.2); the Source Planner's selection logic (M4.6); `contact.facet.*` personal synthesis and its use-gate (M10); the value narrative (M12). Concrete per-tier retrieval-depth/budget numbers are deferred to D7 calibration (Doc C §8).
- **Open decisions:** **D7** (economics) — tier-4 retrieval depth and per-account budget bands are read from config and tuned once real campaign-cost data exists (Doc C §5/§8); proceed on the proposed default bands without hardcoding. **D8** (2026 legal verification) — scraping/synthesis over open-web sources for `account.*` is professional/public-company information and lower-risk than personal data, but DPA stances on scraping are still to be verified before go-live; surfaced, not blocking, and orthogonal to the personal-data gate (Doc D / M10).

### M11.2 — Parallel Task resolver

- **Purpose:** A second, *independent* tier-4 synthesis provider so the subsystem is not single-vendor for its least-trusted source, and so two independent synthesis engines that converge on the same value give the faithfulness judge (M9.3) a much stronger signal than a single-source guess. Parallel's Task API (Basis) returns **citations + reasoning + confidence** (substrate §12) — a different synthesis engine with its own grounding behavior. This issue implements Parallel Task as a second tier-4 `Resolver` behind the same protocol seam, registered in the source registry alongside Exa Deep, so the Source Planner / waterfall can choose between them (or run both for cross-provider convergence) purely by config — preserving the "providers are just resolvers, nothing downstream knows which" rule (conventions §2). It is the concrete proof that the tier-4 seam is provider-agnostic.
- **Architecture sources:** substrate §4 (Resolver protocol, tier-4 last resort), §1 (claim + evidence-span rule; `corroborations` = # independent tier≤3 sources), §6 (corroboration is defined over tier-≤3 sources; independent tier-4 synthesis engines converging is what helps the faithfulness judge distinguish a single-source guess from convergent synthesis), §12 (Parallel Task: "citations + reasoning + confidence", pluggable), §13 (anti-patterns); staged-flow §5 (synthesis within mode M2), §7d (Source Planner). Conventions §2 (swap stays behind the seam), §3 (tier 4), §4 (Resolver, claim, source_manifest, the `corroborations` definition).
- **Scope / deliverables:**
  - A `ParallelTaskResolver` class implementing the shared `Resolver` protocol (`tier = 4`, `resolve(entity, field) -> list[Claim]`), importing all shared types/helpers from M0.2 — DRY-identical structure to M11.1 so the two are interchangeable at the call site.
  - Map Parallel Task's output (value + reasoning + citations + confidence) into `Claim`s: `value_json` typed per the field registry; **each citation becomes the claim's `source_url` + `evidence_span`** (mandatory span rule); Parallel's confidence → normalized `confidence`; `source_tier = 4`, `extraction_method = llm_synthesis`, `cost_cents`, timestamps, `run_id`, `research_mode` (mode M2). Parallel's "reasoning" trace is recorded in the tracing span (M0.5) for auditability but is **not** the evidence span — only cited source text qualifies as `evidence_span` (substrate §1/§6).
  - Same grounded-only + target-lock discipline as M11.1 (no parametric listing; entity-scoped queries via canonical domain/name/aliases; off-entity citations rejected).
  - Same source-bounding (stay within the Source Planner's allowed set, M4.6) and budget reporting (`cost_cents` to M7.5).
  - Register a `source_manifest` row (`source_key = "parallel_task"`, `modality = text`, `entity_scope = account`, `yields = [account.operational_pain, account.strategic_moves, account.resonance.*]`, `tier = 4`, cost/latency/geo/freshness/identity_binding_strength) in M4.2 so the planner/waterfall can select it independently of, or together with, Exa Deep.
  - Config-driven model/endpoint/timeout/retry, read from versioned config (M0.4) — using Parallel's own `CLUE_PARALLEL_API_KEY`, **not** the OpenRouter gateway (Parallel Task is a research-product API, conventions §2 carve-out). Parallel Task ↔ Exa Deep ↔ a future provider is a config/registry change, never code in the engine or workers.
  - **Independence for cross-provider convergence:** when both tier-4 resolvers run on the same field, each writes its own claim with its own citation, so the verification path (M9) can compare two independently-grounded tier-4 values for the same field. Whether and how cross-provider agreement feeds the formal `corroborations` count is a decision owned by M9.2 — and note that the `corroborations` contract (conventions §4, substrate §1/§6) is defined as independent **tier-≤3** sources, so tier-4 convergence is treated as a confidence/judge signal, not assumed to increment the tier-≤3 corroboration count. The resolver never deduplicates against Exa's output — that is the merge/verification path's job.
  - Returns `[]` on miss/low-confidence/no-citation (empty is correct; never fabricate).
- **Interface / seam:**
  - **Exposes:** the shared `Resolver` protocol + a `source_manifest` row in the M4.2 registry — byte-for-byte the same seam as M11.1. The waterfall engine (M4.1) and workers (M7.1) call `resolve(...)`; they cannot tell Exa Deep from Parallel Task. **Swap point:** add/remove/replace a tier-4 provider = a registry/config edit; running *both* tier-4 providers = a Source-Planner/config choice (M4.6), not a code change.
  - **Consumes:** identical inputs to M11.1 — `FieldDef`/field registry (M1.3), resolved `account_entity` (M2.1) for target-lock, the Source Planner's selected source set (M4.6), shared claim/provenance helpers + tracing (M0.2), and the Parallel Task API behind a config-injected client. Writes `Claim`s via the M1 write path.
- **Data model / schema:** Writes `claim` rows (conventions §4) — no new tables; identical field usage to M11.1, with `source_url`/`evidence_span` sourced from Parallel's citations. Registers one `source_manifest` row (conventions §4). Reads `field_definition` and `account_entity`. No DDL changes.
- **Dependencies:** **M4** (M4.1 protocol/waterfall surface; M4.2 registry; M4.6 planner) · **M8** (M8.1 mode-M2 orchestrator) · **M9.2/M9.3** (the verification path that compares the independent tier-4 claims this enables) · **M0.2/M1.3/M2.1** (shared types, field registry, resolved entity). **Unblocks:** M11.3 (field wiring); supplies independent tier-4 claims that strengthen the M9.3 faithfulness signal on synthesized fields. Independent of M11.1 — both implement the same seam and can be built in parallel.
- **Acceptance criteria:**
  - `ParallelTaskResolver` satisfies the `Resolver` protocol (`tier == 4`) and registers a valid `source_manifest` in M4.2.
  - `resolve(entity, field=account.strategic_moves)` returns `Claim`s each carrying `source_tier == 4`, `extraction_method == "llm_synthesis"`, a non-empty `evidence_span` derived from a Parallel citation, a `source_url`, normalized `confidence`, and `cost_cents`.
  - **Reasoning-vs-span test:** Parallel's reasoning string is captured in the trace span but is *never* used as `evidence_span`; a value whose only support is reasoning (no citation) is dropped → `[]`.
  - **Independence test:** running both M11.1 and M11.2 on the same field/entity produces two distinct `Claim`s with distinct `source_url`s, each carrying its own evidence span — so the verification path (M9) has two independently-grounded tier-4 inputs for that field.
  - **Provider-agnostic test:** the waterfall engine and workers behave identically whether the registered tier-4 resolver is Exa Deep, Parallel Task, or both — the call site is unchanged (the swap seam holds).
  - **Grounded-only / target-lock / no-self-promotion / budget / empty-on-miss** tests as in M11.1.
  - Tracing: each call emits a named span (M0.5) including provider, field_key, entity_id, citation count, confidence, cost, latency, outcome.
- **Out of scope:** corroboration rules and any cross-provider agreement counting (M9.2); the faithfulness judge itself (M9.3); the merge/dedup of Exa vs Parallel claims (M1.2); the planner's choice of when to run one vs both (M4.6); `contact.facet.*` synthesis (M10); value narrative (M12).
- **Open decisions:** **D7** — whether to default to running both tier-4 providers (higher cost, stronger convergence signal) or one with the other as fallback is a config/economics choice; proceed on a single-provider-with-fallback default, revisit with cost data. **D8** — same open-web scraping/synthesis verification note as M11.1; surfaced, non-blocking.

### M11.3 — Synthesis fields (operational_pain, strategic_moves, resonance narratives) behind the judge

- **Purpose:** This is the wiring that makes the tier-4 resolvers *safe to ship* and is the literal embodiment of substrate §11 step 6 ("LLM research agents as tier-4 field-fillers … behind the judge — added only now, on top of a substrate that constrains and checks them"). It (1) declares the synthesis fields in the field registry with a tier-4-only or tier-4-last tier plan, (2) tags them `deep` (Pass B only) and attaches the right gate, (3) ensures every value these resolvers produce flows through the verification layer — provenance gate → corroboration → **faithfulness judge** — before the merge view can promote it past `unverified`, and (4) guarantees account-level synthesis cannot leak into personal hooks, keeping `contact.facet.*` under Doc D / M10. The fields in scope are exactly the synthesis fields the architecture names: `account.operational_pain`, `account.strategic_moves`, and the `account.resonance.*` narrative class (substrate §3; Doc C §1–§2; overview §1 Output 2). This issue produces no value itself — it is the policy-as-data + gating glue that turns M11.1/M11.2 from raw resolvers into a governed, judge-gated layer.
- **Architecture sources:** substrate §3 (research-schema: `operational_pain [LLM_synthesis] deep committee-gated`, `strategic_moves [news, LLM_synthesis] deep tier>=1`; the scoring-vs-deep tag), §4 (tier-4 last), §6 (the faithfulness judge: per tier-4 claim, claim-level entailment, unsupported → reject/re-retrieve/leave empty), §1 (no span → cannot promote past unverified), §11 step 6 (added last, behind the judge), §13 (untyped-dossier + after-the-fact-QA anti-pattern this prevents); staged-flow §5 (verification on mode-M2 synthesis), §8 (mode-M2 row: fabricated facts/drift prevented by target-lock + span + judge); Doc C §1 (deep narrative = tier-4, computed on high-tier only), §2 (`account.resonance.*` registered not enumerated; tier-4, evidence-bound); Doc D §5 (appropriateness ≠ accuracy — kept distinct), §7 (contact.facet governed by M10). Conventions §3 (namespaces, tiers), §4 (field_definition, claim, current_value), §5 (the two gates + universal rule).
- **Scope / deliverables:**
  - **Field-registry rows (policy-as-data, M1.3)** for the synthesis fields, each a `field_definition` (conventions §4) with:
    - `account.operational_pain` — type: structured pain narrative; `tier_plan = [exa_deep, parallel_task]` (tier-4 only — no deterministic source can answer it, substrate §3); `pass = deep`; `gate = committee-gated` (synthesize once the committee/account context is established, substrate §3); `freshness_ttl` ≈ 90-day default (substrate §6).
    - `account.strategic_moves` — type: structured moves/narrative; `tier_plan = [news_search(tier3), exa_deep, parallel_task]` (tier-4 *last*, after tier-3 news — substrate §3); `pass = deep`; `gate = tier>=1`; signal-class field, shorter TTL than firmographics (Doc C §1).
    - `account.resonance.*` — a registered field-**class** (not enumerated, Doc C §2) covering employee-sentiment, morale/attrition/layoff signals, eng-blog tone, public-frustrations narratives; each populated by tier-4 synthesis over modality-adapted sources (Glassdoor/reviews/blogs via M4.3 adapters, sourced by M8.2 collectors); `pass = deep`; evidence-bound; ≈90-day TTL.
  - **Two-tier signal mapping (Doc C §1):** confirm each of these is the *deep narrative* half of a signal class whose *cheap proxy* half is a `scoring`-tagged tier-1/2 field owned by Pass A (M6.3) — e.g. `strategic_moves` (deep) pairs with funding/headcount proxies (scoring). The registry must make the split explicit so synthesis never runs in Pass A.
  - **Judge-gating glue:** wire the per-account verification pass (M9) so that **every** tier-4 claim on these fields is routed through, in order: the provenance gate (no `evidence_span` → cannot promote, M1.2 + substrate §6(2)), corroboration (M9.2), and the **faithfulness judge** (M9.3) — value-entailed-by-its-span, claim-level. A claim that fails the judge is rejected (left `unverified`/dropped) and the field stays empty or triggers re-retrieval; **empty is correct** (substrate §6, conventions §5). The merge view (`current_value`, conventions §4) must never surface a tier-4 value that has not cleared the judge.
  - **Pass-B-only enforcement:** these fields are `deep`; the schema compiler (M3.2) and the orchestrator (M8.1) must not invoke tier-4 resolvers for them in Pass A. A guard asserts no `account.operational_pain/strategic_moves/resonance.*` claim is written with a `research_mode` outside Pass B / mode M2.
  - **Personal-data firewall:** `contact.facet.*` is explicitly **excluded** from M11's account-synthesis tier_plans; this issue documents and asserts that tier-4 *contact* synthesis is governed by M10 (use-class tagging at extraction + appropriateness/use gate + identity-binding), and that the account-resonance synthesis here never writes contact-level personal claims. Resonance about *the company* is account-level and use-class-neutral; anything about a *named person* routes through M10 (Doc C §2, Doc D §7).
  - **Verification-health surface hooks:** emit the metric Doc C §6 names — share of tier-4 claims passing the faithfulness judge — as a labeled span/counter per field so M13.4's verification-health surface and the M4.6 source-learning loop (staged-flow §7e) can read it.
  - **Eval coverage:** add the synthesis fields to the M9.6 golden-account eval set with rubric scoring for factual accuracy / citation validity / source quality, so a model or resolver swap that regresses faithfulness is caught (substrate §6, Doc C §6).
- **Interface / seam:**
  - **Exposes:** field-registry rows (`field_definition`) + the gating policy as *data* the engine reads (conventions §2 policy-as-data) — adding/removing a synthesis field, retuning its TTL, or changing its tier plan/gate is a registry edit, not code. It exposes no new runtime API; it composes existing seams (M4 waterfall + M9 verification + M1 merge). **Swap points kept behind seams:** the judge *model* is swappable behind M9.3's seam (verification-health metrics make a regression visible); a tier-4 *provider* is swappable behind M11.1/M11.2's `Resolver` seam; the Postgres state machine→Temporal migration (M7) doesn't touch this wiring.
  - **Consumes:** the field registry write path (M1.3); the tier-4 resolvers (M11.1, M11.2); the verification layer's provenance gate / corroboration / faithfulness judge (M9.2/M9.3) via M9's seam; the merge view promotion policy (M1.2); the mode-M2 orchestrator (M8.1); the schema compiler's scoring-vs-deep tagging (M3.2). - **Acceptance criteria:**
  - The three synthesis field definitions exist in the field registry with tier-4-last/only `tier_plan`, `pass == deep`, the specified `gate`, and a freshness TTL; `account.resonance.*` is registered as a class (a new resonance sub-field can be added by a registry row with no code change).
  - **Judge-gate test:** a synthesized claim that *fails* the faithfulness judge (value not entailed by its span) is **not** surfaced by `current_value` — the field reads empty/flagged; a claim that passes is promoted. No tier-4 value reaches the merge view without a judge verdict on record.
  - **No-span-no-promote test:** a tier-4 claim with empty `evidence_span` cannot be promoted past `unverified` (re-asserts the M1/M9 invariant at the field level).
  - **Pass-B-only test:** attempting to populate any of these fields in Pass A / outside mode M2 is rejected by the schema/orchestrator guard; no such claim is written.
  - **Personal-data firewall test:** no `contact.facet.*` or any contact-level personal claim is ever written by the account-synthesis path; resonance claims are account-scoped (`entity_type == account`); contact synthesis paths remain governed by M10's use-gate (asserted by inspection/integration test).
  - **Tier-4-last test:** for `strategic_moves`, a confident tier-3 news result short-circuits the waterfall so tier-4 synthesis is not invoked (substrate §4 stop-at-first-confident); tier-4 runs only when tiers 1–3 miss.
  - **Verification-health metric test:** the "share of tier-4 claims passing the faithfulness judge" metric is emitted per field and readable by the M13.4 surface / M4.6 learning loop.
  - **Eval test:** the synthesis fields appear in the M9.6 golden set; a deliberately fabrication-prone judge/model swap is caught by a measurable drop in faithfulness pass-rate.
