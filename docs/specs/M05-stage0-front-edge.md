## Goal & scope of this milestone

> **Approved extension, not yet live (2026-08-14):** broad, concurrent official-site acquisition
> for client reverse-profiling is specified separately in the
> [Stage-0 durable official-site crawl plan](./FI-stage0-durable-official-site-crawl-plan.md).
> Until its exit gates pass, M5.1 continues to consume the accepted homepage/field-oriented source
> path; a provider-owned recursive crawl is not an implementation of this extension.

Stage 0 is the **seed of research** (Doc B preamble): every downstream direction — which accounts we look for, which signals we weigh, which sources we trust, what argument we eventually make — is determined here. This milestone delivers the **front edge** of the subsystem: the machinery that takes a client from **near-zero input** (worst case: company name + website, Doc B §1) to (a) a versioned **Client Knowledge Base**, (b) one or more confirmed, versioned **ICP specs**, and (c) for clients who bring a list, a set of **resolved, ICP-back-scored imported accounts** plus seeds for lookalike discovery.

Where it sits in the end-to-end map (overview §2): Stage 0 is the topmost band, feeding two **first-class, symmetric** entry scenarios — Scenario A (discovery, owned by M6) and Scenario B (import, owned here) — both of which converge at the Pass A scoring bridge (staged-flow §4). The project-run state machine's first two phases — `reverse_profiling` and `icp_confirmed` — are entered here (Doc C §4); this milestone produces the artifacts those phases checkpoint on, but the state-machine engine itself is owned by M7 (durable execution), and M5 consumes it via a phase seam.

**This milestone delivers:**
- M5.1 — Client reverse-profiling pipeline → versioned Client Knowledge Base (the client side of every later value narrative; substrate §8, Doc B §2).
- M5.2 — ICP synthesis & proposal, supporting multiple ICPs per client (D5), each compiling its own `ICP spec` via the M3 compiler.
- M5.3 — Import entry scenario: bulk identity resolution + ICP back-scoring + non-fit flagging (D6).
- M5.4 — Hybrid lookalike seeding from imports / existing customers into M6 discovery.

**What is explicitly NOT here:**
- The `claim`, `current_value`, `account_entity`, `Resolver`, `field_definition`, `source_manifest`, `ICP spec`, `account_handoff` contracts themselves — those are **defined once** in `_conventions.md §4` and owned by M0/M1; M5 only **reads/writes/instantiates** them.
- Identity resolution machinery (dedup → linkage → canonicalization, review queue, in-flight locks) — owned by **M2**; M5 calls it as a service.
- The ICP→research-schema **compiler** (field-set selection, tier-plans, source profile, scoring rubric) — owned by **M3**; M5.2 invokes it to compile a confirmed ICP, and does not re-implement it.
- The source registry, modality adapters, Source Planner, and concrete resolvers used during reverse-profiling — owned by **M4**; M5.1 drives them through the `Resolver` protocol and Source Planner seam.
- M1 **account discovery** execution (the expand loop, stopping rule, discovery budget) — owned by **M6**; M5.4 produces the *seed set* M6 consumes, not the discovery run.
- Pass A scoring **engine** (deterministic fit/intent compute) — owned by **M6**; M5.3 invokes it for back-scoring rather than re-implementing the scorer.
- The value-narrative **positioning step** that consumes the Client Knowledge Base — owned by **M12**; M5.1 only produces and versions the base.
- The personal-data **use-gate** and full compliance posture machinery — owned by **M10**; M5.3 tags imported contact claims with `use_class`/`identity_binding`/lawful basis at write time so M10 can govern them later.
- Client-facing UI for editing/confirming ICPs, cost dashboards, and progress surfaces — out of this repo's scope; M5 exposes the **API/contract** behind those surfaces (FastAPI endpoints + structured proposal/diff objects).

## Issues

### M5.1 — Client reverse-profiling pipeline → versioned Client Knowledge Base
- **Purpose:** Before we can research targets, we must research the **client themselves** (Doc B §2). The worst-case input is a company name + website (Doc B §1); everything else — what they sell, to whom, differentiators, proof points, customer evidence — must be *derived*, not required as a form. This pipeline points the same machinery the subsystem uses on accounts (identity resolution → trust-tiered waterfall → typed claims with provenance) **inward** at the client's own footprint, producing a typed, **versioned Client Knowledge Base**. This base is the client side of every later value narrative (Output 4); its depth sets the **quality ceiling** on every downstream artifact (substrate §8, Doc B §2 quality-ceiling note), so it is the first real research run, not onboarding boilerplate.
- **Architecture sources:** Doc B §1 (minimum-input contract), §2 (reverse-profiling surfaces: owned surfaces, positioning & proof, third-party footprint, reviews-as-signal), §5 (Stage 0 output), §6 (reverse-profiling depth/budget — folded into D7 economics); substrate §8 (client knowledge ingestion: ingest → chunk → embed → typed base, versioned, freshness), §2 (identity resolution — the client is itself an `account_entity`), §3 (research-schema compilation — the client's own field set), §4 (trust-tiered waterfall + `Resolver`); staged-flow §5 (the converge pattern — a bounded, checklist-driven fill over one resolved entity), §7 (Source Planner / source profile choosing which surfaces to consult); overview §2 (Stage 0 band).
- **Scope / deliverables:**
  - A **reverse-profiling orchestration** (a bounded converge-pattern run, staged-flow §5, over a single entity — the client) that: (1) resolves the client to a canonical `account_entity` via M2 (deterministic on domain/registry-ID), (2) reads a **client-knowledge field set** (registered `core.*` / `account.*` fields plus a small set of client-profiling-specific field keys — e.g. `client.value_prop`, `client.differentiator`, `client.proof_point`, `client.icp_evidence`, `client.pricing_posture` — registered as rows in the field registry per M1.3, never hardcoded), (3) drives the trust-tiered waterfall (tiers 1–3 deterministic/official/third-party; tier-4 synthesis last and only behind M9) over the client's footprint.
  - Coverage of the four surface classes in Doc B §2: **owned surfaces** (website, product/pricing/docs pages, careers, blog — tier-2 official scrape via Firecrawl), **positioning & proof** (case studies, testimonials, logos, "customers" pages — these double as seed accounts, handed to M5.4), **third-party footprint** (G2/Capterra/TrustRadius category + reviews, directories, news, social), and **reviews-as-signal** (what the client's own customers say they bought it for — the most honest statement of delivered value).
  - **Document/deck/call ingestion path** (substrate §8): any client-volunteered material (a deck, a customer list, a target description, exclusions) is ingested, chunked, embedded into pgvector, and written as **high-trust claims** that shortcut derivation — treated as input that accelerates, never as a precondition (Doc B §1).
  - A **versioned Client Knowledge Base** = the set of client claims at a `client_kb_version`. New reverse-profiling runs **supersede** prior claims (append-only, never UPDATE-in-place) and bump the version; the version is recorded so later value narratives pin to a specific base (positioning/pricing drift — substrate §8 freshness).
  - A **bounded deep pass** on the client entity (Doc B §6 recommended default, folded into the Doc C §5 budget bands / D7): the client is one entity, run once, high leverage — a bounded deep pass rather than a cheap skim. Worker-count/depth caps and a per-client budget cap come from config (cost dial, Doc C §5), enforced as both prompt instruction and hard runtime limit.
  - A **completeness/coverage read** on the base (Doc C §7 spirit, applied to the client): which field classes are filled vs. empty, surfaced so thin profiles are visible (the ceiling is legible).
- **Interface / seam:**
  - **Exposes:** `reverse_profile(client_input: {name, website, optional_materials[]}) -> ClientKnowledgeBaseRef{client_entity_id, client_kb_version}`. The base is **just claims** in the shared `claim` store (`_conventions.md §4`) keyed on the client's resolved `entity_id` with `entity_type=account`; readers (M5.2 ICP synthesis, M12 positioning) consume `current_value(client_entity, field)` and a `client_kb_version` filter — there is no bespoke "client object," only claims at a version. This keeps the base swappable and queryable through the one shared substrate (`_conventions.md §2`).
  - **Consumes:** the M2 **identity service** (resolve client name+domain → `account_entity`); the M4 **`Resolver` protocol** (`_conventions.md §4`) and **Source Planner** (staged-flow §7d) to choose/order surfaces; M3 **`field_definition`** rows for the client field set; M9 **verification** (faithfulness judge over any tier-4 synthesized client claim). Because reverse-profiling is *just resolvers behind the waterfall*, swapping Firecrawl→another scraper, or Clay→direct APIs, is a registry/config change invisible here (`_conventions.md §2`).
  - **Swap points behind the seam:** the embedding/retrieval store (pgvector) sits behind a chunk/embed/retrieve interface; the synthesis tier-4 model is the same pluggable Exa/Parallel resolver used everywhere; the depth/budget config is versioned policy-as-data.
- **Data model / schema:** Writes `claim` rows (`_conventions.md §4`) with `entity_type=account`, `field_key` in the client field set, full provenance (`source_url`, `source_tier`, `extraction_method`, `evidence_span`, `confidence`, `observed_at`, `collected_at`, `cost_cents`, `run_id`); tier-4 client claims **must** carry an `evidence_span` or cannot be promoted past `unverified` (substrate §1). The client resolves to an `account_entity` (`_conventions.md §4`) like any other company. Adds a lightweight `client_kb_version` marker (a versioned label over the client's non-superseded claims; extends — does not redefine — the claim store). Uses `field_definition` rows (M1.3) for client field keys; uses pgvector for chunked client-knowledge retrieval (stack, `_conventions.md §6`).
- **Dependencies:** **M2** (identity resolution — resolve the client entity), **M4** (resolvers + Source Planner + source registry to execute the waterfall over client surfaces), **M3** (field registry / `field_definition` for the client field set), **M1** (claim store + `current_value` merge), **M9** (faithfulness judge for tier-4 client claims) — note M9 is not a hard blocker for tiers 1–3 ingestion; tier-4 client synthesis is gated behind it per build order (substrate §11). **Unblocks:** M5.2 (ICP synthesis reads the base), M5.4 (seed accounts extracted from positioning/proof + customer lists), and downstream **M12** (positioning/value narrative reads the versioned base).
- **Acceptance criteria:**
  - Given only `{name, website}` with no other input, the pipeline resolves the client to a single `account_entity` and produces a non-empty Client Knowledge Base with at least the four surface classes attempted and per-field provenance on every populated claim.
  - Every client claim is queryable via `current_value(client_entity, field)` and filterable by `client_kb_version`; no client fact exists as free text outside the claim store.
  - Volunteered materials (deck/customer list/exclusions) are ingested as high-trust claims and measurably shortcut derivation (e.g. value-prop/differentiator fields filled from the deck instead of synthesized) without becoming a precondition — the no-materials path still completes.
  - Tier ordering is respected: a tier-4 synthesized client claim never overwrites a tier-1–3 client fact (verified via `current_value` merge), and any tier-4 claim lacking an `evidence_span` is left at `unverified` (cannot be promoted).
  - Re-running reverse-profiling supersedes prior claims and bumps `client_kb_version`; the prior version remains queryable (append-only audit trail).
  - The per-client budget cap halts the run gracefully at the cap; the run is idempotent on re-entry (no double-charge / double-write) keyed on `(client_entity, field, tier)` (substrate §5c).
  - A coverage read reports which client field classes are empty, making a thin profile visible.
- **Out of scope:** The **positioning / value-narrative** join of client capability × account evidence (M12, substrate §8). The client-facing onboarding UI (separate repo). Tier-4 LLM synthesis *implementation* (M11) — M5.1 consumes it as a resolver behind the judge, it does not build it. Cross-tenant reuse policy of public client-footprint claims (substrate §2 — governed by M2's tenant-isolation rules).
- **Open decisions:** **D7** (economics/budgets) — proceed on Doc B §6 recommended default (a bounded deep pass on the single client entity) with depth/budget as versioned config, not hardcoded; the reverse-profiling band is the "Client reverse-profiling" row in the Doc C §5 budget table. **D1** (output boundary) touches indirectly: the Client Knowledge Base is the *client side* of the value narrative the subsystem is recommended to own — built here, consumed at the D1 boundary in M12.

### M5.2 — ICP synthesis & proposal (multi-ICP support — D5)
- **Purpose:** From the Client Knowledge Base, the platform must **synthesize candidate ICPs and propose them** as structured hypotheses (not prose), then let the client edit/add/remove/confirm — the platform suggests, the client always has the wheel (Doc B §1, §3; staged-flow §2). A real client often sells into several segments (e.g. mid-market fintech *and* enterprise healthcare payers), so the system must **support multiple ICPs per client** (D5), each compiling its own research plan and running as its own campaign. This issue produces the proposal objects and the confirm→compile flow; the compiler that turns a confirmed ICP into a `field_definition`-backed plan is M3's, invoked here.
- **Architecture sources:** Doc B §3 (ICP synthesis: firmographic, technographic/vertical, candidate signals, seed accounts, starting source profile, scoring rubric; multi-ICP — D5), §1 (always-has-the-wheel), §5 (Stage 0 output: one or more versioned ICP specs); staged-flow §2 (Stage 0 elicitation loop → versioned ICP spec that plans the next stages), §3 (discovery strategy), §7 (source profile per ICP/pack); substrate §3 (research-schema compilation — ICP → typed plan; the research-plan builder / schema resolver), §9/§10 (scoring is provenance-backed; corrections become labeled training data for scoring/extraction); Doc C §1 (candidate signals: two-tier signal model), §5 (cost — pre-run estimate per confirmed ICP/campaign).
- **Scope / deliverables:**
  - An **ICP synthesis step** that reads the Client Knowledge Base (`current_value` over the client entity at a pinned `client_kb_version`) and emits one or more **candidate ICP proposals**, each a structured hypothesis with: **firmographic dimensions** (industry/vertical, size band, geo, revenue band), **technographic/vertical dimensions** (the pack-specific fields that matter for this industry — substrate §3 packs), **candidate signals** (intent/growth/hiring/funding signal classes worth scoring on — Doc C §1, each spanning a cheap proxy and deep narrative), **seed accounts** (drawn from the client's existing customers + obvious lookalikes via M5.4, as concrete anchors), **a starting source profile** (which sources matter for this ICP — staged-flow §7c), and **a scoring rubric** (fit + intent weights over the active fields).
  - **Provenance on the proposal:** each proposed dimension/seed links back to the client claims that justify it (e.g. "size band derived from the geo/size of these 12 existing customers [claim_ids]"), so the client sees *why* the platform proposed it — consistent with the no-score-without-evidence discipline.
  - A **proposal/edit/confirm contract**: the client (via the front-end, out of repo) edits dimensions, adds/removes signals and seeds, and confirms. The API accepts a confirmed proposal and returns a **diff** vs. the platform's suggestion (so corrections are captured as labeled signal, mirroring the corrections-as-labeled-training-data discipline in substrate §9/§10).
  - **Multi-ICP support (D5):** a client may confirm *N* ICPs; each is independent. The synthesis step may itself **propose splitting** into multiple ICPs when the client's customer evidence clusters into distinct segments. There is no "one client = one ICP" assumption anywhere; ICP specs are versioned config rows (Doc B §3 — substrate carries no cost).
  - **Confirm → compile:** on confirmation, invoke the **M3 research-schema compiler** (substrate §3) to produce the **versioned `ICP spec`** (`_conventions.md §4`): active field set (core + packs) · discovery strategy (mode M1) · source profile (M2/M4) · scoring rubric (fit + intent weights). Reproducible because versioned.
  - **Campaign instantiation seam:** each confirmed ICP spec maps to its own **project run** (Doc C §4); M5.2 emits the `icp_confirmed` phase artifact (the compiled spec ref) that the M7 project-run state machine advances on. A **pre-run cost estimate** per confirmed ICP/campaign is surfaced (Doc C §5 — "~N accounts → ~M go deep → ~$X").
- **Interface / seam:**
  - **Exposes:** `synthesize_icps(client_kb_ref) -> ICPProposal[]` and `confirm_icp(ICPProposal, client_edits) -> ICPSpecRef{icp_id, icp_version}`. Each `ICPSpecRef` points at a versioned **`ICP spec`** (`_conventions.md §4`) — the single contract the rest of the subsystem executes against. Downstream (M6 discovery, M6 Pass A scoring, M4 source planning) consume only the `ICP spec`, never the proposal or the synthesis internals — so the LLM-driven synthesis can be swapped/retuned entirely behind the compiled-spec seam (`_conventions.md §2`).
  - **Consumes:** the M5.1 Client Knowledge Base (read-only, `current_value` + `client_kb_version`); the **M3 compiler** (`confirm_icp` delegates compilation to it — M5.2 does not select tier-plans or author source profiles itself); the M3 **field registry / packs** (to know which technographic/vertical dimensions exist for an industry); M5.4 (to populate seed accounts); the M7 **project-run state machine** phase seam (`icp_confirmed`).
  - **Swap point behind the seam:** the proposal-generation model is an LLM call **issued through the shared OpenRouter `LLMGateway` (M0.4, conventions §4)** — its model id and prompt are versioned config — bounded by the available pack field set and client claims (config-bounded, like the Source Planner — staged-flow §7d); swapping the synthesis model (a gateway config change) or the prompt changes nothing downstream because the output contract is the compiled `ICP spec`.
- **Data model / schema:** Reads `claim`/`current_value` over the client entity. Produces an `ICPProposal` (a structured, non-persistent-until-confirmed object: dimensions, candidate signals, seed `account_entity_id`s, proposed source-profile priors, proposed rubric weights, plus `justifying_claim_ids[]` per element). On confirm, persists a versioned **`ICP spec`** (`_conventions.md §4`) via the M3 compiler, keyed `(icp_id, icp_version)`; multiple `ICP spec` rows may exist per client (D5). Stores the **confirm diff** (suggested vs. confirmed) for the scoring/extraction feedback loop (substrate §9/§10). Does **not** redefine the `ICP spec` contract — it extends usage to N-per-client.
- **Dependencies:** **M5.1** (Client Knowledge Base is the input), **M3** (the research-schema compiler + field registry/packs — the spec is compiled, not authored here), **M5.4** (seed accounts for the proposal), **M7** (project-run state machine for `icp_confirmed` phase + per-campaign cost estimate). **Unblocks:** **M6** (discovery + Pass A scoring run against each confirmed `ICP spec`), **M5.3** (import back-scoring scores against the client's confirmed `ICP spec`), and ultimately the whole pipeline (every stage executes against the ICP spec).
- **Acceptance criteria:**
  - Given a Client Knowledge Base, `synthesize_icps` returns at least one structured `ICPProposal` with all six elements populated (firmographic, technographic/vertical, candidate signals, seed accounts, starting source profile, scoring rubric), each element carrying `justifying_claim_ids[]`.
  - When client customer evidence clusters into distinct segments, synthesis proposes multiple ICPs; a client can confirm 2+ ICPs and each compiles to an independent, separately-versioned `ICP spec` (D5) that instantiates its own project run.
  - `confirm_icp` round-trips client edits: removed signals/dimensions are absent from the compiled spec, added ones are present, and the suggested-vs-confirmed diff is persisted.
  - The confirmed `ICP spec` is produced by the M3 compiler (not authored inline) and is deterministically reproducible from `(icp_id, icp_version)` — re-compiling the same confirmed proposal yields the same spec (staged-flow §2 "reproducible because versioned").
  - A pre-run cost estimate is returned per confirmed campaign before any discovery/scoring spend (Doc C §5).
  - Downstream consumers (a mock M6 discovery planner, a mock Pass A scorer) can execute purely from the `ICP spec` with no access to the proposal internals (seam verified).
- **Out of scope:** The compiler internals — tier-plan selection, source-profile authoring, rubric weight mechanics (M3). Discovery execution / Pass A scoring engine (M6). The client-facing ICP editor UI (separate repo). Learning-loop reweighting of source profiles from outcomes (staged-flow §7e — M13). Re-deriving an ICP *from* an imported list (offered as an explicit option in M5.3, not the default).
- **Open decisions:** **D5** (ICP multiplicity) — proceed on Doc B §3 recommended default: support multiple ICPs per client, each compiling its own plan; do not hardcode one-ICP-per-client. **D7** (economics) — the per-campaign pre-run estimate and hard cap are surfaced here but the concrete budget bands are config (Doc C §5), confirmed later. **D1** (output boundary) — the scoring rubric/field set chosen here determine what the eventual handoff contains, but the boundary itself is set downstream.

### M5.3 — Import entry scenario (bulk identity resolution + ICP back-scoring + non-fit flagging — D6)
- **Purpose:** Accounts enter the system one of two ways, and both are **first-class and symmetric** (Doc B §4). Import is **not** a trivial branch — it has its own hard sub-pipeline (Doc B §4 Scenario B). A client list arrives as names/domains of varying quality ("IBM", "I.B.M.", "International Business Machines Corp.", a stale domain); each row must resolve to a canonical `account_entity`, or import quietly fails with duplicates, wrong-entity collapses, and silently-dropped unresolvable rows. The client picked these accounts, but we still **back-score them against their own stated ICP**, because the highest-value early signal we can give is *"3 of your 200 accounts don't actually match the ICP you defined"* or *"these 40 are dramatically better-fit than the rest."* Import skips *discovery*, never *scoring*. This issue owns the import sub-pipeline and converges its output into the same Pass A → tiering → checkpoint → Pass B path as discovered accounts.
- **Architecture sources:** Doc B §4 Scenario B (bulk identity resolution over messy free-text; ICP back-scoring; convergence), §4 non-fit behavior (D6 — flag and proceed), §5 (Stage 0 output: resolved, back-scored imported accounts + seeds); substrate §2 (identity resolution: deterministic-first, probabilistic + review queue, never silently collapse two real companies; cross-tenant reuse), §4 (CRM resolver as tier-1 — pulls existing accounts/contacts as tier-1 claims and detects "already a customer / already in pipeline"), §9 (explainable, provenance-backed scoring); staged-flow §4 (scoring bridge — imports converge here), §3 (existence/identity gate, here served by the same identity service one level up), §9 (identity service is the shared backbone for both axes); Doc C §1 (Pass A signal proxies); overview §3 (Output 1 fit/intent shape); Doc D §2/§4 (imported contact rows carry `use_class` + lawful basis at write time).
- **Scope / deliverables:**
  - A **bulk ingest** path accepting messy free-text lists (CSV/paste/CRM pull): names, domains, optional metadata, varying quality.
  - **Bulk identity resolution** of every row through the **M2 identity service**: deterministic auto-resolve on domain/registry-ID; probabilistic fuzzy match (name+geo+aliases, pgvector candidate set → scorer) otherwise; high-confidence (≈≥0.95) auto-merge; mid-band routed to the **human review queue** rather than guessed; **explicit handling of all three failure classes** — duplicates (collapsed to one `account_entity`), wrong-entity collapses (prevented by never silently merging near-matches), and unresolvable rows (surfaced as a distinct status, never silently dropped) (substrate §2, Doc B §4.1).
  - **Per-row resolution provenance**: each imported row records what it resolved to, by which key (domain/registry/fuzzy), at what confidence, and its status (`resolved` / `needs_review` / `unresolved`) — written as discovery-provenance-flavored claims (staged-flow §9: where/why an entity entered) so the client can audit the resolution.
  - **CRM-aware enrichment:** when the import is (or includes) the client's CRM, pull existing account/contact data in as **tier-1 claims** (substrate §4) — grounding research and detecting "already a customer / already in pipeline" early.
  - **Imported contact rows** (if the list includes people) resolve under their accounts and are written with `identity_binding` and `use_class` tags at extraction time (Doc D §2) plus a recorded lawful basis (Doc D §4), so M10's use-gate can govern them downstream — import does not bypass compliance tagging.
  - **ICP back-scoring:** every resolved imported account is scored against the client's **confirmed `ICP spec`** (M5.2) via the **M6 Pass A scoring engine** — import skips discovery, not scoring (Doc B §4.2). Each fit/intent score is decomposed and links to the claims behind it (substrate §9).
  - **Non-fit flagging (D6 — flag and proceed):** accounts whose fit falls below an ICP-relative threshold are **flagged with the evidence behind the low score** and surfaced to the client to keep or drop. **Do not** silently exclude (the client may know something the ICP doesn't encode) and **do not** auto-re-derive the ICP. **Re-deriving the ICP *from* the imported list is offered as an explicit option, not a default** (Doc B §4 D6).
  - **Convergence:** resolved, back-scored imported accounts flow into the **same Pass A → tiering → tier checkpoint → Pass B** path as discovered accounts (staged-flow §4) — the import path emits the identical account set shape the discovery path emits, so everything after the scoring bridge is mode-agnostic.
- **Interface / seam:**
  - **Exposes:** `import_accounts(rows[], icp_spec_ref) -> ImportResult{resolved[]{account_entity_id, back_score, fit_flag, resolution_provenance}, needs_review[], unresolved[]}`. The `resolved[]` set is the **same `account_entity`-keyed shape** the discovery path produces (staged-flow §4), so the scoring bridge and everything downstream cannot tell discovered from imported accounts except by their provenance flavor. This symmetry is the seam: import and discovery are interchangeable producers of scored accounts (`_conventions.md §2`).
  - **Consumes:** the **M2 identity service** (the *only* thing allowed to turn a free-text name into an `entity_id` — `_conventions.md §2`); the **M6 Pass A scoring engine** (back-scoring delegates to it, against the M5.2 `ICP spec` — M5.3 does not re-implement the scorer); the M4 **CRM `Resolver`** (tier-1 claims); the claim store (`current_value`) for the evidence behind each score and flag; M10 tagging conventions for imported contact claims.
  - **Swap points behind the seam:** the import file/format parser (CSV/Excel/CRM API) sits behind the row-ingest interface; swapping a CRM provider is a CRM-`Resolver` config change; the identity matcher and the scorer are entirely M2/M6 and invisible here.
- **Data model / schema:** Resolves rows to `account_entity` (`_conventions.md §4`, `status` transitions candidate→active on resolve). Writes **discovery-provenance** flavored entries (staged-flow §9: where/why entity entered = "client import, row N, matched on domain") and, for CRM imports, **tier-1 `claim`** rows (`extraction_method=crm_import`). Imported **contact** claims carry `identity_binding` + `use_class` + lawful-basis provenance (Doc D §2/§4 — uses the contact-claim provenance flavor in `_conventions.md §4`). Back-scores are emitted as the **Output-1 fit/intent shape** (fit_score, intent_score, decomposed, each linked to claims — `_conventions.md §4`); these are the same fit/intent score primitives that later compose `account_handoff` at handoff, not the full handoff object, which is assembled downstream (M12). Uses the M2 review-queue tables for `needs_review` rows. Adds an `import_batch` grouping marker (extends, does not redefine).
- **Dependencies:** **M2** (bulk identity resolution + review queue — the core of the import sub-pipeline), **M5.2** (the confirmed `ICP spec` to back-score against), **M6** (Pass A scoring engine for back-scoring; the scoring bridge imports converge into), **M4** (CRM resolver for tier-1 enrichment), **M1** (claim store + provenance), **M10** (use-class/lawful-basis tagging conventions for imported contacts). **Unblocks:** the convergence into Pass A → tiering for imported accounts; **M5.4** (resolved imports + existing customers become lookalike seeds).
- **Acceptance criteria:**
  - A messy list containing exact-duplicate variants of one company ("IBM", "I.B.M.", "International Business Machines Corp.") collapses to a **single** `account_entity`; two genuinely different same-name companies are **never** silently merged (mid-band routes to review).
  - Unresolvable rows appear in `unresolved[]` with a reason; **none are silently dropped**; mid-confidence rows appear in `needs_review[]` routed to the M2 review queue.
  - Every resolved row carries resolution provenance (resolved-to id, match key, confidence, status) auditable by the client.
  - Every resolved imported account is back-scored against the confirmed `ICP spec` with a decomposed fit/intent score, each sub-score linked to its claims (no score without evidence).
  - Non-fit accounts are **flagged with the evidence** and surfaced to keep/drop; they are **not** auto-excluded and the ICP is **not** auto-re-derived; the "re-derive ICP from this list" action exists as an explicit, opt-in option (D6).
  - When the import is a CRM pull, existing accounts/contacts enter as tier-1 claims and "already a customer / already in pipeline" is detectable.
  - Imported contact claims carry `identity_binding`, `use_class`, and a recorded lawful basis at write time (governable by M10).
  - The `resolved[]` output is shape-identical to the discovery path's output and flows through the same Pass A → tiering → checkpoint path (convergence verified end-to-end with a mock checkpoint).
- **Out of scope:** The identity-resolution algorithm itself, the review-queue UI/workflow, and in-flight locks (M2). The Pass A scoring engine internals (M6). The use-gate enforcement that decides whether a tagged imported contact claim may drive outreach (M10 — M5.3 only tags). Lookalike discovery from the imports (M5.4). The tier checkpoint human gate (M6/M7). Re-deriving the ICP from the list (the *action* is offered here; the synthesis it triggers is M5.2).
- **Open decisions:** **D6** (import non-fit behavior) — proceed on Doc B §4 recommended default: **flag + proceed**, surface evidence, never silently exclude, never auto-re-derive; expose re-derive as explicit opt-in. **D4** (contact geography — **resolved: mixed/global**) — imported contacts carry a resolved jurisdiction so Doc D policy applies. **D3** (personal-data posture) — imported contact claims are tagged at write time; which tags are usable is M10 config (Option 1 default), not decided here.

### M5.4 — Hybrid lookalike seeding from imports / existing customers
- **Purpose:** Import and discovery are **not exclusive** — import is often the **highest-quality way to *start* discovery** (Doc B §4 Hybrid). The client's imported list, plus their existing customers surfaced during reverse-profiling (M5.1's positioning/proof/customers pages and any CRM/customer-list import), are the **strongest seeds for lookalike discovery**. The natural default for a client who brings a list is to research *their* accounts **and** discover lookalikes of them, surfaced as "accounts like yours you may have missed." This issue assembles, ranks, and packages those seeds into the seed-set contract that **M6 mode-M1 lookalike expansion** consumes — it produces the seeds, not the discovery run.
- **Architecture sources:** Doc B §4 Hybrid (import list + existing customers = strongest lookalike seeds; "accounts like yours you may have missed"; import as the highest-quality way to start discovery), §2 (case studies / testimonials / "customers" pages double as seed accounts), §5 (Stage 0 output includes seeds for optional lookalike discovery); staged-flow §3 (M1 lookalike expansion from seed accounts and existing customers/CRM is a grounded discovery channel); substrate §4 (CRM resolver as tier-1 — existing-customer detection), §2 (identity resolution — every seed is a resolved entity); overview §2 (hybrid: import list = seeds for lookalike discovery).
- **Scope / deliverables:**
  - A **seed assembler** that collects candidate seed `account_entity`s from three sources, all already resolved to canonical entities: (1) **existing-customer evidence from M5.1** (entities behind case studies, testimonials, logos, "customers" pages), (2) **CRM existing customers** (tier-1, "already a customer" — substrate §4), (3) **resolved imported accounts from M5.3** (especially high-fit ones).
  - **Seed quality ranking / filtering:** prefer seeds that are (a) resolved with high identity confidence, (b) high-fit against the relevant confirmed `ICP spec` (using M5.3 back-scores where available), and (c) genuine customers/strong-fit anchors rather than noise — so lookalike expansion starts from clean anchors, not stale/wrong-entity rows.
  - **Per-ICP seed sets (D5):** because a client may have multiple confirmed ICPs, seeds are partitioned/tagged per ICP (a healthcare-payer customer seeds the healthcare ICP's lookalike search, not the fintech one).
  - **Seed provenance:** each seed records *why* it's a seed (customer / case-study / high-fit import) so the resulting lookalike candidates inherit explainable discovery-provenance ("found as a lookalike of your customer Acme") (staged-flow §9).
  - **Hybrid default policy:** for a client who brings a list, the default proposal is research-their-list **+** discover lookalikes; the client can opt out (always-has-the-wheel — Doc B §1). The opt-in/out is a flag on the campaign, surfaced via the M5.2 proposal flow.
  - **Coverage-confidence framing seam:** the seed set is annotated with which channels lookalike expansion will search, feeding M6/Doc C §7 coverage-confidence reporting ("estimated ~X% of the addressable set; channels not yet searched: …") — M5.4 supplies the seed/channel inputs, not the coverage estimate itself.
- **Interface / seam:**
  - **Exposes:** `assemble_lookalike_seeds(icp_spec_ref, client_kb_ref, {import_result?}) -> SeedSet{client_id, icp_key, icp_version, seeds[]{account_entity_id, seed_reason, seed_confidence, justifying_claim_ids}}`. (Implementation note: M5.3 keeps its back-scores **in-memory** — `account.scoring.*` is M6.3's durable write — so M5.4 consumes the in-memory `ImportResult` directly rather than a persisted `import_batch_ref`; and the ICP key lives on the per-ICP `SeedSet` envelope, not on each seed, per the no-`icp_id` convention — specs are keyed `(client_id, icp_key, version)`.) The `SeedSet` is the **input contract to M6 mode-M1 lookalike expansion** (staged-flow §3) — M6 consumes resolved `account_entity` seeds and runs the grounded expand loop + existence gate; M5.4 never runs discovery itself. The seeds are reusable directly as an `ICPProposal`'s `seed_accounts`, reaching M6 store/spec-mediated via the confirmed spec's `discovery_strategy.seed_account_ids`. This keeps the discovery engine swappable (Exa Websets / Parallel FindAll / Clay lookalike — all behind M6) and M5.4 purely a seed producer (`_conventions.md §2`).
  - **Consumes:** M5.1 (existing-customer entities from the Client Knowledge Base), M5.3 (resolved imported accounts + back-scores + CRM customers), the M2 identity service (all seeds are resolved `account_entity`s — never free-text), the M5.2 `ICP spec` (to scope/partition seeds per ICP and to know fit thresholds).
  - **Swap point behind the seam:** the seed-ranking heuristic (confidence × fit × customer-status) is config/policy; the actual lookalike *expansion* algorithm is entirely M6's and invisible here.
- **Data model / schema:** Reads `account_entity` + `claim`/`current_value` (existing-customer evidence, CRM tier-1 claims, import back-scores). Produces a `SeedSet` keyed per `(client_id, icp_key, icp_version)` containing resolved `account_entity_id`s with `seed_reason` and `seed_confidence`. Records seed-derivation as a discovery-provenance `claim` (`matched_channel='seed'`, unregistered `discovery.provenance` field, tenant-private, idempotent on the deterministic seed run id) so downstream lookalike candidates can cite "lookalike of seed X." Does not introduce new entity contracts — seeds are existing `account_entity` rows tagged for a discovery role.
- **Dependencies:** **M5.1** (existing-customer evidence), **M5.3** (resolved imports + CRM customers + back-scores), **M2** (all seeds resolved to entities), **M5.2** (per-ICP scoping). **Unblocks:** **M6** mode-M1 **lookalike expansion** (the SeedSet is its input); the hybrid path (research-the-list + discover-lookalikes) end-to-end.
- **Acceptance criteria:**
  - Given a client with reverse-profiled existing customers and an imported list, `assemble_lookalike_seeds` returns a `SeedSet` of resolved `account_entity`s, each with a `seed_reason` (customer / case-study / high-fit import) and `seed_confidence`.
  - Seeds are partitioned per confirmed ICP (D5): a healthcare-segment customer appears only in the healthcare ICP's SeedSet, not the fintech ICP's.
  - Low-confidence-resolution or low-fit candidates are filtered out (or down-ranked below a configurable threshold) so the seed set is composed of clean anchors.
  - For a client who imports a list, the default campaign proposal includes lookalike discovery; the client can opt out, and opting out produces an empty/suppressed SeedSet without breaking the import-only path.
  - The SeedSet is shape-valid as input to a mock M6 lookalike-expansion consumer (seam verified); each seed carries discovery-provenance that downstream candidates can cite.
  - No seed is ever a free-text name — every seed is a resolved `account_entity_id` (M2 invariant upheld).
- **Out of scope:** The **lookalike expansion run** itself — query expansion, the expand loop, the stopping rule on marginal yield, the discovery budget cap, and the existence/identity gate on discovered candidates (all **M6**, staged-flow §3). The **coverage-confidence estimate** computation (M6 / Doc C §7 — M5.4 only supplies seed/channel inputs). Pass A scoring of the discovered lookalikes (M6). The cross-tenant reuse policy for public-footprint seeds (M2).
- **Open decisions:** **D5** (ICP multiplicity) — seeds are partitioned per ICP, proceeding on the multi-ICP default. **D6** (import non-fit) — non-fit imported accounts are flagged (M5.3) but may still be intentionally kept by the client; whether a kept non-fit account is allowed as a lookalike seed defaults to *excluded from seeding* (a non-fit anchor seeds non-fit lookalikes) while remaining in the researched list — proceed on this default, surfaced for confirmation alongside D6.
