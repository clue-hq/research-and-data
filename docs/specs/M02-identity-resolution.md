# M2 — Identity Resolution
**Layer label:** layer:identity  ·  **Depends on:** M0, M1  ·  **Priority:** 2 (High)
**Architecture sources:** substrate §2 (identity service); substrate §1 (claim store / `current_value` / `field_definition` / `Resolver`); substrate §6(1) (schema/identity gates as the pre-spend entry gate); staged-flow §3 (existence/identity gate, mode M1), §6 (committee identity-resolution + identity-binding, modes M3/M4), §8 (mode-specific anti-hallucination), §9 (identity service as shared backbone for both axes); Doc B §4 (Scenario B bulk import resolution); Doc C §3 (per-entity hard budget cap — single-flight precondition), §4 (campaign idempotency `(campaign_run, phase)`); Doc D §1 (jurisdiction on contacts — D4), §4 (DSAR/erasure tractability); conventions §2 (modularity/DRY), §3 (taxonomies), §4 (contracts), §6 (stack).

## Goal & scope of this milestone

Identity resolution is the **front door** of the subsystem (substrate §2): the only component allowed to turn a free-text name into a resolved `entity_id`. Conventions §2 makes this a hard rule — *everything keys on a resolved `entity_id`, never a free-text name*, and *identity resolution (M2) is the only thing allowed to turn a name into an id*. Every other component (claim store M1, discovery M6, deep profiling M8, scoring M6, handoff M12) consumes ids from this service and never re-implements matching.

This milestone delivers the standard entity-resolution discipline as a first-class service: **deduplicate → record-link → canonicalize**, with confidence-thresholded auto-merge and a human review queue for the ambiguous mid-band (substrate §2). It is the shared backbone for **both research axes** (staged-flow §9): it powers the discovery *existence-gate* (a discovered candidate must resolve to a real canonical entity before admission — staged-flow §3) *and* the profiling *target-lock* (a profiling run is bound to the entity the service returns — staged-flow §5/§9). It also services **Scenario B bulk import** — resolving messy client-supplied free-text rows to canonical entities (Doc B §4).

Five issues, in build order:
- **M2.1 Entity model** — `account_entity` and contacts-under-accounts, the canonical id every component keys on.
- **M2.2 Dedup → record-link → canonicalize** — deterministic-first, pgvector-probabilistic-second candidate generation, then a scorer; the resolution engine.
- **M2.3 Confidence-thresholded auto-merge + human review queue** — the disposition policy over scorer output (≈≥0.95 auto-merge, mid-band → queue, never silently collapse two real companies).
- **M2.4 Redis in-flight locks** — `lock(entity_id)` before any expensive work, replacing the prototype's `run_pause.flag` / ad-hoc in-flight checks.
- **M2.5 Cross-tenant reuse with tenant isolation** — public-footprint claims amortize across clients; client-specific scoring and any client-private data stay strictly tenant-isolated.

**Explicitly NOT in this milestone.** The discovery *expand* pattern, marginal-yield stopping rule, and discovery-provenance authoring (M6); the import entry scenario itself and ICP back-scoring of imported accounts (M5.3 — Pass A scoring is M6); committee discovery / role inference and the contact resolvers that *feed* people into resolution (M8 — Deep Profiling, research modes M3/M4 in M8.3/M8.4); the `identity_binding` strength computation on contact field-claims (M9.4) and the appropriateness/use gate (M10.3 — M2 stores the `jurisdiction` column but does not adjudicate use); the trust-tiered source waterfall and any specific resolver implementation, e.g. Clay/Apollo/CRM (M4); durable campaign/per-account state machines and budget caps (M7). M2 provides the resolution *seam and store* those layers call; it does not contain their logic. The `Resolver` protocol, shared domain types, claim/provenance helpers, tracing wrapper, and config loaders are owned by **M0.2** and imported here, never re-implemented (conventions §2).

## Issues

### M2.1 — Entity model (account_entity, contacts under accounts)
- **Purpose:** Establish the canonical entity tables that the entire subsystem keys on. Conventions §2 fixes the central invariant: *everything keys on a resolved `entity_id`, never a free-text name.* Before any resolution logic can exist there must be a stable, well-keyed home for the resolved entity, its strong keys (domain, registry ids), its aliases, its lifecycle status, and the merge pointer that makes append-only history coherent. Contacts resolve *under* accounts (substrate §2, §7), so the contact entity is modeled here as a child keyed on its own strong identifiers (LinkedIn URL / verified email) with an account FK — the structural basis for the `(account, persona)` committee graph everything downstream reads.
- **Architecture sources:** substrate §2 (`account_entity` schema; contacts resolve under accounts on LinkedIn URL / verified email); substrate §1 (entities are referenced by `claim.entity_id` / `entity_type`); substrate §7 (the `(account, persona)` committee graph keys on these entities); staged-flow §9 (identity service is the shared backbone for both axes); Doc D §1 (every contact entity carries a resolved jurisdiction — D4 resolved mixed/global); conventions §3 (registry-id taxonomy `{NPI|DUNS|CIK|LEI…}`, committee personas), §4 (`account_entity` contract).
- **Scope / deliverables:**
  - `account_entity` table exactly per the conventions §4 / substrate §2 contract: `id (uuid pk), canonical_name, primary_domain (the strong key), aliases text[], hq_geo jsonb, registry_ids jsonb {NPI|DUNS|CIK|LEI…}, status enum(candidate|active|merged), merged_into uuid (nullable FK → account_entity.id)`.
  - `contact_entity` table (contacts under accounts): `id (uuid pk), account_entity_id uuid FK NOT NULL, full_name, linkedin_url (strong key, unique-when-present), verified_email (strong key, unique-when-present), aliases text[], geo jsonb, jurisdiction text (resolved per Doc D §1 — nullable until a location claim resolves it), status enum(candidate|active|merged), merged_into uuid`.
  - Unique / partial-unique constraints on the strong keys: `account_entity.primary_domain` (partial-unique where non-null, normalized to registrable domain); per-namespace uniqueness on `registry_ids`; `contact_entity.linkedin_url` and `contact_entity.verified_email` (partial-unique where non-null). Indexes on `canonical_name`, `aliases` (GIN), and `status`.
  - `status` lifecycle helpers (`candidate → active → merged`) and the `merged_into` chain resolver that always returns the surviving id (transitive-closure / union-find read, so a chain of merges resolves in one call).
  - A thin read API: `get_entity(id) → Entity`, `resolve_alias(name|domain|registry_id, entity_type) → entity_id | None` (exact strong-key lookup only at this issue; fuzzy is M2.2), and a `surviving_id(id)` helper.
- **Interface / seam:** **Exposes** the `account_entity` / `contact_entity` tables and the `Entity` domain type (from M0.2 shared types) that every other component consumes; this *is* the `entity_id` seam named in conventions §2. The `claim.entity_id` FK (M1) points here. **Consumes** only M0.2 shared domain types / db helpers. The model is implementation-agnostic: the strong-key set is *data* (registry_ids is a JSONB map, so a new vertical's registry — e.g. `healthcare.npi`, conventions §3 — is a new key, never a schema change). Swapping the persistence engine stays behind the read API; nothing downstream queries the tables directly except via the seam helpers.
- **Data model / schema:** `account_entity` and `contact_entity`. `account_entity` is the conventions §4 / substrate §2 contract verbatim — adds only types, indexes, and partial-unique constraints (no contradicting columns). `contact_entity` is the new substrate §2 "contacts resolve under accounts" structure with the Doc D §1 `jurisdiction` column. References the `claim` (M1) table only as the FK target of `claim.entity_id` — does not define `claim` or `current_value`.
- **Dependencies:** Blocked by **M0** (shared types, db migration tooling) and **M1** (the `claim` table whose `entity_id` FK lands here; co-defined so FKs are consistent). Unblocks **M2.2–M2.5**, and every downstream milestone that keys on `entity_id` (M3–M13).
- **Acceptance criteria:**
  - Migrations create `account_entity` and `contact_entity` with all columns/types from the contract; `make migrate && make migrate:down` round-trips cleanly.
  - Inserting two accounts with the same normalized `primary_domain` violates the partial-unique constraint; same for a duplicate `registry_ids.DUNS`; NULL strong keys are permitted (candidate entities pre-resolution).
  - `surviving_id` follows a 3-hop `merged_into` chain (A→B→C) and returns C; a cycle is rejected at write time (or detected and errored, never infinite-looped).
  - A `contact_entity` row cannot be inserted without a valid `account_entity_id` FK (contacts under accounts enforced).
  - `resolve_alias("acme.com", account)` returns the entity whose `primary_domain` or `aliases` matches after normalization; returns `None` for an unknown name with no fuzzy fallback at this issue.
  - `get_entity` returns the full typed `Entity`; reading a `merged` entity surfaces `merged_into`.
- **Out of scope:** Fuzzy/probabilistic candidate generation and scoring (M2.2); merge *decisioning* and the review queue (M2.3); the `identity_binding` strength computation on contact field-claims (M9.4 — only the column home, if any, is reserved, not the logic); resolving jurisdiction *from* location claims (M10.1 — M2 stores the column, the resolution rule is Doc D / M10); the `claim` table itself and `current_value` (M1).
- **Open decisions:** **D4** (resolved: mixed/global) is honoured by carrying `jurisdiction` on `contact_entity` from day one so the strict-case machinery (Doc D) has its hook; no decision hardcoded. **D8** (2026 registry/legal specifics) touches which `registry_ids` namespaces are populated, but the JSONB map is open-by-registration so no schema change is needed when the list firms up.

### M2.2 — Dedup → record-link → canonicalize (deterministic + pgvector probabilistic + scorer)
- **Purpose:** The resolution engine itself — the standard entity-resolution pipeline substrate §2 prescribes: *deduplicate → record-link → canonicalize.* Given a raw observation (a free-text name, a domain, a registry id, geo, aliases — from discovery, import, or committee), produce a ranked set of candidate matches with a calibrated score, so M2.3 can decide. The non-negotiable ordering is **deterministic first, probabilistic second** (substrate §2): an exact strong-key hit (domain / registry id) auto-resolves with no model call; only on a miss do we fall to fuzzy matching (name + geo + aliases) via pgvector candidate generation and a scorer. This is also the engine behind Scenario B's *bulk identity resolution over messy free-text* (Doc B §4) and the existence-gate's resolution step (staged-flow §3).
- **Architecture sources:** substrate §2 (deterministic-first / probabilistic-second; embeddings in pgvector for the candidate set, then a scorer; never let a near-match silently collapse two companies); staged-flow §3 (existence/identity gate — candidate must resolve to a real canonical entity), §6 (contacts resolved on LinkedIn URL / verified email with the same alias+confidence machinery), §8 (mode M1/M3 anti-fabrication via existence gate); Doc B §4 (bulk resolution over messy free-text: "IBM" / "I.B.M." / "International Business Machines Corp." / stale domain); conventions §6 (pgvector for dedup candidate sets).
- **Scope / deliverables:**
  - **Stage 1 — deterministic match.** Normalizers (registrable-domain extraction, legal-suffix stripping, unicode/punctuation folding, registry-id canonicalization) and exact-key lookup against M2.1 strong keys. An exact strong-key hit returns a single candidate at score `1.0` and short-circuits the rest of the pipeline (no embedding, no scorer, no spend).
  - **Stage 2 — blocking / candidate generation (pgvector).** On deterministic miss, embed the normalized name (+ geo/alias context) and pgvector-ANN retrieve a bounded top-K candidate set from existing entities of the same `entity_type`; combine with cheap blocking keys (name-trigram, geo bucket) to keep recall up without scanning the whole table.
  - **Stage 3 — pairwise scorer.** A deterministic feature-based scorer over `(observation, candidate)` pairs — name similarity (token/Jaro-Winkler/embedding cosine), geo agreement, alias overlap, weak-key co-occurrence — emitting a calibrated `match_score ∈ [0,1]` per candidate. Scorer is **policy-as-data** (conventions §2): weights/thresholds live in versioned config, swappable per entity_type/vertical without code change.
  - **Canonicalization** helpers: choose `canonical_name`, merge `aliases`, union `registry_ids`, pick the best `primary_domain` / `hq_geo` when two records are confirmed the same (the actual write is performed by M2.3's auto-merge path).
  - A uniform `resolve(observation, entity_type) → ResolutionResult{ candidates:[(entity_id, score, features)], method: deterministic|probabilistic, top_score }` entry point used by discovery, import, and committee callers.
  - **Bulk mode** for Scenario B: batched resolution over a list of messy rows, returning per-row results (resolved / mid-band / unresolvable) so import can handle each explicitly (Doc B §4) rather than silently best-guessing.
- **Interface / seam:** **Exposes** the `resolve(...)` / bulk-`resolve_many(...)` entry point returning `ResolutionResult` — the single seam callers use to turn an observation into candidate `entity_id`s. **Consumes** M2.1 (entity reads, strong-key lookup, canonicalization writes via M2.3), pgvector (candidate sets), and M0.2 shared types/config loader/tracing wrapper. The matcher is hot-swappable behind this seam: the **scorer model and the embedding model are both swappable** (conventions §2 — judge/scorer swap stays behind the seam) because callers only see `ResolutionResult`; replacing the pgvector blocker with an external ER service, or the heuristic scorer with a learned model, is a config/implementation change invisible to discovery/import/committee. Note the boundary: M2.2 produces *candidates + scores*; it does **not** decide merges (that is M2.3) — keeping the costly-policy decision on its own seam.
- **Data model / schema:** Reads/writes `account_entity` / `contact_entity` (M2.1). Adds a pgvector embedding column/table for entities (e.g. `account_entity_embedding(entity_id, embedding vector, model_version)`) and the versioned **scorer config** (weights, thresholds, normalizer ruleset version) loaded via M0.2 — policy-as-data, not a claim type. No new claim types. Strong keys and aliases are read straight from M2.1 per conventions §4; does not redefine `claim` or `current_value` (M1).
- **Dependencies:** Blocked by **M2.1** (entity model + strong keys) and **M0** (shared types, pgvector setup, config loader). Independent of M4 — M2.2 does not call resolvers; resolvers (M4) *call* M2.2 to resolve the entity they enriched. Unblocks **M2.3** (consumes scores), the M6 discovery existence-gate and the M5.3 import scenario, and committee resolution in **M8** (modes M3/M4).
- **Acceptance criteria:**
  - Exact domain match resolves with `method=deterministic`, `top_score=1.0`, and **zero** embedding/scorer calls (verified by a call-count assertion) — deterministic-first proven, not just configured.
  - The Doc B §4 worked example resolves correctly: `"IBM"`, `"I.B.M."`, `"International Business Machines Corp."`, and a known IBM domain all resolve to the same `entity_id`; a deliberately stale/parked domain does **not** force a wrong collapse (lands mid-band or unresolvable).
  - Two genuinely distinct same-name companies in different geos (e.g. two "Apex Logistics" in different countries) do **not** collapse: they surface as separate candidates with sub-auto-merge scores (the "never silently collapse two real companies" rule, substrate §2, is testable).
  - pgvector candidate generation returns a bounded top-K (K configurable) and recall on a labeled fixture set meets a stated threshold; the scorer's score is monotonic with labeled match likelihood on the eval fixture.
  - Bulk mode returns one result per input row with `method`, `top_score`, and candidate list; partitions rows into resolved / mid-band / unresolvable without throwing on garbage rows.
  - Swapping the scorer config version changes thresholds/weights with no code change; swapping the embedding `model_version` re-embeds without altering the `resolve` signature.
- **Out of scope:** The auto-merge / queue *decision* and the actual merge write/`merged_into` linkage (M2.3); ICP back-scoring of resolved imported accounts (M5.3 import scenario; Pass A scoring is M6 — both distinct from match-scoring); discovery query expansion and the marginal-yield stopping rule (M6); contact role inference / persona tagging (M8 — modes M3/M4); resolver implementations that produce the observations being resolved (M4).
- **Open decisions:** **D8** — the registry-id set used for deterministic Stage-1 matching depends on confirmed vertical registries; handled by data-driven `registry_ids` so no fork. No other Dx is hardcoded.

### M2.3 — Confidence-thresholded auto-merge + human review queue
- **Purpose:** Turn M2.2's scores into safe dispositions. Substrate §2 is explicit: *high-confidence (≈≥0.95) auto-merges; the mid-band routes to the human review queue rather than guessing. Never let a near-match silently collapse two real companies.* This issue owns the **decision policy** and the **review surface** over ambiguous matches — the mode-specific anti-hallucination mechanism for the identity axis (staged-flow §8: "person identity-resolution + role plausibility gate", "existence/identity gate before admission"). It is where the universal rule applies at the entity level: a *wrong merge* is fabrication of identity; routing the ambiguous case to a human is the correct, conservative output, not a failure.
- **Architecture sources:** substrate §2 (confidence-thresholded auto-merge ≈≥0.95; mid-band → human review queue; never silently collapse); substrate §6(1) (schema/identity gates, dedup registry as the pre-spend entry gate); staged-flow §3 (existence gate admits a candidate only after it resolves to a real canonical entity), §6 (person gates), §8 (anti-fabrication table); substrate §10 (human-in-the-loop is a *designed surface*, `interrupt()`-style pause/resume); conventions §4 (`account_entity.status` / `merged_into`), §5 (empty/flagged-is-correct universal rule applied to identity).
- **Scope / deliverables:**
  - **Disposition policy** (policy-as-data, conventions §2): three bands keyed off `ResolutionResult.top_score` and band thresholds in versioned config — **auto-merge** (≥ high threshold, default ≈0.95), **review** (mid-band), **new-entity** (below low threshold → admit as a fresh `candidate` entity). Thresholds per entity_type and overridable per vertical.
  - **Auto-merge executor**: performs canonicalization (M2.2 helpers), writes the surviving entity, sets the loser's `status=merged` and `merged_into`, and **re-points** affected claims' effective entity via the `merged_into` chain (claims are append-only — M1 — so merge never rewrites claim rows; reads resolve through `surviving_id`). Idempotent on the candidate pair so a retried merge is a no-op.
  - **Human review queue**: an `identity_review_task` table holding the observation, the ranked candidates with scores + features, the proposed action, tenant scope, and status; an enqueue path from the mid-band; a resolve API (`merge_into(id)` / `create_new_entity` / `not_a_match` / `split`) that applies the human decision and records it.
  - **Disposition provenance / audit**: every merge or new-entity admission records who/what decided (auto vs. reviewer), the score, and the config version — so an entity's identity history is queryable (mirrors the claim store's audit discipline).
  - **Resume hook**: the queue is designed to be driven by the durable-execution pause/resume surface (substrate §10, M7) — M2.3 exposes the enqueue + resolve API; it does not implement the campaign state machine.
  - **Labeled-data capture**: human dispositions are emitted as labeled pairs (match / not-match) for later scorer training (substrate §9 / §10 feedback loop) — capture only, no model training here.
- **Interface / seam:** **Exposes** `disposition(ResolutionResult) → {auto_merged(id) | enqueued(task_id) | new_entity(id)}` and the review-queue resolve API. This is the seam between *scoring* (M2.2) and *committing identity* — the only place merges are written. **Consumes** M2.2 (`ResolutionResult`), M2.1 (entity writes, `merged_into`, `surviving_id`), M1 (claim reads via `surviving_id`; never UPDATEs claims), and the M7 pause/resume surface (loose coupling — M2.3 enqueues; M7 schedules the human task). The **threshold band is config**, so tuning auto-merge aggressiveness, or swapping the queue UI/transport (Postgres-backed now, a workflow engine later), stays behind the seam. The Postgres-state-machine → Temporal swap (conventions §2) touches only *how* the human task is scheduled, not the enqueue/resolve contract.
- **Data model / schema:** Adds `identity_review_task(id, entity_type, observation_json, candidates_json[{entity_id,score,features}], proposed_action, tenant_id, status enum(open|resolved|dismissed), resolution enum, resolved_by, resolved_at, config_version)`. Mutates `account_entity` / `contact_entity` `status` + `merged_into` (M2.1). Reads `claim` (M1) only through `surviving_id`; never UPDATEs claim rows (append-only preserved). References versioned disposition-policy config (M0.2). Adds nothing new to the `account_handoff` contract.
- **Dependencies:** Blocked by **M2.1** (status/merge fields) and **M2.2** (scores). Soft-depends on **M7** for the human-task scheduling surface (degrade gracefully: queue is populated and resolvable via API even before M7 lands the campaign state machine). Unblocks safe entity admission for the M5.3 import scenario and the M6 discovery existence-gate, and committee gates in **M8** (modes M3/M4).
- **Acceptance criteria:**
  - A pair scoring ≥ the high threshold auto-merges: loser gets `status=merged` + correct `merged_into`; `surviving_id(loser)` returns the survivor; the survivor's `aliases` / `registry_ids` are the union of both; the merge is idempotent (second call is a no-op).
  - A mid-band pair creates exactly one `open` `identity_review_task` with both candidates, scores, features, and proposed action — and does **not** mutate any entity until resolved (the "never silently collapse" rule is enforced, not advisory).
  - A below-low-threshold observation admits a new `candidate` entity and creates no review task.
  - Resolving a task via `merge_into` applies the merge and flips status to `resolved` with `resolved_by` / `resolved_at` / `config_version` recorded; `not_a_match` admits/keeps both as distinct entities; `split` reverses an erroneous prior merge (un-points `merged_into`) and re-resolves claims to the corrected survivor.
  - After a merge, claims attached to the loser are readable under the survivor via `current_value` (M1) with **no claim row UPDATE** (append-only preserved) — verified by row-version assertion.
  - Changing the threshold config version moves a borderline pair between auto-merge and review with no code change.
  - Every disposition (auto or human) is retrievable as an audit record with score + decider + config version.
- **Out of scope:** The threshold *value* tuning against real data (operational, post-launch — informed by D8 risk posture); training the scorer on captured labels (M13 feedback loop, M13.2/M13.3); the campaign/per-account durable state machine and SLA timers that drive the queue (M7); `identity_binding` for contact field-claims (M9.4) and the appropriateness/use gate (M10.3 — distinct gates on claims, not on identity).
- **Open decisions:** **D8** — the conservative posture (favor review over auto-merge in higher-risk jurisdictions/verticals) is expressed via config thresholds, not hardcoded; final values await the compliance/data owner. The empty/flagged-is-correct universal rule (conventions §5) is applied to identity here: routing-to-human beats a wrong auto-merge.

### M2.4 — Redis in-flight locks
- **Purpose:** Prevent two workers from researching (or merging) the same entity concurrently. Substrate §2 prescribes *distributed in-flight locks (Redis) to replace the prototype's `run_pause.flag` and ad-hoc in-flight checks: `lock(account_id)` before any expensive work so two workers never research the same account.* This is both a correctness guard (no double-write / no merge race against an in-flight profiling run) and a cost guard (no duplicate spend on the same entity — Doc C §3 per-entity budget discipline depends on single-flight execution). It is the ephemeral-state half of the stack (conventions §6: *Redis for in-flight account locks and rate-limit coordination*).
- **Architecture sources:** substrate §2 (distributed in-flight locks; `lock(account_id)` before expensive work), §5c (idempotency keyed on `(account, field, tier)`; locks complement idempotency for concurrency); Doc C §3 (per-entity hard budget cap — single-flight is its precondition), §4 (campaign-level idempotency `(campaign_run, phase)`); conventions §6 (Redis for in-flight locks + rate-limit coordination).
- **Scope / deliverables:**
  - A distributed lock primitive over Redis: `lock(entity_id, *, ttl, owner)` / `release(...)` with a context-manager / `async with` ergonomics, atomic acquire (SET NX PX), a fencing token or owner check on release (so a slow worker can't release someone else's lock), and a **TTL with renewal/heartbeat** so a crashed holder's lock auto-expires (no permanent deadlock — the failure the `run_pause.flag` couldn't handle).
  - Lock keyspace conventions: `lock:account:{id}`, `lock:contact:{id}`, namespaced by tenant where reuse boundaries require it (coordinated with M2.5 — public-entity work may be cross-tenant single-flight; client-private work is tenant-scoped).
  - **Rate-limit coordination** primitive (same Redis substrate, conventions §6): a shared token-bucket / sliding-window per `source_key` so resolvers (M4) across workers respect provider rate limits — exposed as a helper the source layer consumes.
  - Integration seam for the merge path (M2.3) and future expensive work (M4/M8): acquire the entity lock before merge/profiling, release after; merges acquire locks on *both* candidates in a deterministic order to avoid deadlock.
  - Observability: lock acquisition/contention/expiry counters surfaced via the M0.2 tracing wrapper so contention is measurable (feeds Doc C §6 observability).
- **Interface / seam:** **Exposes** the `EntityLock` / `acquire` / `release` API and the `RateLimiter` helper — the concurrency seam every expensive-work caller uses. **Consumes** only Redis and M0.2 (tracing/config). The implementation is fully hidden behind the API: swapping Redis for another lock backend (or moving fencing into a Temporal activity when the durable-execution layer graduates — conventions §2 "Temporal-shaped") is invisible to callers. Locks are *advisory coordination*, distinct from M1's append-only / idempotency guarantees and M2.3's merge atomicity — the contract makes clear locks prevent *wasted concurrent work*, while correctness on retry still rests on idempotency keys (substrate §5c) and append-only writes (M1).
- **Data model / schema:** No Postgres tables. Redis keyspace only (`lock:*`, `ratelimit:*`), documented as ephemeral state — explicitly **not** a source of truth (conventions §6: Postgres is the only source of truth; Redis holds locks / ephemeral state). No change to `account_entity` / `claim`.
- **Dependencies:** Blocked by **M0** (Redis client/config in shared package) and **M2.1** (entity ids to lock on). Tightly used by **M2.3** (merge must lock both candidates) and **M2.5** (lock scoping respects tenant boundaries). Unblocks safe concurrent expensive work in **M4/M7/M8** (resolution, profiling, committee).
- **Acceptance criteria:**
  - Two concurrent `acquire(entity_id)` calls: exactly one succeeds; the second either blocks until release/TTL or returns "busy" per the chosen API mode — verified under a concurrent test.
  - A holder that dies without releasing has its lock auto-expire at TTL (no permanent deadlock); a long-running holder renews the lease and is **not** preempted mid-work.
  - Release is owner-safe: worker B cannot release worker A's lock (fencing token / owner check enforced) — verified by a negative test.
  - A merge in M2.3 acquires locks on both candidate ids in deterministic order and completes without deadlock under a two-merge cross-contention test.
  - The rate limiter caps calls per `source_key` across N concurrent workers to the configured budget within tolerance.
  - Lock contention/expiry metrics are emitted through the tracing wrapper.
  - Killing Redis does not corrupt Postgres truth: in-flight work may duplicate (degraded), but idempotency keys (M1 / §5c) prevent double-write — documented and tested as the failure posture.
- **Out of scope:** Per-entity / per-run **budget caps** and the hard-stop on `sum(cost_cents)` (M7.5, substrate §5c / Doc C §3 — locks are a precondition, not the cap); the per-account LangGraph checkpointing (`AsyncPostgresSaver`, M7); the campaign-run state machine and `(campaign_run, phase)` idempotency (M7 / Doc C §4); resolver-specific retry/backoff policy (M4).
- **Open decisions:** None of D1–D8 bind directly. Cross-tenant lock scoping is coordinated with **M2.5** (public-entity single-flight vs. tenant-scoped private work).

### M2.5 — Cross-tenant reuse with tenant isolation
- **Purpose:** Realize the architecture's stated moat while keeping it safe. Substrate §2: *Public-footprint claims about a company (employee count, tech stack, funding) are partially reusable across clients and amortize cost; client-specific scoring and any client-private data stay strictly tenant-isolated. This is a real moat — your claim store gets better and cheaper per account as more clients touch the same public entities.* This issue defines the **reuse boundary** as a property of the data model: which claims are public-footprint (shared, keyed on the canonical entity) versus tenant-private (scoring, CRM-imported, client-knowledge-derived, any contact `facet` / personal data), and enforces the isolation so reuse never leaks one client's private signal to another.
- **Architecture sources:** substrate §2 (cross-tenant reuse, carefully; public-footprint reusable, client-specific scoring + private data tenant-isolated; the moat); substrate §4 (CRM resolver pulls client data as tier-1 claims — inherently tenant-private); substrate §9 (scoring is per-client/per-ICP — tenant-private by construction); Doc D §4 (personal claims, retention, erasure resolve per `contact_entity_id` — DSAR tractability); staged-flow §9 (one substrate, richer typing); conventions §2 (policy-as-data; tenant isolation as a seam), §4 (`claim`, `current_value`, `account_handoff`).
- **Scope / deliverables:**
  - A **reuse-class** classification on claims (extends the §4 `claim` contract by adding a derived/stored dimension, e.g. `reuse_scope enum(public_footprint | tenant_private)` plus `tenant_id` where private). Classification is **policy-as-data**: a config maps `(field_key namespace, extraction_method, source_tier)` → reuse_scope. Defaults: `core.*` / `account.*` public-footprint (firmographic/technographic/funding facts, substrate §2 examples); `crm_import` method, scoring outputs, `contact.facet.*` / personal data, and `account.resonance.*` (client/ICP-shaped consumption) → tenant_private. The classifier is the single point that decides reuse — no caller hardcodes it.
  - **Entity-level reuse**: the canonical `account_entity` (and its strong keys/aliases) is shared across tenants — the same real company resolves once. Contact entities default tenant-scoped given personal-data governance (Doc D), with public professional identity (LinkedIn URL) optionally shared per posture (D3); ship private-default.
  - **Isolation enforcement**: every read path that returns claims is tenant-scoped — extends M1's `current_value(entity, field)` with a tenant filter so a tenant-scoped read returns public-footprint claims (any tenant) ∪ this tenant's private claims, and **never** another tenant's private claims. Row-level guard (RLS or query-layer predicate) on `claim` keyed on `(reuse_scope, tenant_id)`. This adds the scoping filter to the M1-owned read; it does not redefine the merge policy.
  - **Cost amortization hook**: when a resolver (M4) would fill a public-footprint field already satisfied by a fresh enough public claim (within the field's freshness TTL, M1 / §6), the system reuses it instead of re-spending — the "cheaper per account as more clients touch the same entity" payoff, surfaced in per-source yield / cost observability (Doc C §6).
  - **Erasure/DSAR alignment** (Doc D §4): tenant-private personal claims for a `contact_entity` resolve to a deterministic tombstone set; public-footprint sharing is documented as scoped to non-personal company facts so DSAR stays tractable.
  - Tenant-isolation tests as a first-class fixture (the security-sensitive seam).
- **Interface / seam:** **Exposes** the reuse-class classifier (`reuse_scope(field_key, method, tier) → scope`) and the tenant-scoping predicate that M1's `current_value` and all claim reads consume — the isolation boundary. **Consumes** M1 (`claim`, `current_value`, `field_definition` freshness TTLs), M2.1 (shared canonical entity), and the reuse-policy config (M0.2). The classification policy is **data, not code** (conventions §2): adding a vertical pack's public-footprint fields, or tightening a client's posture (D3), is a config change behind the seam. The isolation mechanism (RLS vs. query predicate) is swappable without changing the read contract. Critically, this seam is what lets the claim store (M1) stay a single shared substrate (conventions §2) while honouring multi-tenancy — the tenant dimension is a *filter*, not a fork of the store.
- **Data model / schema:** Extends the §4 `claim` contract additively with `tenant_id` (nullable for public_footprint) and `reuse_scope` (derived from policy at write, stored for fast filtering) — no contradiction with the §4 columns. Index on `(entity_id, field_key, reuse_scope, tenant_id)` for the scoped `current_value` read. References `field_definition` freshness TTLs (M1) for the amortization-reuse decision. Touches `account_handoff` (M12) only insofar as handoff reads are tenant-scoped through this seam. No change to `account_entity` beyond it being shared.
- **Dependencies:** Blocked by **M1** (claim store, `current_value`, freshness TTLs — the read path this scopes) and **M2.1** (shared canonical entity). Coordinates lock scoping with **M2.4**. Informs **M4** (resolvers check public-footprint reuse before spending), **M6** (Pass A scoring reads are tenant-scoped), and **M12** (handoff reads are tenant-scoped). Personal-data classification interlocks with **M10** (use-class/posture) — M2.5 ships the conservative private-default; M10 layers the use-gate.
- **Acceptance criteria:**
  - A public-footprint claim (e.g. `core.employee_count` written by tenant A) is returned by a tenant-scoped `current_value` read for tenant B — reuse works across tenants.
  - A tenant-private claim (e.g. a `crm_import` fact, a scoring output, or a `contact.facet.*` claim written by tenant A) is **never** returned to tenant B under any read path — verified by an isolation test that asserts zero cross-tenant private leakage.
  - The classifier maps the substrate §2 examples correctly: employee_count / tech_stack / funding → `public_footprint`; CRM-imported, scoring, personal/facet, resonance → `tenant_private` — and is driven by config (changing the policy reclassifies without code change).
  - With a fresh-enough public-footprint claim present, a second tenant's resolver run for the same public field reuses it and records **no new cost** for that field (amortization measurable in cost observability).
  - A DSAR/erasure request for a `contact_entity` resolves to exactly the tenant-private personal claims for that contact (tombstoned), leaving shared non-personal company facts intact — Doc D §4 tractability verified.
  - Disabling cross-tenant reuse via config makes every claim behave as tenant_private (safe degradation), with reads still correct.
- **Out of scope:** The use-class taxonomy, jurisdiction policy, and appropriateness/use gate on personal claims (M10 / Doc D — M2.5 only does the *reuse/isolation* boundary, not the *use* boundary); per-client posture selection (D3, M10 config); the scoring engine whose outputs are tenant-private (M6); CRM resolver implementation (M4); cross-tenant claim *attribution* / billing reconciliation (economics, D7 / M13).
- **Open decisions:** **D3** (personal-data posture) — M2.5 ships contacts/personal claims tenant-private by default (Option-1-aligned) and exposes the reuse classifier as config so a posture change is data, not code; not hardcoded. **D7** (cost pass-through) — whether amortization savings surface to clients is a Doc C §5 / M13 surface; M2.5 records the saving, leaves the surfacing decision open. **D8** touches what counts as safely-public per jurisdiction; expressed via the reuse-policy config.
