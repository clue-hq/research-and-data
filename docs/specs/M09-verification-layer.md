# M9 — Verification Layer
**Layer label:** layer:verification  ·  **Depends on:** M1, M4  ·  **Priority:** 2 (High)
**Architecture sources:** substrate §0 (the one bet), §1 (claim store, evidence-span rule, merge view, `corroborations`), §6 (the verification layer — gates, corroboration, faithfulness judge, freshness, evals), §11 (build order — verification before tier-4 agents), §12 (stack), §13 (anti-patterns); staged-flow §5 (M2 target-lock), §6 (identity-binding), §8 (mode-specific anti-hallucination), §9 (verification layer extends with identity-binding; identity service is the shared backbone), §10 (end-to-end map); Doc C §1 (signal proxies churn fast), §2 (field-classes), §6 (verification-health observability); Doc D §3, §4, §5, §7 (two distinct gates — accuracy vs. appropriateness; personal-claim retention; separate observability; use-gate runs after identity-binding + judge).

## Goal & scope of this milestone

This milestone builds **the verification layer** — the substrate's answer to the single product requirement "our research must be correct and accurate" (substrate §6). It turns *verifiability into a property of the data model*, not a QA pass bolted on at the end (substrate §0, the one architectural bet). It is the layer that sits between claim production (resolvers in M4, deep-profiling workers in M8, tier-4 synthesis in M11) and any downstream consumer (scoring in M6, the handoff in M12), promoting only claims that survive its gates and leaving everything else as an `unverified` / empty-flagged correct output.

The verification layer is **layered and ordered** (substrate §6): (1) pre-spend schema/identity gates run *before* a resolver is invoked; (2) structural provenance + corroboration rules run as claims land; (3) the faithfulness judge runs on every tier-4 synthesized claim as its own graph step; (4) identity-binding gates contact claims; (5) freshness TTLs keep the merge view honest and drive re-research; (6) an eval harness measures the whole machine against a golden set so a model/resolver swap cannot silently regress quality. Per the build order (substrate §11), the verification layer (step 5) is stood up **before** the tier-4 LLM agents (step 6) it polices.

**Where it sits in the end-to-end map** (overview §2; staged-flow §10): it is the box labeled *"Verification (gates · corroboration · faithfulness judge · identity-binding · use-gate · freshness)"* (overview §2) — staged-flow §10 draws the same box without the use-gate, which Doc D §7 adds — sitting between Pass B deep research and the output. The **claim's `verification_state`** (accuracy verdict) and its **`freshness_state`** (freshness disposition) are the artifacts this milestone produces and that everything else reads.

**What is in scope here:**
- **M9.1** Pre-spend schema/identity gates (the entry gate — official-domain/canonical-name/geo lock, dedup registry, in-flight lock, target-locked prompt assembly).
- **M9.2** Corroboration rules — promote a scoring/content-load-bearing field only with ≥N independent tier≤3 sources; conflict flags on disagreeing tier≤2 sources.
- **M9.3** The faithfulness judge — LLM-as-judge claim-level entailment over (`value_json`, `evidence_span`), as a distinct trace span; reject/re-retrieve/leave-empty on failure.
- **M9.4** The identity-binding gate — `strong` vs `weak`, weak never promotes / never drives outreach (the contact-axis analogue of the evidence-span rule).
- **M9.5** Freshness TTL engine + re-research cadence — field-level TTLs, staleness as a queryable/discountable signal, re-research scheduling.
- **M9.6** Eval harness + golden account set + rubric scoring — the regression and accuracy-defence battery.

**What is explicitly NOT here:**
- The **appropriateness / use gate** (`use_class × jurisdiction × client_policy`) — a *distinct* gate (Doc D §3, §5) owned by **M10**. M9 builds the *accuracy/identity-binding* gate only; M9.4 produces the `identity_binding` strength that M10's use-gate consumes. The verification *pipeline* is designed (M9.1, M9.4) so the use-gate plugs in after identity-binding and the faithfulness judge (Doc D §7) without a code fork.
- **Tier-4 synthesis itself** (Exa Deep / Parallel Task resolvers, the synthesis fields) — owned by **M11**; M9.3's judge runs *over* M11's output and is built first (substrate §11 build order: verification before the tier-4 agents).
- The **`current_value` merge view** and **field registry / `field_definition`** — owned by **M1**; M9 *reads* the merge policy and *extends* `field_definition` with corroboration thresholds, TTLs, equality modes, and structured gate specs (policy-as-data, not new code). M9.2 sets the verification verdict and conflict flag that M1.2's merge surfaces; it does not own the merge ranking.
- The **observability/tracing skeleton** and **verification-health dashboard** — the named-span scaffold is M0.5; the test/eval-harness scaffold is M0.6; the client-facing verification-health surface is M13.4. M9 *emits* the spans and metrics those consume.
- **Resolvers / collectors** that produce claims (M4, M8, M11) and **re-research execution** (the durable graph / campaign state machine that *runs* a refresh job is M7). M9.5 *emits* re-research candidates and a cadence policy; M7 schedules and runs them.

The verification layer is **policy-as-data** (conventions §2): corroboration thresholds, freshness TTLs, judge model/prompt versions, identity-binding rules, and gate specs are versioned config rows the engine reads — swappable per client/ICP without code changes. The whole layer is exposed behind one **`verify(claim) -> VerificationResult`** seam plus the **`verification_state`** column (and the **`freshness_state`** column), so a judge-model swap, a corroboration-rule change, or a Postgres-state-machine→Temporal migration all stay behind the seam.

**Note on milestone-level dependencies.** Per the milestone map (conventions §7), M9 depends on **M1** (claim store, merge view, field registry) and **M4** (source layer / `source_manifest`). Several M9 issues *also consume* primitives from **M2** (identity resolution: the resolved `entity_id`, verified handle/email, Redis in-flight locks) and **M0** (the OpenRouter `LLMGateway`, tracing, eval scaffold). M2 is **not** a transitive dependency reachable through M1 (it is M2 that depends on M1, not the reverse); the M2 dependency is a direct cross-milestone consumption called out per issue below.

## Issues

### M9.1 — Pre-spend schema/identity gates
- **Purpose:** The cheapest verification is the one that prevents spend on a doomed claim. Before any resolver is invoked or any synthesis dollar is spent, a claim/research request must clear a set of **entry gates** that were the prototype's single strongest contribution (substrate §6(1)): the official-domain requirement, geo/canonical-name lock, dedup registry membership, the in-flight lock, and a **target-locked prompt** ("this exact company, this domain — do not drift to similarly-named orgs"). This issue promotes those into a first-class, declarative pre-spend gate that every claim-producing path (M4 waterfall, M8 workers, M11 synthesis) calls before it acts. It is the structural form of the staged-flow §8 anti-drift mechanism (mode-M2 target-lock) and the existence gate, applied uniformly at the profiling/spend entry.
- **Architecture sources:** substrate §6(1) (schema/identity gates pre-spend), §2 (identity service, in-flight locks), §1 (field registry as the contract); staged-flow §5 (mode-M2 target-lock), §8 (mode-specific anti-hallucination — target-lock, existence gate), §9 (identity service is the shared backbone); Doc C §3 (per-entity hard budget cap — gate fails closed before spend).
- **Scope / deliverables:**
  - A `PreSpendGate.check(request) -> GateDecision{pass|reject, reasons[]}` callable invoked by the M4 waterfall, M8 orchestrator/workers, and M11 resolvers *before* any external call.
  - **Schema gate:** the request's `field_key` must exist in the field registry (M1.3) and the requested source tier must be in that field's `tier_plan`; `value_json` (when present) must satisfy the field's `validation`. A field/tier mismatch fails closed.
  - **Identity gate:** the `entity_id` must resolve to an `account_entity`/contact with `status ∈ {candidate(discovery-only), active}` (M2) — a `merged` entity is rejected (it should redirect to `merged_into`); the bound entity must carry a strong key (`primary_domain` for accounts; LinkedIn URL / verified email for contacts). Free-text names are rejected outright (conventions §2: everything keys on `entity_id`).
  - **Target-lock prompt assembly:** a reusable helper that injects the resolved entity's canonical name, `primary_domain`, `hq_geo`, and disambiguators into any synthesis/scrape query ("`site:` the canonical domain", "do not drift to similarly-named orgs"), so target-lock is constructed, not hand-prompted (staged-flow §5).
  - **In-flight lock check:** confirm the Redis `lock(entity_id)` is held by the calling run before expensive work (substrate §2); reject if another worker owns it (anti-double-spend; idempotency complements M7.4).
  - **Dedup-registry check:** the entity must be in the resolved registry (not a raw discovery hypothesis that hasn't passed M6.2's existence gate).
  - The schema/identity portion applies to **every** claim-producing call regardless of tier (correctness, not just cost); the spend-protection (lock + budget fail-closed) bites hardest on tier≥2. Every decision emits a named trace span (`verification.pre_spend_gate`) and is recorded so "claims blocked pre-spend" is a measurable verification-health metric (Doc C §6).
- **Interface / seam:**
  - **Exposes:** `PreSpendGate.check(GateRequest) -> GateDecision`, where `GateRequest = {entity_id, entity_type, field_key, source_tier, run_id, value_json?}`; and `assemble_target_lock(entity, field) -> PromptContext`. These are the only entry points; the gate set behind them (which checks run, their thresholds) is versioned config in the existing `field_definition.gate` column (whose contents are structured as a `gate_spec`) plus a `pre_spend_policy` table — swappable without touching callers.
  - **Consumes:** `field_definition` (M1.3) for schema/tier/validation/`gate`; `account_entity` + `Resolver` registry (M2/M4) for identity; Redis locks (M2.4); the tracing wrapper (M0.5). The `Resolver` protocol stays untouched — resolvers are gated *by the caller*, not modified, so swapping Clay→direct API is unaffected.
  - **Swap note:** because the gate is config-driven and callable, adding a new gate (e.g. a per-client allowlist) is a `pre_spend_policy` row, not a code change; the seam is the `GateDecision` contract.
- **Data model / schema:** extends the existing **`field_definition.gate`** (conventions §4) by giving it a structured `gate_spec` shape (e.g. `{requires_official_domain: bool, requires_strong_key: bool, min_tier: int}`) — same column, declared contents. New small **`pre_spend_policy`** config table (versioned, per-client/ICP overridable): `policy_id, client_id?, icp_version?, rules_json, version`. Writes a `gate_decision` audit row `{id, run_id, entity_id, field_key, source_tier, decision, reasons[], decided_at}` (append-only). Reads `claim`, `account_entity` (conventions §4); produces no promotable `claim`.
- **Dependencies:** Blocked by **M1** (field registry, claim contract). Directly consumes **M2** primitives (resolved entity/strong key, Redis locks) — a cross-milestone consumption, not a transitive dep of M1. Unblocks **M4** (the waterfall calls it before resolving), **M8** (workers call it pre-spend), **M11** (synthesis calls it before paying). The target-lock helper is consumed by **M8.1** (mode-M2 profiling).
- **Acceptance criteria:**
  - A request for a `field_key` not in the registry, or a tier not in the field's `tier_plan`, returns `reject` with a typed reason and emits a `verification.pre_spend_gate` span; no resolver is invoked.
  - A request bound to a free-text name (no resolved `entity_id`), to an entity lacking a strong key, or to a `merged` entity is rejected.
  - A request for an entity whose in-flight lock is held by a *different* run is rejected (no double-spend).
  - `assemble_target_lock` produces a prompt context containing the canonical domain and a no-drift instruction for a given resolved entity; unit-tested against a same-name pair (two real companies sharing a name resolve to distinct contexts).
  - Gate rules are loaded from `pre_spend_policy` config; flipping a rule in config changes behavior with no code change (covered by a config-swap test).
  - Every claim-producing call routes through `PreSpendGate.check` (enforced by a lint/integration test that fails if a resolver/worker calls out without a prior gate decision in the run), with the strongest enforcement asserted on tier≥2 (spend) paths.
- **Out of scope:** the appropriateness/use gate (M10 — distinct gate, runs *after* identity-binding and the faithfulness judge); the existence/identity gate at *discovery* admission (M6.2 — same discipline, different mode/owner; M9.1 covers the *profiling/spend* entry gate); the budget cap arithmetic (M7.5 — M9.1 fails closed pre-spend, M7.5 owns the running budget total).
- **Open decisions:** none directly; touches **D3** indirectly only insofar as the gate framework must leave a slot for M10's use-gate after identity-binding (proceed on Doc D §7 default ordering — identity-binding + faithfulness judge, then use-gate).

### M9.2 — Corroboration rules (≥N independent tier≤3)
- **Purpose:** Provenance alone (an evidence span) proves a single source said something; it does not prove the fact is *true*. For fields that load-bear on scoring or content, the substrate requires **independent corroboration** before a claim is promoted to `verified` (substrate §6(2)): ≥N independent tier≤3 sources agreeing, with **conflicts between authoritative (tier≤2) sources surfaced as a flag rather than silently resolved** (substrate §1 merge view). This issue builds the corroboration engine: it counts independent agreeing sources per `(entity, field)`, sets `corroborations`, drives the promotion to `verified`, and raises conflict flags. It is the structural verification mechanism — it "falls out of the claim store" (substrate §6(2)) and is deterministic, not an agent.
- **Architecture sources:** substrate §6(2) (provenance + corroboration; ≥N independent tier≤3 corroborations; conflicting tier≤2 → flag), §1 (`corroborations` field; merge view conflict flag on disagreeing tier≤2 sources), §3 (field-level config — which fields require corroboration); staged-flow §8 (mode-M2 fabrication prevention); Doc C §6 (verification-health metrics read corroboration outcomes).
- **Scope / deliverables:**
  - A **corroboration evaluator** that, for a target `(entity, field)`, scans non-superseded claims, groups them by *agreement* on `value_json` (using the field's type-aware equality derived from M1.3's `type`/`validation` — exact for enums/ids, normalized/tolerance for numerics, semantic for text where the registry declares it), counts **independent** tier≤3 sources per value-group, and sets each claim's `corroborations`.
  - **Independence definition:** distinct `source_url` host *and* distinct resolver/`source_key` (two claims from the same vendor or the same domain count once) — encoded so "independent" is testable, not vibes.
  - **Promotion rule:** a claim's `verification_state` advances to `verified` only when its value-group has ≥ the field's `corroboration_threshold` independent tier≤3 sources, OR the claim is from a tier-1 deterministic source on a field the registry marks as `single_source_sufficient` (e.g. a registry-ID). A field with `corroboration_threshold = 1` (or unset, the default) requires no extra corroboration and promotes on a single confident claim — so non-load-bearing fields are not blocked; only fields explicitly marked load-bearing carry N≥2. Below threshold → `unverified` (still readable, flagged).
  - **Conflict flag:** when two or more tier≤2 sources disagree on `value_json` for the same `(entity, field)`, raise a `conflict` flag (feeds M1's `current_value` conflict flag and the review queue), never auto-pick silently.
  - Per-field corroboration config (threshold N, single-source-sufficient, equality mode) as versioned data in `field_definition`.
  - Emits `verification.corroboration` trace span and per-`(ICP, field, source)` precision signal (claims that survived) for the source-learning loop (staged-flow §7e) and verification health (Doc C §6).
- **Interface / seam:**
  - **Exposes:** `Corroborator.evaluate(entity_id, field_key) -> CorroborationResult{value_groups[], promoted_claim_ids[], conflict: bool}`; idempotent, deterministic. The promotion decision is surfaced as a `verification_state` transition the merge view honors.
  - **Consumes:** `claim` rows + `field_definition` (conventions §4); the type-aware equality derived from M1.3's field `type`/`validation`; tracing (M0.5). It reads the same data `current_value` reads (M1.2) and *complements* it: merge picks the winning claim by tier/freshness; corroboration decides whether that winner is `verified`. The two stay decoupled behind the `verification_state` field.
  - **Swap note:** the equality function and the independence rule are pluggable per field (config); a per-vertical pack can register a stricter corroboration requirement (e.g. healthcare facts need ≥2 official sources) without touching the evaluator.
- **Data model / schema:** extends **`field_definition`** with `corroboration_threshold int`, `single_source_sufficient bool`, `equality_mode enum(exact|numeric_tol|semantic)`. Reads/writes **`claim.corroborations`** (conventions §4). Introduces the milestone-wide **`verification_state enum(unverified|verified|rejected)`** column on `claim` — the *accuracy verdict* (also written by M9.3/M9.4; defined once here as the lowest structural layer). Freshness disposition (`stale`/`expired`) is a **separate** `freshness_state` column owned by M9.5, kept orthogonal so marking a claim stale never erases its accuracy verdict. Writes a `conflict_flag` row `{entity_id, field_key, conflicting_claim_ids[], raised_at, resolved_by?}` consumed by the review queue (M13.1).
- **Dependencies:** Blocked by **M1** (claim store, merge view, field registry, field type/validation for equality). Unblocks **M9.3/M9.4** (they share `verification_state`), **M9.5** (orthogonal `freshness_state`, same claim row), **M6.3** (scoring reads only promoted/verified or appropriately-discounted claims), **M12** (handoff carries verified claims), **M13.1** (conflict flags surface in review).
- **Acceptance criteria:**
  - A field with `corroboration_threshold = 2` does not reach `verified` on one tier-3 source; reaches `verified` on two independent tier-3 sources (distinct host + distinct source_key); two claims from the *same* vendor count as one (independence test).
  - A field with `corroboration_threshold = 1` (or unset) promotes on a single confident claim (non-load-bearing path not blocked).
  - A tier-1 claim on a `single_source_sufficient` field is `verified` without corroboration.
  - Two tier-2 sources disagreeing on a value raise a `conflict_flag` and the merge result carries the conflict flag; no value is silently chosen.
  - `corroborations` is set deterministically and re-evaluating is idempotent (same inputs → same result, no new rows).
  - Numeric fields use tolerance equality and text fields use the configured semantic equality (e.g. "Snowflake" vs "uses Snowflake" corroborate; "Snowflake" vs "Databricks" conflict) — covered by fixtures.
  - Changing `corroboration_threshold` in config changes promotion with no code change.
- **Out of scope:** the `current_value` merge ranking itself (M1.2 — M9.2 sets `verification_state` and conflict flags, merge consumes them); the faithfulness check on synthesized values (M9.3); freshness disposition (M9.5); resolving a conflict (M13.1 human review / re-research).
- **Open decisions:** **D7** (economics) touchpoint only — N and which fields require corroboration trade accuracy against cost; defaults proposed per field-class, confirmed against real campaigns; do not hardcode.

### M9.3 — Faithfulness judge (LLM-as-judge, dedicated trace span)
- **Purpose:** This is *the missing eval layer* the substrate calls out as the difference between the prototype's "leaky probabilistic QA" and the literature's 10%→sub-1% hallucination reductions (substrate §6(3)). For **every tier-4 synthesized claim**, a separate **LLM-as-judge** call scores whether `value_json` is actually *entailed by* its `evidence_span` — **claim-level groundedness, not document-level**. Unsupported → the claim is rejected and re-retrieval is triggered, or the field is left empty (which is *correct behavior* — empty beats fabricated, the universal rule). It runs as a **distinct graph step with its own observability span** so faithfulness is measured, not assumed (substrate §6(3), §12). This is the accuracy-half of the two-gate model (Doc D §3, §5) and the mode-M2/M4 anti-fabrication mechanism (staged-flow §8).
- **Architecture sources:** substrate §6(3) (faithfulness judge — claim-level entailment, distinct step + span, reject + re-retrieve, empty-is-correct), §0 (the absent judge is the problem, not the model), §1 (tier-4 + no span → cannot promote; the judge gates the rest), §12 (LLM-as-judge with its own trace span), §13 (untyped dossiers + after-the-fact QA is the anti-pattern this replaces); staged-flow §8 (mode-M2 fabricated facts); Doc D §5 (the faithfulness judge ≠ the appropriateness gate — separate steps, separate observability).
- **Scope / deliverables:**
  - A `FaithfulnessJudge.judge(claim) -> JudgeVerdict{verdict ∈ {supported|partial|unsupported|contradicted}, score(0..1), rationale, judge_model, prompt_version}` callable, invoked as a **dedicated graph step** on every tier-4 claim *before* it can leave `unverified`.
  - **Pre-check (free, structural):** a tier-4 claim with no `evidence_span` is auto-rejected without an LLM call (substrate §1 — no span → not promotable). The judge only runs when a span exists.
  - **Claim-level entailment prompt:** judge whether `value_json` is entailed by `evidence_span` *alone* (not the wider document), with a calibrated rubric (supported / partial / unsupported / contradicted). Versioned prompt; the judge model is config (swappable).
  - **Outcome handling:** `supported` (score ≥ threshold) → eligible for promotion (then subject to M9.2 corroboration / M9.4 binding for contacts); `unsupported`/`contradicted` → set `verification_state = rejected`, emit a **re-retrieval signal** (back to the M8 worker / M11 resolver to re-fetch or leave empty); `partial` → `unverified` + flag for review.
  - **Dedicated trace span** `verification.faithfulness_judge` capturing input claim id, verdict, score, model, prompt_version, latency, cost — so faithfulness is a first-class metric (Doc C §6: "share of tier-4 claims passing the faithfulness judge").
  - **Idempotency + caching:** keyed on `(claim_id, judge_model, prompt_version)` so re-runs don't re-pay; a model/prompt bump invalidates the cache (and is auditable).
  - Records the verdict on the claim so the handoff's provenance index (M12) can show "judged faithful by `<model>@<prompt_version>`".
- **Interface / seam:**
  - **Exposes:** `FaithfulnessJudge.judge(claim) -> JudgeVerdict`; the verdict drives `verification_state`. This is the *only* judge entry point — the model behind it (an OpenRouter model id served by the M0.4 `LLMGateway`), the prompt version, and the threshold are all config (`judge_policy` table), so a **judge-model swap is a config change**, regression-checked by M9.6. The judge is a registered "judge" in the shared package (conventions §6) with its own trace span.
  - **Consumes:** `claim` (value_json, evidence_span, source_tier) from M1; the shared OpenRouter `LLMGateway` + tracing wrapper from M0 (M0.4/M0.5) — the judge model is a gateway model id read from `judge_policy`; for re-retrieval it emits a typed signal consumed by **M8/M11** (it does not itself re-fetch — keeps the judge pure and the seam narrow).
  - **Swap note:** swapping the judge model or moving to an ensemble (two judges) stays behind `JudgeVerdict`; downstream only sees `verification_state`. The re-retrieval handoff is a typed event so the orchestrator owner (M7/M8) can change without touching the judge.
- **Data model / schema:** writes **`claim.verification_state`** and a **`faithfulness_verdict`** row `{id, claim_id, verdict, score, rationale, judge_model, prompt_version, cost_cents, latency_ms, judged_at}` (append-only; one per `(claim, model, prompt_version)`). New versioned config **`judge_policy`** `{policy_id, judge_model, prompt_version, supported_threshold, client_id?, version}`. Reads `claim`, `field_definition` (conventions §4).
- **Dependencies:** Blocked by **M1** (claim store, evidence-span field, `verification_state` from M9.2) and **M0** (LLM client, tracing). Tightly paired with **M11** (tier-4 synthesis — the judge gates M11's output; per build order substrate §11 the verification layer is built *before* M11 ships any synthesis). Unblocks **M11** (synthesis may only promote behind the judge), **M8** (deep workers' synthesized claims are judged), **M12** (provenance index cites the verdict), **M13.4** (verification-health surface).
- **Acceptance criteria:**
  - A tier-4 claim with no `evidence_span` is rejected with zero LLM calls (structural pre-check) and emits the span.
  - On a fixture where `value_json` is *not* entailed by its span (a plausible fabrication), the judge returns `unsupported` (or `contradicted`), sets `verification_state = rejected`, and emits a re-retrieval signal; the claim never reaches `verified`.
  - On a fixture where the value is entailed, the judge returns `supported` and the claim becomes promotion-eligible.
  - Every judge call produces a `verification.faithfulness_judge` span with model, prompt_version, score, cost, latency.
  - Re-judging the same `(claim, model, prompt_version)` is cached (no second LLM call); bumping `prompt_version` forces a fresh judgment.
  - The judge model is read from `judge_policy` config; swapping the configured model changes which model is called with no code change, and the swap is caught by the M9.6 eval battery (golden-set faithfulness scores recomputed).
  - Judge operates at the **claim/span level**, not the document level (verified by a fixture where the wider document supports a value but the cited span does not → `unsupported`).
- **Out of scope:** producing the synthesized claims themselves (M11); the appropriateness/use gate (M10 — explicitly a *separate* step with separate observability, Doc D §5); document-level RAG retrieval (M4/M11); re-retrieval *execution* (M8/M11 act on the emitted signal).
- **Open decisions:** **D8** (2026 legal verification) is unrelated; the relevant note is that the judge is the accuracy gate only — **D3** posture (M10) decides the *use* gate that runs after it. Proceed on Doc D §7 default ordering (identity-binding + judge, then use-gate).

### M9.4 — Identity-binding gate (strong vs weak)
- **Purpose:** For contact claims, getting a personal fact *wrong* in 1:1 outreach is worse than omitting it (staged-flow §6). The evidence-span rule kills fabrication for account facts; the **identity-binding gate** is its contact-axis analogue: every personal claim carries an `identity_binding` strength — **strong** (evidence on the person's *verified* profile/handle, or co-occurring with multiple strong identifiers: name + employer + role + location) or **weak** (name match only — the same-name trap). **Weak-binding claims are never promoted and never drive outreach.** This issue builds the gate that classifies binding strength at claim ingestion and enforces the no-promote-on-weak rule. It is the verification-layer extension the staged-flow names explicitly (staged-flow §9: "Verification layer extends with identity-binding for contacts").
- **Architecture sources:** staged-flow §6 (mode-M4 identity-binding strong vs weak; weak never promoted), §8 (mode-M4 misattributed personal facts → identity-binding mechanism), §9 (verification layer extends with identity-binding); substrate §6(1) (identity lock); Doc D §3, §5 (accuracy/identity-binding gate is one of the two distinct gates; it answers "is it *this* person?", separate from the use-gate). Field-class: Doc C §2 (`contact.facet.*`).
- **Scope / deliverables:**
  - An `IdentityBindingGate.classify(contact_claim, contact_entity) -> Binding{strong|weak, strength_score, evidence_signals[]}` callable, run on every `contact.*` / `contact.facet.*` claim at ingestion.
  - **Strong criteria (any one):** the `source_url`/`evidence_span` is on the contact's *verified* profile/handle (the LinkedIn URL / verified email that M2 resolved the contact on), OR the evidence co-occurs with ≥K strong identifiers (name + employer + role + geo) bound to *this* `contact_entity_id`.
  - **Weak criteria:** name-only match (no verified handle, insufficient corroborating identifiers) → classified `weak`.
  - **Enforcement:** a `weak` claim's `verification_state` can never advance past `unverified`; it is stored (audit trail) but excluded from promotion, from scoring, and from the handoff's usable set. A `strong` claim is eligible (then still subject to M9.3 if synthesized, M9.2 if corroboration-required).
  - Writes `claim.identity_binding` (the field already on contact field-claim provenance, conventions §4 / staged-flow §9) and the strength score + signals for auditability.
  - Emits `verification.identity_binding` trace span and the "share of personal claims at strong binding" metric (Doc C §6 verification health).
  - Designed so M10's **appropriateness/use gate runs *after* this gate and the faithfulness judge** (Doc D §7 ordering): identity-binding answers "is it this person?", the use-gate answers "may we use it?"; this issue exposes the seam, M10 plugs in.
- **Interface / seam:**
  - **Exposes:** `IdentityBindingGate.classify(contact_claim, contact_entity) -> Binding`; the result writes `claim.identity_binding` and gates `verification_state`. The classification *rules* (what counts as a strong identifier, K, the strength scorer) are config (`binding_policy`), swappable per client/pack without code.
  - **Consumes:** `account_entity`/contact resolution from **M2** (the verified handle/email is the canonical strong key); `claim` provenance from M1; `source_manifest.identity_binding_strength` from **M4** (a source's inherent binding-strength prior informs but does not override per-claim classification); tracing (M0.5).
  - **Swap note:** because binding rules are config and the `source_manifest` carries a per-source `identity_binding_strength` prior (conventions §4), adding a new high-binding source (e.g. a verified-email vendor) is a manifest + config change. The gate's output (`identity_binding` on the claim) is the stable seam M10's use-gate and M12's handoff both read.
- **Data model / schema:** writes **`claim.identity_binding enum(strong|weak)`** (conventions §3/§4 contact field-claim provenance) and an audit **`identity_binding_eval`** row `{id, claim_id, contact_entity_id, strength, strength_score, evidence_signals_json, evaluated_at}`. New config **`binding_policy`** `{policy_id, strong_identifier_set, min_identifiers_k, client_id?, version}`. Reads `account_entity`/contact (conventions §4 — `aliases`, registry/handle keys), `source_manifest` (conventions §4).
- **Dependencies:** Blocked by **M1** (claim, `identity_binding` provenance field) and **M2** (contact resolution, verified handle/email). Reads **M4** `source_manifest`. Unblocks **M8.4** (mode-M4 contact profiling only promotes strong-bound claims), **M8.5** (`contact.facet.*`), **M10** (use-gate runs after, on strong-bound claims only), **M12** (handoff carries `identity_binding` per contact claim).
- **Acceptance criteria:**
  - A `contact.facet.*` claim sourced from the contact's *verified* LinkedIn profile is classified `strong`.
  - A claim sourced from a name-only web match (different employer, no verified handle) is classified `weak`, stays `unverified`, and is excluded from the handoff's usable set even though it is stored.
  - The same-name trap is covered: two real people sharing a name resolve to distinct `contact_entity_id`s, and a claim bound to one does not promote on the other (fixture test).
  - `claim.identity_binding` is written for every contact claim; account claims are untouched (the gate runs only on `contact.*`).
  - Changing `min_identifiers_k` or the strong-identifier set in `binding_policy` changes classification with no code change.
  - The "share of personal claims at strong binding" metric is emitted per run.
  - The gate runs **before** any use-gate hook (ordering test: a weak claim never reaches the M10 stub).
- **Out of scope:** the appropriateness/use gate itself (`use_class × jurisdiction × client_policy`) — **M10**; use-class *tagging at extraction* — M10.2; resolving/merging duplicate contacts — M2.3. This issue produces `identity_binding` strength; M10 consumes it alongside `use_class`.
- **Open decisions:** **D3** (personal-data posture) and **D4** (contact geography — resolved: mixed/global) are M10's; M9.4 is posture-agnostic — it only answers "is it this person?". Note them as touchpoints; proceed without hardcoding posture.

### M9.5 — Freshness TTL engine + re-research cadence
- **Purpose:** "The master database is a myth" — the modern workforce and tech stack churn constantly, so **freshness is a first-class signal**, not an afterthought (substrate §6). Every claim has `observed_at` + a **field-level TTL**; the merge view treats stale claims as eligible for refresh, the scoring layer can **discount** them, and **re-research runs on a cadence** (≈90-day default; signal-fields faster — substrate §6, Doc C §1). Personal claims carry **shorter retention/freshness TTLs** (Doc D §4 — both because people change and to minimize retained personal data). This issue builds the TTL engine (compute staleness per claim against its field's TTL), the staleness signal the merge/scoring layers read, and the **re-research candidate emitter** that feeds the durable executor's refresh scheduling.
- **Architecture sources:** substrate §6 (freshness as a first-class signal — `observed_at` + field-level TTL; merge view treats stale as refresh-eligible; scoring discounts stale; re-research on a cadence, ~90-day default, signal-fields faster), §1 (`observed_at`, merge view, `freshness_ttl` in `field_definition`); Doc C §1 (signal proxies churn fast → faster cadence), §6 (freshness is a verification-health metric); Doc D §4 (shorter retention/freshness TTLs on personal claims; expired personal claims age out).
- **Scope / deliverables:**
  - A **freshness evaluator** `staleness(claim, now) -> {state ∈ {fresh|stale|expired}, age, ttl}` that compares `observed_at` (publish/seen time, falling back to `collected_at`) against the field's `freshness_ttl` (M1.3) — per field-class, with **faster TTLs for signal fields** (intent/hiring/funding proxies) and **shorter TTLs for personal `contact.facet.*` / `contact.*`** (Doc D §4).
  - **Staleness as a queryable signal:** the merge view (M1.2) treats `stale` claims as still-usable-but-refresh-eligible and `expired` claims as ineligible to win; scoring (M6.3) reads a freshness factor to discount stale signals. M9.5 exposes the signal; M1.2/M6.3 consume it (decoupled).
  - **`freshness_state = stale`** for claims past TTL, and **`freshness_state = expired`** for claims past their retention horizon (personal claims age out per Doc D §4). `freshness_state` is a **separate column from `verification_state`** (M9.2), kept orthogonal so a stale claim retains its accuracy verdict and can still be the current_value when nothing fresher exists (substrate §1).
  - **Re-research candidate emitter:** a query/job that, per `(entity, field)`, yields the set of stale claims due for refresh, ranked by field cadence and tier — emitted as typed candidates the **M7** campaign/durable executor schedules and runs (M9.5 does *not* execute the refresh; it identifies what's due).
  - **Cadence policy as data:** default ~90-day, per-field-class overrides (signal fields faster, personal fields shorter), versioned config, per-client/ICP overridable.
  - Emits `verification.freshness` span and the freshness-health metric (Doc C §6). The **lawful** retention horizon and erasure are owned by **M10.5** (conventions §7); M9.5 consumes M10.5's personal-claim retention horizon to compute `expired` and surfaces aged-out claims to M10.5 — one shared TTL spine, M9.5 the freshness/refresh half, M10.5 the lawful-retention/erasure half.
- **Interface / seam:**
  - **Exposes:** `Freshness.evaluate(claim, now) -> Staleness`; `Freshness.due_for_refresh(scope) -> ReResearchCandidate[]`; and the per-claim `freshness_state ∈ {fresh|stale|expired}` transitions. The freshness TTLs and refresh cadence are config (`field_definition.freshness_ttl` + a `cadence_policy` table); the lawful retention horizon is read from M10.5's policy — swappable per field/client without code.
  - **Consumes:** `claim.observed_at`/`collected_at` + `field_definition.freshness_ttl` (conventions §4); the personal-claim retention horizon from **M10.5**; tracing (M0.5). **Emits** `ReResearchCandidate` events to **M7** (campaign-run state machine / durable executor schedules them) — the executor swap (Postgres state machine → Temporal, conventions §2) stays behind this event seam.
  - **Swap note:** the cadence policy and TTLs are data; the re-research *scheduling/execution* lives entirely behind the `ReResearchCandidate` seam, so changing the scheduler (Postgres→Temporal) or the refresh worker doesn't touch the freshness engine.
- **Data model / schema:** reads/extends **`field_definition.freshness_ttl`** (conventions §4); writes a new **`claim.freshness_state enum(fresh|stale|expired)`** column (orthogonal to `verification_state`). New config **`cadence_policy`** `{policy_id, field_class, ttl, refresh_cadence, client_id?, version}` for the freshness/refresh dial; the personal-claim **retention horizon** is owned and defined by **M10.5** and referenced here, not redefined. Emits **`re_research_candidate`** rows `{id, entity_id, field_key, stale_claim_ids[], due_at, priority}` consumed by M7.
- **Dependencies:** Blocked by **M1** (claim `observed_at`, field TTLs, merge view) and (for the `freshness_state` column / orthogonality) coordinated with **M9.2**. Unblocks **M6.3** (scoring discounts stale signals), **M1.2** (merge treats stale as refresh-eligible — consumes M9.5's signal), **M7** (schedules re-research from emitted candidates), **M13.4** (freshness verification-health metric). Coordinates bidirectionally with **M10.5** (shares the TTL/retention spine for personal-claim age-out; M10.5 owns the retention horizon).
- **Acceptance criteria:**
  - A claim past its field's `freshness_ttl` is reported `stale`; the merge view keeps it usable-but-refresh-eligible and never lets an `expired` claim win over a fresh one; the claim's `verification_state` (accuracy verdict) is unchanged by going stale.
  - A signal-class field (e.g. `hiring_velocity_eng`) has a *shorter* TTL than a firmographic field (e.g. `employee_count`); a `contact.facet.*` field has a shorter TTL than an account firmographic field (Doc D §4) — verified by config + fixtures.
  - The scoring layer can read a freshness factor and a stale signal is discounted (integration test with M6.3 stub).
  - `due_for_refresh` returns exactly the stale-and-due claims for a scope, ranked by cadence/tier, as `ReResearchCandidate`s; it does not itself fetch anything.
  - Changing `refresh_cadence` / `ttl` in `cadence_policy` changes staleness/refresh behavior with no code change.
  - Personal claims past the M10.5-owned retention horizon are marked `expired` and surfaced to M10.5 for age-out (coordination test).
  - Re-evaluation is idempotent and deterministic given a fixed `now`.
- **Out of scope:** *executing* the re-research (M7 schedules; M8/M11 produce the new claims); lawful-basis recording, the retention-horizon policy, and DSAR/erasure tombstoning of personal claims (M10.5 — M9.5 provides the freshness/age-out signal, M10.5 owns the legal retention/erasure machinery); the scoring discount math itself (M6.3); the accuracy verdict (M9.2's `verification_state`).
- **Open decisions:** **D7** (economics) — re-research cadence is a cost dial (more frequent refresh = more spend); default ~90-day proposed, confirm against real campaigns; do not hardcode. **D3/D4** touch personal-claim retention horizons (M10 owns the posture and the horizon); proceed on Doc D §4 defaults.

### M9.6 — Eval harness + golden account set + rubric scoring
- **Purpose:** This is how an accuracy claim is **defended to an enterprise buyer** and how regressions are caught **when a model or resolver is swapped** (substrate §6 evals). Stand up an eval set of hand-verified accounts and run the standard battery: **LLM-as-judge with rubrics for factual accuracy / citation validity / source quality**, plus periodic **human spot-checks** to catch what judges miss. The eval harness is the measurement instrument over the *whole* verification layer (gates, corroboration, faithfulness judge, identity-binding, freshness) — it is what makes "verification health" (Doc C §6) a number rather than a hope, and it is the regression gate for every swap the modularity seams permit (judge-model swap, resolver swap, corroboration-rule change).
- **Architecture sources:** substrate §6 (evals — golden set, rubric LLM-as-judge for factual accuracy/citation validity/source quality, human spot-checks, catch regressions on model/resolver swap), §0 (claim-level eval layer is the answer to shipped hallucinations), §11 (verification layer = gates → corroboration → faithfulness judge + evals, built before tier-4 agents); Doc C §6 (verification-health metrics — share passing faithfulness, share at strong binding); staged-flow §8 (the mode-specific failures the evals must catch); conventions §2/§6 (the test/eval-harness scaffold is M0.6; M9.6 fills it with the verification battery).
- **Scope / deliverables:**
  - A **golden account/contact set** — hand-verified `(entity, field, expected_value, expected_source, expected_tier)` fixtures spanning the four research modes (M1–M4) and the field-classes (`core.*`, `account.*`, `account.resonance.*`, `contact.*`, `contact.facet.*`), including **negative fixtures** (known fabrications, same-name traps, stale facts, unsupported spans) so each verification mechanism has a failing case it must catch.
  - **Rubric scorers** (LLM-as-judge **via the shared OpenRouter `LLMGateway`, M0.4**, with their own spans, reusing the M9.3 judge infra where applicable): **factual accuracy** (does the claim match ground truth?), **citation validity** (does the `evidence_span`/`source_url` actually support the value?), **source quality** (is the winning tier appropriate?). Each emits a 0..1 rubric score + rationale.
  - **End-to-end verification metrics** computed over the golden set: faithfulness pass-rate (M9.3), corroboration promotion accuracy (M9.2), identity-binding precision/recall on the same-name fixtures (M9.4), freshness correctness (M9.5), pre-spend gate block correctness (M9.1) — i.e. the harness exercises *all six* issues.
  - **Human spot-check surface:** a sampler that pulls a stratified sample of *production* promoted claims for human review (catches what judges miss), with results folding back as new golden fixtures.
  - **Regression gate:** a CI-runnable command that scores the current config (judge model, prompt version, corroboration thresholds, resolver set) against the golden baseline and **fails on regression** beyond a tolerance — so any swap behind a seam is caught.
  - Reporting wired to the verification-health metrics (Doc C §6) that M13.4 surfaces to the client.
- **Interface / seam:**
  - **Exposes:** an `EvalHarness.run(suite, config) -> EvalReport{per_rubric_scores, per_mechanism_metrics, regressions[]}` and a CLI entry; the golden set is versioned fixtures (data, not code). The harness is config-driven so it scores *whatever* judge model / resolver set / thresholds are configured — it is the cross-seam regression instrument.
  - **Consumes:** the M0.6 eval-harness scaffold + CI; the M9.3 judge infra (rubric scorers reuse the judge wrapper + spans); `claim`/`field_definition`/`account_entity` (conventions §4) to read what the pipeline produced; the tracing wrapper (M0.5) for spans. It depends on the *outputs* of M9.1–M9.5 but not their internals — it reads `verification_state`, `freshness_state`, and provenance, so any of them can be re-implemented and the eval still measures correctness.
  - **Swap note:** this is the issue that makes every other modularity seam safe — swapping the judge model (M9.3), a resolver (M4), or a corroboration rule (M9.2) is gated by `EvalHarness.run` regression results. The golden set itself is swappable/extendable (new fixtures = data).
- **Data model / schema:** golden fixtures stored as versioned files/rows `golden_fixture {id, entity_ref, field_key, expected_value_json, expected_source_url, expected_tier, fixture_kind(positive|negative-fabrication|negative-samename|negative-stale|negative-unsupported), mode}`. Eval runs recorded as `eval_run {id, suite, config_snapshot_json, started_at, report_json}` (append-only, for trend/regression). Reads `claim`, `field_definition`, `account_entity`, `faithfulness_verdict`, `identity_binding_eval` (this milestone's tables). Reuses `judge_policy` (M9.3) for rubric judge config.
- **Dependencies:** Blocked by **M0.6** (eval scaffold + CI) and **M9.3** (judge infra reused by rubric scorers). Exercises and therefore soft-depends on **M9.1, M9.2, M9.4, M9.5** (their outputs are measured) and **M1/M2/M4** (the substrate that produces claims). Unblocks confident swaps everywhere (judge model, resolver, thresholds) and feeds **M13.4** (verification-health surface) and the source-learning loop (staged-flow §7e via per-source precision).
- **Acceptance criteria:**
  - The golden set contains positive *and* negative fixtures for each research mode (M1–M4) and each verification mechanism (gate-block, corroboration, faithfulness, identity-binding, freshness) — each negative fixture has a documented expected catch.
  - `EvalHarness.run` produces per-rubric scores (factual accuracy, citation validity, source quality) and per-mechanism metrics over the golden set, each with its own trace span.
  - A deliberately weakened judge prompt / a swapped-in weaker model produces a measurable regression in the report and the CI regression gate **fails** (proves the harness catches model swaps — substrate §6).
  - A swapped resolver that returns a known-wrong value is caught by the factual-accuracy rubric against ground truth.
  - The same-name negative fixture is caught by the identity-binding metric (M9.4 recall on the trap); the unsupported-span fixture is caught by the faithfulness metric (M9.3); the stale fixture is caught by the freshness metric (M9.5).
  - The human spot-check sampler returns a stratified sample of production promoted claims and ingests reviewed results back as new golden fixtures.
  - Eval runs are recorded with a config snapshot so a regression can be traced to the exact judge model / threshold / resolver change.
- **Out of scope:** the client-facing verification-health dashboard (M13.4 — M9.6 emits the metrics, M13.4 renders them); the disposition feedback loop / source reweighting (M13.2/M13.3 — distinct signal, though both read provenance); the generic test/CI scaffold (M0.6 — M9.6 fills it with the verification battery).
- **Open decisions:** **D7** (economics) — the human-spot-check sampling rate and eval-run frequency are cost dials; default proposed, confirm against real ops load. **D8** (2026 legal verification) is M10's concern, not measured here. Proceed on defaults without hardcoding.
