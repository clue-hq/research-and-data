# M8 — Deep Profiling — modes M2 Account · M3 Committee · M4 Contact
**Layer label:** layer:deep-profiling  ·  **Depends on:** M4, M6, M7  ·  **Priority:** 3 (Medium)
**Architecture sources:** staged-flow §5 (M2 converge + target-lock), §6 (M3/M4, identity-binding), §8 (mode-specific anti-hallucination), §9 (composition); substrate §5b (orchestrator-worker), §7 (contact graph + persona keys); Doc C §2 (resonance + facet field-classes), §3 (bounded two-level fan-out); Doc D §2–§3 (use-class, two gates); overview §1 (Outputs 2 & 3), §3 (handoff)

## Goal & scope of this milestone

M8 is **Pass B — Deep Research**: the narrow, deep, precision-optimized half of the 2×2 (staged-flow §1), running **only on high-tier accounts** that cleared the Pass A scoring / tier checkpoint (M6, substrate §5a). It implements three of the four research modes — **M2 Account Profiling**, **M3 Committee Discovery**, **M4 Contact Profiling** — plus the two deep-pass field-classes those modes populate, `account.resonance.*` and `contact.facet.*` (Doc C §2). Mode M1 Account Discovery and Pass A live in M6, not here.

Where it sits in the end-to-end map (overview §2, staged-flow §10): Stage 0 → mode M1 discovery + existence gate (M6) → Pass A scoring + tiering + human checkpoint (M6) → **M8 runs M2/M3/M4 on high tiers** → Verification (M9) → Value narrative + handoff (M12). M8 is the producer of **Output 2** (verified, fully-sourced account profile incl. resonance) and **Output 3** (the identity-resolved, persona-tagged, governed buying committee). It writes typed claims into the M1 claim store; the handoff object (overview §3) is assembled downstream in M12 by reading those claims.

M8 is the **caller** of the M7 execution substrate and the M4 source substrate; it is not a re-implementation of either. M2/M3/M4 are planned/spawned by the per-account orchestrator-worker graph and bounded-recursion knob from M7 (substrate §5b, Doc C §3), and they fill fields by calling the M4 trust-tiered waterfall (substrate §4) and config-bounded Source Planner (staged-flow §7d). Each mode is a distinct **graph node / worker family** with its own orchestration shape, source emphasis, and gate emphasis — the central reframe that "research is four operations, not one" (staged-flow §1), and the structural answer to the prototype's single-agent collapse.

**Explicitly NOT in this milestone:**
- The faithfulness judge, corroboration rules, pre-spend gates, freshness engine, identity-binding *judge*, and eval harness — these are the **Verification Layer (M9)**. M8 *tags* every claim with `evidence_span`, `source_tier`, `confidence`, and (for contacts) `identity_binding` and `use_class`, and it *invokes* the M9 gate steps, but the gate logic itself is M9. M8 produces claims at status `unverified`; M9 promotes them.
- The **appropriateness/use gate** logic and the three postures — **Compliance (M10)**. M8 tags `use_class` at extraction (the hinge Doc D §2 requires) and carries `identity_binding`, but the `(use_class × jurisdiction × client_policy)` decision and posture-driven source scoping are M10.
- **Tier-4 LLM synthesis resolvers** (Exa Deep, Parallel Task) — **M11**. Resonance narratives, operational pain, and strategic moves are tier-4 *fields* M8 requests; the synthesis resolvers behind them are M11, reached through the same M4 `Resolver` seam.
- **Per-account orchestrator-worker graph, bounded-recursion knob, campaign-run state machine, idempotency keys, budget caps** — all **M7**. M8 supplies the per-mode worker logic that runs *inside* M7's graph and respects its caps; it does not own scheduling, checkpointing, or budgets.
- **Resolver implementations, source registry, modality adapters, Source Planner engine** — **M4**. M8 declares which field-classes/modes it needs and consumes the planner's ordered source set; it does not implement adapters.
- **Value narrative / positioning and the `account_handoff` assembly** — **M12**. M8 stops at verified, persona-keyed claims in the store.

The milestone's discipline in one line (staged-flow §10): **profiling is narrow, deep, and target-locked; nothing — no fact, no person, no personal hook — enters the store without surviving the gate appropriate to its mode**, and an empty, flagged field is a correct output (_conventions.md §5).

## Issues

### M8.1 — Account Profiling (mode M2, converge pattern + target-lock)
- **Purpose:** Fill a resolved high-tier account's active field schema with verified, sourced claims — the deep account picture (operational pain, strategic moves, and the resonance layer) that is **Output 2**. Mode M2 is *Profiling*: closed, target-locked, optimized for precision and resistance to drift — the opposite failure profile from discovery (staged-flow §1). It exists because account-level deep facts are expensive and must run only on accounts that earned it (Pass B), and because the prototype's single research agent drifted to similarly-named orgs and fabricated facts. M2 promotes the prototype's "do not drift" prompt into a structural constraint of the mode (staged-flow §5).
- **Architecture sources:** staged-flow §5 (converge pattern, target-lock, source choice via Source Planner), §1 (Discovery vs Profiling axis), §8 (M2 anti-hallucination: target-lock + evidence-span + faithfulness judge); substrate §5b (orchestrator-worker, workers return references), §3 (scoring vs deep field tags), §4 (waterfall); Doc C §3 (bounded fan-out, per-tier depth caps); overview §1 (Output 2).
- **Scope / deliverables:**
  - The **M2 account-profiling worker family** that runs as aspect workers inside the M7 per-account orchestrator-worker graph (substrate §5b): given the resolved `account_entity` and the active `deep`-pass field set from the ICP spec, read current claims via `current_value`, compute the **gap-field set** (deep fields not yet `verified` or stale per their TTL), and fill each gap-field by calling the M4 waterfall.
  - The **converge loop**: a bounded, checklist-driven iteration — read schema + current claims → identify gaps → fill → re-check → stop when the schema is satisfied OR sources are exhausted OR the per-account budget cap (M7) is hit (staged-flow §5). Explicitly the *opposite* shape from M6's open-ended `expand`; no marginal-yield stopping rule, a schema-completion stopping rule.
  - **Target-lock enforcement** as a structural constraint (staged-flow §5, §8): every query the workers hand the Source Planner / resolvers is entity-scoped — `site:` the account's `primary_domain`, canonical name + `hq_geo`/disambiguators from `account_entity`, registry-ID-scoped where available; and every synthesized (tier-4) claim must cite entity-bound `evidence_span`. A target-lock validator rejects claims whose evidence does not bind to the resolved entity before they are written.
  - **Aspect partitioning** into parallel field-cluster workers with no cross-talk (substrate §5b): e.g. `firmographics/funding`, `tech-stack`, `signals/intent` (deep narratives), `strategic_moves`, `operational_pain`, `resonance` (delegated to M8.2). Workers write claims to the store and return **references (claim ids), not blobs** (the artifact pattern).
  - Per-aspect **Source Planner invocation** (staged-flow §7d): for each gap-field-class, ask the planner (M4.6) for the ordered, weighted source set bounded by the ICP source profile; the planner decides when an expensive modality is worth triggering (gated to high tier and to profiles weighting that source class high).
  - **Depth/worker caps wired to tier** (Doc C §3): top tier gets the full set of aspect workers and may delegate facet sub-workers; lower tiers get a reduced aspect set or single-level depth. Caps are read from the M7 bounded-recursion knob, not hardcoded here.
  - Every M2 claim is written with `research_mode = M2`, `entity_type = account`, full provenance (value/source_url/source_tier/evidence_span/confidence/collected_at/cost_cents/run_id), and **field-claim provenance** (staged-flow §9). Tier-4 claims with no `evidence_span` are written but cannot be promoted past `unverified` (the M1/M9 rule).
- **Interface / seam:**
  - **Exposes:** a `profile_account(account_entity_id, icp_version, tier, run_id) -> AccountProfileResult` worker entrypoint (returns claim-id references + per-aspect coverage summary + cost) callable by the M7 orchestrator as a graph node. The mode is replaceable as a whole behind this entrypoint — its converge strategy can be reworked without touching M7 scheduling or M4 resolvers.
  - **Consumes:** the M7 orchestrator-worker graph + bounded-recursion knob (substrate §5b, Doc C §3) for spawning/capping; the M4 `Resolver` protocol + trust-tiered waterfall (substrate §4) and Source Planner (staged-flow §7d) for filling fields — so a Clay→direct-API swap or Exa→Parallel tier-4 swap is invisible to M2; M2 entity model from `account_entity` (substrate §2); M3 `field_definition` + ICP spec active field set/source profile; writes via the M1 claim store + `current_value` merge view. Invokes M9 verification as a downstream graph step (M2 does not judge its own claims).
  - **Swap points behind the seam:** tier-4 synthesis provider (M11, behind `Resolver`), source provider per field (M4), per-tier depth caps (M7 config), Postgres state machine → Temporal (M7) — none change the M2 worker contract.
- **Data model / schema:** writes `claim` rows (§4 contract) with `research_mode=M2`, `entity_type=account`, field keys in `core.*`/`account.*`/`account.resonance.*`/`<pack>.*` namespaces (§3). No new tables; reads `account_entity` (§4), `field_definition` (§4, `pass=deep`, `tier_plan`, `freshness_ttl`, `gate`), and the versioned `ICP spec` (§4) for the active field set + source profile. Reads `current_value(entity, field)` to compute gap-fields. Emits per-run coverage metadata (fields targeted / filled / left-empty) for the observability surface (Doc C §6) — stored on the M7 workflow row, not a new M8 table.
- **Dependencies:** **blocked by** M4 (Resolver/waterfall/Source Planner), M6 (high-tier accounts + tier assignment exist), M7 (orchestrator-worker graph, recursion knob, budget caps, campaign state machine). Consumes M1 (claim store, `current_value`), M2 (`account_entity`), M3 (field registry, ICP spec). **Unblocks** M8.2 (resonance is an M2 aspect), M9 (claims to verify), M11 (tier-4 fields requested here), M12 (Output-2 claims feed the handoff). Sibling of M8.3/M8.4 (committee runs as the contact-axis aspect of the same account graph).
- **Acceptance criteria:**
  - Given a resolved high-tier `account_entity` and an ICP spec, `profile_account` returns only after every `pass=deep` account field is either filled (claim written) or explicitly left empty/flagged, or the budget cap fires — never silently incomplete.
  - The converge loop is checklist-driven and **terminates**: a test with an account whose sources are exhausted halts with empty flagged fields (no infinite loop), and a test with a low budget cap halts at the cap with a partial-but-flagged result.
  - **Target-lock holds:** with a fixture of two similarly-named companies, no claim about company B is written to company A's `entity_id`; queries handed to resolvers are entity-scoped (assertable: every query contains the canonical domain or a registry ID); a tier-4 claim whose `evidence_span` does not bind to the resolved entity is rejected before write.
  - Aspect workers run in parallel, do not call each other, and return claim-id references — a worker's return payload contains no claim `value_json` blobs (artifact-pattern assertion).
  - Every written M2 claim has `research_mode=M2`, a non-null `source_tier`, and (for tier-4) a non-null `evidence_span` OR is left at `unverified` status; this is assertable per claim.
  - Per-tier depth: a top-tier account spawns the full aspect set; a lower-tier account spawns a strictly smaller set (cap respected, asserted against the M7 knob config).
  - Re-running `profile_account` for the same `(account, field, tier)` does not double-write or double-charge (idempotency delegated to and verified through M7).
- **Out of scope:** the faithfulness/corroboration/freshness gates (M9 — M8.1 only tags + invokes); tier-4 synthesis resolver internals (M11); resonance collectors (M8.2); committee/contact modes (M8.3/M8.4); value-narrative assembly (M12); the orchestrator graph engine, budget engine, idempotency keys themselves (M7); resolver/adapter implementations (M4).
- **Open decisions:** **D7** (economics) — per-tier fan-out depth/worker counts and per-account budget caps are read from M7 config; M8.1 proceeds on Doc C §5 default bands without hardcoding numbers. **D1** (output boundary) — M8.1 produces Output-2 *claims* only; whether the value narrative is included downstream is M12's concern, recommended-default `+ value narrative`.

### M8.2 — `account.resonance.*` field-class + collectors
- **Purpose:** Register and populate the `account.resonance.*` field-class — the account's emotional/cultural texture: employee sentiment (Glassdoor-style), morale/attrition/layoff signals, engineering-blog tone, public frustrations, "what it's like to work and buy here" (Doc C §2). This is the resonance layer the founders explicitly asked for; it feeds the *emotional register* of the value narrative (Output 4), not just its ROI math, and it is the part of Output 2 that account-level platforms structurally miss. It exists as a distinct issue because resonance is **tier-4 by nature, evidence-bound, and modality-heavy** (it consumes review sites, blogs, social) and so needs its own registered fields, source-profile weighting, and collector wiring — registered, never enumerated (open by construction, like the rest of the registry).
- **Architecture sources:** Doc C §2 (`account.resonance.*` definition, tier-4, populated by modality adapters); staged-flow §7 (Source Intelligence Layer, modality adapters, source profiles), §5 (lives in mode M2); substrate §3 (field registry, deep tag), §4 (waterfall, tier-4 last); overview §1 (Output 2); _conventions.md §3 (`account.resonance.*` namespace, registered).
- **Scope / deliverables:**
  - **Registered field definitions** under `account.resonance.*` (e.g. `account.resonance.employee_sentiment`, `account.resonance.attrition_signal`, `account.resonance.eng_blog_tone`, `account.resonance.public_frustrations`, `account.resonance.buying_culture`) as rows in the M3 field registry (`field_definition`), each with `type`, `validation`, `tier_plan` (tier-3 review/news → tier-4 synthesis), `freshness_ttl`, `pass=deep`, and `gate` — **not** a hardcoded enum (substrate §3, Doc C §2). The set is extensible by adding rows.
  - **Resonance collectors** wired as a resonance aspect worker invoked by M8.1's converge loop: they call the Source Planner (M4.6) for the resonance field-class within the ICP source profile, then the M4 waterfall — tier-3 reputable sources (review sites, news) first, tier-4 synthesis last (substrate §4). Synthesis is reached through the M11 resolver behind the `Resolver` seam.
  - **Source-profile weighting hooks** for the resonance class per industry pack (staged-flow §7c): e.g. Glassdoor/review sites high for service businesses, engineering-blog tone high for `frontier_ai`/`data_infra`. Authored as pack priors (M3.3), overridable per client — M8.2 declares the field-class needs these weights; it does not own the pack authoring tool.
  - **Modality routing** (Doc C §2, staged-flow §7b): resonance often comes from non-text or semi-structured surfaces (review-site pages, blog posts); collectors request the source via the M4 modality-adapter framework (fetch→adapt→extract) so adding a new resonance source is a manifest+adapter registration, not a code fork.
  - Every resonance claim is written `research_mode=M2`, `entity_type=account`, with mandatory `evidence_span` for tier-4 (Doc C §2 "evidence-bound"); no span → not promotable past `unverified`.
  - **Sensitivity awareness note in field defs:** account resonance is account-level, not personal, so it is *not* governed by Doc D's contact use-class machinery — but `validation`/extraction must not let an account-resonance field smuggle a named individual's special-category data (that belongs to `contact.facet.*`/M10). Flag at field-definition level.
- **Interface / seam:**
  - **Exposes:** the registered `account.resonance.*` field set (consumable by any pack/ICP via the field registry) and a `collect_resonance(account_entity_id, icp_version, tier, run_id) -> list[claim_ref]` collector entrypoint invoked by M8.1 as its resonance aspect worker. Replaceable: the collector set can change source mix without touching M8.1's converge loop or the registry rows.
  - **Consumes:** M3 field registry (`field_definition`) to register the class; M4 Source Planner + waterfall + modality adapters to fetch/adapt/extract; M11 tier-4 synthesis behind the `Resolver` seam; M1 claim store to write. Source weights consumed from M3.3 industry packs.
  - **Swap points behind the seam:** which review/sentiment source is used (M4 resolver swap), tier-4 synthesis provider (M11), per-pack source weights (M3.3 config) — none change the field-class contract or the collector entrypoint.
- **Data model / schema:** new `field_definition` rows in the `account.resonance.*` namespace (§4 `field_definition` contract, no schema change). Writes `claim` rows (§4) with those field keys, `research_mode=M2`, `source_tier∈{3,4}`. No new tables. `value_json` shape per field (e.g. a sentiment field carries `{label, polarity, summary}`); shape declared in the field def, consistent with substrate §1 ("shape defined by field registry").
- **Dependencies:** **blocked by** M3 (field registry to register the class; industry packs for source weights), M4 (Source Planner, waterfall, modality adapters), and M8.1 (the M2 converge loop that invokes the resonance aspect). Will reach M11 for tier-4 synthesis (resonance narratives) once that exists; until then resonance fields populate from tier-3 only and tier-4 fields stay empty/flagged (a correct output). **Unblocks** M12 (resonance claims feed the value narrative's emotional register).
- **Acceptance criteria:**
  - The `account.resonance.*` fields are present as `field_definition` rows with `pass=deep` and a `tier_plan` ending in tier-4 synthesis; adding a new resonance field is a single row insert with no code change (assertable via a test that registers `account.resonance.<new>` and sees it picked up by the collector).
  - For a high-tier account, `collect_resonance` writes at least the tier-3-reachable resonance claims with `evidence_span` populated; tier-4 resonance fields with no available synthesis resolver are left empty and flagged (not fabricated).
  - Every tier-4 resonance claim has a non-null `evidence_span` or remains `unverified` (assertable per claim).
  - Source weighting is honored: with a pack that weights Glassdoor high and journals low, the Source Planner's ordered set for resonance puts the review source ahead of journals (assertable against the planner output).
  - A resonance source delivered via a non-text modality (e.g. a blog requiring scrape/extract) is consumed via the M4 modality-adapter path, not a bespoke fetch in M8.2.
  - No `account.resonance.*` claim carries a named individual's special-category attribute (validation rejects it; such data must route to `contact.facet.*`/M10).
- **Out of scope:** tier-4 synthesis resolver implementation (M11); contact-level personal hooks and the use-gate (`contact.facet.*`/M8.5/M10); pack authoring tooling and per-client source-weight UI (M3.3); the faithfulness judge over resonance claims (M9); narrative synthesis from resonance (M12).
- **Open decisions:** **D3** (personal-data posture) — account resonance is account-scoped and not personal; but the field-def sensitivity note exists so a posture change (M10) cannot leak individual special-category data via resonance. **D7** (economics) — resonance is the most synthesis-heavy account class; its tier-4 spend is bounded by the M8.1/M7 per-account cap, proceeding on Doc C defaults.

### M8.3 — Committee Discovery (mode M3, person resolution + role plausibility gate, persona keys)
- **Purpose:** Within a known high-tier account, find the relevant people and hypothesize each one's committee role (champion / economic_buyer / technical_evaluator / blocker), producing the **buying committee** that is Output 3 and the V1 contact graph (substrate §7). Mode M3 is *bounded Discovery* — recall over a bounded universe (this company's people) — and is the contact-axis analogue of M6's account discovery: same existence-gate discipline, one level down. It exists because account truth is necessary but not sufficient (the email goes to a *person*); building the contact graph + persona keys in V1 avoids re-paying for it in V2 (substrate §7). It prevents the prototype's "invented / wrong people" failure via person identity-resolution + a role plausibility gate (staged-flow §8).
- **Architecture sources:** staged-flow §6 (M3 bounded discovery, person identity-resolution + gate, sources), §8 (M3 anti-hallucination: identity-resolution + role plausibility gate), §1 (Discovery axis at contact level); substrate §7 (committee roles, persona key, per-contact signal), §2 (contacts resolve under accounts); overview §1 (Output 3); _conventions.md §3 (committee personas/roles).
- **Scope / deliverables:**
  - The **M3 committee-discovery worker** running as the contact-axis aspect of the M7 account graph (substrate §5b): given a resolved high-tier `account_entity`, find candidate people via people/org sources (Apollo/ZoomInfo/LinkedIn-style, the account's own team/leadership pages, signals of public activity) — all through the M4 `Resolver`/waterfall/Source Planner seam (staged-flow §6).
  - **Bounded-discovery orchestration (`expand` within one account):** parallel candidate queries across the planned people-sources, results streamed into the identity service for dedup; a stopping rule on marginal new-candidate yield OR a per-account committee budget cap — open-ended, but bounded to the company's people, never the open web.
  - **Person identity-resolution + existence gate** (staged-flow §6, §8): every candidate person must resolve to a real canonical contact entity under the account (keyed on LinkedIn URL / verified email) via the M2 identity service before admission, carrying **discovery-provenance** (where found, matched signal, discovery confidence). A hallucinated person has nothing to resolve to and dies here — same gate as M6, one level down. Contacts resolve **under** the account (substrate §2).
  - **Role plausibility gate + role inference** (staged-flow §8, substrate §7): for each admitted person, infer `role_on_committee` from title + org context, stored as a `contact.role_on_committee` claim with confidence; the plausibility gate rejects implausible role assignments (e.g. an intern as economic_buyer) rather than guessing. Role is one of the four canonical personas (_conventions.md §3).
  - **Persona keys** (substrate §7): tag each contact with a `contact.persona` claim so downstream content/design key on `(account, persona)` — the ROI-vs-architecture framing split. Persona keying is established here, not in a later phase.
  - **Coverage confidence over the committee** (Doc C §7 applied at contact level): report estimated committee coverage and name the people-channels not searched, rather than implying the committee is exhaustive.
  - Claims written `research_mode=M3`, `entity_type=contact`, with **discovery-provenance** for the existence match and **field-claim provenance** for role/persona (staged-flow §9).
- **Interface / seam:**
  - **Exposes:** a `discover_committee(account_entity_id, icp_version, tier, run_id) -> CommitteeResult` worker entrypoint (returns admitted `contact_entity_id`s + role/persona claim refs + committee coverage estimate) callable by the M7 orchestrator. The committee output structurally matches the `committee[]` shape of `account_handoff` (overview §3) so M12 assembles it without translation. Replaceable as a whole: the people-source mix and role-inference model can change behind this entrypoint.
  - **Consumes:** M2 identity service (the shared existence-gate/target-lock backbone — staged-flow §9) to resolve persons under accounts; M4 `Resolver`/waterfall/Source Planner for people-sources (Apollo→ZoomInfo→LinkedIn swappable behind `Resolver`); M7 orchestrator graph + budget caps; M1 claim store + `current_value`; M3 ICP spec (which personas/roles matter for this ICP). Hands admitted contacts to M8.4 for deep contact profiling.
  - **Swap points behind the seam:** people/org provider (M4 resolver swap), role-inference model (swappable), identity-resolution thresholds (M2 config) — none change the committee entrypoint or the `committee[]` shape.
- **Data model / schema:** creates/links contact entities under accounts via M2 (substrate §2 — contacts resolve under accounts on LinkedIn URL/verified email; no new table here). Writes `claim` rows (§4) with `entity_type=contact`, `research_mode=M3`, field keys `contact.role_on_committee`, `contact.persona`, plus **discovery-provenance** for the match. Reads `account_entity` and the ICP spec. Role/persona values from the canonical sets (_conventions.md §3). Contact field-claim provenance will additionally carry `identity_binding`/`use_class` once M8.4 profiles them (here, role/persona claims are professional-public by construction → `use_class=professional-public`, `identity_binding` per the resolution strength).
- **Dependencies:** **blocked by** M2 (identity resolution — the person existence gate; this is the make-or-break dependency), M4 (people-sources via Resolver/waterfall/planner), M6 (high-tier accounts exist), M7 (orchestrator graph, budget caps). Consumes M1, M3. **Unblocks** M8.4 (deep contact profiling runs on M3's admitted, role-tagged contacts) and M12 (the `committee[]` of the handoff). Priority raised to **2 (High)** within the milestone: M8.4 cannot run without M3's resolved, gated committee, and the contact graph is the V1 wedge (substrate §7).
- **Acceptance criteria:**
  - For a high-tier account, `discover_committee` returns only contacts that **resolved** through the M2 identity service under that account (keyed on LinkedIn URL / verified email); an unresolvable candidate is dropped at the gate (assertable with a fabricated-person fixture that has nothing to resolve to).
  - Bounded discovery **terminates** on marginal-yield drop or the committee budget cap; a test with a people-source returning duplicates halts without unbounded querying.
  - Every admitted contact has a `contact.role_on_committee` claim with a value in {champion, economic_buyer, technical_evaluator, blocker} and a confidence; the role plausibility gate rejects an implausible assignment (test: a clearly junior title is not admitted as economic_buyer, or is flagged not promoted).
  - Every admitted contact carries a `contact.persona` claim so `(account, persona)` keying is available downstream (assertable).
  - Committee coverage confidence is reported (estimated coverage + named unsearched people-channels), not an exhaustiveness claim.
  - Claims carry `research_mode=M3`, discovery-provenance on the existence match, and resolve under the correct `account_entity_id` (no orphan contacts).
- **Out of scope:** deep personal facts / `contact.facet.*` and identity-binding-strength assessment (M8.4/M8.5); the appropriateness/use gate and jurisdiction (M10); the identity-resolution algorithm itself (M2 owns dedup→link→canonicalize); the orchestrator/budget engine (M7); the handoff assembly (M12); contact-level intent signals beyond role/persona discovery (deep per-contact signal is M8.4).
- **Open decisions:** **D4** (contact geography — **resolved: mixed/global**) — resolved persons carry a jurisdiction (set in M10) from location claims; M3 records location where found but does not gate on jurisdiction. **D3** (posture) — Option 3 (professional-public only) would scope M3 sources to professional surfaces; M3 proceeds on the recommended default (Option 1) and treats role/persona as `professional-public`. **D5** (ICP multiplicity) — which personas matter is read per ICP version, supporting multiple ICPs.

### M8.4 — Contact Profiling (mode M4, target-lock + identity-binding strength)
- **Purpose:** For each verified committee member, gather "everything publicly true about *this verified person*" — role-relevant background, posts, podcasts, talks, publications, stated interests — the deep contact picture that completes Output 3 and supplies the "they really know me" hooks. Mode M4 is *Profiling*: closed, target-locked per person, the contact-axis analogue of M2 — and the mode where open-internet heterogeneity truly bites (it consumes YouTube/X/Substack/podcasts/journals via the long-tail Source Intelligence Layer). It exists because account data is insufficient and the email lands on a desk; and it is the mode whose make-or-break safeguard is **identity-binding strength** — getting a personal fact *wrong* in 1:1 outreach is worse than omitting it (staged-flow §6).
- **Architecture sources:** staged-flow §6 (M4 closed/target-locked per person, identity-binding strong/weak, long-tail sources), §8 (M4 anti-hallucination: identity-binding, weak never promoted), §7 (Source Intelligence Layer / modality adapters for the long tail); substrate §7 (per-contact signal, persona key); Doc C §2–§3 (`contact.facet.*`, bounded fan-out incl. facet sub-workers), Doc D §2–§3 (use-class tagging at extraction, two gates); overview §1 (Output 3); _conventions.md §3 (identity-binding strength strong/weak).
- **Scope / deliverables:**
  - The **M4 contact-profiling worker family** running on each admitted committee member (from M8.3), inside the M7 graph: read the active `pass=deep` contact field set (`contact.*`, `contact.facet.*`) + current claims, compute gap-fields, fill via the M4 waterfall/Source Planner (staged-flow §6). May spawn **facet sub-workers** (the second level of the bounded fan-out, Doc C §3) for the richest aspects (e.g. a single contact's interests), capped per tier by the M7 recursion knob.
  - **Target-lock per person** (staged-flow §6, the M2 analogue): every query and synthesis bound to the *resolved* contact — verified profile/handle, name + employer + role + location disambiguators; entity-scoped so the run does not drift to a same-name stranger.
  - **Identity-binding strength assessment** on every personal claim (staged-flow §6, §8 — the central deliverable): tag each claim `identity_binding ∈ {strong, weak}` — **strong** = evidence on the person's *verified* profile/handle or co-occurring with multiple strong identifiers (name + employer + role + location); **weak** = name-match only (the same-name trap). M8.4 *computes and tags* the strength as field-claim provenance; the *promotion gate* that drops weak-binding claims is M9's identity-binding gate. M8.4 must never write a weak-binding personal claim without the `weak` tag.
  - **Use-class tagging at extraction** (Doc D §2 — tagged the moment the claim is extracted, independent of accuracy): every `contact.*`/`contact.facet.*` claim tagged `use_class ∈ {professional-public, personal-public-non-sensitive, sensitive}`. M8.4 *tags*; the appropriateness/use gate and posture logic are M10. Sensitive-adjacent interests (a hobby tied to a religious/political cause) must be tagged `sensitive` (Doc D §2 note).
  - **Per-contact deep signal** (substrate §7): recent activity, role changes, posts, mentions — the per-person layer keyed under the contact, feeding intent and the value narrative.
  - **Long-tail modality consumption** (staged-flow §7, Doc C §2): video→transcript, audio→transcript, PDF→text via the M4 modality-adapter framework — the Source Planner gates whether transcribing a 90-min podcast is worth it (high tier + source-class weighted high). M8.4 requests sources; it does not implement adapters.
  - Claims written `research_mode=M4`, `entity_type=contact`, with **field-claim provenance including `identity_binding` + `use_class`** (staged-flow §9, the contact-claim provenance flavor), mandatory `evidence_span` for tier-4.
- **Interface / seam:**
  - **Exposes:** a `profile_contact(contact_entity_id, account_entity_id, icp_version, tier, run_id) -> ContactProfileResult` worker entrypoint (returns claim refs + per-claim `identity_binding`/`use_class` summary + cost) callable by the M7 orchestrator per committee member. Replaceable behind this entrypoint.
  - **Consumes:** M8.3's admitted/role-tagged contacts; M2 identity service for the target-lock binding; M4 `Resolver`/waterfall/Source Planner + modality adapters (long-tail sources swappable behind `Resolver`/`source_manifest`); M7 orchestrator + bounded recursion knob (facet sub-workers) + per-contact budget cap; M1 claim store + `current_value`; the `contact.facet.*` field-class (M8.5). Each contact claim carries the **contact field-claim provenance flavor** (staged-flow §9): standard provenance **plus** `identity_binding ∈ {strong, weak}` and `use_class ∈ {professional-public, personal-public-non-sensitive, sensitive}` (these extend the `claim` contract for contact claims, §4 + Doc D). Reads `account_entity`/contact entities (substrate §2), `field_definition` (deep contact fields), ICP spec. No new tables; `value_json` shapes per field def.
- **Dependencies:** **blocked by** M8.3 (needs resolved, role-tagged committee members to profile), M2 (the target-lock binding), M4 (long-tail sources + modality adapters + planner), M7 (graph, facet sub-workers, per-contact budget caps), M8.5 (the `contact.facet.*` field-class definitions). Consumes M1, M3. - **Acceptance criteria:**
  - For a verified committee member, `profile_contact` writes contact claims each tagged with `identity_binding` and `use_class`; no contact claim is written without both tags (assertable per claim).
  - **Identity-binding correctness:** with a same-name fixture (a fact on a stranger's page sharing the contact's name), the claim is tagged `identity_binding=weak`; a fact on the contact's verified handle is tagged `strong`. (M8.4 only tags; M9 drops weak — assert the tag here.)
  - **Use-class correctness:** a professional post → `professional-public`; an alma-mater mention → `personal-public-non-sensitive`; a health/religion-adjacent interest → `sensitive` (Doc D §2). Assertable on a fixture set.
  - **Target-lock holds per person:** queries are entity-scoped to the resolved contact (verified handle / name+employer+role+location); no claim about a same-name stranger is written to the contact's `entity_id`.

### M8.5 — `contact.facet.*` field-class
- **Purpose:** Register the `contact.facet.*` field-class — the rich personal hooks that produce "they really know me": nickname, stated interests, communication style, public appearances (podcasts/talks), publications, causes, alma mater, professional history beyond the title (Doc C §2). It is a distinct issue because, per the architecture's explicit rule, **power and governance are specified together, never separately**: every `contact.facet.*` claim is governed by Doc D — it requires strong identity-binding *and* an allowed use-class before it can drive outreach (Doc C §2, Doc D §7). This issue defines the field-class so M8.4 can populate it and M10 can govern it, with the governance hooks (`identity_binding` + `use_class` required on every claim, retention TTLs) built into the field definitions rather than bolted on.
- **Architecture sources:** Doc C §2 (`contact.facet.*` definition, governed by Doc D, populated by modality adapters); Doc D §2 (use-class tagged at extraction), §4 (retention TTLs on personal claims, DSAR/erasure tractability), §7 (binds to verification + handoff); staged-flow §6 (identity-binding); substrate §3 (field registry); _conventions.md §3 (`contact.facet.*` namespace; use-classes; identity-binding strength).
- **Scope / deliverables:**
  - **Registered field definitions** under `contact.facet.*` (e.g. `contact.facet.nickname`, `contact.facet.stated_interests`, `contact.facet.communication_style`, `contact.facet.public_appearances`, `contact.facet.publications`, `contact.facet.causes`, `contact.facet.alma_mater`, `contact.facet.career_history`) as rows in the M3 field registry — **registered, never enumerated** (Doc C §2, substrate §3). Each carries `type`, `validation`, `tier_plan`, `pass=deep`, `gate`, and a **shorter retention/freshness `freshness_ttl`** than firmographic facts (Doc D §4 — personal data minimization; people change).
  - **Governance hooks in the field definition** (Doc C §2, Doc D §7): mark every `contact.facet.*` field as requiring, on each claim, a non-null `identity_binding` and a non-null `use_class` (the field-def `gate` references both the M9 identity-binding gate and the M10 use-gate). A `contact.facet.*` claim missing either tag is structurally non-promotable — the schema-level expression of "power and governance together."
  - **Default use-class hints per field** (Doc D §2) to guide M8.4's extraction-time tagging: e.g. `alma_mater`→`personal-public-non-sensitive`, `publications`/`public_appearances`→`professional-public`, `causes`→potentially `sensitive` (religion/politics-adjacent). Hints, not hardcoded values — the actual tag is computed per claim by M8.4 from the evidence.
  - **Source-profile weighting hooks** per pack (staged-flow §7c) for the facet class (e.g. podcasts/X high for thought-leader personas), authored in packs (M3.3), overridable per client.
  - **Modality routing declaration** (Doc C §2, staged-flow §7b): facets come heavily from video/audio/long-tail surfaces consumed via M4 modality adapters; the field-class declares this so adding a facet source is a manifest+adapter registration.
  - **Erasure/DSAR alignment** (Doc D §4): because `contact.facet.*` claims key on a resolved `contact_entity_id` in the append-only store, the field-class is defined so an erasure request resolves to a deterministic set of facet claims to tombstone — M8.5 ensures facet fields carry no out-of-band copies that escape the store.
- **Interface / seam:**
  - **Exposes:** the registered `contact.facet.*` field set (consumable by M8.4 to populate, by M10 to govern, by M12 to read for the handoff) and the per-field governance contract (every claim must carry `identity_binding` + `use_class`; shorter retention TTL). Replaceable: facet fields can be added/removed as registry rows without code change.
  - **Consumes:** M3 field registry (`field_definition`) to register; M3.3 packs for source weights; the M4 modality-adapter framework (declared, used by M8.4); the Doc D use-class taxonomy + identity-binding-strength taxonomy (_conventions.md §3) as the value domains for the required tags.
  - **Swap points behind the seam:** which facet source/modality (M4 manifest+adapter), per-pack weights (M3.3 config), posture (M10 config) — none change the field-class definition or its governance contract.
- **Data model / schema:** new `field_definition` rows in the `contact.facet.*` namespace (§4 `field_definition` contract; adds the convention that facet fields require `identity_binding` + `use_class` on every claim and carry a short personal-data retention TTL — an extension of the contract for this class, consistent with Doc D §4, not a contradiction). Claims of these fields are written by M8.4 as `claim` rows (§4) with the contact field-claim provenance flavor. No new tables; `value_json` shapes per field def.
- **Dependencies:** **blocked by** M3 (field registry to register the class; packs for source weights). Tightly coupled to M8.4 (which populates the class) and M10 (which governs it — use-gate, postures, jurisdiction, retention/erasure) and M9 (identity-binding gate). **Unblocks** M8.4 (cannot populate facets without their field defs) and M12 (facet claims in the handoff carry `identity_binding` + `use_class`).
- **Acceptance criteria:**
  - The `contact.facet.*` fields exist as `field_definition` rows with `pass=deep`, a `tier_plan`, and a **shorter `freshness_ttl`** than a firmographic field like `core.employee_count` (assertable).
  - Each `contact.facet.*` field def declares that every claim must carry a non-null `identity_binding` and a non-null `use_class`; a facet claim missing either is non-promotable (assertable: a facet claim with `identity_binding=null` cannot pass the promotion check).
  - Adding a new facet field is a single registry-row insert picked up by M8.4 with no code change (assertable via a `contact.facet.<new>` registration test).
  - Default use-class hints are present per field and used by M8.4 as a starting point, but the per-claim tag is computed from evidence (a `causes` claim about a religious cause is tagged `sensitive`, not just defaulted).
  - Facet fields route through M4 modality adapters for non-text sources (declared, exercised by an M8.4 integration test).
  - An erasure request for a `contact_entity_id` resolves to a deterministic set of `contact.facet.*` claims to tombstone (assertable that the field-class holds no escaped copies; full DSAR/erasure flow is M10).
- **Out of scope:** populating the facets (M8.4); the use-gate, three postures, jurisdiction resolution, lawful-basis recording, and the DSAR/erasure *flow* (M10); the identity-binding *promotion* gate and faithfulness judge (M9); tier-4 synthesis (M11); modality-adapter *implementation* (M4); pack authoring tooling (M3.3); narrative use of facets (M12).
- **Open decisions:** **D3** (posture — recommended default Option 1) — the field-class is the surface the use-gate "primarily polices" (Doc D §7); Option 3 (professional-public only) would source-scope facets to professional surfaces, Option 2 would store `sensitive` facets gated-at-use. M8.5 defines all facet fields and lets M10 config decide gather/store/use; it does not hardcode a posture. **D8** (2026 legal verification) — retention TTLs and the special-category handling in facet defs proceed on Doc D fundamentals pending D8.
