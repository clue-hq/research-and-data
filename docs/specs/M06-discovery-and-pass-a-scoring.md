# M6 — Discovery (mode M1) + Pass A Scoring & Tiering
**Layer label:** layer:discovery-scoring  ·  **Depends on:** M2 (Identity Resolution), M3 (ICP & Research-Schema Compiler), M4 (Source Layer & Source Intelligence)  ·  **Priority:** 2 (High)
**Architecture sources:** staged-flow §3 (mode M1 grounded discovery, expand pattern, stopping rule, existence/identity gate), §4 (the scoring bridge), §8 (mode-specific anti-hallucination), §9 (claim-store provenance flavors); substrate §5a (two passes), §9 (explainable scoring), §3 (scoring-vs-deep field tags), §1 (claim store, current_value), §2 (identity service); Doc C §1 (two-tier signal model), §5 (cost dial), §6 (per-source yield), §7 (coverage confidence); Doc B §4 (import convergence at the Pass A bridge), §3/§4 (D5/D6); overview §1 (Output 1), §2 (end-to-end map), §3 (output contract), §5 (open decisions D1–D8)

## Goal & scope of this milestone

M6 is the **wide-and-cheap front half** of the research pipeline. It turns a confirmed, versioned ICP spec (from M3/Stage 0) into **Output 1** of the subsystem — a scored, ICP-fit account list where every candidate carries a fit score, an intent score, the cheap deterministic signals behind those scores, and a provenance link behind every signal (overview §1). It sits in the end-to-end map (overview §2; staged-flow §10) at exactly the segment between Stage 0 and Pass B: `ICP spec → [discovery (mode M1) | import] → existence/identity gate → Pass A scoring → tiering → human checkpoint`.

Concretely, this milestone delivers five components:

1. **Account Discovery (mode M1)** — grounded-only, recall-optimized candidate generation via the `Resolver` seam (M4), orchestrated as an *expand* pattern with a marginal-yield stopping rule and a discovery budget cap (M6.1).
2. **Existence/identity gate + discovery-provenance** — the anti-fabrication spine for the discovery axis: every candidate must resolve to a real canonical `account_entity` through the M2 identity service before admission, and is stamped with a *discovery-provenance* claim (M6.2).
3. **Pass A scoring engine** — cheap, deterministic-first fit + intent scoring over the *whole* admitted/imported list, computing the two-tier signal model's cheap proxies (intent/growth/hiring/technographic/firmographic) into decomposed, provenance-backed sub-scores (M6.3).
4. **Tiering + human checkpoint** — deterministic tier assignment from scores plus an `interrupt()`-based durable human gate where the client reviews/adjusts tier cutoffs and the pre-run cost estimate before any Pass B spend (M6.4).
5. **Coverage-confidence estimator** — a *separate* estimate (distinct from the cost-driven stopping rule) of "estimated ~X% of the addressable set found via these channels," naming the channels not yet searched (M6.5).

**The discipline this milestone enforces** (staged-flow §10, §3; Doc C §1): discovery stays **existence-only and grounded** — it never produces deep facts and the LLM never *is* the source of an entity; the **signals live in Pass A**, deterministic-first and cheap, not in M1; and nothing enters the account store without surviving the existence/identity gate. The scoring bridge (staged-flow §4) is the **convergence point** for both entry scenarios: discovered accounts (Scenario A) and resolved+back-scored imported accounts (Scenario B, owned by M5 but converging here, Doc B §4) flow into the *same* Pass A → tiering → checkpoint path.

**Explicitly NOT in this milestone:**
- **Scenario B import ingestion** (bulk identity resolution over messy free-text, the import sub-pipeline) — owned by **M5 (Stage 0 Front Edge)**, Doc B §4. M6 only guarantees imported accounts converge at the Pass A bridge on identical contracts.
- **The ICP spec compiler** (field set, discovery strategy, source profile, scoring rubric) — owned by **M3**. M6 *consumes* the ICP spec; it does not author it.
- **Resolvers / the source registry / the Source Planner** — owned by **M4**. M6 calls resolvers behind the `Resolver` protocol and consumes the `source_manifest`; it does not implement any provider.
- **Identity resolution internals** (dedup → linkage → canonicalization, review queue) — owned by **M2**. M6 calls the identity service and never turns a name into an id itself.
- **Pass B deep research** (modes M2/M3/M4, the bounded two-level fan-out, resonance/facet field-classes) — owned by **M8**. M6 produces the tiered list Pass B consumes.
- **The campaign-run state machine** (the outer scheduler, phase idempotency, pause/resume/adjust) — owned by **M7 (Durable Execution)**. M6 components run *inside* the `discovery`, `scoring`, and `tier_checkpoint` phases of that machine and expose phase-idempotent, resumable seams to it.
- **The faithfulness judge, corroboration thresholds, freshness refresh** — owned by **M9 (Verification Layer)**. M6 writes claims that M9 later verifies; Pass A is deterministic-first so it does not depend on the judge.
- **The disposition feedback loop and the source-yield learning loop** that *consume* per-source yield — owned by **M13** (and staged-flow §7e). M6 *emits* the per-source yield signal but does not reweight anything.

## Issues

### M6.1 — Account Discovery (mode M1, grounded-only, expand pattern, stopping rule)
- **Purpose:** Produce a high-recall candidate account set for a confirmed ICP — including companies the client did not know existed — *without ever fabricating an entity*. This is the open-ended half of the discovery/profiling 2×2 (staged-flow §1): optimized for recall, and structurally constrained so candidates may **only originate from real returned records or URLs**, never from an LLM "name 50 companies that fit" (the exact source of the prototype's fabricated accounts, staged-flow §3, §8). The component fans discovery queries across the ICP's planned channels (the *expand* pattern), streams raw candidate hypotheses to the gate (M6.2), and knows when to stop — both on a marginal-yield drop and on a hard discovery budget cap, because open-ended search otherwise runs forever.
- **Architecture sources:** staged-flow §3 (grounded-only principle, the forbidden parametric-listing case, the *expand* pattern, the stopping rule on marginal yield, discovery budget cap), §1 (Discovery = recall axis), §10 (sequence position); Doc B §4 Scenario A + Hybrid (lookalike expansion from seeds/customers/import); Doc C §1 (discovery stays existence-only; signals come at Pass A, not M1); overview §2 (map position).
- **Scope / deliverables:**
  - A **discovery orchestrator** that reads the active **ICP spec**'s `discovery strategy` (which channels, which ICP filters, which seeds for lookalikes — staged-flow §2) and plans a set of parallel discovery queries across the planned channels.
  - **Grounded channel adapters invoked behind the `Resolver` seam** (M4): structured-DB ICP-filtered company search (Clay/Apollo/ZoomInfo), web entity discovery returning real domains (Exa Websets / Parallel FindAll-style), curated lists/directories/association/exhibitor lists, and **lookalike expansion** from the client's seed accounts + existing customers (CRM) + (hybrid) imported list. Each returns *real records/URLs only*; no provider is hardcoded — selection is config from the ICP's discovery strategy and the source profile (M4).
  - **Config-bounded LLM query planning/expansion only** (staged-flow §7d discipline): the orchestrator may use an LLM — **called through the shared OpenRouter `LLMGateway` (M0.4), model id as config** — to *plan and expand queries* and pick among the allowed channels, but the LLM is never permitted to emit a candidate entity. Enforce this as a structural invariant: every candidate object must carry a `source_url`/`source_record_ref` originating from a resolver call, or it is dropped before the gate.
  - The **expand pattern**: parallel query fan-out, results streamed (deduped via the identity service candidate-set, M2) toward the gate (M6.2); workers return references, not blobs.
  - The **stopping rule**: stop when the new-candidate (post-dedup) rate over a sliding window drops below a configured marginal-yield threshold, OR the discovery budget cap (sum of resolver `cost_cents`) is reached — whichever first. Both thresholds are versioned config (per ICP / per pack), not code.
  - Emit, per channel/query: the raw candidate stream + the per-channel running yield counters that M6.5 (coverage) and Doc C §6 (per-source yield) consume.
- **Interface / seam:**
  - **Consumes:** the versioned **`ICP spec`** (`discovery strategy` field, §4 contract) from M3; the **`Resolver` protocol** (substrate §4) for all channel adapters — *every entity-producing channel is just a resolver*, so swapping Clay→direct API or adding a new directory is a registry/config change (M4) behind this seam, invisible here; the **`source_manifest`** (`entity_scope=account`, `yields`, `cost`, `latency`) to pick/order discovery channels; the M2 identity-service **candidate-set** API for in-stream dedup.
  - **Exposes:** a `discover(icp_spec_version, run_id) -> stream[CandidateHypothesis]` seam where `CandidateHypothesis = {raw_name?, candidate_domain/url, matched_channel, matched_signal, resolver_confidence, source_record_ref, cost_cents}` — a *hypothesis*, explicitly **not** an `account_entity` until M6.2 admits it. Also exposes per-channel yield counters and a `stopping_reason{marginal_yield|budget_cap|exhausted}`.
  - **Replaceability:** the whole discovery engine sits behind `discover(...)`; the *expand* orchestration could be re-implemented (e.g. on Temporal child workflows under M7) without changing the gate (M6.2) or the scoring bridge (M6.3). Channels are pure config + resolvers.
- **Data model / schema:** No new persisted entity tables. Writes are deferred to M6.2 (admission). The raw candidate stream is in-memory/queue state owned by the `discovery` campaign-run phase (M7). Reads: **`ICP spec`** (§4), **`source_manifest`** (§4), `account_entity` candidate-set (§4, via M2). Per-channel yield counters persist as run-scoped counters keyed `(run_id, source_key)` (shared shape with Doc C §6 per-source yield and M6.5 coverage; no bespoke table — extend the run telemetry M7 owns).
- **Dependencies:** Blocked by **M3** (ICP spec with discovery strategy), **M4** (resolvers + source registry/manifests + Source Planner config bounds), **M2** (identity candidate-set for in-stream dedup). Hands its candidate stream to **M6.2** (gate). Runs inside the `discovery` phase of **M7**'s campaign-run state machine. Unblocks **M6.5** (consumes yield/stopping signals).
- **Acceptance criteria:**
  - Given an ICP spec whose discovery strategy names channels C1…Cn, the orchestrator issues parallel queries across all configured channels and produces a candidate stream whose every item carries a non-null `source_record_ref`/`source_url` and a `matched_channel`.
  - **Anti-fabrication invariant test:** with all real resolvers stubbed to return empty, the orchestrator emits **zero** candidates (it cannot invent any), even when LLM query-planning is enabled.
  - The stopping rule halts the run when post-dedup new-candidate rate over the configured window falls below threshold; a separate test halts the run when the discovery budget cap is hit; the returned `stopping_reason` correctly distinguishes the two.
  - Lookalike expansion seeded from a known customer/seed/import set produces candidates and tags each with `matched_channel=lookalike` and the seed it expanded from.
  - Swapping a discovery channel's underlying provider (config change only, no code in M6) yields an identical candidate-stream contract — verified by a resolver double.
  - Per-channel yield counters are emitted and queryable by `(run_id, source_key)`.
- **Out of scope:** the existence/identity gate and admission (M6.2); any deep facts or signals (Pass A, M6.3; deep pass, M8); Scenario B import ingestion (M5); resolver/provider implementations and the Source Planner itself (M4); the outer scheduler/durability (M7).
- **Open decisions:** **D5** (multiple ICPs per client — recommended supported): the seam keys discovery on a specific `icp_spec_version`, so multiple ICPs run as independent discovery passes; proceed on the multi-ICP default without hardcoding one-ICP-per-client. **D7** (economics: discovery budget cap magnitude, typical campaign size hundreds vs thousands): the cap and marginal-yield threshold are versioned config, not constants; proceed with config-driven defaults pending confirmation.

### M6.2 — Existence/identity gate + discovery-provenance
- **Purpose:** The anti-fabrication spine of the discovery axis (staged-flow §3, §8 row M1). A discovered candidate is a *hypothesis, not an account*. Before it is admitted to the store it must resolve to a **real canonical entity** (live domain + corroborating record) via the M2 identity service. A hallucinated entity has nothing to resolve to and **dies here, before a cent of profiling spend**. Surviving candidates become `account_entity` rows and carry a **discovery-provenance** record — *where they were found, the matched signal, the discovery confidence* — so admission itself is auditable and Output 1's "no score without its evidence" holds back to the moment of entry. This is the one component every candidate must pass through; it is the contract that makes the whole discovery axis trustworthy.
- **Architecture sources:** staged-flow §3 (the existence/identity gate; "discovery yields admitted candidates with discovery-provenance; no deep facts yet"), §8 (M1 mechanism: grounded-only + existence/identity gate before admission), §9 (claim store gains a `research_mode` dimension and the *discovery-provenance* flavor); substrate §2 (identity service: deterministic-first → probabilistic → review queue, ≈0.95 auto-merge; in-flight Redis lock), §1 (append-only claim store; tier rules); overview §1 (provenance behind every signal); Doc B §4 (imported accounts resolve through the same identity service — symmetric gate, one source already resolved).
- **Scope / deliverables:**
  - An **admission gate** `admit(candidate_hypothesis, run_id) -> AdmissionResult` that calls the M2 identity service to resolve the hypothesis to a canonical `account_entity` (deterministic on `primary_domain`/`registry_ids`; otherwise probabilistic fuzzy match on name+geo+aliases). Outcomes: **admitted** (resolved → `account_entity.status=candidate`, dedup-merged if it matches an existing entity), **needs-review** (mid-band confidence → routed to M2's human review queue, *not* guessed), **rejected** (no live domain / nothing to resolve to → fabricated/dead hypothesis dropped).
  - **Existence checks** appropriate to discovery: live-domain check + at least one corroborating record from the matching resolver (so admission requires real-world existence, not just a syntactically valid domain).
  - **Discovery-provenance write:** for each admitted entity, persist a **discovery-provenance claim** (the staged-flow §9 flavor of `claim`) capturing `matched_channel`/`source_url`, `matched_signal` (which ICP filter/signal it matched), `discovery_confidence`, `research_mode='M1'`, `run_id`, `cost_cents`. This is a *discovery-provenance* claim, distinct from later *field-claim provenance*.
  - **Idempotent, locked admission:** acquire the M2 in-flight `lock(account_id)` (Redis) and key admission on the resolved entity so two parallel discovery workers can't double-admit the same company; re-running admission for an already-admitted entity is a no-op (supports M7 phase replay).
  - **Symmetry with import (Scenario B):** expose the same `admit(...)`/discovery-provenance contract for imported, already-resolved accounts so M5's import pipeline (Doc B §4) records an equivalent provenance (`matched_channel='import'`) and converges identically — *one gate discipline, two entry scenarios*.
- **Interface / seam:**
  - **Consumes:** M6.1's `CandidateHypothesis` stream; the **M2 identity service** (resolve / dedup / review-queue / canonicalize + Redis in-flight lock) — the *only* component allowed to turn a name into an id (conventions §2); the **claim store** (M1) append-only write API.
  - **Exposes:** `admit(candidate, run_id) -> {status: admitted|needs_review|rejected, account_entity_id?, discovery_provenance_claim_id?}`. Admitted entities (status=`candidate`) + their discovery-provenance claims are the *only* output of the discovery axis that the Pass A bridge (M6.3) reads. This is the **convergence contract** both Scenario A and Scenario B emit.
  - **Replaceability:** the gate hides the identity service entirely — swapping M2's matcher, or moving the review queue, changes nothing here. Because admission writes only *claims* + an `account_entity` row, the gate is decoupled from scoring (M6.3) and from Pass B (M8): they read the store, never call the gate.
- **Data model / schema:** Writes **`account_entity`** (§4: sets `status=candidate`, `merged_into` on dedup). Writes a **discovery-provenance `claim`** (§4 + staged-flow §9 flavor): `entity_id`, `entity_type='account'`, `field_key='discovery.provenance'` (or a registered `core.discovery_provenance` key, M1.3), `value_json={matched_channel, matched_signal, discovery_confidence}`, `source_url`, `source_tier` (per resolver), `extraction_method∈{api|scrape|crm_import}`, `research_mode='M1'`, `run_id`, `cost_cents`, `collected_at`. **Rule honored:** discovery-provenance is grounded (tier 1–3 record); no tier-4 fabrication is ever admitted. No new tables.
- **Dependencies:** Blocked by **M2** (identity service + review queue + lock), **M1** (claim store + `account_entity` + `current_value`), **M6.1** (candidate stream). Unblocks **M6.3** (Pass A reads admitted entities), **M5** (reuses the gate/provenance contract for import convergence), **M6.5** (admitted-vs-seen counts feed coverage). Runs inside the `discovery` phase of **M7**.
- **Acceptance criteria:**
  - A candidate with a resolvable live domain + corroborating record is admitted as `account_entity.status=candidate` and gets exactly one discovery-provenance claim with the correct `matched_channel`, `matched_signal`, `discovery_confidence`, and `research_mode='M1'`.
  - A fabricated/dead candidate (no live domain, nothing to resolve to) is **rejected** and creates **no** `account_entity` and **no** claim — verified end-to-end (the anti-fabrication guarantee).
  - A mid-band-confidence candidate routes to the M2 review queue and is **not** auto-admitted.
  - Two parallel admissions of the same company (same domain) produce a single `account_entity` (dedup/merge) and a single admission outcome — no double-admit, no double-charge (idempotency + lock test).
  - Re-running admission for an already-admitted entity is a no-op (M7 replay-safe).
  - An imported, pre-resolved account admitted through the same seam records a discovery-provenance claim with `matched_channel='import'` and is indistinguishable downstream from a discovered account except by `matched_channel` (symmetry test).
- **Out of scope:** identity-resolution internals/matcher/review-queue UI (M2); any field claims/signals beyond discovery-provenance (M6.3); deep-pass facts (M8); faithfulness judging / corroboration thresholds (M9 — note discovery-provenance is grounded, so no judge is needed here); the import ingestion pipeline that *produces* pre-resolved rows (M5).
- **Open decisions:** **D6** (import non-fit behavior — recommended flag-and-proceed): the gate admits imported accounts regardless of fit and tags provenance `matched_channel='import'`; the *non-fit flag* is applied later at scoring (M6.3), not at the gate — proceed on flag-and-proceed without hardcoding exclude/re-derive. **D8** (2026 legal specifics): admission is account-level existence only (no personal data), so Doc D gates do not apply here; noted so personal-data handling is not accidentally pulled forward.

### M6.3 — Pass A scoring engine (two-tier deterministic proxies: intent/growth/hiring/technographic/firmographic)
- **Purpose:** Compute **Output 1** — a decomposed, explainable, provenance-backed fit + intent score for **every** admitted/imported account, cheaply and deterministically. This is where the founders' "signal-rich discovery" actually lives: the **cheap proxy** half of the two-tier signal model (Doc C §1) — a deterministic tier-1/2 fact per signal class (intent, growth, hiring, technographic, firmographic), computed on the *whole* list at cents/account, *not* in M1 and *not* via synthesis. It reads the ICP spec's scoring rubric (fit + intent weights) and the scoring-pass fields, populates those fields via the trust-tiered waterfall (tiers 1–3, minimal/no LLM), and emits sub-scores each traceable to the claims that produced them ("trending because eng hiring +40%"). No score without its evidence; an empty, flagged signal field is a correct output, never a fabricated proxy.
- **Architecture sources:** Doc C §1 (the two-tier signal model — cheap proxy table: intent=job-count delta/funding/headcount growth; growth=headcount trend/funding stage/geo expansion; hiring=open-req/eng-req count; technographic=BuiltWith/job-posting tech mentions; firmographic=size/revenue/geo band — all tier-1/2; "Pass A is signal-rich but deterministic-first and cheap"); substrate §5a (Pass A: populate scoring-pass fields only, tiers 1–3, minimal/no LLM, fully parallel), §9 (decompose fit vs intent; provenance-backed sub-scores; the free disposition feedback loop), §3 (field `pass` tag `scoring`; same signal class spans scoring+deep), §1 (claim store; `current_value` merge); overview §1 (Output 1, "no score without its evidence"); Doc B §4 (ICP back-scoring of imported accounts — import skips discovery, not scoring); Doc C §6 (per-source yield emitted from scoring).
- **Scope / deliverables:**
  - A **Pass A scoring orchestrator** that, for each admitted `account_entity` (status=candidate) — discovered *or* imported — reads the ICP spec's **scoring-pass field set** (fields tagged `pass=scoring`, M3) and the **scoring rubric** (fit + intent weights), and fills the scoring fields via the **trust-tiered source waterfall** behind the `Resolver` seam (tier 1 deterministic APIs → tier 2 official scrape → tier 3 reputable third party; **no tier-4 in Pass A**), stopping at the first result clearing each field's confidence threshold.
  - **Two-tier signal model — cheap proxies only** (Doc C §1): compute the deterministic proxy for each signal class — intent (job-count delta, recent funding event, headcount growth), growth (headcount trend, funding stage, office/geo expansion), hiring (open-req count, eng-req count), technographic (BuiltWith / job-posting tech mentions), firmographic (size band, revenue band, geo). Each proxy is written as a typed **`claim`** (tier 1–3). The *deep narrative* half of each class is **explicitly deferred to Pass B (M8)** — this engine never synthesizes.
  - **Decomposed, explainable scoring** (substrate §9): produce **fit_score** (firmographic/technographic/vertical sub-scores) and **intent_score** (signal/growth/hiring/funding sub-scores) as separate inspectable values, each computed by the rubric's weights over the merged **`current_value`** of the scoring fields, and each carrying the **claim ids** that produced it (the provenance link). No opaque single number.
  - **ICP back-scoring for imports** (Doc B §4): imported accounts are scored against the client's *own stated ICP* on the identical path; produce a **non-fit flag** (with the evidence behind the low fit score) for imports that fall below the ICP's fit floor — *flag-and-proceed* (D6), do not exclude.
  - **Provenance-backed score object** per account: the fit/intent decomposition + per-sub-score claim-id index, written to the store (a *score claim*/score row) so M6.4 (tiering), the eventual `account_handoff` (M12), and the human checkpoint all read the same substrate.
  - **Per-source yield emission** (Doc C §6, staged-flow §7e): record, per `(run_id, source_key, field_class)`, the count of scoring claims produced (and later, which survived verification) — the same provenance signal the learning loop (M13) consumes. Pass A *emits* it; it does not reweight.
  - **Idempotency** on `(account_id, field_key, source_tier)` (substrate §5c) and on `(account_id, rubric_version)` for the score object, so M7 phase replay never double-charges or double-scores.
- **Interface / seam:**
  - **Consumes:** the **`ICP spec`** (scoring-pass field set + **scoring rubric** weights, §4) from M3; **`field_definition`** rows (`pass=scoring`, `tier_plan`, `freshness_ttl`, confidence threshold, §4) from M1.3; the **`Resolver` protocol** (tiers 1–3) for waterfall field-fill (M4) — providers fully swappable behind it; **`current_value(entity, field)`** (§4, M1) for merged inputs; **`source_manifest`** to order waterfall sources.
  - **Exposes:** for each account, a **decomposed score** `{fit_score, fit_subscores{...}, intent_score, intent_subscores{...}, evidence: {subscore_key -> claim_ids[]}, rubric_version, non_fit_flag?}` — the exact primitives `account_handoff.fit_score/intent_score (decomposed, each linked to its claims)` (§4) expects, and what M6.4 reads to assign tiers. The **scoring rubric is data, not code** (conventions §2), so reweighting the model (or later, learning from disposition) is a config/version change behind this seam.
  - **Replaceability:** the score is a pure function of `current_value` over scoring fields × rubric weights; the scorer can be swapped (e.g. a learned fit model) without touching discovery, the gate, or tiering, because all of them communicate through claims + the score object in the store. Resolver swaps stay behind the `Resolver` seam.
- **Data model / schema:** Writes typed **`claim`** rows for each scoring proxy field (`field_key` ∈ registered `account.*`/`core.*` scoring fields, e.g. `account.hiring_velocity_eng`, `core.employee_count`, `account.recent_funding`, `core.primary_tech_stack`; `source_tier∈1..3`; `extraction_method∈{api|scrape}`; `pass=scoring`; `run_id`; `cost_cents`). Reads via **`current_value`** (§4). Writes a **score object** (a score `claim` with `field_key='score.fit'`/`'score.intent'` or a dedicated `account_score` row referencing claim ids) holding the decomposition + per-sub-score evidence index + `rubric_version` + `non_fit_flag`. Per-source-yield counters keyed `(run_id, source_key, field_class)` (shared with M6.1/M6.5; reuse run telemetry, no bespoke table). No tier-4 claims are written in this milestone.
- **Dependencies:** Blocked by **M6.2** (admitted entities to score), **M3** (scoring rubric + scoring field set), **M4** (tier-1–3 resolvers + source registry), **M1** (claim store, field registry, `current_value`). Unblocks **M6.4** (tiering reads the score object), **M6.5** (scored counts), and downstream **M12** (handoff reuses these decomposed scores). Runs inside the `scoring` (Pass A) phase of **M7**; converges Scenario B (M5) here.
- **Acceptance criteria:**
  - For each admitted/imported account, the engine produces a `fit_score` and an `intent_score`, each decomposed into named sub-scores, and **every** sub-score resolves to ≥1 backing `claim` id (no score without evidence) — verified by walking the evidence index.
  - All scoring claims are **tier 1–3** with `pass=scoring`; the engine emits **zero tier-4 / llm_synthesis claims** in Pass A (deterministic-first invariant test).
  - The five cheap proxies (intent, growth, hiring, technographic, firmographic) are computed where the underlying source is available, and a missing source yields an **empty, flagged** signal field — *not* a fabricated proxy (universal-rule test).
  - Scoring is idempotent: re-running Pass A for an account with unchanged sources/rubric writes no new claims and produces an identical score object (idempotency on `(account, field, tier)` and `(account, rubric_version)`).
  - An imported account scoring below the ICP fit floor is admitted, scored, and carries a `non_fit_flag` with the evidence claim ids (flag-and-proceed, D6) — it is **not** excluded.
  - Changing the rubric weights (config/version change only) changes the score object and bumps `rubric_version`, with no code change in M6.3.
  - Per-source yield counters are emitted per `(run_id, source_key, field_class)`.
- **Out of scope:** the deep-narrative half of any signal class and resonance/facet field-classes (Pass B / M8, Doc C §2); any tier-4 synthesis (M11); the faithfulness judge / corroboration thresholds / freshness refresh (M9 — Pass A is deterministic so it does not depend on them); tier assignment + the human checkpoint (M6.4); the disposition/source-yield *reweighting* loops that consume the emitted signal (M13); the import ingestion that produces resolved rows (M5).
- **Open decisions:** **D6** (import non-fit — flag-and-proceed) realized here as `non_fit_flag` + evidence, not exclusion. **D7** (economics: per-pass budget bands, cents/account target): Pass A is the "cents/account, deterministic-only, all accounts" band (Doc C §5) — budget caps are config; proceed config-driven. **D5** (multiple ICPs): scoring is keyed on a specific `rubric_version`/ICP, so an account can be scored under multiple ICP rubrics independently. **D1** (output boundary — claims + value narrative): the decomposed score object is the Output-1 primitive `account_handoff` consumes downstream; produced here, not bound to any content schema.

### M6.4 — Tiering + human checkpoint (interrupt-based)
- **Purpose:** Convert Pass A scores into **tier assignments** and present the client with the **designed human checkpoint** — the gate that makes the two-pass unit economics legible and builds trust *before* expensive credits are spent (substrate §5a, §10; Doc C §5). Pass B (M8) runs **only on high tiers**, and depth scales with tier, so where the cutoffs land *is the spend decision*. The checkpoint is a durable, `interrupt()`-style pause-and-resume (the secure-input pattern, substrate §10) where the client reviews provisional scores, sees a **pre-run cost estimate** ("~N discovered → at these cutoffs ~M go deep → ~$X"), and adjusts tier cutoffs (or pauses/raises the budget) before resuming into Pass B. This is "the client always has the wheel" made into a concrete, resumable surface.
- **Architecture sources:** substrate §5a (two passes; "human checkpoint: review/adjust tier cutoffs"; depth scales with tier), §10 (Tier-1 review as a *designed* `interrupt()`-based durable checkpoint, not a disclaimer), §9 (explainable provenance-backed scores the client reviews); Doc C §5 (pre-run cost estimate, client-set per-campaign hard cap, "stops gracefully at a checkpoint"), §4 (campaign-run state machine: `tier_checkpoint(human)` phase, pause/resume/adjust mid-run, phase idempotency); staged-flow §4, §10 (the scoring bridge → tiering → human checkpoint on cutoffs); overview §2 (map: the human-checkpoint bar).
- **Scope / deliverables:**
  - A **deterministic tiering function** `assign_tiers(scores, cutoffs) -> {account_id -> tier}` that maps the decomposed fit/intent scores (M6.3) to tiers (e.g. Tier 1/2/3) using **versioned cutoff config** from the ICP spec (overridable at the checkpoint). Tiering is a pure policy over scores — *not* an agent — mirroring the `current_value` discipline.
  - A **pre-run cost estimate** (Doc C §5): given the tier distribution and the per-tier Pass B fan-out/budget bands (config), compute "~M accounts go deep → estimated $X" and present it with the projected vs cap burn-down.
  - The **interrupt-based checkpoint**: at the `tier_checkpoint` phase the run **suspends durably** (LangGraph `interrupt()` / the secure-input pause-resume pattern) and surfaces a review payload: per-account provisional fit/intent (with the M6.3 evidence links so each score is inspectable), the proposed cutoffs, the resulting tier distribution, and the cost estimate.
  - **Client actions on resume:** adjust cutoffs (re-runs `assign_tiers` deterministically and re-estimates cost without re-spending Pass A), raise/lower the per-campaign budget cap, pause, or approve. On approve, the run resumes into the `deep` (Pass B) phase (M8). On a projected-spend-over-cap condition, the run **stops gracefully at this checkpoint** and asks the client to raise the cap or tighten cutoffs (Doc C §5).
  - **Persisted tier decision** per account (a tier claim/assignment row) + the approved cutoff version + the approved cost estimate snapshot, so Pass B and the audit trail read a durable decision.
  - **Phase idempotency** on `(campaign_run, 'tier_checkpoint')` (Doc C §4): re-entry after a crash re-presents the same checkpoint state and never double-applies the resume action.
- **Interface / seam:**
  - **Consumes:** the **score object** from M6.3 (decomposed fit/intent + evidence index); **cutoff config** + **per-tier budget/fan-out bands** from the ICP spec / config (M3, Doc C §5); the **campaign-run state machine** pause/resume primitive (M7) — this component *implements* the `tier_checkpoint(human)` phase behavior but the state machine itself is M7.
  - **Exposes:** a **tier assignment** per account `{account_id, tier, cutoff_version}` (the seam Pass B / M8 reads to decide who goes deep and at what depth) + a **checkpoint review payload** and **resume API** `resume(decision: {cutoffs?, budget_cap?, action: approve|pause})`. Tiering and cost-estimate logic sit behind these seams so the cutoff policy, the estimate model, or the UI can change independently. The durable-pause mechanism is **swap-safe**: the `interrupt()`/Postgres-state-machine implementation can migrate to Temporal human-task timers (conventions §2; substrate §5c) without changing the `resume(...)` contract.
  - **Replaceability:** because tiering is a pure function over the stored score object and cutoffs are config, the checkpoint can be re-skinned or the tiering policy swapped without touching scoring (M6.3) or Pass B (M8).
- **Data model / schema:** Writes a **tier assignment** per account (a tier `claim` `field_key='tier.assignment'` or an `account_tier` row: `{account_id, tier, cutoff_version, score_ref, run_id}`). Persists the **checkpoint record**: `{campaign_run, phase='tier_checkpoint', proposed_cutoffs, tier_distribution, cost_estimate, status: awaiting|resumed, decision}`. Reads the M6.3 score object and the ICP **cutoff/budget config**. Idempotency key `(campaign_run, 'tier_checkpoint')` (Doc C §4) and `(account_id, cutoff_version)` for tier rows. No new global tables beyond the tier row + the checkpoint record (the latter co-owned with M7's phase store).
- **Dependencies:** Blocked by **M6.3** (score object to tier), **M7** (campaign-run state machine + durable pause/resume; this issue implements the `tier_checkpoint` phase logic that M7 schedules). Unblocks **M8** (Pass B reads tier assignments + approved budget). Consumes config from **M3**. Surfaces to the review/observability surface (**M13**) but does not depend on it.
- **Acceptance criteria:**
  - `assign_tiers` is a deterministic pure function: identical (scores, cutoffs) always yield identical tier assignments; changing cutoffs alone (no re-score) re-tiers without writing new scoring claims or spending Pass A.
  - At the `tier_checkpoint` phase the run **suspends durably** and the review payload contains, per account, the provisional fit/intent with working evidence links (each score inspectable back to its claims), the proposed cutoffs, the tier distribution, and the cost estimate.
  - The pre-run cost estimate equals (accounts above cutoff per tier) × (per-tier Pass B budget band) and updates when the client adjusts cutoffs — *without* re-spending Pass A.
  - On `resume(approve)` the run transitions to the `deep` (Pass B) phase; on `resume(pause)` it stays suspended and resumable; on a projected-spend-over-cap condition the run halts at the checkpoint and prompts to raise the cap or tighten cutoffs.
  - Crash/restart during the checkpoint re-presents the identical checkpoint state and the resume action is applied at most once (phase idempotency on `(campaign_run, 'tier_checkpoint')`).
  - The approved cutoff version, cost-estimate snapshot, and per-account tier are persisted and readable by Pass B and the audit trail.
- **Out of scope:** the campaign-run state machine / outer scheduler / phase store itself (M7); Pass B depth/fan-out execution (M8); the per-claim Tier-1 *content* review that happens before content generation (substrate §10; later milestone M13/M12 — this is the *tier-cutoff* checkpoint, distinct); cost pass-through billing UI specifics (D7/M13); the disposition feedback loop (M13).
- **Open decisions:** **D7** (economics: per-pass budget bands, % that goes deep, cost pass-through client-facing vs internal): the checkpoint is built as a *client-facing* cost surface (recommended default) with config-driven bands; proceed without hardcoding the pass-through decision. **D5** (multiple ICPs): cutoffs and tiers are per-ICP/per-campaign-run, so each ICP campaign has its own checkpoint.

### M6.5 — Coverage-confidence estimator
- **Purpose:** The founders want "all the accounts that fit," but open-ended discovery can **never prove completeness** (staged-flow §3; Doc C §7). This component produces the honest alternative: a **coverage-confidence estimate** — "estimated ~X% of the addressable set found via these channels" — and **names the channels not yet searched**, so the client can ask for more rather than being misled into believing the search was exhaustive. Crucially, coverage is a **separate estimate from the cost-driven stopping rule** (M6.1): the stopping rule is a *cost* control (when to stop spending), coverage is a *trust* statement (how much we likely found and what we skipped). Honesty here is a product trust feature; implying "we found them all" is a claim the subsystem cannot back.
- **Architecture sources:** Doc C §7 (coverage confidence — explicitly *not* a completeness guarantee; coverage is separate from the cost-control stopping rule; report ~X% found via these channels + name unsearched channels); staged-flow §3 (stopping rule on marginal yield — the diminishing new-candidate rate this estimator reads), §7 (the Source Registry's per-source coverage/geo metadata); Doc C §6 (per-source yield, shared provenance signal); overview §1 (coverage as part of the trustworthy Output-1 story).
- **Scope / deliverables:**
  - A **coverage estimator** that, given a completed/stopped discovery run, computes an estimated coverage fraction from the **diminishing new-candidate (marginal-yield) curve** across the searched channels (e.g. a capture-recapture / saturation-style estimate over the per-channel yield counters from M6.1/M6.2) — expressed as a band ("~X–Y%"), never a false-precision point claim.
  - An **unsearched-channels report:** diff the channels the ICP/source registry *could* cover (from `source_manifest` `entity_scope=account` + `geo_coverage`) against the channels actually queried this run, and list the channels **not yet searched** (and any geos/segments under-covered), so the client can request expansion.
  - A **coverage report object** per discovery run: `{coverage_estimate_band, channels_searched[], channels_not_searched[], per_channel_new_candidate_curve, stopping_reason}` — readable by the checkpoint surface (M6.4) and the observability surface (M13).
  - Explicit framing in the output: coverage is an *estimate over the channels searched*, not a guarantee; surfaces the `stopping_reason` (marginal-yield vs budget-cap vs exhausted) so the client understands *why* the run stopped (a budget-cap stop with high marginal yield = low coverage confidence + "raise budget to find more").
- **Interface / seam:**
  - **Consumes:** per-channel yield counters + `stopping_reason` from **M6.1**; admitted-vs-seen counts from **M6.2**; the **`source_manifest`** registry (M4) for the universe of account-scope channels + their `geo_coverage` (to compute "not yet searched"); the ICP spec's discovery strategy (which channels were *planned*).
  - **Exposes:** a `coverage_report(run_id) -> CoverageReport` seam consumed by the human checkpoint (M6.4) and observability (M13). The estimation method sits entirely behind this seam, so the estimator (e.g. saturation curve → capture-recapture → a learned model) can be swapped without changing any consumer.
  - **Replaceability:** purely read-only over run telemetry + the source registry; it computes and reports, it does not gate discovery or alter scoring — so it can be added, swapped, or improved with zero impact on M6.1–M6.4.
- **Data model / schema:** No new entity tables. Reads per-channel yield counters keyed `(run_id, source_key)` (M6.1/M6.2), `stopping_reason` (M6.1), and **`source_manifest`** (§4). Writes a **coverage report** record keyed `(run_id)` (run telemetry, co-owned with M7's run store): `{coverage_estimate_band, channels_searched[], channels_not_searched[], per_channel_curve, stopping_reason}`. No claims are written (coverage is run-level metadata, not an account fact).
- **Dependencies:** Blocked by **M6.1** (yield counters + stopping reason), **M6.2** (admitted counts), **M4** (source registry for the channel universe + geo coverage). Surfaces through **M6.4** (checkpoint) and **M13** (observability). Does not block Pass B.
- **Acceptance criteria:**
  - Given a discovery run's per-channel new-candidate curve, the estimator returns a coverage **band** (not a single false-precise number) and the computation is deterministic for fixed inputs.
  - The unsearched-channels list correctly equals (account-scope channels in the source registry, filtered by ICP applicability/geo) minus (channels actually queried this run); a run that searched a strict subset of channels reports the remainder as not-yet-searched.
  - The report distinguishes a **budget-cap stop with high marginal yield** (low coverage confidence; recommend raising budget) from a **marginal-yield-exhausted stop** (higher coverage confidence) via `stopping_reason` + the curve.
  - The output never asserts completeness/exhaustiveness; copy/structure frames it as "estimated coverage via these channels" + named gaps (verified against the Doc C §7 wording rule).
  - The coverage report is queryable by `run_id` and consumed by the M6.4 checkpoint payload.
- **Out of scope:** the stopping rule itself (M6.1 — coverage *reads* its output but does not control stopping); acting on coverage (re-running discovery on more channels is a client-initiated action via M6.4/M7); per-source quality reweighting / the learning loop (M13, staged-flow §7e); any account-level claims.
- **Open decisions:** **D7** (economics / campaign size hundreds vs thousands): the coverage estimation method and its confidence calibration are config-driven and improve once real campaign-size data exists; proceed with a saturation/capture-recapture default without hardcoding population assumptions.
