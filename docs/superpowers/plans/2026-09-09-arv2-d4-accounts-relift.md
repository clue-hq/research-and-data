# ARV2 D4 — the accounts re-lift into `apps/frontend` (S8) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace `apps/frontend`'s accounts feature with the dummy frontend's (`clue-frontend` `integration/live-backend-v1` @ `84f8ee7`), reading the real backend through the D3 contract-v1 endpoints (`/frontend/v1/…?contract=v1`) behind the authenticated BFF, with the D0 rulings applied, the sixteen client-side derivations removed, the FI-2 behaviours the founder kept (bulk add-to-project / send-to-chat, single-contact email lookup, the recovery screen) ported onto the dummy's components, an explicit fixture flag for demos, and the three Zafran pages plus the four remaining contact pages rendering from the real backend.

**Architecture:** The dummy is a fork of `apps/frontend` with later UI work, so the lift is a file-for-file move of `src/features/accounts/**`, the accounts routes, the accounts layout shell, the `/api/source-favicon` route and the `packages/design-system` package, followed by three kinds of edits: (1) the model amendments (the vendored Zod from `tests/api/contract_v1/zod/` becomes `model/*.ts`), (2) the removal of every derivation the source map's §6 checklist names, (3) the transport swap — every repository reads through `fetchRead` (the authenticated server request → same-origin `/api/clue/frontend/v1/…` BFF) with `contract=v1`, and a fixture repository is selected **only** when `CLUE_ACCOUNTS_FIXTURE_MODE=true`. Tokens are merged additively: the dummy's design-system package replaces ours and a committed legacy-compat stylesheet keeps the 48 variables only today's other features use, until the separate CSS re-sync job. The backend is not changed in D4 (the FI-2 branch deletion is a follow-up PR); the four contact pages are generated live with the D2 CLI.

**Tech Stack:** Next.js App Router / TypeScript / Tailwind v4 / Zod 4 / CSS modules; `tsx --test` for unit tests; `npm run design-system:build && npm run lint && npm run build` as the feature's gate; the gstack `/browse` skill for the rendered walk; the D2 CLI for page generation.

**Spec:** `docs/specs/ARV2-MASTER-PLAN.md` §6 (contract v1), §7 (presentation decisions), §8 (rulings R1–R13), §9 Track D (D4 row); `docs/specs/ARV2-DATA-SOURCE-MAP.md` §1 (mount point / pagination), §6 (the sixteen derivations to stop); `docs/specs/ARV2-WORK-SPLIT.md` S8; `apps/frontend/docs/architecture/frontend.md` (the seam rules); `apps/frontend/docs/api-contracts/accounts.md` "Contract v1". ## Decisions this plan takes (each overturnable; ledgered)

1. **Additive token merge (ruling 2a).** `apps/frontend/packages/design-system` becomes the dummy's package (`source/production`, its `build-tokens.mjs`, its `generated/tokens.css`, README). The 48 variables only the old `tokens.css` defined are extracted **once** into a committed `packages/design-system/generated/legacy-compat.css` (header: "temporary — removed by the CSS re-sync job"), imported in `src/app/globals.css` immediately after `tokens.css`. The old `source/figma` + `source/product` inputs are deleted with the old generator (the compat file is data, not a generator layer). A test asserts every `var(--clue-…)` referenced anywhere under `src/` resolves in `tokens.css ∪ legacy-compat.css`.
2. **Full-list read for the browser-side table (ruling 2c).** The dummy's `getAccounts()` expects the whole list. E1 caps `limit` at 200, so the accounts repository follows `meta.nextCursor` with `limit=200` until exhausted, capped at 25 pages (5,000 rows; beyond that it stops and the table shows what it has — recorded). Search/filter/sort/pagination stay in the browser exactly as the dummy does them.
3. **Layout nesting.** `src/app/(protected)/accounts/layout.tsx` (new) renders the dummy's `AccountsLayoutShell` inside the existing protected layout; `ProjectApplicationShell` already returns `children` unchanged for non-project routes, so the accounts shell is the only shell on `/accounts/**`. `AccountsLayoutShell` keeps its own `ApplicationShell activeHref="/accounts"`.
4. **Profile from the session (ruling 2g).** `WorkspaceProfileProvider` stays; its `profile` is built server-side in the layout from `getProtectedSession()` — `fullName`/`displayName` from the principal's name when present else the email local-part else the user id; `initials` = first letters of up to two words; `avatarColor` = a fixed palette entry chosen by a stable hash of the user id; `avatarUrl` absent. The `SettingsWorkspace` type is replaced by a local `WorkspaceProfile` type in `features/accounts/model/workspace-profile.ts` (the dummy's `features/settings` is not ported).
5. **Fixture flag (ruling 2h).** `CLUE_ACCOUNTS_FIXTURE_MODE` (server-only; documented in `apps/frontend/.env.example` if that file exists, else in `apps/frontend/README.md` + the architecture doc): `"true"` → the dummy's fixture repositories (Zafran + the OpenAI sample) for all five reads and the layout's account list; anything else → live. The live path throws/recovers, never substitutes fixtures. The flag is read in exactly one place, `data/repository-mode.ts::accountsFixtureMode()`.
6. **Recovery (ruling 2d).** `accounts-read-result.ts` (typed classification of transport failures) and `accounts-recovery-screen.tsx` stay; the accounts **layout** performs the list read and renders the recovery screen instead of the shell when classification says so; detail/workspace/contact pages keep `notFound()` on `null` and let other errors surface to the recovery boundary (a page-level `error.tsx` is not added — out of the dummy's design).
7. **Bulk actions (ruling 2b).** The apps `accounts-screen.tsx` bulk toolbar (project select + "Add to project", "Send to chat") is ported onto the dummy's `accounts-screen.tsx`/`accounts-table.tsx` selection model (the dummy already has `selectedAccountIds` and checkboxes); the bulk email-lookup action, `lookupContactEmails`, `ContactBulkCapabilities` and the contact-side bulk UI are deleted. Capabilities keep coming from `readAccountBulkCapabilities()` on the page.
8. **Email lookup (master plan D4).** The dummy's `LookupEmailButton` stub + `use-email-lookup-controller.ts` (a `setTimeout`) are replaced by the apps controller's real start + poll (`contact-email-lookup.repository.ts` over `fetchMutation`), keeping the dummy's button visuals; on `resolved` with an address the row's `emailLabel` is set locally and `emailStatus` becomes `"available"`. Note the D3 finding: the backend serves `emailStatus: "lookup"` for every real contact until a writer keeps the verdict, so the button shows for all contacts today.
9. **Create account (ruling 2f).** `createLocalAccount` produces `{fitScore: null, overallFit: null, revenueBand: "Unknown", employeeBand: "Unknown", locationCount: 0, industryLabels: [], socials: [], projects: [], customFields: [], primaryProjectId: null, researchStatus: "not_started", researchStatusLabel: "Not started", researchIsRefreshing: false, logoPath: null, websiteUrl}` and the row is marked `isLocalDraft: true` in a **local UI type** (not the wire model); the table renders the same as any row; a small "not saved" hint is the only addition (text only, no new component). Follow-up recorded: a `POST /frontend/v1/accounts` write endpoint.
10. **Section keys.** The lifted spec-content parser (`data/zafran/spec-content.ts`) slugs the dummy's `h1` into keys; the fixtures are regenerated/edited so keys are the contract-v1 keys (`what-they-do`, `problem-right-now`, …) and `h1`s are bare (R9); components that switch on keys (`overview-section-toggle`, `research-item-presentation`) are updated to the contract keys.
11. **Contract v1 additions honoured:** `BuyingCommitteeMember.linkedinUrl` nullable (render the link only when present); E4 `title: null` renders "—" client-side; `AccountContactDetail.linkedinUrl` stays required (the backend's site-root fallback covers it; a nullable ruling is a follow-up); `emailClaimId` resolves the email chip (R5); `lastModifiedAt` on the contact header (R8).
12. **Tests travel and adapt.** The dummy's 16 feature tests move with the feature; the apps tests for kept pieces (`bulk-actions.repository.test.ts`, `bulk-capabilities.repository.test.ts`, `contact-email-lookup.repository.test.ts`, `accounts-read-result.test.ts`, `frontend-api.test.ts`, `account-live-repositories.test.ts` rewritten for the new adapters) stay; tests for deleted pieces are deleted with them.
