# ARV2 D3 — the read surface (A5, with S2 contract v1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve the five contract-v1 payloads on `/frontend/v1` — account list, account detail (with `overviewDisplay`, `buyingCommittee`, `researchEvidence`, `activity`), the new account workspace (with `insightsDisplay`, `insightSummary`, `artifacts: []`), contacts list and contact detail (with `contactDisplay`) — from Postgres rows and the D2 display module, validated field-for-field against the dummy frontend's Zod models as amended by the D0 rulings, with contract v1 written into `apps/frontend/docs/api-contracts/accounts.md` first.

**Architecture:** Contract v1 is made executable twice: as strict pydantic wire models in `frontend_read/contract_v1.py` (the backend's own gate, `extra="forbid"`) and as the amended Zod schemas vendored under `tests/api/contract_v1/zod/` (run through `npx tsx` when a Node toolchain with `zod` is reachable, skipped otherwise; these files are also the D0-a edit D4 re-lifts). The four existing route modules keep their FI-2 fields on the wire and gain the v1 fields additively (data source map §1); the workspace route is new. One shared module holds every backend-owned label rule and the ARV2 display predicate (`arv2_display_allowed`, ruling S10). One display seam module wraps D2's `ensure_page`: stored blocks are composed on every read, missing sections are generated on first request when generation is enabled and a key is configured, and stale sections are served as-is while a bounded background task regenerates them through the app's connection factory.

**Tech Stack:** FastAPI routes on the existing `/frontend/v1` router (`frontend_read/app.py`), pydantic v2 wire models, SQLAlchemy async `text()` SQL, the D2 display package (`clue_api.arv2.display`), httpx `ASGITransport` tests over `create_projections_app` with the `tests/profiling` DB harness, Node 24 + `tsx` + `zod@4` for the schema oracle.

**Spec:** `docs/specs/ARV2-MASTER-PLAN.md` §6 (contract v1), §7 (display), §8 (rulings R1–R13), §9 Track D (D3 row); `docs/specs/ARV2-DATA-SOURCE-MAP.md` §1 (endpoints), §3.1–§3.9 (element → source rules), §4 (display-block path), §5 (rulings S1–S12); `docs/specs/ARV2-WORK-SPLIT.md` A5 + §6.2 (S2 charter); the dummy's Zod at `clue-frontend` `integration/live-backend-v1` @ `84f8ee7` (`src/features/accounts/model/{account,account-detail,account-workspace,account-contact,research-display}.ts`); `platform/api/clue_api/arv2/README.md` "D2" section.

## Global Constraints

1. **The contract is the amended dummy Zod, field for field.** Base = the five model files at `84f8ee7`. Amendments (all ruled 2026-09-07): `logoPath: string | null` (S2), `websiteUrl: HttpUrl | null` (§3.1), `overallFit: High|Medium|Low|null` and `fitScore: 0–100 | null` (R7), `researchStatus ∈ not_started|in_progress|needs_review|completed|suspended` (S11) with `researchStatusLabel` served, contact `title: string | null` (S7), `summaryParagraphs`/`businessParagraphs`/`overviewParagraphs`/`industryLabels` default `[]` (S5), `emailClaimId: string | null` and `lastModifiedAt` on contact detail (R5, R8), `accountLogoPath: string | null`, `h1` served bare (R9), `tenureLabel` served (R8). 3. **Envelopes:** E2, E3, E5 return `{ "data": {...} }` (the dummy's repositories parse `*ResponseSchema.data`); E1 `{data, meta}`; E4 `{data, meta: {total}}`. The `apps/frontend` detail and contact-detail adapters (`account-details.repository.ts`, `account-contacts.repository.ts`) and their tests are updated in the same commit that adds the wrapper (T5, T7).
4. **Display gate = `arv2_display_allowed(claim, policy)`** (ruling S10), defined in the new shared module and used by every v1 field built from a contact claim: account claims pass; `use_class = sensitive` refused unless `policy.display_sensitive`; a contact claim with `outreach_safe = True` passes regardless of `identity_binding`; a contact claim with `outreach_safe = False` never reaches a v1 field outside a restricted display section (the display module already routes it); the professional/personal use-class switches (`policy.display_professional_public`, `policy.display_personal_public_non_sensitive`) still apply. `display_allowed` and every C7 surface stay untouched; the FI-2 fields keep using `display_allowed` exactly as today.

## Decisions this plan takes (each overturnable; recorded in the ledger)

1. **Two executable copies of the contract, one source.** `contract_v1.py` (pydantic, strict) is what the routes return; `tests/api/contract_v1/zod/*.ts` (the amended dummy schemas) is the oracle; a parity test asserts the pydantic JSON schema's required/optional field sets equal the Zod-derived field sets for each payload (the Zod runner prints its shape when Node is available; a committed `zod-fields.json` snapshot is the fallback so the parity test never silently skips).
2. **Committee source for v1 = the latest coverage row** (`entity_research_account_coverage.committee_member_ids`, D2's `committee_members`) — §3.3/§3.5. The FI-2 `committee[]`/rows keep the governed reader. On E4 the row set is the coverage committee; FI-2-only fields on a row (`roleOnCommittee`, `signals`, `projectIds`, `titleRestricted`) are filled from the governed member when that person is also in the governed union, else from the person's own claims (`roleOnCommittee = {value: persona, confidence: null, reasoning: rationale or null}`, `signals.typeCount` counted with `arv2_display_allowed`, `projectIds` = the account's memberships).
3. **Fit thresholds and the two scoring fields.** `overallFit`/`fitScore` come from the live `account.scoring.fit` claim attributed to the primary project through `run_lineage` (the existing `_read_scores`); `null` when absent. Bands from the two thresholds.
4. **`researchStatus` on E1 is the primary project's** status (the existing per-project machinery evaluated for `primaryProjectId`; `not_started` when there is no membership or no job). `researchIsRefreshing` = a later non-terminal job exists for the account after a terminal `completed` one. `researchStatusLabel` from one map.
5. **`lastModifiedAt`** = `GREATEST(account_entity.updated_at, MAX(claim.collected_at) live, MAX(display_block.generated_at) live)`; on E1 computed in ONE batched statement over the page's ids. Contact `lastModifiedAt` = `MAX(claim.collected_at)` over the contact's live claims, else the entity's `updated_at`.
6. **Owners** resolve `account_entity.owner_user_id` / `created_by_user_id` through `platform_user` (`{id: user_id, name: display_name or first+last or user_id}`) in one batched read; `null` when unset.
7. **`customFields`** = active `workspace_field_definition` rows with `pack = 'client'` whose key has a live claim on the account: `{id: field_key, label: description or field_key, value: render_value_text(...), presentation, primary}`; `primary = True` for the first four in registry order (S6). One batched claims read per page.
8. **`activity[]`** reads `account_activity_event` (§3.8), newest first, limit 100, `actor` = `{type:"clue"}` or `{type:"person", id, name}` via `platform_user`, `timeLabel` = a relative label computed at request time ("just now", "N minutes ago", "N hours ago", "yesterday", "N days ago", else the ISO date), `occurredAt` ISO. E6 (`/activity`, the FI-2 ledger projection) is untouched.
9. **`ResearchEvidence`** = D2's `EvidenceRef.to_wire()` with two read-layer overrides from §3.9: `sourceUrl` passes `safe_public_url` (else `null`); `provider` is mapped through one label map (`ai_ark→"AI Ark"`, `exa_contents→"Exa"`, `exa_search→"Exa"`, `ashby_posting_api→"Ashby"`, `gemini→"Gemini transcript"`, `client_interview→"Interview"`, unknown → raw). Evidence rows are the union of ids cited by the page's display block plus `emailClaimId`/`locationClaimId` where those exist.
10. **Display generation is per request and synchronous on a miss** (master plan §7: the first open waits ~15 s); the route wraps the display call so a provider failure (`ProviderHalted`, transport errors, `Arv2Error`) degrades to `empty: true` sections and a logged warning — a page is never a 500 because a model call failed.
11. **Background regeneration** lives in `frontend_read/display_pages.py` as an in-process registry of `asyncio.Task`s keyed by `(workspace_id, subject_kind, subject_id, page)`; a stale read schedules `ensure_page(regenerate_stale=True)` on a fresh `conn_factory()` transaction; the registry drops finished tasks. This is the D2 README's "background driver is D3's".
12. **Persona display:** `persona` on the wire is the raw vocabulary value (`economic_buyer`); `personaTone` from `{economic_buyer: olive, champion: orange, technical_evaluator: blue, user: cyan, blocker: red}`; `influence` from `contact.role_on_committee.value_json.influence` when present else `{economic_buyer: High, champion: High, technical_evaluator: Medium, user: Medium, blocker: Medium}` (S8); committee ordering by persona rank `economic_buyer, champion, technical_evaluator, user, blocker`, then name.
13. **`emailStatus`/`emailLabel`:** from the `core.work_email` claim: `value_json.status ∈ {verified_smtp, catch_all_valid}` → `available` + `emailLabel = value_json.address`; else `lookup`, no label. `emailVerifiedAt` = `date(observed_at)` when `status == verified_smtp`. `emailClaimId` = that claim's id or `null`. The dummy's `emailLabel` is `z.string().email()`; a malformed address is served as `lookup` with no label rather than a validation failure.
14. **Contact rail fields:** `linkedinLabel` = last path segment of `linkedin_url` (`/in/nicholastfisher` → `nicholastfisher`); `locationLabel`/`locationClaimId` from `contact.current_location`; `educationLabel` from `contact.facet.alma_mater` (`"{institution}, {degree}"` for an object, the string otherwise; when the field holds several live claims, the most recent); `tenureLabel`/`employmentStartedAt` from `contact.facet.career_history` `value_json` when it is a list of objects with `date.start` and `date.end IS NULL` (the current position) → `"{y} years {m} months"` from that ISO date at request time; `linkedinFollowers` from `contact.network_statistics.value_json.followers` (int); `linkedinCreator` = `"creator"` in `contact.member_badges` value (list or string, case-insensitive); `bestFirstChannelLabel` from `contact.facet.best_channel`; `reports[]` = committee members whose `contact.reports_to.value_json.contact_id` equals this contact; `recentSignalsLabel` = `"{k} signals"` (k = live contact claims with `signal_priority ≤ 2` and `outreach_safe`) or `"No signals yet"`; `xUrl`/`xLabel` absent.
15. **Account rail labels:** `websiteLabel` = bare host; `headcountLabel` = `"{count} ({range})"` / whichever exists / `"Unknown"`; `revenueLabel` = `core.annual_revenue` rendered via `render_value_text`, else `revenueBand`, else `"Unknown"`; `foundedLabel` = `str(core.founded_year)`; `fundingLabel` = `"{round} · {total}"` from `account.recent_funding.value_json.round` and `account.total_funding` rendered, whichever exist; `locationsLabel` = `core.hq_location` rendered, `locationCount` = 1/0; `employeeBand` = `core.employee_range` else `band_for_headcount(core.employee_count)` (`1-10, 11-50, 51-200, 201-500, 501-1000, 1001-5000, 5001-10000, 10001+`) else `"Unknown"`; `industryLabels` = `core.industry` then `core.industries_all` entries, deduped; `socials` from `core.company_linkedin_url` / `core.company_twitter_url` passing `safe_public_url`; `previewTitle = name`; `fitScoreLabel` absent; `headerMetadata: []`; `logoPath: null`; `contacts[]` (rail) = the coverage committee projected to `{id, name, title?, persona?, emailVerified?, hasDetail: true}`.
16. **When a v1 string field would be empty** where the Zod requires `min(1)` (`name`, `revenueBand`, `employeeBand`, `headcountLabel`, `locationsLabel`, `revenueLabel`), the served value is the documented placeholder `"Unknown"` for bands/labels; `name` falls back to `primary_domain` then the id — never an empty string.

### Ruling amendment (controller, 2026-09-08, before Task 3) — contract v1 is selected per request, not merged into the FI-2 payloads

The FI-2 field renames that Global Constraints 2, 3 and 11 describe (`researchStatus`→`projectResearchStatus`, `projects`→`projectMemberships`, `{data}` wrappers on E2/E5 with same-commit adapter edits, retiring five FI-2 tests) would touch 33 usages across 7 files of today's `apps/frontend` and put two shapes in every row, for one intermediate step. **Superseding rule:** every route on `/frontend/v1` serves contract v1 when the request carries the query parameter **`contract=v1`**, and the FI-2 payload exactly as today otherwise. Consequences, binding for T3–T8:

- **No FI-2 field is renamed, wrapped, or removed**; no `apps/frontend` adapter, model, or test changes in D3. Global Constraints 2 and 3 apply only to the `contract=v1` branch (which returns the `contract_v1` models directly: `AccountsResponseV1`, `AccountDetailResponseV1`, `AccountWorkspaceResponseV1`, `AccountContactsResponseV1`, `AccountContactDetailResponseV1`). E3 is new and serves v1 in both modes (`contract` absent or `v1`).
- **Global Constraint 11 collapses:** the existing FI-2 route tests stay green **unchanged**; each route suite gains a `?contract=v1` half. The "known list" of tests to update is void.
- Implementation shape: a shared dependency `ContractDep = Annotated[Literal["fi2","v1"], Depends(contract_mode)]` in `frontend_read/app.py` (`contract_mode(contract: Annotated[str | None, Query()] = None)` → `"v1"` when `contract == "v1"`, `"fi2"` when absent, HTTP 422 `VALIDATION_ERROR` otherwise); each v1 branch lives in its own `read_*_v1(conn, …)` function next to the FI-2 reader, sharing the account/contact resolution helpers (`surviving_id`, the client-entity exclusion, `AccountNotFound`); the route handler dispatches on the mode. The E7 evidence-stream routes authorise against the union of what either mode exposes for that id.
- D4 re-points the adapters at `?contract=v1`; the FI-2 branch and the parameter are deleted together after D4. Record this in `accounts.md` (T3 adds one paragraph under "Envelopes") and in the D3 memory note.
