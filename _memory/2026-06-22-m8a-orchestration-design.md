## The gap, precisely (why no existing issue owns it)
- M8 spec (`docs/specs/M08-deep-profiling.md`) issues are: **M8.1** account profiling (ENG-132), **M8.2** resonance fields+collectors (ENG-136), **M8.3** committee discovery (ENG-142), **M8.4** contact profiling (ENG-149), **M8.5** `contact.facet.*` field-class (ENG-154). **M8.5 is the facet field-class, NOT orchestration** — and is substantially seeded already (`profiling/fields.py`).
- M8 spec **explicitly punts** the connective tissue: lines 17/19 — "Per-account orchestrator-worker graph, **campaign-run state machine**, idempotency keys, budget caps — all **M7**"; "Value narrative / the **`account_handoff` assembly** — **M12**." So per-account sequencing of M2→M3→M4 sits in a **seam between M7, M8, M12 that no issue owns**.
- The M8 kickoff (`_memory/2026-06-22-m8-kickoff-handoff.md`) assumed "DEEP phase = M8.1 trunk + api root" and that integration = "register aspect workers + load packs + inject gates." It **never foresaw** that committee/contact don't slot into the graph's field-clustering. That assumption is the bug.

## Why committee/contact can't ride the M7 graph as-is (verified in `durable/graph.py`)
- `AccountResearchGraph` is **M2-only**: `plan → fan_out(parallel aspect workers) → collect → handoff`. The planner (`build_plan`/`compute_gap_fields`) clusters **account gap-fields** into aspects; it never emits `committee` (people-enumeration, no field) or `contact.facet.*` (different entity, and a **data dependency**: contacts come *from* the committee result).
- The graph has **one parallel fan-out super-step** — it structurally cannot express "committee must finish before contact fan-out." So a single graph can't sequence M2→M3→M4 without redesign.
- `AspectContext.params` is built at **`graph.py:466`** carrying ONLY `{"recursion": {...}}`. Committee `worker.py:363-365` / contact `worker.py:181-184` read campaign coords by **direct subscript** of `ctx.params` → KeyError if dispatched in-graph today (the account worker is fail-soft via `RunContext.from_params`). This is issue **#2**.

## Verified interfaces (the orchestration's building blocks)
- **Phase layer** (`core/execution.py`, FROZEN): `PhaseContext{campaign_run_id, phase, client_id, icp_key, icp_version, budget_cap_cents, params}` → `PhaseResult{status∈COMPLETED/PAUSED/FAILED, accounts_processed, cost_cents, payload}`. `PhaseHandler{phase: CampaignPhase; async run(ctx)->PhaseResult}`. **The DEEP handler already receives client_id/icp_key/icp_version** — exactly the coords committee/contact need.
- **`PhaseHandlerRegistry`** (`durable/phases.py`): handlers register at the **api composition root**; `durable` never imports a handler. Exemplars already live INSIDE milestone packages: `discovery_scoring/phases.py` (Discovery/Scoring/TierCheckpoint), `stage0/*` (ReverseProfiling/IcpConfirmed). The state machine owns checkpoint/pause AROUND the handler.
- **`CampaignPhase.DEEP`** exists; sequence `… tier_checkpoint → DEEP → VERIFICATION → HANDOFF`. So **verification (M9 promotion) is its own phase AFTER deep** — M8A produces `unverified` claims + invokes the pre-spend gate; it does NOT promote.
- **Per-account cursor** `account_run` (`durable/account_run.py`): mutable, resume-safe (`ensure_account_run` no-ops on re-entry, id = LangGraph thread_id = `claim.run_id`), `references_index` JSONB (aspect→claim ids). One account_run can cover M2+M3+M4 (all stamp the same run_id).
- **Outer checkpoint** `campaign_phase_checkpoint` upsert on `(campaign_run, phase)`. **Idempotency** (`IdempotencyScope`): `ACCOUNT_STEP=(account_run, entity, field, tier)` + `CAMPAIGN_PHASE=(campaign_run, phase)`. (M7.4 ledger; graph mentions per-step dedup.)
- **Budget** `core.BudgetEngine` (FROZEN): `estimate / check(scope∈ACCOUNT|PASS|RUN, projected_cents, campaign_run_id, entity_id, account_run_id)->BudgetDecision{ALLOW|DENY|GRACEFUL_STOP} / record / set_campaign_cap / burn_down`. The cost dial = fan-out-per-account × accounts-per-pass.
- **Recursion knob** `config.RecursionPolicy` + `durable.SpawnGuard`: per-tier `max_aspect_workers`, `max_facet_workers_per_aspect`, `max_depth`. Hard cap in-graph.
- **The three deep callables (all in `profiling/`, siblings):**
  - `profile_account(account_entity_id, icp_version, tier, run_id) -> AccountProfileResult` (account.py:241) + the in-graph `AspectWorker`s (account / account.resonance).
  - `discover_committee(conn, *, account_entity_id, run_id, tenant_id, sources, gateway, spec, role_model, relevant_personas, source_plan, budget_cap_cents, config) -> CommitteeResult` (committee/worker.py:194). `CommitteeResult.members: tuple[CommitteeMemberRef{contact_entity_id, persona, role_on_committee, role_confidence, role_plausible, *_claim_id}]`.
  - `profile_contact(conn, *, contact_entity_id, account_entity_id, run_id, tenant_id, tier, spec, facet_subworker_budget, field_keys, binding_classifier, use_class_tagger, config) -> ContactProfileResult`. **No `pre_spend_gate` param yet — that's issue #1.**
- **The data model already anticipates the chain:** `CommitteeMemberRef.as_committee_member()` → `CommitteeMember(profile_claims=())` with the comment *"M8.3 produces the resolved member; M8.4 fills profile_claims; M12 joins the two (overview §3)."* So orchestration = `discover_committee` → for each `member.contact_entity_id` → `profile_contact(contact_entity_id=…, account_entity_id=…)`. One-to-one.

## Independence-contract facts (decide where the orchestrator lives)
- `make contracts` (import-linter, 11 contracts): `core` imports nothing internal; **milestone packages (`profiling`, `durable`, `verification`, …) may NOT import each other**; `api` is the composition root (exempt) and is currently a near-empty placeholder (`api/__init__.py` only; **no `composition.py` on this branch** — the transcript's wiring lived on `m8/integrate-track-b`, not merged here).
- An orchestrator that drives the **M7 `AccountResearchGraph` (durable)** AND the **M8 callables (profiling)** AND the **M9 gate/binding (verification)** therefore cannot live in any milestone package. It must live at the composition layer: either **(a) in `api/`** or **(b) a new dedicated `orchestration` package** explicitly permitted (new import-linter contract) to import the milestone packages, with nothing importing it but `api`. → **OPEN DECISION** (lean: dedicated package, keep `api` thin; gives M8A real tests).
- `profiling/context.py` already ships `RunContext.from_params` (consumer) + `params_for_run` (producer) for #2 — worker registration lives in `api/composition.py` (`build_profiling_workers` / `register_profiling_workers`), not a separate `profiling/wiring.py`. So #2 = thread `params_for_run(...)` output into the graph's `_GraphState`→`AspectContext.params` construction site (`graph.py:466`), additive, default-None = today's behavior.

## Preliminary design lean (to be confirmed/revised by the workflow synthesis)
Hybrid (campaign-state-machine phase + per-account orchestrator object), driving committee/contact via **direct callables** (how they're tested today), account profiling via the **M7 graph** (its native home):
1. New `DeepPhaseHandler` for `CampaignPhase.DEEP`, registered at api root, living in the composition layer. Iterates high-tier accounts (from tiering checkpoint).
2. Per account, one `account_run`; sub-phases: **(M2)** `AccountResearchGraph.run` → **(M3)** `discover_committee` → **(M4)** bounded fan-out of `profile_contact` over admitted members.
3. Fan-out bounded+budgeted via `BudgetEngine.check(scope=ACCOUNT)` before each contact + a committee-size cap (config); checkpointed/resumable via account_run sub-status + M7.4 idempotency ledger keyed `(account_run,"committee")` / `(account_run,"contact:<id>")` — **claim-store gap-recompute is the correctness backstop** (every stage is gap-driven + idempotent).
4. Handoff: M8A does NOT build `account_handoff` (M12's job); it ensures the claims exist + keyed, emits a per-account deep-complete checkpoint payload (references + committee member ids + coverage + cost). M12 reads claims.
5. #2 graph param-threading folded in (needed for spec-driven account planning + tenant_id; NOT needed for committee/contact since they use callables).
6. Composes with #1: orchestrator passes the concrete `PreSpendGate` + `binding_classifier` (M9.4 `classify_binding`) into the workers/graph; depends on #1 having added the gate hook to the workers.
