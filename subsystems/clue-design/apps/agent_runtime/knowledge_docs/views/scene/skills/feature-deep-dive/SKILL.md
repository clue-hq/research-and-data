# Feature deep dive

Make one capability intelligible: what the person can do, what the feature does,
and why that matters in the task. A feature name alone is rarely an explanation.
Use authentic-product when recognition of the product is sufficient; use
educational-guide when the viewer needs instruction independent of purchasing.
Avoid squeezing an entire feature catalogue into this family.

## Select the demonstrable claim

Read the feature's current source and inspect the authentic interface or product
detail. Identify the action, observable effect, relevant prerequisites and scope.
For permissions, for example, distinguish controlling access to one document from
an organization-wide security guarantee. A screenshot proves visible appearance;
documentation establishes behavior that a still image cannot show. Bind the claim
to the appropriate evidence, not whichever asset looks most persuasive.

Write a headline naming the useful action or effect in the audience's language.
Use support for the mechanism or necessary qualification. If a term is unfamiliar,
explain it before adding additional benefits. Preserve exact user-provided copy;
otherwise avoid copying interface labels into a feature-list headline. Match any
CTA to an actual demo, documentation or available feature destination. An artwork
button is optional when the placement already supplies the action.

Inspect the company's feature ads and associated campaign assets. Determine how
much UI they expose, whether they enlarge one control, how they use callouts and
how brand identity remains legible. Record the chosen relationship between type
and product, the observed treatment and deliberate departures. References supply
art direction; they cannot substantiate a capability in the current product.

## Three ways to explain one feature

- **Detail with context:** retain a small recognizable source view and a larger
  exact crop of the relevant control or output. One native connector establishes
  where the detail belongs. Use when the full screen is dense but location matters.
- **Action and effect:** a short native action label leads to the authentic
  resulting state, or to a plainly illustrative diagram when the behavior is
  nonvisual. Use when the useful change matters more than the control's location.
- **Product anatomy:** a product photograph or interface detail carries one or
  two precise native annotations, with sufficient room for the benefit statement.
  Use when the feature has a visible physical or structural property.

Choose from the source and request; multiple crops and labels are not mandatory.
An enlarged decorative button with no explanation is still an unexplained feature.

## Layers, gaps and review

Read `knowledge/scene/components.md` for native text, callouts, frames, logo and
CTA construction. Keep exact UI or product pixels as independent authentic image
layers; crop only with supported operations. Read `knowledge/scene/references.md`
when imagery is involved. Generate a separate contextual background or material
treatment when requested or justified, preserving the product independently.
Generated UI is not evidence of a real control or output.

If documentation exists but imagery does not, a native conceptual diagram may
explain the capability without impersonating a screenshot. If behavior itself is
unsupported, record the gap and use a supported capability or another family.

Apply `knowledge/scene/placement.md` for square/portrait adaptation. Keep the
demonstrating detail readable; reposition context, crop and labels instead of
scaling a desktop screen down uniformly. In the final composite check that the
feature remains understandable with the headline covered, and that copy adds its
purpose without overstating what the picture proves.
