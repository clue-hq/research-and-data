# Brand and tokens

Read the real brand card. Its compact color roles are a shortlist. If their
values do not support the inspected ads' treatment, read the run workspace's
`brand_colors.json`: the pinned kit's complete color definitions, aliases and
mode variants. Compare supplied values to the observed artwork and choose the
existing token that supports the intended use. A body-text role need not become
display ink; a page role need not describe every campaign background. Palette
tokens are available choices too. Preflight supplies actual active-mode results.

Record a material source/kit difference in the direction: the visible property,
selected token/value and whether it preserves the treatment or is a deliberate
variation. Token validity does not make a gray field white or a flat fill blurred.
If no supplied choice supports the required treatment, record the kit gap or use
an appropriate independently layered image; do not quietly call a compromise a
match. Preserve explicit logo/background restrictions and surface any conflict.

Use the kit's spacing and typography definitions. A token example is not evidence
that the token exists. New branded text binds `style($type.<role>)`; do not invent
weights, font files or token names. Record missing roles honestly.

`knowledge/design-systems/token-taxonomy.md`, `brand-kits.md`, `modes.md` and
`brand-validation.md` own token mechanics and diagnostics. The actual card owns
identity definitions. `knowledge/scene/components.md` owns authentic independent logo/image
placement; `knowledge/scene/review.md` owns visible brand fit. Token-valid colors
still need enough contrast in the actual composition.
