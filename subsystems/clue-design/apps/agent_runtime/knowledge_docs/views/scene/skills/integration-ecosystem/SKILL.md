# Integration and ecosystem

Use this family to explain what works together and why that matters for a real
task. It introduces a relationship-evidence decision, not a mandatory logo cloud.
If a single screenshot already explains the feature, authentic-product may be
sufficient. A customer's use of two tools does not establish an integration,
partnership or endorsement between their vendors.

## Name the relationship before drawing it

Read the relevant official listing, integration documentation or approved product
source. For every visible connection, identify the supported operation and its
direction: import, export, embed, notification, synchronization or another
documented behavior. Record relevant availability, plan, permission or setup
conditions. Different kinds of connection must not all become arrows suggesting
continuous two-way data flow. A generic connector supports a possibility, not
every named application by inference.

Write copy around one audience task that the relationship enables. Use precise
verbs from the evidence; “works with” may need clarification. Brand voice can
emphasize practical utility, technical clarity or creative possibility. Do not
borrow a partner's category claim as the advertiser's capability. Preserve the
brand's observed ad language without importing unsupported speed, “all your
tools,” instant setup or frictionless-operation promises.

## Select a useful relationship view

- **A focused pairing:** Two authentic identities accompany one supported joint
  task or a relevant product detail. Useful when a named connection is the news;
  the product's outcome can dominate rather than making both logos enormous.
- **A task path:** Native labels and connectors show the documented handoff,
  with authentic UI fragments only where they clarify it. Useful when direction
  or transformation is more valuable than the list of available apps.
- **An ecosystem field:** A selective set of verified integrations surrounds or
  accompanies a clear organizing idea. Useful for breadth; group by supported
  function, and use non-directional grouping when no data flow is claimed.

Treat these as alternatives, not default geometry. Follow the relevant original
ads' identity hierarchy, density, visual treatment and CTA presence when the
request asks for continuity. A partner mark's color is its identity, not license
to change the whole advertiser palette. Vary topology only when its meaning
remains correct; swapping node positions must not invent an operational sequence.

## Build an honest, editable explanation

Read `knowledge/scene/components.md` and `knowledge/scene/references.md`.
Keep app names, relationship labels, headline and CTA text native; build
connectors, grouping and any button geometry natively. Place genuine logos and
UI as independent authentic images. Never regenerate partner marks or create
a pseudo-interface that appears to prove the integration. Native graphs require
evidence for their nodes, edges and labels; decorative paths must not masquerade
as measured throughput, architecture or certified compatibility.

Use `knowledge/scene/placement.md` for square and portrait adaptation. Reduce
the selected integration set or recompose the task, rather than shrinking every
logo into an illegible network. Check that the headline identifies the benefit,
the advertiser remains recognizable and each edge reads as the intended claim.
CTA wording and artwork treatment follow the relevant original ads and actual
requested action, such as viewing documentation or exploring an integration.

Without relationship evidence, omit the claimed connection and name the gap;
logo availability alone is insufficient. Counterexamples: a bidirectional arrow
for one-way import, an “official partner” badge inferred from an app listing,
or a limitless hub inferred from three connectors. Probe “Show how we work with
our customers' apps” using mixed connection types and a logo-only source set.
