# Build the page's argument

Establish the arriving audience and traffic context, the offered value, one
primary decision, the evidence and the real next destination. Select only the
sections that answer that reader's questions. Preserve explicit user choices;
do not invent an offer, default to a pilot/demo or claim measured conversion gains.

1. Separate seller capabilities, supplied assertions, verified target facts and
   proposed-use hypotheses. Read `web-account-personalization` for 1:1, 1:few,
   1:many or contact relevance; identity is not research. Missing target research
   permits a supported invitation, not assumed pains or a name-only substitute
   for requested relevance.
2. For a new or substantially reshaped page, read
   [argument and shell judgment](references/argument-and-shell.md). Choose native
   navigation or available campaign chrome from traffic, trust and the brief.
   A named target alone does not mandate either. Follow the selected tool's
   actual contract; shell refusal does not authorize release or approval.
3. Read `conversion-copywriting` for wording and action/destination alignment.
   Put the argument, source choices, preservation scope and unresolved needs in
   the run's existing plan; do not create a new schema or fabricate source IDs.
4. Let `create-website` own a new build and `edit-website` a scoped change. Reuse
   suitable released source components before composing missing bands. Preserve
   human changes outside the request. Adding account markers is not a reason
   for replacing an entire healthy page.
5. Apply `review-website` to the current result. A clear argument, saved artifact
   or schema pass alone does not prove fidelity, account grounding or conversion.

For an exact-copy/logo-only edit, preserve that scope and skip a new strategy
exercise. Event details, audience membership, proof and destinations must come
from the brief or available sources, never from examples in these skills.
