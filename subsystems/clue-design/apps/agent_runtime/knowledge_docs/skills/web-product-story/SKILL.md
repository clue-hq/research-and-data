# Make the product visual carry the story

`web-media-composition` owns authentic assets, resolution, crop and custody.
This skill connects those assets to the reader's task while protecting their
composition. Use `web-decision-material` for the reader's actual decision.

## Pair meaning with a visible state

For each demonstration write one short internal row: reader task → supported
product action → actual visible state → adjacent explanation. Inspect the state
before writing the explanation. A screenshot of an inbox is not proof of every
integration, automation or result; do not paint invented customer data into it.
Write useful adjacent copy about what to look at and why it matters.

If the source component's card/FAQ copy is unbound, follow
`repair-cloned-sections` for a bounded text inventory and exact copy variant.
Keep its visual system while replacing generic explanation with a sourced
account use case. Do not rebuild the component or retain unrelated homepage
copy solely because its slot detector omitted that text. Judge new wrapping
and the actual image/copy pairing at phone and desktop widths.

## Preserve the stage

Inspect the source/current good section before changing it. Record the real
background asset or CSS field, product asset, crop/object-position, clipping/radius,
shadow/frame, overlap and text location. Reuse a complete authentic composite when
it already contains the treatment; do not duplicate a baked background or frame.

For separate layers use: branded background behind → authentic product UI above →
optional source-supported framing/accents. Keep copy legible outside the UI or in
the source's reserved negative space. Never cover the interface with a background.
If the brief requires an image background, that is a required layer: reuse a suitable
custodied image, or use an authorized decorative derivative when genuinely missing.
A flat color is not an equivalent replacement. Preserve source CSS backgrounds
where that is the requested treatment. Missing assets are a specific gap, not a
reason to flatten a good band or start repeated image generations.

## Keep hierarchy and behavior together

- Measure the source heading/body family, weight, size, line-height and text width.
  Use [layout evidence](../web-source-readiness/references/layout-evidence.md)
  for current rendered nodes, including measured glyph-font usage. Match actual
  source and authored faces before changing an alias; resolve the source asset
  separately. A loaded font with the wrong face/weight is still a mismatch.
  Carry the resolved font roles into new siblings. Judge the page hierarchy together:
  do not accidentally make its opening smaller than ordinary later section headings.
- Preserve the strong visual wrapper when replacing a missing controller. Use
  `web-motion-fidelity` to select supported tabs/state switching. Map every control
  to its actual image and explanation; a controller repair does not authorize a new
  layout, lost background or smaller product visual.
- On phone, confirm the interface itself remains visible and readable. A surviving
  background with no UI is failure. Prefer an evidenced responsive crop or separate
  source rendition; never silently swap in unrelated product imagery.

Use `edit-website` for the smallest native change. Before/after compare the same
section at desktop and phone widths, including all required states. Count an
improvement only when the diagnosed defect is repaired and the preserved layers,
typography and working behavior remain intact. No repeated speculative polishing.
