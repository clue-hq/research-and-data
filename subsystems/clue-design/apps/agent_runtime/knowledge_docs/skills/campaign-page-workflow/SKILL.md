# Campaign page workflow

Use this sequence for a substantial build. For a local edit, start with
`edit-website` and perform only the affected work. The runtime also supplies the
[shared source and format contract](../create-website/references/source-format-contract.md)
to every website role; it does not depend on project instructions.

A step already established by current evidence needs no repeated tool call.
An agent proposal, unread source or earlier screenshot is not that evidence.
Reuse the existing `workspace/plan.md`, amend changed decisions before acting,
and keep user requirements distinct from working choices and source facts.

## 1. Establish the actual request

Read `campaign-landing-page` and `plan-design`. Quote the actual user message,
not the delegation brief. Choose reader, purpose and action from the request and
available evidence. Treat an inherited assistant's claimed approval as reported
context until its user source is available. A short account-page request does
not mandate paired navigation logos, a demo, a pilot or a section count.

## 2. Retrieve the material needed for this page

Read `web-source-readiness`: kit, candidate source bands, pixels, HTML/CSS,
slots, overrides, lineage and behavior evidence. Continue reported pagination
for relevant unseen material; stop searching when results repeat known IDs.
Read `web-account-personalization` for scoped account evidence and, for a named
person, `web-contact-personalization`. Complete the bounded research overview
and required section chunks, then read only supporting claim families. Read
relevant seller product/proof/voice documents from the supplied seller index.
A source capture, research overview and genuine logo answer different questions.
Record missing capture/research as an acquisition handoff to its real owner;
do not seed a replacement pack or start another research pipeline in design.

## 3. Write the argument and finished copy

Use `conversion-copywriting` and, for researched pages, `web-decision-material`.
Write the supported account context → seller mechanism → proposed application
→ useful evidence/evaluation → next action. Make it visitor-facing explanation,
not an audit disclaimer or a generic feature list. Choose one primary action's
purpose, label and supported destination; source CTA styling does not dictate
the offer. Carry finished headings, descriptions, panels and all retained actions
into the section records before assembly. Keep claim scope and limits internally.

## 4. Choose source structure and record its format

Read `create-website` before the first assembly/composition. Match the argument
to existing source sections. In `plan-design`, name each source, exact requested
change, preserved structure and measured text roles at desktop/tablet/phone.
Keep source hierarchy, typography, geometry and media framing together. Generic
font-family names are not a measured format. Target identity belongs in opening
content outside navigation; follow the campaign skill's explicit-user exception.
For product imagery, read `web-media-composition` and `web-product-story` before
placement. Captured state controls or `controller_not_retained` require
`web-motion-fidelity`, even if the user never said “animation.”

## 5. Assemble and adapt using the smallest sufficient tool

On an empty page, `assemble_cloned_sections` pins the selected released bands
with their slot values. On an existing page, use `edit-website`; preserve healthy
pins, human edits and section IDs. Read `repair-cloned-sections` before a variant.

| Observed need | Construction choice |
|---|---|
| Existing editable copy/link/image/visibility slot | Rebind inspected keys and preserve all other values. |
| Suitable source, unbound plain copy or CTA | Inspect the text/anchor targets and use exact-text or exact-anchor repair with a campaign-variant note. No HTML/CSS transcription. |
| Actual structural change required | Derive from the complete original HTML/CSS; name the changed structure and preserve everything else. |
| Diagnosed capture/render defect | Repair that defect; preserve unrelated content and controls. |
| No suitable source structure after targeted inspection | Compose the missing section using an inspected structural ancestor and its measured roles. |

No slot is not the same as no suitable component. Account relevance alone is not
a reason to rebuild. Raw variants may expose slots; exact-text variants create
no new slots. Inspect the returned manifest before claiming later rebindability.
Raw mint/release and typed vocabulary drafts have different lifecycle contracts;
report actual returned status. Shell refusal does not authorize kit approval.
On a multipage request, create the named pages and complete one page at a time.

## 6. Review the current page before finalizing

Read `review-website` before judging. The director/solo renders 1440/768/375,
inspects readable strips through `coverage.next_target`, and checks all required
interaction states and the final `view("review")`. Authors hand back for rendering;
reviewers use current supplied evidence. Compare each changed component with its
source format, actual assets and neighbors. Verify the visible argument and every
CTA promise/destination. A clean clone walk cannot qualify composed sections.
An old render or one final tile cannot qualify a newer full page.

Batch diagnosed fixes into one scoped amendment; reuse unchanged evidence and
healthy sections. If a pass has no new diagnosis, stop with the specific gap.
Do not regenerate a page or image just to see whether another attempt improves it.

## 7. Finalize against observed evidence

Call `finalize_web_run` with the actual result: built and verified sections,
source/variant/composed lineage, library effects, assumptions and remaining gaps.
Unverified typography, structure, missing content, inert controls or inadequate
mobile coverage remain open; a saved draft can be `completed_with_warnings`.
A plan amendment, successful mint or delivery test is not visual acceptance.
