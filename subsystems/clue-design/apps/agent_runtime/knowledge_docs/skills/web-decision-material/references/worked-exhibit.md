# Worked decision exhibit — fictional teaching example

These names and facts are invented solely to demonstrate a technique. Never copy
them into a customer's page or treat them as research.

**Inputs:** Aster wants consistent release signoff across acquired units. Keel's
documented features are versioned release checklists, named approvals and a status
dashboard. The actual checklist/approval screenshot is available. ERP support,
automation and performance improvements are unknown.

**Weak output:** “Keel for Aster. Standardize release workflows with powerful AI.
Explore checklists, approvals and dashboards. Book a demo.” This repeats features
and invents AI; it gives the reader little to examine.

**Internal reasoning:** Aster's priority changes what we demonstrate: compare the
release checklist and approval responsibility for a proposed release at two units.
The product supports showing versions and named approvals, not a claim that it
automatically standardizes every acquired process. The task is a proposed scenario,
not a description of Aster's current deployment.

**Visitor material:**

“Make release signoff explicit across units.”

“For Aster's signoff initiative, Keel brings the checklist version, named approvals
and release status into view. In a proposed release review, each unit can use its
applicable checklist while the reviewer sees the named approvals and current
status together. The signoff discussion starts from those visible records.”

| In a proposed release review | Product application |
| --- | --- |
| Prepare a unit's release | The versioned checklist identifies the steps being reviewed, making the chosen version explicit. |
| Follow the approvals | Named approvals show who is attached to a signoff. The authentic approval view makes this the focus of the demonstration. |
| Bring the review together | The status dashboard provides a view of release state alongside the checklist/approval discussion. Do not claim automatic enforcement or cross-unit reporting unless documented. |

For a reader actively evaluating the product, a later worksheet can ask which
checklist and responsibility rules their units need. Do not make a questionnaire
the whole page or ask the reader to supply the explanation the page owes them.

Place the authentic approval view next to the second item, with a short caption
describing the real visible feature. Preserve its branded background/frame and UI.
Do not add Aster names, successful metrics or invented integration badges inside
the screenshot. If only one product state is available, show that one honestly.

An in-page “Explore the signoff workflow” link can point to this real section.
A demo, guide, trial or meeting becomes a sales CTA only if that offer exists and
fits the brief. The existence of a booking URL does not decide the page's purpose.

The added depth comes from a concrete task, mechanism, artifact and decision—not
from word count. In another industry, change the task and exhibit, not just nouns.
