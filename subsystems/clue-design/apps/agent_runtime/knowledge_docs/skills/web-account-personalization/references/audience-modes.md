# Choose the unit of relevance

Use the request's actual mode. These are content decisions, not a new scaling API
or proof that a particular artifact is bound or published.

| Intent | Argument and evidence | Identity and output |
| --- | --- | --- |
| 1:1 account | Select the supported capability that matters to the supplied team/task; add verified account context only when available. | Exact resolved company; authentic target mark when requested/available. Distinguish named concept from bound account-derived page. |
| 1:1 contact | Tie the account argument to that person's supplied professional responsibility. A personal facet needs identity and allowed-use evidence. | Confirm the specific contact belongs to the intended account; a matching name is insufficient. Do not expose internal claim metadata in the page. |
| 1:few | Use a documented shared problem, role or segment thesis. Record who is in the group and why the thesis is shared. | Do not project one member's research/results onto every member. Use a segment page when output is shared; account variants require real bindings and per-account checks. |
| 1:many | Explain an evidenced product capability for the defined audience or ICP. | Do not imply every anonymous visitor is researched or identified. Use broad audience language; no invented per-visitor facts or account markers. |
| Event | Explain the real event's value, audience, format and next step; include supported date/time/timezone/location or online details. | Registration, replay or agenda is the actual offer when supplied. Never invent speakers, sponsors, deadlines or availability. |
| Regular product/landing page | Follow product purpose, traffic and buyer questions; prioritize the actual signup, purchase, contact or resource flow. | Native navigation may support orientation/trust. Neither an ABM identity treatment nor a booking dialog is automatic. |

For every mode, state the visitor's job, the seller capability that serves it,
the support for that connection and the action the real destination enables.
A shared headline can remain when its supporting copy and media carry the relevant
argument. A logo wall is not a substitute for that argument or relationship proof.

## Named concept versus reusable template

Read existing account context and the artifact's intended use. When the brief only
names a company and no binding is available, a supportable addressed concept is
possible, but report the missing binding and research. Do not silently call this
verified account personalization or manufacture a platform ID.

When the task requests a reusable template, preserve the actual supported
`{{account.name}}`, `{{account.domain}}`, `{{account.logo}}` slot markers and
`data-var`/`data-slot`/`data-slot-when` semantics used by its authoring lane. Inspect
the existing schema and slot types; do not invent variables from an imagined
contact or segment schema. Raw slots and derived campaign variants may already
serve the requirement; markers alone never justify rebuilding the whole page.

Only actual derived outputs and bindings prove derivation. Verify representative
long names, absent logos and missing optional claims in the resulting pages; a
literal fallback rendered in one preview is not a derivation test. Keep a required
but unavailable logo explicit; if optional, omit its empty container cleanly.
Do not report a requested batch as done after reviewing only its template.

Existing template-publish refusal and derived-page noindex rules remain in force.
Noindex/unlinked limits discovery, not access. An authorized content edit does not
by itself authorize publication, a batch derive or re-deriving frozen descendants.
