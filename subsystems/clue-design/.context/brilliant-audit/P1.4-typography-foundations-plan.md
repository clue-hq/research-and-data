## 1. What the post-P1.3 runs proved

P1.3 fixed the engine deadlock: both `a4` and `linkedin` now reach
`completed_with_warnings` (preflight-clean, best draft returned) instead of
`failed` on an un-repairable `LUMV0810`. The loop converges; the PNG critic now
judges real pixels. Two **composition** defects became visible (honest, not bugs):

- **A4 appointment card** — genuinely good. Dominant headline, clean left spine,
  legible hierarchy, centered CTA. Nits only: empty bottom third, `+` chip reads
  as placeholder. NOT the focus of this plan.
- **LinkedIn 1080² — type does not establish hierarchy.** The DSL is *correct*
  (`style($type.headline)`, no bare numbers). The fault is in the token values:
  `$type.headline = 56pt` is too small to dominate a 1080pt canvas, and
  `$type.stat = 48pt` reads as **equal weight** to the headline → the critic's
  "squint test fails / nothing dominates" (a blocker + an error). Compounded by
  `y(sb)` distributing 4 sparse regions into dead bands.

## 2. Root cause

Our type scale **bakes size into the semantic role**. `$type.headline` is one
fixed value for every surface (great at A4 595pt, too small at 1080pt) and the
scale **tops out at `$type.display = 72`**. The author cannot reach a bigger step:
the role hides the number, and bare numbers are off-system. So a big-canvas hero
is unreachable, and `stat (48) ≈ headline (56)` violates hierarchy on large
surfaces.

## 3. How Brilliant handles it (the model we adopt) — evidence

Brilliant does **NOT** auto-scale type to the canvas. It uses a fixed pixel scale
too, but the architecture differs (`brilliant/knowledge/design/typography.md`,
`foundations.md`):

1. **Scale is decoupled from role.** Size is a pure *step* token
   `$font.size.xs…9xl` = `12,14,16,20,24,32,36,40,48,64,80,96,128`
   (`typography.md:13–23`). "hero / large hero / display" are *annotations on the
   steps*, not baked into a role. The author/block picks the step for the surface;
   the scale runs to **128**, so a big canvas always has a dominant step.
2. **Hierarchy is enforced by canvas-independent RELATIVE rules:**
   - Jump rule: heading = 150–200% of body (`typography.md:26`).
   - Anchor principle: ONE focal element 2–3× body; don't equally weight multiple
     "biggest" things — one dominates (`typography.md:38–40`).
   - Foundations squint test: if nothing dominates, raise contrast
     (`foundations.md:30–32`); heroes "at 48–64px read confident" (`:42`).
3. **The block catalog picks the right step per surface.**
4. **The render-and-look critic** catches "nothing dominates" on pixels — ours
   already did exactly this.

### Why NOT the auto-scaler I first proposed
Two independent reasons:
- **Not faithful to Brilliant** — Brilliant relies on the decoupled scale +
  relative rules + per-surface choice + critic, not a canvas-relative resolver.
- **Editor-hostile** — our platform also supports human direct-manipulation
  editing. If a node's resolved size were a function of canvas size, then resizing
  the artboard would silently mutate every text node, "what you set is what you
  get" breaks, the size field has no stable value, and drag-resize/undo become
  ambiguous. A token must resolve to the SAME value regardless of canvas. The
  decoupled-scale model has exactly this property → editor-safe by construction.

## 4. Design decision

Keep our **semantic roles** (they carry weight + color + line-height + tracking —
a real advantage over Brilliant's atomic tokens; encodes taste in one keyword) but
**add the missing decoupling primitive**: a pure size-step token ladder the
catalog/author can use to override a role's *size* per surface. Roles stay the
easy default for standard surfaces (A4, postcard); big surfaces override size with
a step. This is Brilliant-faithful, editor-safe, and keeps our descriptive roles.

### New token: `$type.size.*` scalar ladder (mirror Brilliant's values)
```
$type.size.xs=12  sm=14  md=16  lg=20  xl=24  2xl=32  3xl=36
$type.size.4xl=40  5xl=48  6xl=64  7xl=80  8xl=96  9xl=128
```
Namespace `$type.size.*` (not a new top-level `$font.*`) to keep all typography
under `$type.` and parallel the existing scalar ladders (`$space.*`, `$radius.*`).
These are pure scalars (like `$space.*`), resolution is identity (editor-safe).

### Usage idiom (catalog + docs)
```
# role gives weight/color/lh/tracking; step token gives surface-appropriate size
headline text "…" style($type.headline) font_size($type.size.7xl) ...   # 80pt hero on 1080²
```
Roles' built-in default sizes are unchanged (A4 keeps `style($type.headline)` → 56).

## 5a. A0 GATE RESULTS (empirical, done)

- **DECISIVE ENGINE FINDING:** `style($type.headline)` **hard-locks** the size — a
  trailing `font_size(72/80/96)` is *completely ignored* (renders byte-identical).
  So the fix is not merely "add a size token"; **an explicit size override must take
  precedence over the role's default size.** This sharpens Phase A2.
- **Pixel calibration deferred to Phase D.** A standalone PNG probe can't resolve
  brand tokens without the loop's resolve step (export emits `LUME0205/0209/0206`
  and renders blank). The post-P1.3 e2e renders DID resolve correctly, so final
  pixel confirmation happens there.
- **Target hero step picked from Brilliant's own annotations** (the faithful source
  of truth, `typography.md`): a 1080² social hero is "display / large hero" = 6xl–7xl
  (64–80). With our `stat = 48` and `body = 18`, **hero = `$type.size.7xl` (80)** gives
  80/48 = 1.67 (headline dominates the stat) and 80/18 = 4.4× body (strong anchor) —
  squarely Brilliant's display zone. 6xl (64) is the fallback / secondary-heading step.

## 5b. DEVIATIONS FROM BRILLIANT (flagged for explicit sign-off)

**Deviation 1 — STRUCTURAL (needs the user's call).** We KEEP semantic role tokens
(`$type.headline`, `.stat`, …); Brilliant has *no* roles — only atomic
`$font.size.*` + separate `$font.weight.*` / `$color.text.*`, composed per call.
- Why deviate: our roles bundle size+weight+lh+tracking+color in one keyword, the
  catalog + P1.1 surface-aware color + P0.2 blocks all key off roles. Going pure-atomic
  would regress that work and make every text line more verbose.
- My approach is a **SUPERSET**: keep roles as the convenient default, ADD Brilliant's
  decoupled size ladder, and let an explicit size override win. We get Brilliant's
  decoupling + relative rules + per-surface choice + critic, AND keep richer roles.
- Risk: it's two mechanisms (role default size + override) instead of one. Mitigated by
  docs ("role for styling, step for surface size") + catalog encoding the idiom.

**Deviation 2 — NAMING (minor).** `$type.size.*` (our namespace) vs Brilliant's
`$font.size.*`. Chosen to keep all typography under `$type.` and parallel `$space.*`/
`$radius.*`. Trivially switchable to `$font.size.*` for exact parity if preferred.

**Deviation 3 — VALUES (pre-existing, not introduced here).** Our `body = 18` vs
Brilliant's 16; our role default sizes differ. The new *ladder* mirrors Brilliant's
values exactly (12…128).

## 6. Risks / watch-items
- **Don't over-extend roles.** No new hero/display *roles* — the step override is
  the mechanism. Avoid two ways to do the same thing.
- **Stat vs headline ratio** is a *catalog choice*, enforced by the foundations
  rule + critic, not a hard engine constraint (keeps the editor free).
- **`font(...)` size-arg token** is nice-to-have; if it widens blast radius, ship
  `font_size($type.size.x)` only and defer the 4-arg form.
- **Keep bare-number `font_size` working** (compat); token-strict mode stays out of
  scope.
- A0 gate may show 72 is "enough" for *this* prompt — still ship the ladder
  (the model is the point; 72 ceiling fails larger canvases / display heroes).
